## 왜 지금 엔진을 배우나

React는 결국 JavaScript다. 컴포넌트 렌더링, State 업데이트, 데이터 패칭 전부 이 엔진 위에서 돈다. 콜스택과 이벤트 루프를 모르면 "화면이 왜 멈추지", "왜 `setState`가 바로 반영이 안 되지" 같은 문제를 계속 감으로만 때우게 된다. 그래서 React 문법보다 먼저 엔진을 본다.

<Callout type="info">
  이 챕터는 엔진의 **큰 그림**과 **콜스택**에 집중한다. Promise·마이크로태스크 같은 비동기의 세부 동작은 33번 챕터(동기 vs 비동기의 원리)에서 다시 깊게 판다.
</Callout>

## 자바스크립트 엔진이란

우리가 쓰는 JS는 사람이 읽는 텍스트일 뿐이다. 이걸 CPU가 실행할 수 있는 기계어로 바꿔주는 프로그램이 **자바스크립트 엔진**이다.

| 엔진 | 만든 곳 | 쓰이는 곳 |
| --- | --- | --- |
| **V8** | Google | Chrome, Edge, **Node.js**, Deno |
| SpiderMonkey | Mozilla | Firefox |
| JavaScriptCore | Apple | Safari |

우리가 다룰 건 **V8**이다. 브라우저와 Node를 둘 다 굴리는 엔진이라, React 개발 환경에서 계속 마주치게 된다.

## V8은 코드를 어떻게 실행하는가

예전엔 "JS는 인터프리터 언어라 느리다"고 했지만, 지금은 아니다. V8은 실행 중에 코드를 기계어로 컴파일하는 **JIT(Just-In-Time) 컴파일**을 쓴다.

<Steps>

### 파싱 → AST

소스 코드를 토큰으로 쪼갠 뒤, 문법 구조를 나타내는 **AST(추상 구문 트리)** 로 만든다.

### 바이트코드 생성 (Ignition)

AST를 **Ignition** 인터프리터가 **바이트코드**로 변환해 곧바로 실행한다. 시작이 빠르고 메모리도 적게 먹는다.

### 실행하며 관찰

실행하는 동안 어떤 함수가 자주 불리는지, 어떤 타입이 들어오는지(객체 모양, 숫자/문자 여부)를 계속 기록한다. 이 정보가 다음 단계의 최적화 근거가 된다.

### 뜨거운 코드는 컴파일 (JIT)

자주 실행되는("hot") 코드는 관찰한 정보를 바탕으로 **최적화된 기계어**로 다시 컴파일한다. 인터프리터보다 훨씬 빠르게 돈다.

</Steps>

V8은 이 최적화를 지금 **4단계 계층**으로 나눠서 한다. 아래로 갈수록 컴파일은 오래 걸리지만 결과 코드는 빠르다.

```text
Ignition   →  Sparkplug  →   Maglev    →  TurboFan
(인터프리터)   (베이스라인)    (중간 최적화)   (최고 최적화)
 빠른 시작                                    가장 빠른 실행
```

최적화된 코드가 관찰과 다르게 동작하면(예: 숫자만 들어오던 함수에 갑자기 문자열이 들어옴) V8은 **역최적화(deoptimization)** 로 Ignition까지 다시 내려가 안전하게 실행한다.

<Callout type="warning">
  **구버전 주의.** 오래된 블로그·강의는 V8을 **Full-codegen + Crankshaft** 조합으로 설명한다. 이 구조는 **2017년(V8 v5.9)** 에 Ignition + TurboFan으로 완전히 교체됐고, 이후 **Sparkplug(2021)**, **Maglev(2023, Chrome M117)** 가 추가돼 지금의 4단계가 됐다. Crankshaft라는 단어가 보이면 오래된 자료다.
</Callout>

## 메모리 — 힙과 콜스택

V8이 코드를 실행할 때 메모리는 크게 두 곳으로 나뉜다.

<Tabs items={['콜스택 (Call Stack)', '힙 (Heap)']}>
  <Tabs.Tab>
    함수 호출을 순서대로 쌓아 실행 흐름을 추적하는 곳. 구조가 정해져 있고 크기가 작다. 원시값(숫자, 불리언 등)과 함수 실행 정보가 여기 올라간다.
  </Tabs.Tab>
  <Tabs.Tab>
    객체·배열·함수처럼 크기가 정해지지 않은 데이터가 저장되는 곳. 넓고 구조가 자유롭다. 변수는 콜스택에서 힙의 주소를 **참조**한다. (이 "참조" 개념이 22번 챕터의 참조 비교로 이어진다.)
  </Tabs.Tab>
</Tabs>

## 콜스택의 원리

콜스택은 **LIFO(Last In, First Out)** — 마지막에 넣은 게 먼저 빠지는 접시 쌓기 구조다. 함수를 호출하면 스택에 **쌓이고(push)**, 함수가 끝나면 **빠진다(pop)**.

```js
function multiply(a, b) {
  return a * b;
}

function square(n) {
  return multiply(n, n);
}

function printSquare(n) {
  const result = square(n);
  console.log(result);
}

printSquare(4);
```

이 코드의 콜스택 흐름:

<Steps>

### `printSquare(4)` push

스택: `[printSquare]`

### `square(4)` push

`printSquare` 안에서 `square`를 부른다. 스택: `[printSquare, square]`

### `multiply(4, 4)` push

`square` 안에서 `multiply`를 부른다. 스택: `[printSquare, square, multiply]`

### 위에서부터 pop

`multiply`가 `16`을 반환하고 빠진다 → `square`가 `16`을 반환하고 빠진다 → `console.log(16)`이 잠깐 올라갔다 빠진다 → `printSquare`가 빠진다. 스택: `[]`

</Steps>

에러가 났을 때 콘솔에 찍히는 **스택 트레이스**가 바로 이 콜스택을 아래에서 위로 뒤집어 보여준 것이다. 디버깅할 때 "어떤 함수가 어떤 함수를 불렀는지"를 읽는 근거가 된다.

### 스택 오버플로

콜스택 크기는 유한하다. 끝나지 않는 재귀는 스택을 넘치게 한다.

```js
function recurse() {
  return recurse(); // 종료 조건이 없다
}

recurse(); // RangeError: Maximum call stack size exceeded
```

<Callout type="error">
  React에서 이 에러가 뜬다면 대개 **렌더 중에 State를 업데이트**해서 무한 리렌더 루프가 생겼거나, `useEffect` 의존성을 잘못 걸어 서로를 계속 부르는 경우다. (35번 챕터에서 다룬다.)
</Callout>

## 자바스크립트는 싱글 스레드다

**콜스택은 딱 하나뿐이다.** 그래서 JS는 한 번에 한 가지 일만 한다. 이걸 **싱글 스레드**라고 한다.

문제는, 오래 걸리는 작업이 콜스택을 붙잡으면 그동안 아무것도 못 한다는 것이다.

```js
function blockFor3Seconds() {
  const end = Date.now() + 3000;
  while (Date.now() < end) {} // 3초간 스택 점유
}

blockFor3Seconds();
// 이 3초 동안 클릭·스크롤·애니메이션 전부 멈춘다
```

브라우저의 화면 그리기도 이 스레드를 쓴다. 그래서 무거운 동기 작업이 콜스택을 오래 잡으면 **화면이 얼어붙는다**. React가 렌더링을 잘게 쪼개는 Fiber 아키텍처(7번 챕터)를 만든 이유가 바로 이 지점이다.

## 그럼 `setTimeout`이나 `fetch`는 어떻게 기다리나

싱글 스레드인데 어떻게 "3초 뒤에 실행"이나 "네트워크 응답 기다리기"가 화면을 안 멈추고 될까? 답은 **엔진 혼자 하는 게 아니라는 것**이다.

`setTimeout`, `fetch`, DOM 이벤트 같은 건 **JS 엔진의 기능이 아니다.** 브라우저(또는 Node)라는 **런타임 환경**이 제공하는 별도 기능이다. 엔진은 이 작업을 런타임에 맡겨두고 콜스택을 비운다.

```text
┌──────────────────────────────────────────────┐
│                 브라우저 런타임                  │
│                                                │
│   ┌────────────┐          ┌─────────────┐      │
│   │ Call Stack │          │  Web APIs   │      │
│   │            │──넘김──▶  │ setTimeout  │      │
│   │            │          │ fetch, DOM  │      │
│   └────────────┘          └──────┬──────┘      │
│         ▲                        │ 완료         │
│         │                        ▼             │
│   ┌─────┴──────┐          ┌─────────────┐      │
│   │ Event Loop │◀─────────│ Callback Q  │      │
│   └────────────┘          └─────────────┘      │
└──────────────────────────────────────────────┘
```

동작 순서는 이렇다.

<Steps>

### 콜스택에서 넘김

`setTimeout(cb, 1000)`을 만나면, 엔진은 이 일을 **Web API**에 넘기고 콜스택에서 즉시 빠진다. 그래서 뒤 코드가 안 막힌다.

### 대기 후 큐로 이동

Web API가 타이머를 세거나 응답을 받으면, 콜백을 **콜백 큐(Callback Queue)** 에 넣는다. 아직 실행되는 건 아니다.

### 이벤트 루프가 감시

**이벤트 루프**는 딱 한 가지 일만 반복한다 — "콜스택이 비었나?" 확인. 비어 있으면 큐에서 콜백을 하나 꺼내 콜스택에 올린다.

### 실행

그제서야 콜백이 실행된다.

</Steps>

<Callout type="info">
  그래서 `setTimeout(fn, 0)`도 **즉시** 실행되지 않는다. 지금 콜스택에 있는 동기 코드가 전부 끝나고 스택이 비어야 큐에서 꺼내지기 때문이다. "0ms"는 "지연 없음"이 아니라 "최소 대기 후, 스택이 비면"이라는 뜻이다.
</Callout>

## React와 무슨 상관인가

지금 배운 게 React 전반의 뼈대다.

- **렌더링도 콜스택 위에서 돈다.** 컴포넌트 함수 실행 → JSX 계산 → DOM 커밋 전부 이 스레드다. 렌더가 무거우면 화면이 멈춘다. → **Fiber**(7번)가 이걸 쪼갠다.
- **싱글 스레드라 이벤트가 몰아친다.** 그래서 React는 여러 State 업데이트를 한 번에 모아 처리한다. → **배치 업데이트**(20번).
- **데이터 패칭은 전부 이 이벤트 루프 위에서 벌어진다.** `fetch`가 왜 화면을 안 막고, 응답이 왜 "나중에" 오는지가 여기서 설명된다. → **useEffect 데이터 패칭**(34~40번).

콜스택 · 싱글 스레드 · 이벤트 루프 — 이 세 개만 손에 쥐고 있으면, 앞으로 나올 "왜 이렇게 동작하지?" 대부분을 스스로 추론할 수 있다.
