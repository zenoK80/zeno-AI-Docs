## 브라우저는 화면을 어떻게 그릴까

1편에서 "React는 데이터가 바뀌면 화면을 다시 그린다"고 했다.
그런데 정작 **"화면을 그린다"는 게 브라우저 안에서 무슨 일인지**는 짚지 않았다.

이걸 모르면 뒤에서 "왜 DOM 조작이 느린가", "왜 Virtual DOM이 필요한가"를 외워야 한다.
알고 나면 저절로 이해된다. 그래서 한 편을 통째로 여기 쓴다.

## 브라우저 안에는 두 개의 엔진이 있다

브라우저가 웹 페이지를 처리할 때 크게 두 엔진이 나눠 일한다.

| 엔진 | 담당 |
| --- | --- |
| **렌더링 엔진** | HTML·CSS를 읽어 화면에 그리기 (이번 편 주제) |
| **JavaScript 엔진** | JS 코드를 실행하기 (3편 주제) |

크롬·엣지는 **Blink**, 사파리는 **WebKit**, 파이어폭스는 **Gecko**라는 렌더링 엔진을 쓴다.
이름은 달라도 하는 일의 큰 흐름은 같다.

## HTML과 CSS가 화면이 되기까지

렌더링 엔진이 문서를 받아서 픽셀로 바꾸는 과정은 정해진 순서를 따른다.

<Steps>

### HTML을 읽어 DOM을 만든다

태그를 위에서부터 읽으며 **DOM**<sup>Document Object Model</sup>이라는 트리 구조를 만든다.
DOM은 "지금 이 문서에 어떤 요소가 어떤 부모-자식 관계로 있는지"를 객체로 표현한 것이다.

```html
<body>
  <div>
    <p>안녕</p>
  </div>
</body>
```

이 HTML은 대략 이런 트리가 된다.

```
body
 └─ div
     └─ p
         └─ "안녕"
```

### CSS를 읽어 CSSOM을 만든다

같은 방식으로 CSS를 읽어 **CSSOM**<sup>CSS Object Model</sup>을 만든다. "어떤 요소가 어떤 스타일을 갖는지"를 담은 트리다.

### 둘을 합쳐 렌더 트리를 만든다

DOM과 CSSOM을 합쳐, **실제로 화면에 그려질 것만** 남긴 트리를 만든다.
`display: none`인 요소는 여기서 빠진다. (안 보이지만 자리는 차지하는 `visibility: hidden`과는 다르다.)

### 레이아웃 — 위치와 크기를 계산한다

렌더 트리의 각 요소가 **화면 어디에, 얼마만 한 크기로** 놓일지 좌표를 계산한다.

### 페인트 — 픽셀을 칠한다

계산된 위치에 실제로 색, 글자, 이미지를 그려 넣는다.

</Steps>

<Callout type="info">
이 다섯 단계를 합쳐 흔히 **렌더링 파이프라인**이라 부른다. 지금은 순서만 기억하면 충분하다.
</Callout>

## 이게 React랑 무슨 상관인가

핵심은 여기다. **레이아웃과 페인트는 공짜가 아니다.**

DOM 요소 하나의 크기를 바꾸면, 그 주변 요소들의 위치도 다시 계산해야 할 수 있다.
브라우저는 이걸 처음부터 다시 계산한다 — 이 재계산을 **리플로우**<sup>Reflow</sup>라 한다.

```js
const box = document.querySelector('.box')

box.style.width = '200px'   // 리플로우 발생 가능
box.style.height = '100px'  // 또 리플로우 발생 가능
box.textContent = '변경됨'   // 또 리플로우 발생 가능
```

이 세 줄을 실행하면 브라우저에 따라 **레이아웃 계산이 여러 번** 일어날 수 있다.
한 번의 사용자 동작(클릭 한 번)이 DOM 조작 수십 줄로 이어지는 화면이라면, 이 비용이 쌓여 버벅임으로 나타난다.

<Callout type="important">
**"DOM 조작이 느리다"는 정확한 표현이 아니다.**

DOM 자체를 읽고 쓰는 건 빠르다. 느려지는 건 **DOM을 바꾼 뒤 브라우저가 다시 계산해야 하는 레이아웃·페인트** 쪽이다.
그래서 문제는 "얼마나 자주, 얼마나 무분별하게 이 재계산을 유발하는가"에 있다.
</Callout>

## jQuery 시절의 실전 문제

1편에서 본 "좋아요 버튼" 예시로 돌아가 보자.

```js
function increaseLike() {
  const countEl = document.querySelector('#like-count')
  const badgeEl = document.querySelector('#badge')

  let count = Number(countEl.textContent) + 1
  countEl.textContent = count            // ① DOM 변경

  if (count > 100) {
    badgeEl.style.display = 'block'      // ② DOM 변경
  }

  document.querySelector('.summary').textContent = `총 ${count}개`  // ③ DOM 변경
}
```

화면이 복잡해질수록 이런 코드가 페이지 곳곳에 흩어진다. 각 조작마다 브라우저가 다시 계산할 일이 생긴다.
개발자가 "어디를 바꿔야 하는지" 직접 찾아 하나씩 건드리는 방식 자체가, **필요 이상으로 브라우저를 재계산시키기 쉬운 구조**다.

## React의 전략을 미리 살짝 보면

React는 이 문제를 두 가지로 다룬다. 지금은 이름만 알아두자. 원리는 6·7편에서 다룬다.

<Callout type="info">
- **Virtual DOM** — 실제 DOM을 매번 직접 건드리는 대신, 메모리 위에서 먼저 "무엇이 바뀌었는지" 비교부터 하고
- **일괄 반영(batching)** — 여러 변경사항을 모아서 **한 번에** 실제 DOM에 반영

즉 React는 "언제, 얼마나 자주 브라우저에 재계산을 요청할지"를 개발자 대신 관리해 준다.
</Callout>

## 개발자 도구로 직접 확인하기

크롬 개발자 도구의 **Performance** 탭에서 페이지를 조작하며 녹화하면, **Layout**·**Paint** 항목이 실제로 얼마나 걸리는지 눈으로 볼 수 있다.

<Callout type="default">
지금 바로 실습: 아무 웹페이지에서 <kbd>F12</kbd> → Performance 탭 → 녹화 시작 → 스크롤이나 클릭 몇 번 → 녹화 종료.
결과 그래프에서 노란색(Scripting), 보라색(Rendering/Layout), 초록색(Painting) 구간을 확인해 보자.
</Callout>

## 정리

<Callout type="default">
- 브라우저는 **DOM(구조) + CSSOM(스타일) → 렌더 트리 → 레이아웃 → 페인트** 순서로 화면을 만든다
- DOM 조작 자체보다, **그 뒤에 따라오는 레이아웃·페인트 재계산 비용**이 진짜 문제다
- 이 재계산을 **리플로우**라 부른다
- React의 Virtual DOM과 일괄 반영은 이 비용을 줄이기 위한 장치다
</Callout>

다음 편에서는 반대쪽 엔진, 즉 **JavaScript 엔진이 코드를 어떻게 실행하는지**를 본다.
렌더링과 JS 실행이 어떻게 얽혀 있는지 알아야 React의 동작을 온전히 이해할 수 있다.
