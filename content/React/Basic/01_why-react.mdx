## 왜 React인가

React를 배우기 전에 던져야 할 질문이 있다.

**"그냥 자바스크립트로 화면을 만들면 안 되나?"**

이 질문에 스스로 답할 수 있으면 React의 모든 개념이 "왜 이렇게 생겼는지" 이해된다.
그래서 첫 편은 문법이 아니라 **React가 풀려는 문제**부터 본다.

## 웹은 원래 문서였다

초창기 웹은 **문서를 보여주는 것**이 전부였다. 서버가 완성된 HTML을 내려주면 브라우저가 그렸다.
링크를 누르면 서버가 **새 페이지 전체**를 다시 내려줬다. 화면이 깜빡이며 처음부터 다시 그려졌다.

지금 기준으로는 답답하지만, "문서를 읽는" 용도에는 충분했다.

## 문제는 "앱처럼" 만들면서 시작됐다

지메일, 구글 지도 같은 서비스가 등장하며 웹은 **문서가 아니라 앱**이 되기 시작했다.
페이지를 새로고침하지 않고 화면 일부만 바꾸는 요구가 생겼다. 메일 목록에서 별표 하나만 눌러도 그 부분만 즉시 바뀌어야 했다.

이걸 초기에는 **jQuery** 같은 도구로 직접 DOM을 조작해 해결했다.

```js
// 좋아요 수를 1 올리는 코드 (직접 DOM 조작)
const countEl = document.querySelector('#like-count')
let count = Number(countEl.textContent)
count = count + 1
countEl.textContent = count

if (count > 100) {
  document.querySelector('#badge').style.display = 'block'
}
```

한두 군데면 괜찮다. 그런데 화면이 복잡해지면서 문제가 터졌다.

## 직접 DOM을 조작하면 왜 힘든가

핵심 문제는 **"데이터와 화면을 손으로 계속 맞춰야 한다"** 는 것이다.

좋아요 수가 바뀌면 개발자가 직접:
- 숫자 텍스트를 바꾸고
- 100을 넘으면 배지를 켜고
- 버튼 색을 바꾸고
- 어딘가의 합계도 갱신하고 …

**"바뀐 데이터"를 화면 곳곳에 손으로 반영**해야 한다. 반영할 곳을 하나라도 빠뜨리면 화면과 데이터가 어긋난다.
숫자는 101인데 배지는 안 뜨는 버그가 이렇게 나온다.

<Callout type="important">
화면을 이루는 조각이 많아질수록 "지금 화면이 어떤 상태인지"를 사람이 추적할 수 없게 된다.
**이것이 React가 등장하기 전 프론트엔드의 가장 큰 고통이었다.**
</Callout>

## React의 발상 — "화면을 다시 그린다고 생각하자"

React의 아이디어는 발상의 전환이다.

> 데이터가 바뀌면, **화면을 손으로 고치지 말고, 그 데이터로 화면 전체를 다시 그린다.**

맨 처음 봤던 옛날 웹의 "페이지 전체 새로고침"과 비슷하게 들린다. 그 방식이 편했던 이유가 있었다.
**개발자는 "현재 데이터로 화면이 어떻게 생겼는지"만 정의하면 됐기 때문이다.** 바뀐 부분을 일일이 찾아 고칠 필요가 없었다.

React는 그 편함을 가져오되, 새로고침의 단점(느리고 깜빡임)은 없앤다.

```jsx
// React 방식 — "이 데이터일 때 화면은 이렇게 생겼다"를 정의
function LikeButton({ count }) {
  return (
    <div>
      <span>{count}</span>
      {count > 100 && <span className="badge">인기!</span>}
    </div>
  )
}
```

이 코드는 **"어떻게 바꿀지"를 지시하지 않는다.** 그저 **"count가 이 값이면 화면은 이 모습"** 이라고 선언할 뿐이다.
count가 바뀌면 React가 알아서 화면을 다시 계산한다.

<Callout type="info">
**명령형 vs 선언형**

- **명령형**<sup>Imperative</sup>: "숫자를 바꾸고, 배지를 켜라" — 과정을 하나하나 지시 (기존 DOM 조작)
- **선언형**<sup>Declarative</sup>: "count가 100 초과면 배지가 있는 화면" — 결과만 선언 (React)

React의 핵심은 **선언형으로 UI를 짜는 것**이다. 이 관점이 앞으로 계속 나온다.
</Callout>

## "전체를 다시 그리면 느리지 않나?"

당연한 의문이다. 데이터가 바뀔 때마다 화면 전체를 다시 그리면 옛날 새로고침처럼 느려야 한다.

React는 여기서 영리한 방법을 쓴다. **진짜 화면(DOM)을 통째로 갈아엎지 않는다.**
대신 메모리 속에 가상의 화면 구조를 만들어 **바뀌기 전과 후를 비교**하고, **실제로 달라진 부분만** 진짜 DOM에 반영한다.

이 가상의 화면 구조를 **Virtual DOM**<sup>가상 돔</sup>이라 한다.

<Callout type="info">
Virtual DOM이 정확히 어떻게 비교하고 어디만 바꾸는지는 6편에서 자세히 다룬다.
지금은 **"전체를 다시 그리는 것처럼 코드를 짜되, 실제로는 바뀐 곳만 바꾼다"** 는 것만 기억하면 된다.
</Callout>

## React가 뭘 해주는지 한 줄로

<Callout type="important">
**데이터를 화면에 자동으로 반영해 준다.**

개발자는 "이 데이터일 때 화면은 이 모습"만 정의한다. 데이터가 바뀌면 화면을 맞추는 일은 React가 한다.
개발자가 DOM을 손으로 건드릴 일이 사라진다.
</Callout>

이 하나를 위해 React는 여러 장치를 갖고 있고, 앞으로 그것들을 하나씩 배운다.

- 화면을 조각으로 나누는 **컴포넌트** (10편~)
- 변하는 데이터를 담는 **State** (16편~)
- 데이터가 바뀌면 화면을 다시 그리는 **렌더링** (17편)

## React는 라이브러리다

마지막으로 정체성 하나. React는 **프레임워크가 아니라 라이브러리**다.

<Callout type="info">
- **라이브러리** — 필요한 기능만 가져다 쓰는 도구. 나머지 선택은 개발자 몫
- **프레임워크** — 전체 구조를 정해두고 그 틀 안에서 개발하게 하는 것

React는 **"화면을 그리는 일"만** 담당한다. 라우팅(주소 이동), 데이터 패칭, 빌드 설정 등은 React가 강제하지 않는다.
그래서 자유롭지만, 그만큼 **다른 도구와 조합**해야 한다. Next.js 같은 것이 그 조합을 미리 갖춰 놓은 것이다.
</Callout>

React는 2013년 페이스북(현 메타)이 공개했고, 지금은 웹 프론트엔드에서 가장 널리 쓰이는 도구 중 하나다.
2024년 말 나온 **React 19**가 현재 최신 메이저 버전이며, 이 시리즈는 이를 기준으로 쓴다.

<Callout type="warning">
검색하면 나오는 오래된 React 코드는 지금과 문법이 꽤 다를 수 있다. `class`로 컴포넌트를 만들거나
`componentDidMount` 같은 걸 쓰는 코드가 그렇다. 이 시리즈는 **함수 컴포넌트와 훅**이라는 현재 방식으로 배우고,
옛 방식은 "읽을 줄만 알면 되는 것"으로 마지막 편에서 짚는다.
</Callout>

## 정리

<Callout type="default">
- 웹은 **문서 → 앱**으로 진화하며 "화면 일부만 바꾸기"가 필요해졌다
- 직접 DOM을 조작하면 **데이터와 화면을 손으로 맞춰야 해서** 복잡해질수록 무너진다
- React는 **"데이터로 화면을 다시 그린다"** 는 선언형 방식으로 이 문제를 푼다
- 전체를 다시 그리는 것처럼 짜되, **Virtual DOM**으로 바뀐 곳만 실제 반영한다
- React는 화면 그리기만 담당하는 **라이브러리**다
</Callout>

다음 편에서는 한 단계 내려가, **브라우저가 화면을 어떻게 그리는지** 원리부터 본다.
React가 최적화하는 대상이 바로 그것이기 때문이다.
