## 02편 복습

## 문제 1

브라우저가 화면을 그리는 다섯 단계를 순서대로 나열한 것은?

<Quiz>
  <Quiz.Option>페인트 → 레이아웃 → DOM 생성 → CSSOM 생성 → 렌더 트리</Quiz.Option>
  <Quiz.Option correct>DOM 생성 → CSSOM 생성 → 렌더 트리 생성 → 레이아웃 → 페인트</Quiz.Option>
  <Quiz.Option>CSSOM 생성 → DOM 생성 → 레이아웃 → 렌더 트리 → 페인트</Quiz.Option>
  <Quiz.Option>순서는 정해져 있지 않고 브라우저 마음대로다</Quiz.Option>

  <Quiz.Explanation>
  **DOM**(HTML로 만든 문서 구조 트리)과 **CSSOM**(CSS 스타일 정보를 담은 트리)을 각각 만든 뒤, 이 둘을 합쳐 실제로 화면에 그려질 것만 남긴 **렌더 트리**를 만든다. 그다음 각 요소가 어디에 얼마만 한 크기로 놓일지 계산하는 **레이아웃**, 마지막으로 실제 픽셀을 칠하는 **페인트** 순서로 진행된다.
  </Quiz.Explanation>
</Quiz>

## 문제 2

"DOM 조작이 느리다"는 말을 정확하게 고쳐 말하면?

<Quiz>
  <Quiz.Option>DOM을 읽고 쓰는 것 자체가 원래 느리다</Quiz.Option>
  <Quiz.Option correct>DOM을 바꾼 뒤 브라우저가 다시 계산해야 하는 레이아웃·페인트 작업이 비용이 크다</Quiz.Option>
  <Quiz.Option>사실은 전혀 느리지 않고 아무 문제 없다</Quiz.Option>
  <Quiz.Option>오래된 브라우저에서만 느리다</Quiz.Option>

  <Quiz.Explanation>
  DOM 자체를 읽거나 쓰는 동작은 빠르다. 진짜 비용이 드는 건 그 변경 때문에 브라우저가 다시 실행해야 하는 **레이아웃**(위치·크기 재계산)과 **페인트**(다시 그리기) 작업이다. 그래서 DOM을 자주, 무분별하게 바꿀수록 이 재계산 비용이 쌓여서 화면이 버벅이게 된다.
  </Quiz.Explanation>
</Quiz>

## 문제 3

React의 Virtual DOM과 일괄 반영(batching)이 실제로 하는 일은?

<Quiz>
  <Quiz.Option>DOM 조작을 아예 없애버린다</Quiz.Option>
  <Quiz.Option correct>"언제, 얼마나 자주 브라우저에 재계산을 요청할지"를 개발자 대신 관리해서 반영 횟수를 줄인다</Quiz.Option>
  <Quiz.Option>브라우저의 레이아웃 계산 자체를 더 빠른 알고리즘으로 바꿔치기한다</Quiz.Option>
  <Quiz.Option>CSS를 자동으로 최적화해준다</Quiz.Option>

  <Quiz.Explanation>
  **Virtual DOM**(진짜 DOM을 건드리기 전에 메모리 위에서 먼저 비교해보는 가상의 구조)과 **일괄 반영**<sup>Batching, 여러 변경 사항을 모아서 한 번에 처리하는 것</sup>은, 여러 변경을 모아 **최소한의 횟수로** 실제 DOM에 반영해 준다. DOM 조작 자체를 없애는 게 아니라(A는 오답), 얼마나 효율적으로 반영할지를 대신 관리해주는 것이다.
  </Quiz.Explanation>
</Quiz>

## 실습 — Performance 탭으로 리플로우 직접 관찰하기

<Steps>

### 아무 웹페이지에서 개발자 도구를 연다

<kbd>F12</kbd> → **Performance** 탭

### 녹화 버튼을 누른다

빨간 원 버튼을 클릭한다.

### 페이지를 스크롤하거나 버튼을 몇 번 클릭한다

3~5초 정도면 충분하다.

### 녹화를 멈추고 결과를 본다

그래프에서 **노란색(Scripting, 자바스크립트 실행)**, **보라색(Rendering, 레이아웃 계산)**, **초록색(Painting, 색칠하기)** 구간의 비율을 확인한다.

</Steps>

어느 색이 가장 큰 비중을 차지했는가? 그 이유를 이 편의 내용으로 설명해 보자.
