브라우저는 HTML 파일을 읽어
화면에 보여주는 단순한 프로그램이 아닙니다.

주소창과 탭을 관리하고,
서버에서 파일을 내려받고,
HTML·CSS·JavaScript를 처리하고,
화면을 그리며,
사용자 입력과 저장소까지 관리합니다.

이 많은 작업을 하나의 실행 흐름에 몰아넣으면
한 페이지의 오류가 브라우저 전체에 영향을 줄 수 있습니다.

현대 브라우저는 작업을 여러 **프로세스**와 **스레드**로 나누어
안정성·보안·응답성을 높입니다.

<Callout>
  **브라우저는 하나의 프로그램이지만,**
  **실제로는 여러 프로세스와 스레드가 협력하여 동작합니다.**

  다만 프로세스를 나누는 정확한 방식은
  웹 표준이 아니라 각 브라우저의 구현에 따라 달라집니다.
</Callout>

이 문서에서는 특정 브라우저의 내부 클래스나 소스 코드보다
웹 개발자가 알아야 하는 공통 구조를 중심으로 설명합니다.

## 먼저 전체 구조 보기

브라우저의 내부 구조를 단순화하면
다음과 같이 볼 수 있습니다.

```text
브라우저
├─ 브라우저 프로세스
│  ├─ 주소창·탭·뒤로 가기·앞으로 가기
│  ├─ 탐색과 권한 관리
│  ├─ 파일과 운영체제 기능 접근
│  └─ 다른 프로세스 생성·관리
│
├─ 렌더러 프로세스
│  ├─ HTML과 CSS 처리
│  ├─ DOM 구성
│  ├─ JavaScript 실행
│  ├─ 이벤트 처리
│  └─ 페이지의 시각적 결과 계산
│
├─ 네트워크 관련 프로세스 또는 서비스
│  ├─ DNS 조회
│  ├─ HTTP·HTTPS 통신
│  ├─ 프록시와 인증서 처리
│  └─ 응답 데이터 전달
│
├─ GPU·그래픽 관련 프로세스
│  ├─ 여러 페이지의 그래픽 결과 합성
│  ├─ GPU 명령 처리
│  └─ 화면 출력 지원
│
└─ 유틸리티 프로세스
   ├─ 오디오·비디오 디코딩
   ├─ 확장 프로그램 관련 작업
   └─ 격리가 필요한 보조 작업
```

이 구조는 개념을 이해하기 위한 단순화입니다.

실제 프로세스 이름과 개수는
브라우저 종류, 운영체제, 메모리 상태,
열린 사이트와 사용 중인 기능에 따라 달라집니다.

## 프로세스란?

**프로세스(process)**는
운영체제에서 실행 중인 프로그램의 작업 단위입니다.

각 프로세스는 일반적으로
자신만의 메모리 공간과 자원을 가집니다.

```text
프로세스 A의 메모리          프로세스 B의 메모리
┌─────────────────┐        ┌─────────────────┐
│ 코드            │        │ 코드            │
│ 객체와 데이터   │        │ 객체와 데이터   │
│ 실행 상태       │        │ 실행 상태       │
└─────────────────┘        └─────────────────┘
```

프로세스 A가 사용하는 객체를
프로세스 B가 일반 변수처럼 바로 읽을 수는 없습니다.

서로 다른 프로세스가 데이터를 주고받으려면
운영체제가 제공하는 통신 방식이 필요합니다.

### 프로세스를 나누는 이유

브라우저가 페이지마다 작업을 분리하면
다음과 같은 장점이 생깁니다.

- 한 페이지가 멈춰도 다른 탭을 계속 사용할 수 있습니다.
- 문제가 발생한 페이지의 영향을 일정 범위 안에 가둘 수 있습니다.
- 서로 다른 사이트의 작업을 여러 CPU 코어에서 병렬로 처리할 수 있습니다.
- 신뢰할 수 없는 웹 콘텐츠의 운영체제 접근 권한을 제한할 수 있습니다.

하지만 프로세스가 늘어나면
각 프로세스의 기본 메모리와 관리 비용도 증가합니다.

따라서 브라우저는
격리와 메모리 사용량 사이에서 균형을 잡습니다.

## 스레드란?

**스레드(thread)**는
하나의 프로세스 안에서 실제 작업을 실행하는 흐름입니다.

하나의 프로세스에는
여러 스레드가 존재할 수 있습니다.

```text
렌더러 프로세스
├─ 메인 스레드
├─ 컴포지터 스레드
├─ 래스터 작업 스레드
├─ 미디어 관련 스레드
└─ Worker 실행 스레드
```

같은 프로세스 안의 스레드는
프로세스의 메모리를 공유할 수 있습니다.

이 때문에 데이터 전달은 빠를 수 있지만,
동시에 같은 데이터에 접근하면
동기화 문제가 발생할 수 있습니다.

  **프로세스와 스레드는 같은 개념이 아닙니다.**

  “JavaScript는 싱글 스레드다”라는 설명은
  브라우저 전체에 스레드가 하나뿐이라는 뜻이 아닙니다.

  일반적인 페이지 JavaScript의 주 실행 흐름이
  렌더러 프로세스의 메인 스레드에서 처리된다는 의미에 가깝습니다.
</Callout>

이벤트 루프와 메인 스레드의 구체적인 동작은
뒤의 문서에서 별도로 다룹니다.

## 브라우저 프로세스

**브라우저 프로세스(browser process)**는
브라우저 전체를 관리하는 중심 프로세스입니다.

문서에 따라 다음 이름으로도 부릅니다.

- Browser Process
- Main Process
- Parent Process
- UI Process

브라우저마다 용어는 다르지만
대체로 다음 역할을 담당합니다.

### 브라우저 UI 관리

주소창, 탭, 북마크,
뒤로 가기와 앞으로 가기 버튼처럼
웹 페이지 바깥의 브라우저 인터페이스를 관리합니다.

웹 페이지 안의 버튼은
렌더러 프로세스가 다루는 페이지 콘텐츠이지만,
주소창과 탭 버튼은
브라우저 자체의 UI입니다.

### 탐색 관리

사용자가 주소를 입력하거나
링크를 클릭하면
어느 문서로 이동할지 판단하고
필요한 네트워크 요청과 렌더러 프로세스를 준비합니다.

브라우저의 **탐색(navigation)**은
단순히 URL 문자열을 바꾸는 작업이 아닙니다.

새 문서를 받을 준비를 하고,
보안 정책을 확인하고,
적절한 렌더러 프로세스를 선택한 뒤,
새 문서의 로딩을 시작하는 전체 과정입니다.

### 권한과 운영체제 자원 관리

웹 페이지는 신뢰할 수 없는 외부 코드일 수 있습니다.

따라서 파일 시스템, 카메라, 마이크,
클립보드와 같은 민감한 자원에
렌더러 프로세스가 무제한으로 직접 접근하게 두지 않습니다.

브라우저 프로세스가 권한을 확인하고
필요한 작업을 중개하는 구조를 사용합니다.

### 자식 프로세스 관리

브라우저 프로세스는
렌더러, GPU, 네트워크,
유틸리티 같은 다른 프로세스를 생성하고 관리합니다.

자식 프로세스가 종료되거나 멈췄을 때
해당 상태를 감지하고
페이지 오류 화면을 표시하거나
프로세스를 다시 준비할 수 있습니다.

## 렌더러 프로세스

**렌더러 프로세스(renderer process)**는
웹 페이지 콘텐츠를 처리하는 프로세스입니다.

Firefox 문서에서는 비슷한 역할의 프로세스를
**콘텐츠 프로세스(content process)**라고 부르기도 합니다.

렌더러 프로세스는 주로 다음 작업을 담당합니다.

- HTML 파싱
- DOM 구성
- CSS 처리
- JavaScript 실행
- 이벤트 전달과 처리
- 레이아웃 계산
- 페인트 정보 생성
- 스크롤과 애니메이션 처리 지원

렌더러 프로세스 안에는
여러 스레드와 엔진이 함께 존재합니다.

```text
렌더러 프로세스
├─ 렌더링 엔진
│  ├─ HTML 파서
│  ├─ CSS 처리
│  ├─ DOM
│  └─ 레이아웃·페인트 관련 기능
│
├─ JavaScript 엔진
│  └─ JavaScript 코드 실행
│
└─ 여러 실행 스레드
   ├─ 메인 스레드
   ├─ 컴포지터 스레드
   └─ 보조 작업 스레드
```

렌더링 엔진과 JavaScript 엔진의 차이는
다음 문서에서 자세히 다룹니다.

### 렌더러는 제한된 권한으로 실행된다

웹 페이지는 인터넷에서 받은
신뢰할 수 없는 콘텐츠를 처리합니다.

따라서 현대 브라우저는
렌더러 프로세스를 **샌드박스** 안에서 실행하여
운영체제 자원에 대한 직접 접근을 제한합니다.

렌더러가 파일이나 장치에 관련된 작업을 요청하면
권한이 더 높은 브라우저 프로세스가
요청을 검사하고 필요한 작업을 중개합니다.

이 구조는 렌더러의 취약점이 악용되더라도
피해 범위를 줄이는 방어층이 됩니다.

## 네트워크 프로세스와 네트워크 서비스

브라우저는 웹 페이지가 요청한 리소스를
네트워크에서 가져와야 합니다.

예를 들면 다음과 같습니다.

- HTML 문서
- CSS 파일
- JavaScript 파일
- 이미지와 글꼴
- API 응답
- 오디오와 비디오 데이터

네트워크 관련 구성 요소는
다음 작업을 처리합니다.

- DNS 조회
- TCP 또는 QUIC 연결
- TLS 인증서 확인
- HTTP 요청과 응답
- 프록시 설정
- 캐시 확인
- 쿠키와 인증 정보 처리
- 다운로드 데이터 전달

브라우저에 따라
이 기능이 독립된 네트워크 프로세스에 있거나,
브라우저 프로세스의 서비스 형태로 구성될 수 있습니다.

웹 개발자는 보통 이 내부 프로세스에 직접 접근하지 않습니다.

`fetch()` 같은 Web API를 호출하면
브라우저 내부의 여러 구성 요소가 협력하여
실제 네트워크 요청을 수행합니다.

## GPU·그래픽 프로세스

화면을 그리는 작업에는
CPU뿐 아니라 GPU도 사용됩니다.

브라우저는 그래픽 관련 작업을
별도의 GPU 또는 그래픽 프로세스로 분리할 수 있습니다.

주요 목적은 다음과 같습니다.

- 여러 페이지의 그래픽 결과 합성
- GPU 명령 실행
- 그래픽 드라이버 문제의 영향 격리
- Canvas·WebGL·비디오 같은 작업 지원
- 스크롤과 애니메이션의 부드러운 처리 지원

Chromium 계열의 현재 문서에서는
여러 렌더러의 합성 결과를 모으고
GPU를 이용해 화면에 그리는 구성 요소를
**Viz 프로세스**라고 설명합니다.

하지만 브라우저마다 이름과 책임 범위는 다릅니다.

따라서 “모든 브라우저에 정확히 같은 GPU 프로세스가 있다”고
가정하면 안 됩니다.

## 유틸리티 프로세스

브라우저에는 주요 프로세스 외에도
특정 작업을 분리하기 위한
여러 유틸리티 프로세스가 존재할 수 있습니다.

예를 들면 다음과 같습니다.

- 오디오·비디오 디코더
- PDF 처리
- 확장 프로그램
- 데이터 디코딩
- 인쇄 관련 작업
- 보안상 별도 격리가 필요한 기능

이러한 작업을 별도 프로세스로 나누면
오류나 취약점의 영향을 줄이고
작업별로 더 적절한 권한을 적용할 수 있습니다.

다만 실제 목록은
브라우저 버전과 운영체제에 따라 자주 달라집니다.

## 탭 하나는 프로세스 하나일까?

브라우저 구조를 처음 배울 때
다음처럼 설명하는 경우가 많습니다.

```text
탭 1 → 렌더러 프로세스 1
탭 2 → 렌더러 프로세스 2
탭 3 → 렌더러 프로세스 3
```

개념을 시작하기에는 편리하지만
항상 정확한 설명은 아닙니다.

<Callout>
  **탭과 렌더러 프로세스는 항상 1:1 관계가 아닙니다.**

  하나의 탭이 여러 렌더러 프로세스를 사용할 수도 있고,
  여러 문서가 조건에 따라 하나의 프로세스를 공유할 수도 있습니다.
</Callout>

### 한 탭이 여러 프로세스를 사용할 수 있다

페이지 안에 다른 사이트의 `iframe`이 포함되어 있다고 가정해 보겠습니다.

```text
https://shop.example
└─ iframe: https://payment.example
```

브라우저가 사이트 격리를 적용하면
상위 문서와 외부 결제 문서를
서로 다른 렌더러 프로세스에 배치할 수 있습니다.

```text
탭 하나
├─ shop.example 문서    → 렌더러 프로세스 A
└─ payment.example iframe → 렌더러 프로세스 B
```

Chromium에서는 이런 구조의 프레임을
**OOPIF(Out-of-Process iframe)**라고 부릅니다.

즉, 하나의 화면에 보이는 문서 트리가
여러 프로세스에 나뉘어 있을 수 있습니다.

### 여러 문서가 프로세스를 공유할 수 있다

프로세스마다 메모리 비용이 발생하므로
브라우저는 기기의 자원과 현재 상태에 따라
적절한 경우 프로세스를 재사용할 수 있습니다.

예를 들어 같은 사이트의 관련 문서나
메모리가 부족한 환경에서는
일부 콘텐츠가 프로세스를 공유할 수 있습니다.

정확한 배치 규칙은
브라우저·플랫폼·메모리 상황에 따라 달라집니다.

따라서 다음 공식으로 외우면 안 됩니다.

```text
탭 개수 = 렌더러 프로세스 개수
```

## Site Isolation이란?

**Site Isolation**은
서로 다른 사이트의 문서를
가능한 한 다른 렌더러 프로세스에 배치하여
사이트 사이의 보안 경계를 강화하는 구조입니다.

렌더러 프로세스에 취약점이 생기더라도
다른 사이트의 민감한 데이터를
같은 프로세스 메모리에서 직접 다루지 못하게 하는 것이 목적입니다.

```text
site-a.example → 렌더러 프로세스 A
site-b.example → 렌더러 프로세스 B
```

Site Isolation은 샌드박스와 함께 사용됩니다.

- **샌드박스**는 렌더러가 운영체제 자원에 접근하는 범위를 제한합니다.
- **Site Isolation**은 서로 다른 사이트의 콘텐츠를 프로세스 수준에서 분리합니다.

둘은 같은 기능이 아니라
서로 다른 위험을 줄이는 방어층입니다.

### Site와 Origin은 같은 말이 아니다

웹 보안에서 **origin**은 일반적으로
다음 세 요소의 조합입니다.

```text
scheme + host + port
```

예를 들면 다음 두 주소는
호스트는 같아도 포트가 다르므로
서로 다른 origin입니다.

```text
https://example.com:443
https://example.com:8443
```

**site**는 브라우저의 격리 정책에서
origin보다 더 넓은 단위로 사용될 수 있습니다.

정확한 사이트 계산과 origin 규칙은
뒤의 보안 문서에서 자세히 다룹니다.

여기서는 다음만 기억하면 됩니다.

> 브라우저는 탭 번호보다
> 문서 사이의 접근 관계와 보안 경계를 기준으로
> 프로세스를 배치합니다.

## IPC란?

서로 다른 프로세스는
메모리 공간이 분리되어 있으므로
일반 변수로 직접 대화할 수 없습니다.

프로세스 사이에서 메시지와 데이터를 주고받는 방식을
**IPC(Inter-Process Communication)**라고 합니다.

```text
브라우저 프로세스
       │
       │ IPC 메시지
       ▼
렌더러 프로세스
```

예를 들어 렌더러 프로세스에서
사용자가 링크를 클릭했다고 가정해 보겠습니다.

렌더러는 링크 클릭과 이동 요청을 처리한 뒤
브라우저 프로세스와 IPC로 통신합니다.

브라우저 프로세스는
탐색 가능 여부와 보안 정책을 확인하고,
네트워크 구성 요소 및 적절한 렌더러와 협력합니다.

### IPC는 보안 경계이기도 하다

브라우저 프로세스는
렌더러가 보낸 요청을 무조건 신뢰하면 안 됩니다.

렌더러는 외부 웹 콘텐츠를 실행하는 공간이므로
오염되거나 공격받을 가능성을 고려해야 합니다.

따라서 브라우저 프로세스는
IPC 메시지의 내용과 권한을 검사하고,
허용된 작업만 수행해야 합니다.

웹 개발자가 IPC 메시지를 직접 작성하지는 않지만,
브라우저의 Web API가 내부적으로
여러 프로세스와 서비스를 연결한다는 점을 이해하면
API의 비동기성과 보안 제약을 이해하기 쉬워집니다.

## 샌드박스란?

**샌드박스(sandbox)**는
프로세스가 사용할 수 있는 권한과 자원을 제한하는 보안 환경입니다.

렌더러 프로세스는 일반적으로
다음 작업을 마음대로 수행할 수 없도록 제한됩니다.

- 임의의 로컬 파일 읽기
- 운영체제 설정 변경
- 장치에 무제한 접근
- 다른 프로세스의 메모리 읽기
- 사용자 권한 없이 카메라나 마이크 사용

웹 페이지가 민감한 기능을 사용하려면
브라우저가 정의한 Web API와 권한 절차를 거쳐야 합니다.

예를 들어 카메라 사용은
페이지가 운영체제 장치를 직접 여는 방식이 아닙니다.

브라우저가 제공하는 API를 호출하고,
브라우저가 보안 컨텍스트와 사용자 권한을 확인한 뒤,
허용된 범위의 기능을 제공합니다.

### 샌드박스만으로 모든 공격이 막히는 것은 아니다

샌드박스는 중요한 방어층이지만
완전한 보안을 뜻하지는 않습니다.

브라우저는 보통 다음 방어를 함께 사용합니다.

- 프로세스 분리
- 렌더러 샌드박스
- Site Isolation
- 동일 출처 정책
- 권한 시스템
- 네트워크 응답 검사
- 운영체제 보안 기능

여러 방어층을 겹쳐 사용하는 방식을
**심층 방어(defense in depth)**라고 합니다.

## 주소를 입력하면 어떤 일이 일어날까?

사용자가 주소창에 URL을 입력하고 Enter를 누르면
브라우저 내부에서는 여러 구성 요소가 협력합니다.

아래 흐름은 이해를 위한 단순화입니다.

<Steps>

### 브라우저 UI가 입력을 받는다

주소창은 웹 페이지가 아니라
브라우저 자체의 UI입니다.

브라우저 프로세스는 입력이
검색어인지 URL인지 판단합니다.

### 탐색을 시작한다

URL로 판단하면
브라우저 프로세스가 탐색을 시작합니다.

필요한 보안 정책과 현재 문서 상태를 확인하고
네트워크 요청을 준비합니다.

### 네트워크에서 응답을 받는다

네트워크 관련 구성 요소가
DNS 조회, 연결, TLS, HTTP 요청을 처리합니다.

서버가 리다이렉트를 응답하면
새 주소로 탐색을 다시 진행할 수 있습니다.

### 응답 종류를 확인한다

응답 헤더와 데이터가
HTML 문서인지, 다운로드 파일인지,
다른 종류의 리소스인지 확인합니다.

### 렌더러 프로세스를 선택한다

새 문서를 어느 렌더러 프로세스에서 실행할지 결정합니다.

다른 사이트로 이동하거나
추가 격리가 필요한 경우에는
새로운 렌더러 프로세스가 선택될 수 있습니다.

### 탐색을 커밋한다

브라우저 프로세스가 렌더러 프로세스에
새 문서를 로드하도록 전달합니다.

이 시점을 **탐색 커밋(navigation commit)**이라고 합니다.

주소창, 보안 표시, 방문 기록도
새 문서에 맞게 갱신됩니다.

### 렌더러가 문서를 처리한다

렌더러 프로세스가 HTML 데이터를 받아
DOM을 만들고,
CSS와 JavaScript를 처리하고,
화면에 표시할 결과를 준비합니다.

### 그래픽 결과가 화면에 표시된다

렌더러가 만든 결과를
컴포지터와 GPU 관련 구성 요소가 합성하여
최종 화면에 표시합니다.

</Steps>

```text
주소창 입력
   ↓
브라우저 프로세스
   ↓
네트워크 요청
   ↓
응답 확인
   ↓
렌더러 프로세스 선택
   ↓
탐색 커밋
   ↓
HTML·CSS·JavaScript 처리
   ↓
그래픽 합성
   ↓
화면 표시
```

이 흐름을 이해하면
네트워크 응답을 받는 일과
JavaScript가 실행되는 일이
브라우저 내부에서 같은 작업이 아니라는 점을 알 수 있습니다.

## 프로세스 분리가 주는 장점

### 안정성

한 렌더러 프로세스가 충돌해도
브라우저 UI와 다른 프로세스가 살아 있다면
다른 탭을 계속 사용할 수 있습니다.

사용자는 문제가 생긴 탭만 닫거나
다시 로드할 수 있습니다.

### 보안

신뢰할 수 없는 웹 콘텐츠를
권한이 제한된 렌더러 프로세스에 배치하고,
다른 사이트와도 분리하여
공격의 영향을 줄일 수 있습니다.

### 응답성

서로 다른 사이트의 작업을
여러 프로세스와 스레드에서 나누어 처리하면
하나의 작업이 전체 브라우저를 막는 상황을 줄일 수 있습니다.

### 병렬 처리

여러 CPU 코어를 사용하여
서로 다른 페이지나 보조 작업을
동시에 처리할 수 있습니다.

## 프로세스 분리의 비용

멀티프로세스 구조에는 장점만 있는 것은 아닙니다.

### 메모리 사용량 증가

프로세스마다
자신의 메모리 공간과 실행 상태가 필요합니다.

여러 렌더러 프로세스에는
렌더링 엔진과 JavaScript 엔진의 상태도 존재하므로
프로세스 수가 늘면 메모리 사용량이 증가할 수 있습니다.

### 프로세스 간 통신 비용

서로 다른 프로세스는
IPC를 사용해야 합니다.

데이터를 직렬화하거나 복사하고,
메시지를 전달하고,
응답을 기다리는 비용이 발생할 수 있습니다.

### 구조 복잡성 증가

한 페이지가 여러 프로세스에 걸쳐 구성되면
브라우저 내부 구현과 디버깅이 복잡해집니다.

브라우저는 이러한 비용을 감수하고도
안정성과 보안이 더 중요하다고 판단하여
멀티프로세스 구조를 사용합니다.

- 정확한 프로세스 배치는 브라우저의 구현 세부 사항입니다.

## 브라우저 지원과 Baseline

브라우저의 프로세스 모델은
웹 개발자가 호출하는 하나의 Web API가 아닙니다.

따라서 MDN의 **Baseline** 상태를
이 문서 전체에 적용할 수 없습니다.

또한 웹 표준은
브라우저가 반드시 몇 개의 운영체제 프로세스를 사용해야 하는지,
탭을 어떤 프로세스에 배치해야 하는지 정의하지 않습니다.

브라우저 개발사는
보안, 성능, 메모리,
운영체제 제약을 고려하여
자신의 프로세스 모델을 구현합니다.

<Callout>
  프로세스 이름과 개수는
  브라우저 업데이트로 달라질 수 있습니다.

  웹 페이지 코드는 특정 탭이
  반드시 독립된 렌더러 프로세스를 가진다고
  가정해서는 안 됩니다.
</Callout>

## 직접 확인하기

Chromium 계열 브라우저에서는
브라우저 작업 관리자를 사용하여
현재 실행 중인 프로세스와 자원 사용량을 확인할 수 있습니다.

### 1. 여러 사이트를 연다

서로 다른 사이트를
여러 탭에서 열어 봅니다.

한 페이지 안에 외부 사이트의 `iframe`이 있다면
추가 렌더러 프로세스가 표시될 수도 있습니다.

### 2. 브라우저 작업 관리자를 연다

Chrome에서는 일반적으로
브라우저 메뉴의 **도구 더보기 → 작업 관리자**에서 열 수 있습니다.

운영체제의 작업 관리자와
브라우저 자체 작업 관리자는 서로 다릅니다.

### 3. 항목을 비교한다

다음 항목을 확인합니다.

- 탭 또는 페이지 이름
- 프로세스 ID
- 메모리 사용량
- CPU 사용량
- 네트워크 사용량

### 4. 탭 개수와 프로세스 개수를 비교한다

탭 개수와 렌더러 프로세스 개수가
항상 같지 않을 수 있습니다.

같은 사이트의 문서가 프로세스를 공유하거나,
한 탭의 외부 `iframe`이
별도 프로세스를 사용할 수 있기 때문입니다.

### 5. 페이지가 멈췄을 때 범위를 관찰한다

특정 탭의 작업이 무거워졌을 때
브라우저 UI와 다른 탭이
계속 반응하는지 확인합니다.

프로세스 분리와 스레드 분리의 효과를
간접적으로 관찰할 수 있습니다.

## 흔한 실수

### 브라우저 전체에 스레드가 하나라고 생각한다

JavaScript의 기본 실행 흐름을
싱글 스레드라고 설명한다고 해서
브라우저 전체가 하나의 스레드만 사용하는 것은 아닙니다.

브라우저에는 네트워크, 그래픽,
컴포지팅, 미디어, Worker 등
여러 작업을 위한 프로세스와 스레드가 존재합니다.

### 탭 하나가 항상 프로세스 하나라고 생각한다

탭과 렌더러 프로세스는
항상 1:1 관계가 아닙니다.

사이트 격리로 인해
한 탭 안의 다른 사이트 `iframe`이
별도 프로세스에서 실행될 수 있습니다.

반대로 브라우저의 자원 정책에 따라
일부 문서가 프로세스를 공유할 수도 있습니다.

### 렌더러 프로세스가 직접 모든 일을 한다고 생각한다

렌더러는 페이지 콘텐츠를 처리하지만
네트워크, 파일, 권한,
브라우저 UI와 같은 모든 작업을
혼자 직접 수행하지 않습니다.

브라우저 프로세스와 네트워크·GPU·유틸리티 구성 요소가
IPC를 통해 협력합니다.

### 렌더러 프로세스와 렌더링 엔진을 같은 말로 사용한다

렌더러 프로세스는
운영체제 수준의 실행 공간입니다.

렌더링 엔진은
그 프로세스 안에서 HTML·CSS·DOM과
페이지 렌더링을 처리하는 소프트웨어 구성 요소입니다.

둘은 서로 관련되어 있지만
같은 개념은 아닙니다.

### 프로세스 분리가 있으면 메모리 누수가 다른 탭에 절대 영향을 주지 않는다고 생각한다

프로세스 분리는
오류와 메모리 공간을 격리하는 데 도움이 됩니다.

하지만 전체 시스템 메모리는 공유 자원이므로
한 페이지가 지나치게 많은 메모리를 사용하면
브라우저와 운영체제 전체의 자원 압박이 커질 수 있습니다.

브라우저는 백그라운드 탭 정리,
프로세스 재사용, 페이지 폐기 같은 정책을 사용할 수 있습니다.

### 브라우저 내부 구조가 웹 표준이라고 생각한다

DOM, Fetch, HTML 파싱 규칙처럼
웹 표준이 정의하는 동작이 있습니다.

하지만 브라우저가 프로세스를 몇 개 생성하고
어떤 문서를 어느 프로세스에 배치하는지는
대부분 브라우저 구현 세부 사항입니다.

웹 코드는 특정 구현을 전제로 작성하면 안 됩니다.

## 확인 문제

### 1. 프로세스와 스레드의 가장 큰 차이는 무엇일까?

<details>
  <summary>정답 보기</summary>

  프로세스는 일반적으로 독립된 메모리 공간을 가지는 실행 단위입니다.

  스레드는 하나의 프로세스 안에서 실행되며
  같은 프로세스의 메모리를 공유합니다.

</details>

### 2. 브라우저가 렌더러 프로세스를 분리하는 이유는 무엇일까?

<details>
  <summary>정답 보기</summary>

  한 페이지의 충돌이나 멈춤이
  다른 페이지와 브라우저 전체에 미치는 영향을 줄이고,
  서로 다른 사이트를 보안상 격리하며,
  여러 작업을 병렬로 처리하기 위해서입니다.

</details>

### 3. 탭 하나는 항상 렌더러 프로세스 하나를 사용할까?

<details>
  <summary>정답 보기</summary>

  아닙니다.

  한 탭 안의 다른 사이트 `iframe`이
  별도 렌더러 프로세스를 사용할 수 있습니다.

  반대로 자원 상황과 문서 관계에 따라
  일부 문서가 프로세스를 공유할 수도 있습니다.

</details>

### 4. IPC가 필요한 이유는 무엇일까?

<details>
  <summary>정답 보기</summary>

  서로 다른 프로세스는
  일반적으로 메모리 공간이 분리되어 있기 때문입니다.

  브라우저 프로세스와 렌더러 프로세스는
  IPC 메시지를 사용하여 탐색, 권한,
  입력과 렌더링 관련 정보를 주고받습니다.

</details>

### 5. 샌드박스와 Site Isolation은 같은 기능일까?

<details>
  <summary>정답 보기</summary>

  아닙니다.

  샌드박스는 렌더러 프로세스가
  운영체제 자원에 접근하는 범위를 제한합니다.

  Site Isolation은 서로 다른 사이트의 콘텐츠를
  가능한 한 다른 렌더러 프로세스에 배치하여
  사이트 사이의 보안 경계를 강화합니다.

</details>

## 요약

- 브라우저는 여러 프로세스와 스레드가 협력하는 멀티프로세스 애플리케이션입니다.
- 프로세스는 일반적으로 독립된 메모리 공간을 가지며, 스레드는 같은 프로세스의 메모리를 공유합니다.
- 브라우저 프로세스는 UI, 탐색, 권한과 다른 프로세스를 관리합니다.
- 렌더러 프로세스는 HTML·CSS·JavaScript와 페이지 콘텐츠를 처리합니다.
- 네트워크, GPU, 미디어와 보조 작업은 별도 프로세스나 서비스로 분리될 수 있습니다.
- 탭과 렌더러 프로세스는 항상 1:1 관계가 아닙니다.
- Site Isolation은 서로 다른 사이트를 프로세스 수준에서 분리하여 보안을 강화합니다.
- 프로세스 사이의 통신에는 IPC가 사용됩니다.
- 샌드박스는 렌더러의 운영체제 접근 권한을 제한합니다.
- 정확한 프로세스 배치 방식은 웹 표준이 아니라 브라우저의 구현 세부 사항입니다.
