title: "05. window와 브라우저 전역 환경"
description: "브라우저 전역 객체인 Window와 globalThis, WindowProxy, iframe별 전역 환경의 관계"
---

브라우저에서 다음 코드는 별도의 객체를 가져오지 않아도 실행됩니다.

```js
console.log(document.title);
console.log(location.href);
setTimeout(() => {
  console.log("실행 완료");
}, 1000);
```

`document`, `location`, `setTimeout()`은
ECMAScript 언어가 기본으로 제공하는 기능이 아닙니다.

브라우저가 현재 페이지의 JavaScript 실행 환경에
전역 프로퍼티와 메서드로 노출한 Web API입니다.

이 브라우저 전역 환경의 중심에 있는 객체가
**`Window`**입니다.

```js
console.log(window.document === document); // true
console.log(window.location === location); // true
console.log(window.setTimeout === setTimeout); // true
```

하지만 브라우저 전역 환경을 이해할 때
단순히 “전역 객체는 `window`다”라고만 외우면 부족합니다.

다음 개념을 함께 구분해야 합니다.

- `Window` 인터페이스
- 전역 객체와 전역 스코프
- `window`, `self`, `globalThis`
- 실제 접근 과정에 존재하는 `WindowProxy`
- 문서와 탐색 컨텍스트의 관계
- iframe마다 분리되는 전역 환경
- 동일 출처 정책이 제한하는 창 간 접근

<Callout>
  **`Window`는 브라우저 탭의 UI 자체를 뜻하지 않습니다.**

  현재 브라우징 컨텍스트에서 실행되는 스크립트에
  문서, 탐색, 타이머, 크기, 이벤트 같은 기능을 제공하는
  웹 플랫폼의 전역 인터페이스입니다.
</Callout>

## 먼저 전체 관계 보기

브라우저 페이지의 전역 환경을 단순화하면
다음과 같이 볼 수 있습니다.

```text
탭 또는 iframe의 브라우징 컨텍스트
│
├─ WindowProxy
│  └─ 현재 활성 Window를 가리키는 접근 창구
│
├─ Window
│  ├─ document ─────────────> Document
│  ├─ location ─────────────> Location
│  ├─ history ──────────────> History
│  ├─ navigator ────────────> Navigator
│  ├─ screen ───────────────> Screen
│  ├─ localStorage ─────────> Storage
│  ├─ setTimeout()
│  ├─ requestAnimationFrame()
│  └─ addEventListener()
│
└─ 현재 활성 Document
   └─ DOM 트리
```

JavaScript 코드에서 `window`를 사용하면
겉으로는 현재 `Window` 객체를 직접 사용하는 것처럼 보입니다.

웹 표준의 내부 모델에서는
브라우징 컨텍스트에 연결된 `WindowProxy`가
현재 활성 `Window`로 작업을 전달합니다.

이 차이는 일반적인 DOM 작업에서는 거의 드러나지 않지만,
페이지 이동과 iframe 구조를 이해할 때 중요합니다.

## `Window`란?

`Window` 인터페이스는
DOM 문서를 포함하는 창의 전역 환경을 나타냅니다.

현재 창에 로드된 문서는
`window.document`로 접근할 수 있습니다.

```js
console.log(window.document);
console.log(window.document === document); // true
```

`Window`에는 한 종류의 기능만 들어 있지 않습니다.

브라우저가 페이지에 제공하는 여러 기능이
하나의 전역 인터페이스 주변에 모여 있습니다.

### 문서 관련 기능

```js
window.document;
window.getSelection();
window.getComputedStyle(document.body);
```

### 탐색 관련 기능

```js
window.location;
window.history;
```

### 창과 뷰포트 관련 기능

```js
window.innerWidth;
window.innerHeight;
window.scrollX;
window.scrollY;
```

### 일정 예약 관련 기능

```js
window.setTimeout(() => {}, 1000);
window.setInterval(() => {}, 1000);
window.requestAnimationFrame(() => {});
```

### 이벤트 관련 기능

```js
window.addEventListener("resize", () => {
  console.log(window.innerWidth);
});
```

### 브라우저 환경 관련 객체

```js
window.navigator;
window.screen;
window.performance;
window.crypto;
```

이 기능들은 모두 같은 명세에서 한꺼번에 정의된 것이 아닙니다.

HTML, DOM과 여러 Web API 명세가 정의한 기능이
브라우저의 전역 환경을 통해 함께 노출됩니다.

## `window`는 어디에서 오는가?

`window`는 현재 창의 전역 객체에 접근하기 위해
브라우저가 제공하는 전역 프로퍼티입니다.

```js
console.log(window);
console.log(window.window === window); // true
```

`window.window`가 다시 자기 자신을 가리키므로
다음 표현도 모두 같은 값을 반환합니다.

```js
console.log(window.window === window); // true
console.log(window.window.window === window); // true
```

실무에서는 `window.window.window`처럼 작성하지 않습니다.

이 예제는 `window` 프로퍼티가
현재 창의 전역 객체 자신을 참조한다는 사실을 보여주기 위한 것입니다.

## 왜 `window.`를 생략할 수 있을까?

브라우저 전역 객체의 프로퍼티는
전역 이름으로도 조회할 수 있습니다.

```js
console.log(window.document === document); // true
console.log(window.location === location); // true
console.log(window.navigator === navigator); // true
```

전역 메서드도 마찬가지입니다.

```js
window.setTimeout(() => {
  console.log("window.setTimeout");
}, 0);

setTimeout(() => {
  console.log("setTimeout");
}, 0);
```

따라서 다음 두 코드는 같은 브라우저 API를 호출합니다.

```js
window.alert("안녕하세요");
alert("안녕하세요");
```

다만 `window.`를 생략했다고 해서
그 기능이 JavaScript 언어 자체의 기능으로 바뀌는 것은 아닙니다.

```js
// 브라우저 전역 환경에서 제공
window.document;
window.fetch;
window.setTimeout;
```

`document`, `fetch`, `setTimeout()`은
브라우저가 노출한 Web API입니다.

<Callout type="warning">
  **전역에서 보인다는 것과 ECMAScript 내장 기능이라는 것은 다릅니다.**

  `Array`, `Promise`, `Map`은 ECMAScript 표준 내장 객체입니다.

  `document`, `location`, `localStorage`는
  브라우저 호스트 환경이 제공하는 Web API입니다.
</Callout>

## 전역 객체와 전역 스코프는 같은 말일까?

**전역 객체(global object)**와
**전역 스코프(global scope)**는 밀접하지만 같은 개념은 아닙니다.

- 전역 객체는 프로퍼티를 가진 객체입니다.
- 전역 스코프는 코드에서 이름을 해석하는 범위입니다.

브라우저의 일반 스크립트에서는
전역 이름과 `window` 프로퍼티가 연결되는 경우가 많습니다.

하지만 모든 전역 선언이
반드시 `window`의 프로퍼티가 되는 것은 아닙니다.

<Callout>
  **전제 지식**

  `var`, `let`, `const`의 스코프 규칙 자체는
  ECMAScript 영역입니다.

  여기서는 브라우저 전역 객체와 연결되는 결과만 확인합니다.
</Callout>

## 일반 스크립트의 `var`와 `window`

클래식 스크립트의 최상위에서 `var`로 선언한 이름은
전역 객체의 프로퍼티와 연결됩니다.

```html
<script>
  var siteName = "Browser JavaScript";

  console.log(window.siteName); // "Browser JavaScript"
  console.log(siteName === window.siteName); // true
</script>
```

최상위 함수 선언도 일반적으로
전역 객체의 프로퍼티로 나타납니다.

```html
<script>
  function greet() {
    return "안녕하세요";
  }

  console.log(window.greet === greet); // true
</script>
```

이 동작 때문에 오래된 브라우저 스크립트에서는
서로 다른 파일이 같은 전역 이름을 덮어쓰는 문제가 자주 발생했습니다.

```html
<script>
  var config = { mode: "development" };
</script>

<script>
  var config = { mode: "production" };
</script>
```

두 번째 스크립트가 같은 전역 프로퍼티를 다시 사용합니다.

## `let`과 `const`는 `window` 프로퍼티가 아니다

클래식 스크립트의 최상위에서 선언하더라도
`let`과 `const`는 `window` 프로퍼티가 되지 않습니다.

```html
<script>
  let pageCount = 1;
  const appName = "Docs";

  console.log(pageCount); // 1
  console.log(appName); // "Docs"

  console.log(window.pageCount); // undefined
  console.log(window.appName); // undefined
</script>
```

이름은 전역 범위에서 사용할 수 있지만
전역 객체의 일반 프로퍼티로 추가되지는 않습니다.

```js
let value = 10;

console.log("value" in window); // false
console.log(Object.hasOwn(window, "value")); // false
```

따라서 “전역에 선언한 모든 변수는 `window`에 들어간다”는 설명은
정확하지 않습니다.

## ES Module의 최상위 선언

`type="module"` 스크립트는
자체 모듈 스코프를 가집니다.

최상위 선언이 `window` 프로퍼티가 되지 않습니다.

```html
<script type="module">
  var moduleValue = 1;
  let moduleState = 2;
  const moduleName = "example";

  console.log(window.moduleValue); // undefined
  console.log(window.moduleState); // undefined
  console.log(window.moduleName); // undefined
</script>
```

모듈 내부에서도 브라우저 전역 API는 사용할 수 있습니다.

```html
<script type="module">
  console.log(window.location.href);
  console.log(document.title);
  console.log(globalThis === window); // 일반적인 브라우저 창에서 true
</script>
```

모듈 스코프와 브라우저 전역 객체는
서로 다른 문제입니다.

- 선언한 이름은 모듈 내부에 유지됩니다.
- 브라우저가 제공한 전역 API는 계속 접근할 수 있습니다.

## `globalThis`란?

`globalThis`는 실행 환경에 관계없이
전역 `this` 값에 접근하기 위한 표준 프로퍼티입니다.

브라우저 창에서는 일반적으로 다음 비교가 참입니다.

```js
console.log(globalThis === window); // true
console.log(globalThis.document === document); // true
```

하지만 `globalThis`의 장점은
브라우저 창에만 묶이지 않는다는 점입니다.

```js
function getGlobalObject() {
  return globalThis;
}
```

같은 코드를 다음과 같은 환경에서도 사용할 수 있습니다.

- 브라우저의 페이지
- Web Worker
- Node.js
- 그 밖의 JavaScript 호스트 환경

각 환경의 실제 전역 객체와 제공 API는 다릅니다.

```js
console.log(typeof globalThis);
console.log(typeof globalThis.document);
```

브라우저 페이지에서는 `document`가 보통 `"object"`이지만,
Worker나 Node.js에서는 페이지 DOM이 없으므로
`"undefined"`가 될 수 있습니다.

<Callout>
  여러 실행 환경에서 동작해야 하는 코드라면
  브라우저 전용 이름인 `window`보다
  `globalThis`가 의도를 더 정확하게 표현할 수 있습니다.
</Callout>

## `self`는 무엇일까?

브라우저 창에서 `self`는
현재 전역 환경을 가리키는 프로퍼티입니다.

```js
console.log(self === window); // true
console.log(self === globalThis); // true
```

`self`는 Worker 전역 환경에서도 제공됩니다.

```js
// worker.js
console.log(self === globalThis); // true
console.log(typeof self.document); // "undefined"
```

따라서 `self`라는 이름만 보고
항상 `Window` 객체라고 판단하면 안 됩니다.

브라우저 페이지에서는 `Window`를 가리키지만,
Worker에서는 `WorkerGlobalScope` 계열의 전역 객체를 가리킵니다.

### 창 환경에서의 관계

```text
window ─────┐
self ───────┼─> 현재 창의 전역 접근 값
frames ─────┤
globalThis ─┘
```

일반적인 최상위 페이지에서는
다음 비교가 모두 참입니다.

```js
console.log(window === self);
console.log(window === frames);
console.log(window === globalThis);
```

`frames`는 현재 창의 프레임 컬렉션에 접근하는 성격도 가지므로
일반 전역 객체 접근에는 `window`, `self`, `globalThis` 중
의도에 맞는 이름을 사용하는 편이 좋습니다.

## 전역 `this`는 항상 `window`일까?

클래식 스크립트의 최상위 `this`는
브라우저 창에서 일반적으로 `window`와 같습니다.

```html
<script>
  console.log(this === window); // true
</script>
```

ES Module의 최상위 `this`는 `undefined`입니다.

```html
<script type="module">
  console.log(this); // undefined
  console.log(globalThis === window); // true
</script>
```

따라서 전역 객체가 필요할 때
최상위 `this`에 의존하는 코드는 실행 방식에 따라 달라질 수 있습니다.

명시적으로 다음 중 하나를 사용합니다.

```js
window;     // 브라우저 창임을 전제로 할 때
globalThis; // 여러 실행 환경을 고려할 때
```

## `WindowProxy`란?

웹 표준의 내부 모델에서
스크립트가 창을 참조할 때 받는 값은
일반적으로 `WindowProxy`입니다.

`WindowProxy`는 현재 활성 `Window`를 감싸고
대부분의 작업을 해당 `Window`로 전달하는 특수 객체입니다.

```text
브라우징 컨텍스트
└─ WindowProxy
   └─ 현재 활성 Window
      └─ 현재 활성 Document
```

일반 코드에서는 다음처럼 단순히 `window`로 사용합니다.

```js
console.log(window.document.title);
```

`WindowProxy`가 존재하는 이유는
같은 탭이나 iframe에서 페이지가 이동하면
활성 문서와 `Window`는 바뀔 수 있지만,
해당 브라우징 컨텍스트를 가리키는 참조는
계속 유지할 필요가 있기 때문입니다.

## 페이지를 이동하면 무엇이 바뀔까?

한 탭에서 다른 문서로 이동하면
기존 문서의 전역 환경을 그대로 재사용하는 것이 아닙니다.

개념적으로 다음과 같은 변화가 일어납니다.

```text
이동 전
WindowProxy ──> Window A ──> Document A

페이지 이동

이동 후
WindowProxy ──> Window B ──> Document B
```

브라우징 컨텍스트에 연결된 `WindowProxy`는 유지되지만
내부에서 가리키는 활성 `Window`가 바뀝니다.

이 구조는 다음 상황을 설명하는 데 도움이 됩니다.

- iframe의 `contentWindow` 참조
- 새 창의 반환값
- 페이지 탐색 후 창 참조
- 동일 출처와 교차 출처 접근 제한

실무 코드에서 `WindowProxy`의 내부 슬롯을
직접 다루는 API는 없습니다.

표준의 동작 모델을 이해하기 위한 개념입니다.

## `window`와 `document`의 관계

`Window`는 문서를 포함하는 전역 환경이고,
`Document`는 현재 웹 문서와 DOM 트리의 진입점입니다.

```text
Window
└─ document
   └─ Document
      └─ DOM 트리
```

```js
console.log(window.document === document); // true
console.log(document.defaultView === window); // true
```

`document.defaultView`는
해당 문서와 연결된 `Window`를 반환합니다.

```js
const view = document.defaultView;

if (view) {
  console.log(view.innerWidth);
}
```

일반적인 HTML 문서에서는 `window`가 반환됩니다.

문서를 다른 방식으로 생성했거나
연결된 뷰가 없는 경우에는 상황이 다를 수 있으므로
재사용 가능한 코드에서는 반환값을 확인할 수 있습니다.

## 하나의 탭에는 `window`가 하나뿐일까?

최상위 문서만 있는 단순한 페이지에서는
하나의 전역 환경만 보이는 것처럼 느껴집니다.

하지만 페이지 안에 iframe이 있으면
각 iframe은 자신의 브라우징 컨텍스트와 전역 환경을 가집니다.

```html
<iframe id="preview" src="./preview.html"></iframe>
```

```text
최상위 브라우징 컨텍스트
├─ WindowProxy
├─ Window
└─ Document
   └─ iframe
      └─ 중첩 브라우징 컨텍스트
         ├─ WindowProxy
         ├─ Window
         └─ Document
```

부모 페이지와 iframe 안의 페이지는
각자 별도의 `window`와 `document`를 가집니다.

## iframe의 `contentWindow`

부모 문서에서는 iframe 요소의 `contentWindow`를 통해
해당 iframe의 창 참조를 얻을 수 있습니다.

```js
const frame = document.querySelector("#preview");

console.log(frame.contentWindow);
```

같은 출처인 경우에는
iframe의 문서 내용에도 접근할 수 있습니다.

```js
const frame = document.querySelector("#preview");

frame.addEventListener("load", () => {
  const childWindow = frame.contentWindow;

  if (!childWindow) return;

  console.log(childWindow.document.title);
});
```

`contentWindow` 자체의 참조를 얻는 것과
그 안의 모든 프로퍼티를 자유롭게 읽는 것은 다른 문제입니다.

출처가 다르면 동일 출처 정책 때문에
`document` 같은 민감한 프로퍼티 접근이 제한됩니다.

<Callout type="warning">
  **교차 출처 iframe의 DOM을 직접 읽을 수 없습니다.**

  출처가 다른 창과 데이터를 주고받아야 한다면
  직접 DOM에 접근하려 하지 말고
  `window.postMessage()`를 사용해야 합니다.
</Callout>

## `window.parent`

iframe 안에서 `window.parent`는
현재 프레임을 포함하는 바로 위 부모 창을 가리킵니다.

```js
console.log(window.parent);
```

최상위 문서에는 부모 프레임이 없으므로
`window.parent`가 자기 자신을 가리킵니다.

```js
const isTopLevel = window.parent === window;
console.log(isTopLevel);
```

iframe 안에서는 일반적으로 다음 비교가 거짓입니다.

```js
console.log(window.parent === window); // iframe 안에서는 보통 false
```

단, 부모 창의 내부 데이터에 접근할 수 있는지는
동일 출처 정책에 따라 결정됩니다.

## `window.top`

`window.top`은
프레임 계층에서 가장 위쪽의 창을 가리킵니다.

```text
최상위 창           window.top
└─ iframe A         window.parent
   └─ iframe B      현재 window
```

iframe B 안에서 다음 관계를 생각할 수 있습니다.

```js
window;        // iframe B
window.parent; // iframe A
window.top;    // 최상위 창
```

최상위 문서에서는 다음 비교가 참입니다.

```js
console.log(window.top === window); // true
```

중첩 iframe 안에서는 보통 거짓입니다.

```js
console.log(window.top === window); // 보통 false
```

`window.top` 참조를 얻을 수 있더라도
교차 출처 최상위 창의 DOM을 자유롭게 읽을 수는 없습니다.

## `window.frameElement`

iframe 안에서 `window.frameElement`는
현재 창을 포함하고 있는 프레임 요소를 반환합니다.

```js
console.log(window.frameElement);
```

최상위 문서에서는 보통 `null`입니다.

```js
if (window.frameElement === null) {
  console.log("최상위 문서입니다.");
}
```

교차 출처 관계에서는 보안상 `null`이 반환될 수 있습니다.

따라서 `frameElement`만으로
항상 최상위 문서 여부를 판별할 수 있다고 가정하면 안 됩니다.

## `window.opener`

`window.open()`이나 특정 링크 탐색으로 열린 창은
자신을 연 창에 대한 참조를 `window.opener`로 가질 수 있습니다.

```js
console.log(window.opener);
```

하지만 보안 정책과 링크 속성에 따라
`null`일 수 있습니다.

특히 새 탭으로 외부 사이트를 열 때는
불필요한 `opener` 연결을 남기지 않는 것이 안전합니다.

```html
<a
  href="https://example.com"
  target="_blank"
  rel="noopener"
>
  외부 사이트 열기
</a>
```

현대 브라우저는 `target="_blank"`에 대해
안전한 기본 동작을 적용하는 경우가 많지만,
명시적인 보안 의도를 보여 주기 위해
`rel="noopener"`를 사용할 수 있습니다.

<Callout type="warning">
  새 창과 부모 창의 연결은
  탐색 변경이나 피싱 공격에 악용될 수 있습니다.

  외부 페이지와의 창 연결이 필요하지 않다면
  `noopener`를 적용하고,
  필요한 통신은 출처를 검증한 `postMessage()`로 제한합니다.
</Callout>

## 동일 출처 정책과 창 접근

두 창이 서로의 DOM과 JavaScript 상태에 접근하려면
기본적으로 같은 출처여야 합니다.

출처는 일반적으로 다음 세 요소의 조합으로 판단합니다.

```text
스킴 + 호스트 + 포트
```

예를 들어 다음 두 URL은 같은 출처입니다.

```text
https://example.com/page-a
https://example.com/page-b
```

다음 조합들은 출처가 다릅니다.

```text
https://example.com
http://example.com
```

스킴이 다릅니다.

```text
https://example.com
https://api.example.com
```

호스트가 다릅니다.

```text
https://example.com
https://example.com:8443
```

포트가 다릅니다.

교차 출처 창 참조에서 일부 제한된 작업은 가능할 수 있지만,
다음과 같은 민감한 접근은 제한됩니다.

```js
// 교차 출처라면 SecurityError가 발생할 수 있음
otherWindow.document;
otherWindow.localStorage;
otherWindow.someGlobalValue;
```

창 사이 통신이 필요하면
`postMessage()`를 사용합니다.

```js
otherWindow.postMessage(
  { type: "READY" },
  "https://example.com"
);
```

메시지를 받을 때는 반드시 `origin`을 검증합니다.

```js
window.addEventListener("message", (event) => {
  if (event.origin !== "https://example.com") return;

  console.log(event.data);
});
```

`postMessage()`의 상세한 사용법과 보안 규칙은
창·iframe·메시징 문서에서 별도로 다룹니다.

## `Window`에 이벤트를 등록하기

`Window`는 `EventTarget`의 기능을 사용하여
전역 수준의 이벤트를 받을 수 있습니다.

```js
function handleResize() {
  console.log(window.innerWidth, window.innerHeight);
}

window.addEventListener("resize", handleResize);
```

페이지가 닫히거나 코드가 더 이상 필요하지 않을 때
리스너를 제거할 수 있습니다.

```js
window.removeEventListener("resize", handleResize);
```

`window`에 자주 등록하는 이벤트에는 다음이 있습니다.

- `resize`
- `scroll`
- `online`
- `offline`
- `message`
- `storage`
- `pageshow`
- `pagehide`
- `beforeunload`

각 이벤트의 의미와 권장 사용 방식은 다릅니다.

특히 `scroll`, `resize`처럼 자주 발생할 수 있는 이벤트에서는
무거운 DOM 계산을 반복하지 않도록 주의합니다.

## 전역 프로퍼티를 직접 추가해도 될까?

다음 코드는 `window`에 사용자 정의 프로퍼티를 추가합니다.

```js
window.appConfig = {
  apiBaseUrl: "/api",
  debug: false,
};
```

작은 예제에서는 동작하지만
대규모 애플리케이션에서는 문제가 생길 수 있습니다.

- 다른 스크립트와 이름이 충돌할 수 있습니다.
- 외부 라이브러리가 같은 이름을 사용할 수 있습니다.
- 테스트 간 전역 상태가 남을 수 있습니다.
- 코드의 의존 관계가 숨겨집니다.
- 페이지 수명 동안 메모리에 오래 남을 수 있습니다.

정말 전역 공개가 필요하다면
하나의 명확한 네임스페이스 아래로 모읍니다.

```js
window.myApp = {
  version: "1.0.0",
  start() {
    console.log("앱 시작");
  },
};
```

더 좋은 기본 선택은
ES Module의 `export`와 `import`를 사용하는 것입니다.

```js
// config.js
export const config = {
  apiBaseUrl: "/api",
};
```

```js
// main.js
import { config } from "./config.js";

console.log(config.apiBaseUrl);
```

전역에 공개해야 하는 이유가 없다면
모듈 내부에 상태를 유지합니다.

## HTML 요소의 `id`가 전역 이름이 될 수 있다

일부 HTML 요소는 `id`나 `name`을 통해
`window`의 이름 기반 프로퍼티로 노출될 수 있습니다.

```html
<div id="status">준비</div>

<script>
  console.log(window.status);
</script>
```

하지만 이런 접근 방식에 의존하면 안 됩니다.

`window`에는 이미 많은 표준 프로퍼티가 있고,
요소 이름이 기존 API나 다른 전역 값과 충돌할 수 있습니다.

명시적으로 DOM 검색 API를 사용합니다.

```js
const statusElement = document.querySelector("#status");

if (statusElement) {
  console.log(statusElement.textContent);
}
```

<Callout type="warning">
  **요소의 `id`를 전역 변수처럼 사용하지 마세요.**

  이름 충돌과 브라우저 동작 차이를 만들 수 있습니다.

  `document.getElementById()`나 `querySelector()`로
  의도를 명시하는 편이 안전합니다.
</Callout>

## 전역 이름 충돌 확인하기

사용하려는 이름이 이미 `window`에 존재하는지
확인할 수 있습니다.

```js
console.log("location" in window); // true
console.log("document" in window); // true
console.log("myApplication" in window); // 보통 false
```

자체 프로퍼티인지 확인하려면
`Object.hasOwn()`을 사용할 수 있습니다.

```js
console.log(Object.hasOwn(window, "document"));
```

다만 “비어 있는 이름을 찾았으니 전역으로 사용해도 안전하다”는 뜻은 아닙니다.

향후 브라우저가 같은 이름의 표준 API를 추가할 수도 있고,
다른 스크립트가 먼저 사용할 수도 있습니다.

전역 확장을 최소화하는 것이 기본 원칙입니다.

## 브라우저 기능을 확인하는 방법

브라우저 전역 API를 사용할 때는
사용자 에이전트 문자열보다 기능 존재 여부를 확인하는 편이 낫습니다.

```js
if ("IntersectionObserver" in window) {
  console.log("IntersectionObserver 사용 가능");
}
```

메서드라면 타입도 확인할 수 있습니다.

```js
if (typeof window.requestIdleCallback === "function") {
  window.requestIdleCallback(() => {
    console.log("유휴 작업 실행");
  });
}
```

단순 존재 여부만으로
모든 세부 기능과 옵션이 지원된다고 단정할 수는 없습니다.

필요한 동작 단위로 검사하고
MDN의 호환성 표와 Baseline 정보를 함께 확인합니다.

## 전역 객체를 열거하면 모든 API를 알 수 있을까?

다음 코드는 현재 환경에서 열거 가능한
전역 프로퍼티 이름 일부를 확인합니다.

```js
const names = Object.getOwnPropertyNames(window);

console.log(names.sort());
```

특정 문자열로 필터링할 수도 있습니다.

```js
const storageNames = Object
  .getOwnPropertyNames(window)
  .filter((name) => name.toLowerCase().includes("storage"));

console.log(storageNames);
```

하지만 이 결과는 브라우저, 버전,
실행 컨텍스트와 활성화된 기능에 따라 달라질 수 있습니다.

목록에 보인다는 이유만으로
해당 API가 안정적이거나 권장된다고 판단하면 안 됩니다.

반대로 열거 결과에 없더라도
프로토타입 체인이나 다른 객체를 통해 제공되는 기능이 있을 수 있습니다.

API 문서와 명세를 기준으로 판단합니다.

## `typeof window` 검사의 의미

서버와 브라우저에서 함께 실행될 수 있는 코드에서는
다음 검사를 자주 사용합니다.

```js
const isBrowserWindow = typeof window !== "undefined";
```

선언되지 않은 이름에 직접 접근하면 오류가 발생하지만,
`typeof` 연산자는 존재하지 않는 식별자에도 사용할 수 있습니다.

```js
if (typeof window !== "undefined") {
  console.log(window.location.href);
}
```

이 검사는 `window`라는 전역 이름이 존재하는지만 확인합니다.

다음까지 보장하지는 않습니다.

- DOM이 완전히 로드되었는지
- 특정 Web API가 지원되는지
- 안전한 컨텍스트인지
- 사용자 권한이 허용되었는지
- 실제 브라우저 UI가 존재하는지

필요한 조건을 각각 확인해야 합니다.

```js
if (
  typeof window !== "undefined" &&
  "document" in window &&
  typeof window.matchMedia === "function"
) {
  console.log("필요한 브라우저 기능 사용 가능");
}
```

## 창의 크기와 화면의 크기는 다르다

`window.innerWidth`는
현재 페이지 레이아웃 뷰포트의 내부 너비를 나타냅니다.

`screen.width`는
사용자의 화면과 관련된 값을 나타냅니다.

```js
console.log(window.innerWidth);
console.log(window.screen.width);
```

두 값은 같은 의미가 아닙니다.

- 브라우저 창 크기
- 개발자 도구의 도킹 상태
- 브라우저 확대·축소
- 모바일 화면과 시각적 뷰포트
- 운영체제의 디스플레이 설정

등에 따라 차이가 날 수 있습니다.

`window`, `document`, `screen`의 역할을 섞지 않아야 합니다.

관련 내용은 뒤의 `document·navigator·screen` 문서와
뷰포트·좌표 문서에서 자세히 다룹니다.

## 창 이름과 `window.name`

`window.name`은 현재 브라우징 컨텍스트의 이름을 나타내며
링크나 폼의 대상 이름과 관련하여 사용됩니다.

```js
console.log(window.name);
```

직접 설정할 수도 있습니다.

```js
window.name = "preview-window";
```

하지만 애플리케이션 데이터를 저장하는 공간처럼
사용해서는 안 됩니다.

페이지 탐색과 창 관계에 걸쳐 값이 유지될 수 있고,
보안과 개인정보 보호 측면에서 예상하기 어려운 동작을 만들 수 있습니다.

일반 데이터 저장에는 목적에 맞는 저장소 API를 사용합니다.

## 브라우저 지원과 Baseline

이 문서의 핵심 기능은 대부분
오래전부터 주요 브라우저에서 지원됩니다.

- `Window`: Baseline Widely available
- `window.document`: Baseline Widely available
- `window.parent`: Baseline Widely available
- `iframe.contentWindow`: Baseline Widely available
- `globalThis`: 주요 브라우저에서 2020년부터 폭넓게 지원
- `window.postMessage()`: Baseline Widely available

`Window` 인터페이스 전체가
하나의 동일한 호환성 상태를 가지는 것은 아닙니다.

개별 프로퍼티와 메서드마다 지원 범위가 다릅니다.

새로운 API를 사용할 때는
해당 API 문서의 Baseline과 호환성 표를 별도로 확인합니다.

`index.html`의 본문에 iframe을 추가합니다.

```html
<iframe
  id="demo-frame"
  src="./frame.html"

></iframe>
```

부모 페이지의 스크립트에 다음 코드를 추가합니다.

```js
const frame = document.querySelector("#demo-frame");

frame.addEventListener("load", () => {
  const childWindow = frame.contentWindow;

  if (!childWindow) return;

  console.log(childWindow === window); // false
  console.log(childWindow.parent === window); // true
  console.log(childWindow.document.title); // 같은 출처일 때 접근 가능
});
```

## 흔한 실수

### 전역에서 보이는 API를 ECMAScript 기능이라고 생각한다

`document`, `location`, `fetch()`와 `setTimeout()`은
브라우저가 제공하는 Web API입니다.

ECMAScript 언어 자체가 제공하는 기능과 구분해야 합니다.

### 전역 선언은 모두 `window` 프로퍼티가 된다고 생각한다

클래식 스크립트의 최상위 `var`와 함수 선언은
전역 객체 프로퍼티와 연결될 수 있습니다.

`let`, `const`, `class` 선언은
`window`의 프로퍼티가 되지 않습니다.

ES Module의 최상위 선언도
모듈 스코프에 유지됩니다.

### `window`와 브라우저 탭 UI를 같은 것으로 생각한다

`Window`는 주소창과 탭 버튼 같은
브라우저 제품 UI를 나타내는 객체가 아닙니다.

현재 브라우징 컨텍스트의
웹 페이지 전역 환경을 나타냅니다.

### iframe도 부모와 같은 `window`를 사용한다고 생각한다

각 iframe은 별도의 브라우징 컨텍스트와
자신의 전역 환경을 가집니다.

부모와 자식의 `window`는 서로 다른 값입니다.

### `contentWindow`를 얻으면 교차 출처 DOM도 읽을 수 있다고 생각한다

창 참조를 얻는 것과
그 창의 민감한 프로퍼티에 접근하는 것은 다릅니다.

교차 출처에서는 동일 출처 정책이
DOM과 JavaScript 상태 접근을 제한합니다.

### `window.top.document`는 항상 읽을 수 있다고 생각한다

`window.top` 참조가 존재해도
최상위 문서가 다른 출처라면
`document` 접근은 차단됩니다.

창 사이 통신은 `postMessage()`를 사용합니다.

### 메시지 이벤트에서 `origin`을 검사하지 않는다

`message` 이벤트의 데이터를 무조건 신뢰하면
다른 출처가 보낸 메시지를 처리할 수 있습니다.

허용할 출처를 정확히 비교해야 합니다.

```js
window.addEventListener("message", (event) => {
  if (event.origin !== "https://trusted.example") return;

  // 검증한 메시지만 처리
});
```

### HTML 요소의 `id`를 전역 변수처럼 사용한다

이름 기반 전역 접근은
표준 프로퍼티와 충돌할 수 있습니다.

명시적으로 DOM 검색 API를 사용합니다.

### 애플리케이션 상태를 모두 `window`에 저장한다

전역 상태는 충돌과 테스트 문제,
숨은 의존성과 메모리 유지 문제를 만들 수 있습니다.

기본적으로 ES Module과 명시적인 상태 관리 구조를 사용합니다.

### `typeof window !== "undefined"`만 확인하면 모든 브라우저 API를 쓸 수 있다고 생각한다

이 검사는 `window` 이름의 존재만 확인합니다.

특정 기능, 권한, 보안 컨텍스트와
문서 로딩 상태는 따로 확인해야 합니다.

### `window.name`을 일반 저장소처럼 사용한다

`window.name`은 브라우징 컨텍스트의 이름입니다.

애플리케이션 데이터 저장에는
목적에 맞는 저장소 API를 사용해야 합니다.

## 확인 문제

### 1. `Window`의 역할은 무엇일까?

<details>
  <summary>정답 보기</summary>

  현재 브라우징 컨텍스트의 전역 환경을 나타내며,
  현재 문서와 탐색, 타이머, 창 크기,
  이벤트와 여러 Web API에 접근할 수 있게 합니다.

</details>

### 2. `window.document`와 `document`는 어떤 관계일까?

<details>
  <summary>정답 보기</summary>

  일반적인 브라우저 페이지에서 같은 `Document` 객체를 가리킵니다.

  `document`는 전역 객체의 `document` 프로퍼티를
  전역 이름으로 접근한 것입니다.

</details>

### 3. 최상위 `let` 선언은 `window` 프로퍼티가 될까?

<details>
  <summary>정답 보기</summary>

  아닙니다.

  클래식 스크립트의 최상위 `let`과 `const`는
  전역 범위에 이름을 만들지만
  `window`의 일반 프로퍼티로 추가되지 않습니다.

</details>

### 4. `globalThis`를 사용하는 이유는 무엇일까?

<details>
  <summary>정답 보기</summary>

  브라우저 창, Worker, Node.js처럼
  서로 다른 JavaScript 환경에서
  전역 값에 접근하는 공통 방법을 제공하기 때문입니다.

</details>

### 5. `WindowProxy`는 왜 필요할까?

<details>
  <summary>정답 보기</summary>

  브라우징 컨텍스트의 페이지가 이동하면서
  활성 `Window`와 `Document`가 바뀌더라도
  해당 창을 나타내는 참조를 유지하고
  현재 활성 `Window`로 작업을 전달하기 위해 사용됩니다.

</details>

### 6. iframe 안에서 `parent`와 `top`의 차이는 무엇일까?

<details>
  <summary>정답 보기</summary>

  `parent`는 현재 프레임을 직접 포함하는 부모 창을 가리키고,
  `top`은 프레임 계층의 가장 위쪽 창을 가리킵니다.

</details>

### 7. 교차 출처 iframe의 DOM을 직접 읽을 수 있을까?

<details>
  <summary>정답 보기</summary>

  기본적으로 읽을 수 없습니다.

  동일 출처 정책이 교차 출처 창의
  DOM과 JavaScript 상태 접근을 제한합니다.

  필요한 통신은 `postMessage()`를 사용합니다.

</details>

### 8. HTML 요소의 `id`를 전역 이름으로 사용하면 안 되는 이유는 무엇일까?

<details>
  <summary>정답 보기</summary>

  기존 `Window` 프로퍼티나 다른 스크립트의 이름과
  충돌할 수 있고 코드의 의도가 불명확해지기 때문입니다.

  명시적인 DOM 검색 API를 사용해야 합니다.

</details>

## 요약

- `Window`는 브라우저의 현재 브라우징 컨텍스트에 연결된 전역 인터페이스입니다.
- `document`, `location`, `navigator`, 타이머와 여러 Web API가 `Window`를 통해 노출됩니다.
- 전역 이름으로 API를 사용할 수 있어도 해당 기능이 ECMAScript 내장 기능이라는 뜻은 아닙니다.
- 클래식 스크립트의 최상위 `var`와 함수 선언은 `window` 프로퍼티와 연결될 수 있습니다.
- 최상위 `let`과 `const`는 `window` 프로퍼티가 되지 않습니다.
- ES Module의 최상위 선언은 모듈 스코프에 유지됩니다.
- 브라우저 창에서 `window`, `self`, `globalThis`는 일반적으로 같은 전역 접근 값을 가리킵니다.
- Worker에는 `window`와 `document`가 없지만 `self`와 `globalThis`를 사용할 수 있습니다.
- 웹 표준 내부 모델에서 창 참조는 현재 활성 `Window`를 감싸는 `WindowProxy`를 통해 동작합니다.
- 페이지를 이동하면 활성 `Window`와 `Document`는 바뀔 수 있지만 브라우징 컨텍스트의 창 참조는 유지됩니다.
- 각 iframe은 자신의 `window`와 `document`를 가진 별도의 전역 환경입니다.
- `parent`는 직접 부모 창, `top`은 최상위 창, `opener`는 현재 창을 연 창을 가리킬 수 있습니다.
- 교차 출처 창의 DOM과 JavaScript 상태에는 직접 접근할 수 없습니다.
- 교차 출처 통신에는 출처를 검증한 `postMessage()`를 사용합니다.
- HTML 요소의 `id`를 전역 변수처럼 사용하는 방식과 무분별한 `window` 확장은 피해야 합니다.
