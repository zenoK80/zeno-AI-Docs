---

브라우저는 HTML·CSS·JavaScript를 받아
사용자가 보고 조작할 수 있는 웹 페이지로 만듭니다.

이 과정의 중심에는 서로 역할이 다른
두 종류의 엔진이 있습니다.

- **렌더링 엔진**은 HTML과 CSS를 해석하고 페이지의 구조와 모양을 계산합니다.
- **JavaScript 엔진**은 JavaScript 코드를 해석하고 실행합니다.

두 엔진은 독립적으로 존재하지만
웹 페이지 안에서는 계속 데이터를 주고받으며 협력합니다.

JavaScript가 `document.querySelector()`로 요소를 찾고,
`textContent`나 `classList`를 변경할 수 있는 것도
JavaScript 엔진이 혼자 처리하는 일이 아닙니다.

JavaScript 엔진이 코드를 실행하면
브라우저가 제공하는 연결 계층을 통해
렌더링 엔진의 DOM 기능을 호출하는 구조입니다.

<Callout>
  **렌더링 엔진은 페이지를 해석하고 그립니다.**

  **JavaScript 엔진은 JavaScript를 실행합니다.**

  `document`, `window`, `fetch`, `setTimeout` 같은 기능은
  ECMAScript 언어 자체가 아니라 브라우저가 제공하는 Web API입니다.
</Callout>

## 먼저 전체 관계 보기

브라우저 안의 관계를 단순화하면
다음과 같이 볼 수 있습니다.

```text
브라우저
├─ 브라우저 UI와 탐색 관리
├─ 네트워크 기능
├─ 렌더러 프로세스
│  ├─ 렌더링 엔진
│  │  ├─ HTML 파싱
│  │  ├─ DOM 구성
│  │  ├─ CSS 파싱과 스타일 계산
│  │  ├─ 레이아웃
│  │  ├─ 페인트
│  │  └─ 합성에 필요한 정보 생성
│  │
│  ├─ JavaScript 엔진
│  │  ├─ JavaScript 파싱
│  │  ├─ 코드 실행
│  │  ├─ 객체 메모리 관리
│  │  └─ 가비지 컬렉션
│  │
│  └─ Web API 연결 계층
│     ├─ DOM API
│     ├─ 이벤트
│     ├─ 타이머
│     ├─ 네트워크 API
│     └─ 저장소·미디어·그래픽 API
│
└─ GPU·그래픽 관련 프로세스
```

이 구조는 개념을 이해하기 위한 단순화입니다.

실제 브라우저에서는 작업 일부가
별도 프로세스나 보조 스레드로 이동할 수 있습니다.

브라우저 종류와 운영체제에 따라
구현 방식도 달라집니다.

## 엔진이란?

소프트웨어에서 **엔진(engine)**은
특정 종류의 입력을 처리하여
정해진 결과를 만드는 핵심 구성 요소를 뜻합니다.

브라우저에는 하나의 엔진만 있는 것이 아닙니다.

페이지를 처리하는 렌더링 엔진,
JavaScript를 실행하는 JavaScript 엔진,
그래픽 처리를 돕는 구성 요소,
네트워크와 미디어를 처리하는 구성 요소가 협력합니다.

### 브라우저와 엔진은 같은 말이 아니다

Chrome, Firefox, Safari는
사용자가 설치하고 실행하는 **브라우저 제품**입니다.

Blink, Gecko, WebKit은
웹 콘텐츠를 처리하는 **웹·렌더링 엔진**입니다.

V8, SpiderMonkey, JavaScriptCore는
JavaScript를 실행하는 **JavaScript 엔진**입니다.

  페이지 렌더링과 탭 관리는
  V8 바깥의 브라우저 구성 요소가 담당합니다.
</Callout>

## 렌더링 엔진이란?

**렌더링 엔진(rendering engine)**은
웹 문서와 스타일 정보를 해석하여
화면에 표시할 결과를 만드는 구성 요소입니다.

렌더링 엔진은 단순히 그림을 그리는 기능만 담당하지 않습니다.

HTML을 읽어 문서 구조를 만들고,
CSS를 적용하며,
요소의 크기와 위치를 계산하고,
어떤 순서와 방식으로 그릴지 결정합니다.

브라우저 엔진 또는 웹 엔진이라는 표현은
렌더링뿐 아니라 DOM, 네트워크 연결,
이벤트와 여러 웹 플랫폼 기능까지 포함하는
더 넓은 의미로 사용되기도 합니다.

따라서 문서마다 엔진의 범위가 조금 다를 수 있습니다.

### 렌더링 엔진의 주요 역할

렌더링 엔진이 담당하는 작업을
크게 나누면 다음과 같습니다.

1. HTML을 파싱하여 DOM을 구성합니다.
2. CSS를 파싱하여 스타일 규칙을 준비합니다.
3. 각 요소에 적용될 스타일을 계산합니다.
4. 요소의 크기와 위치를 계산합니다.
5. 화면에 그릴 명령을 만듭니다.
6. 필요한 레이어를 구성하고 합성을 준비합니다.
7. 사용자 입력과 DOM 변경에 따라 결과를 갱신합니다.

이를 단순화하면 다음 흐름으로 볼 수 있습니다.

```text
HTML ── 파싱 ──> DOM
                  │
CSS ─── 파싱 ──> CSSOM
                  │
                  ▼
             스타일 계산
                  │
                  ▼
               레이아웃
                  │
                  ▼
                페인트
                  │
                  ▼
                 합성
                  │
                  ▼
                화면 출력
```

실제 렌더링 파이프라인은
브라우저 내부 최적화와 그래픽 구조에 따라 더 복잡합니다.

이 문서에서는 두 엔진의 관계를 이해하는 데 필요한 만큼만 다룹니다.

스타일 계산, 레이아웃, 페인트와 합성은
뒤의 CSSOM과 렌더링 문서에서 자세히 다룹니다.

## HTML 파싱과 DOM 구성

브라우저가 HTML 응답을 받으면
렌더링 엔진의 HTML 파서가 문자를 읽어
문서의 구조를 해석합니다.

예를 들어 다음 HTML이 있다고 하겠습니다.

```html
<main>
  <h1>렌더링 엔진</h1>
  <p>HTML은 DOM 트리로 변환됩니다.</p>
</main>
```

렌더링 엔진은 이를 개념적으로
다음과 같은 DOM 구조로 만듭니다.

```text
Document
└─ html
   └─ body
      └─ main
         ├─ h1
         │  └─ "렌더링 엔진"
         └─ p
            └─ "HTML은 DOM 트리로 변환됩니다."
```

DOM은 화면에 보이는 픽셀 자체가 아닙니다.

현재 문서의 요소와 텍스트,
속성과 부모·자식 관계를 표현하는
메모리 안의 객체 구조입니다.

JavaScript가 DOM API를 사용할 때는
이 구조를 조회하거나 변경합니다.

## CSS 파싱과 스타일 계산

CSS도 렌더링 엔진이 해석합니다.

```css
main {
  max-width: 720px;
  margin: 0 auto;
}

h1 {
  font-size: 2rem;
}
```

브라우저는 CSS 규칙을 분석하고
어떤 규칙이 어떤 요소에 적용되는지 계산합니다.

이때 다음과 같은 요소가 함께 고려됩니다.

- 선택자 일치 여부
- 상속
- 명시도
- 선언 순서
- 사용자 에이전트 스타일
- 사용자가 설정한 스타일
- 미디어 쿼리와 현재 환경

DOM에 요소가 존재한다고 해서
그 요소의 최종 모양이 바로 결정되는 것은 아닙니다.

렌더링 엔진은 DOM과 CSS 규칙,
브라우저의 기본 스타일과 현재 환경을 종합하여
최종 계산 스타일을 만듭니다.

## 레이아웃·페인트·합성

스타일이 결정되면
브라우저는 요소의 크기와 위치를 계산합니다.

이 과정을 일반적으로 **레이아웃(layout)**이라고 합니다.

```text
요소 A: x=24, y=40, width=320, height=80
요소 B: x=24, y=136, width=320, height=120
```

그다음 배경, 테두리, 텍스트와 그림자를
어떤 순서로 그릴지 기록합니다.

이 과정을 **페인트(paint)**라고 합니다.

필요한 경우 페이지의 일부를 여러 레이어로 나눈 뒤
각 레이어의 결과를 결합합니다.

이 과정을 **합성(compositing)**이라고 합니다.

<Callout>
  DOM 변경이 발생했다고 해서
  화면의 픽셀이 같은 순간에 바로 바뀌는 것은 아닙니다.

  DOM 상태는 JavaScript 실행 중에 변경될 수 있지만,
  실제 렌더링은 브라우저가 렌더링 작업을 수행할 기회를 얻었을 때 진행됩니다.
</Callout>

## JavaScript 엔진이란?

**JavaScript 엔진(JavaScript engine)**은
JavaScript 소스 코드를 읽고 실행하는 프로그램입니다.

JavaScript 엔진은 보통 다음 작업을 담당합니다.

- JavaScript 소스 코드 분석
- 문법 오류 확인
- 실행에 필요한 내부 표현 생성
- 코드 실행
- 함수 호출과 실행 상태 관리
- JavaScript 객체의 메모리 할당
- 사용하지 않는 객체의 메모리 회수
- 자주 실행되는 코드의 최적화

JavaScript 엔진의 핵심 대상은
ECMAScript 언어입니다.

`let`, `const`, 함수, 객체, 배열,
연산자와 제어문 같은 언어 기능은
JavaScript 엔진이 처리합니다.

반면 다음 기능은 JavaScript 엔진 자체의 기능이 아닙니다.

```js
document.querySelector("button");
window.addEventListener("resize", handler);
setTimeout(callback, 1000);
fetch("/api/items");
localStorage.setItem("theme", "dark");
```

이 기능들은 브라우저가 제공하는 Web API입니다.

JavaScript 엔진은 브라우저가 연결해 둔 객체와 함수를 통해
Web API를 호출할 수 있습니다.

### JavaScript 엔진은 브라우저 밖에서도 사용된다

V8은 Chromium 기반 브라우저뿐 아니라
Node.js 같은 브라우저 밖의 환경에도 사용됩니다.

같은 V8을 사용하더라도
Node.js에는 브라우저의 DOM이 기본 제공되지 않습니다.

```js
console.log(typeof document);
```

브라우저 페이지에서는 일반적으로
다음 결과를 확인할 수 있습니다.

```text
object
```

Node.js에서는 기본적으로
다음과 같은 결과가 나옵니다.

```text
undefined
```

이 차이는 JavaScript 엔진이 달라서가 아닙니다.

JavaScript 엔진을 둘러싼 **호스트 환경**이 다르기 때문입니다.

<Callout type="info">
  JavaScript 엔진은 ECMAScript를 실행합니다.

  브라우저는 JavaScript 엔진에
  `window`, `document`, DOM, 이벤트, 네트워크 같은
  호스트 기능을 연결합니다.
</Callout>

## JavaScript 코드는 어떻게 실행될까?

JavaScript 엔진마다 내부 구현은 다르지만
개념적으로 다음 단계를 거칩니다.

```text
JavaScript 소스 코드
        │
        ▼
      파싱
        │
        ▼
내부 표현 또는 바이트코드 생성
        │
        ▼
      코드 실행
        │
        ├─ 실행 정보 수집
        │
        └─ 자주 실행되는 코드 최적화
```

### 파싱

JavaScript 엔진은 소스 코드를 읽고
문법에 맞는지 분석합니다.

```js
const message = "Hello";
console.log(message);
```

문법이 잘못되면
실행 전에 `SyntaxError`가 발생할 수 있습니다.

```js
const message = ;
```

### 실행 준비와 코드 실행

현대 JavaScript 엔진은
소스 코드를 바로 한 줄씩 단순 해석하는 방식만 사용하지 않습니다.

엔진은 코드를 내부 표현이나 바이트코드로 변환하고,
인터프리터와 컴파일러를 조합하여 실행할 수 있습니다.

자주 실행되는 코드에 대한 정보를 수집한 뒤
더 빠른 기계어 코드로 최적화하기도 합니다.

이 방식은 엔진의 구현 세부 사항이며
ECMAScript 명세가 특정 인터프리터나 컴파일러를 강제하지 않습니다.

<Callout type="warning">
  **V8의 Ignition, Sparkplug, Maglev, TurboFan 같은 이름은**
  V8의 내부 실행 계층입니다.

  모든 브라우저가 같은 구조를 사용하는 것은 아니며,
  웹 코드는 특정 최적화 단계가 존재한다고 가정해서는 안 됩니다.
</Callout>

### 최적화와 역최적화

JavaScript 엔진은 실행 중에 관찰한 정보를 바탕으로
코드를 최적화할 수 있습니다.

그러나 이전 가정과 다른 값이 들어오면
최적화된 코드를 계속 사용하기 어려울 수 있습니다.

이때 엔진은 더 일반적인 실행 방식으로 돌아갈 수 있습니다.

이를 **역최적화(deoptimization)**라고 부릅니다.

역최적화 자체는 오류가 아닙니다.

동적 언어를 빠르게 실행하기 위해
JavaScript 엔진이 사용하는 정상적인 전략 중 하나입니다.

이 시리즈는 ECMAScript 엔진 최적화를
본문의 중심 주제로 다루지 않습니다.

브라우저에서 JavaScript 실행이
렌더링과 사용자 입력에 어떤 영향을 주는지를 중심으로 봅니다.

## 가비지 컬렉션

JavaScript 객체는 메모리에 저장됩니다.

```js
const user = {
  name: "Lee",
  active: true
};
```

JavaScript 엔진은 객체에 필요한 메모리를 할당하고,
더 이상 도달할 수 없는 객체의 메모리를 회수합니다.

이 과정을 **가비지 컬렉션(garbage collection)**이라고 합니다.

개발자가 JavaScript 객체의 메모리를
직접 `free()`하는 방식은 사용하지 않습니다.

하지만 자동 메모리 관리가 있다고 해서
메모리 누수가 발생하지 않는 것은 아닙니다.

이벤트 리스너, 타이머, Observer,
분리된 DOM 노드와 전역 참조가 남아 있으면
객체가 계속 도달 가능한 상태로 유지될 수 있습니다.

브라우저 메모리와 메모리 누수는
뒤의 성능·메모리 문서에서 자세히 다룹니다.

## 렌더링 엔진과 JavaScript 엔진은 어떻게 연결될까?

JavaScript 엔진은 `document`의 내부 구현을
직접 가지고 있지 않습니다.

브라우저는 JavaScript에서 호출할 수 있는 객체와 메서드를 만들고
이를 렌더링 엔진의 DOM 구현과 연결합니다.

이 연결을 개념적으로 다음과 같이 볼 수 있습니다.

```text
JavaScript 코드
  document.querySelector("#title")
              │
              ▼
JavaScript 엔진에서 함수 호출 처리
              │
              ▼
브라우저의 Web API 바인딩
              │
              ▼
렌더링 엔진의 DOM 구현
              │
              ▼
해당 Element를 JavaScript 객체로 노출
```

브라우저 내부에서는
C++과 같은 구현 언어로 작성된 네이티브 객체와
JavaScript 객체 사이를 연결하는 계층이 존재합니다.

웹 개발자가 이 연결 계층을 직접 다룰 필요는 없지만,
다음 사실은 이해해야 합니다.

- JavaScript 객체와 DOM 객체는 완전히 같은 종류의 객체가 아닙니다.
- DOM 작업은 JavaScript 엔진 밖의 브라우저 기능을 호출합니다.
- DOM을 자주 조회하고 변경하면 렌더링 작업이 늘어날 수 있습니다.
- JavaScript가 메인 스레드를 오래 점유하면 화면 갱신과 입력 처리가 늦어질 수 있습니다.

## DOM 객체는 JavaScript 객체일까?

JavaScript에서는 DOM 요소도
객체처럼 사용할 수 있습니다.

```js
const title = document.querySelector("h1");

console.log(title.nodeName);
title.textContent = "새 제목";
```

`title`은 JavaScript 코드에서 참조할 수 있는 객체입니다.

그러나 일반 객체 리터럴과 달리
브라우저의 DOM 구현과 연결된 **호스트 객체**입니다.

```js
const plainObject = {
  textContent: "새 제목"
};
```

두 객체 모두 `textContent`라는 프로퍼티를 가질 수 있지만
동작은 완전히 다릅니다.

```js
plainObject.textContent = "변경";
```

일반 객체의 값만 변경됩니다.

```js
title.textContent = "변경";
```

DOM 노드의 텍스트가 변경되고
렌더링 엔진은 페이지의 시각적 결과를 다시 계산해야 할 수 있습니다.

<Callout>
  JavaScript 문법으로 DOM을 조작하지만,
  실제 대상은 브라우저가 관리하는 문서 객체입니다.
</Callout>

## 한 줄의 DOM 변경이 처리되는 과정

다음 코드를 실행한다고 하겠습니다.

```js
const title = document.querySelector("#title");
title.textContent = "변경된 제목";
```

브라우저 안에서는 개념적으로 다음 과정이 일어납니다.

<Steps>

### JavaScript 엔진이 코드를 실행한다

JavaScript 엔진이 변수 선언과 함수 호출을 처리합니다.

### `document`의 메서드를 호출한다

`document.querySelector()`는
브라우저가 제공하는 DOM API입니다.

호출은 Web API 연결 계층을 거쳐
렌더링 엔진의 DOM 구현으로 전달됩니다.

### DOM에서 요소를 찾는다

렌더링 엔진이 현재 문서의 DOM에서
`id="title"`인 요소를 찾습니다.

### DOM 객체의 참조가 반환된다

찾은 요소를 JavaScript에서 사용할 수 있는
객체 형태로 반환합니다.

### `textContent`를 변경한다

JavaScript 엔진의 프로퍼티 대입이
브라우저의 DOM 구현에 전달되고
해당 텍스트 노드가 변경됩니다.

### 렌더링 상태가 무효화된다

브라우저는 이 변경이
스타일, 레이아웃 또는 페인트 결과에 영향을 주는지 판단합니다.

### 브라우저가 화면을 갱신한다

현재 JavaScript 작업이 끝나고
브라우저가 렌더링할 기회를 얻으면
필요한 계산과 그리기 작업을 수행합니다.

</Steps>

중요한 점은
DOM 변경과 화면 출력이 같은 개념이 아니라는 것입니다.

## JavaScript 실행과 화면 갱신

대부분의 일반적인 페이지 JavaScript와
DOM 처리, 스타일 계산과 레이아웃의 주요 작업은
렌더러의 메인 스레드와 밀접하게 연결되어 있습니다.

JavaScript가 메인 스레드를 오래 점유하면
브라우저는 다음 작업을 제때 처리하기 어렵습니다.

- 클릭과 키보드 입력
- 스크롤 관련 처리
- DOM 변경 반영
- 스타일 계산
- 레이아웃
- 페인트
- 애니메이션 프레임 준비

다음 예제를 실행해 보겠습니다.

```html
<button id="startButton">작업 시작</button>
<p id="status">대기 중</p>

<script>
  const startButton = document.querySelector("#startButton");
  const status = document.querySelector("#status");

  startButton.addEventListener("click", () => {
    status.textContent = "작업 중";

    const endTime = performance.now() + 2000;

    while (performance.now() < endTime) {
      // 메인 스레드를 의도적으로 점유하는 실습 코드
    }

    status.textContent = "작업 완료";
  });
</script>
```

버튼을 클릭하면 코드상으로는
다음 순서로 텍스트가 변경됩니다.

```text
대기 중
→ 작업 중
→ 작업 완료
```

하지만 화면에서는
`작업 중`이 보이지 않고
곧바로 `작업 완료`가 보일 수 있습니다.

JavaScript 실행이 끝날 때까지
브라우저가 중간 화면을 그릴 기회를 얻지 못했기 때문입니다.

<Callout type="warning">
  위의 `while` 반복문은
  메인 스레드 차단을 관찰하기 위한 실습 코드입니다.

  실제 서비스에서 시간을 지연시키는 목적으로 사용하면 안 됩니다.
</Callout>

### 렌더링 기회를 나누어 주기

브라우저가 중간 상태를 그릴 수 있도록
긴 작업을 다른 작업으로 나누어야 합니다.

간단한 관찰용 예제는 다음과 같습니다.

```html
<button id="startButton">작업 시작</button>
<p id="status">대기 중</p>

<script>
  const startButton = document.querySelector("#startButton");
  const status = document.querySelector("#status");

  function blockMainThread(duration) {
    const endTime = performance.now() + duration;

    while (performance.now() < endTime) {
      // 실습을 위한 의도적 차단
    }
  }

  startButton.addEventListener("click", () => {
    status.textContent = "작업 중";

    requestAnimationFrame(() => {
      setTimeout(() => {
        blockMainThread(2000);
        status.textContent = "작업 완료";
      }, 0);
    });
  });
</script>
```

이 예제는 첫 번째 상태 변경 뒤에
브라우저가 렌더링할 기회를 얻도록
후속 작업을 분리합니다.

실제 무거운 계산은
작은 단위로 분할하거나 Web Worker로 옮기는 방법을 검토해야 합니다.

이벤트 루프, 태스크, 마이크로태스크와
`requestAnimationFrame()`의 정확한 순서는
11번 문서에서 자세히 다룹니다.

## 메인 스레드에서 경쟁하는 작업

렌더러 프로세스의 메인 스레드에서는
다음 작업들이 서로 실행 시간을 사용합니다.

```text
JavaScript 실행
      │
      ├─ DOM 이벤트 처리
      ├─ DOM 변경
      ├─ 스타일 계산
      ├─ 레이아웃
      ├─ 일부 페인트 준비
      └─ 다음 작업 처리
```

모든 렌더링 작업이 항상 메인 스레드에서만 처리되는 것은 아닙니다.

현대 브라우저는 합성, 래스터화,
이미지 처리와 JavaScript 컴파일 일부를
보조 스레드나 별도 프로세스로 이동할 수 있습니다.

하지만 페이지의 주요 JavaScript가
메인 스레드를 오래 차단하면
사용자가 체감하는 응답성이 떨어질 수 있습니다.

### 긴 JavaScript 작업의 영향

```js
button.addEventListener("click", () => {
  runVeryHeavyCalculation();
});
```

`runVeryHeavyCalculation()`이 오래 걸리면
클릭 이벤트의 콜백이 끝날 때까지
다음 입력과 렌더링이 지연될 수 있습니다.

사용자는 다음과 같은 현상을 경험할 수 있습니다.

- 버튼이 눌리지 않은 것처럼 보입니다.
- 로딩 표시가 나타나지 않습니다.
- 스크롤이 끊깁니다.
- 애니메이션이 멈춥니다.
- 입력한 글자가 늦게 표시됩니다.

이 문제는 JavaScript 엔진이 느리다는 한 문장으로만 설명할 수 없습니다.

메인 스레드에서 JavaScript 실행과 렌더링 작업이
같은 시간 자원을 두고 경쟁하기 때문에 발생합니다.

## `setTimeout()`은 V8의 기능일까?

다음 코드는 JavaScript로 작성됩니다.

```js
setTimeout(() => {
  console.log("1초 후 실행");
}, 1000);
```

하지만 타이머의 시간 측정과 콜백 등록은
ECMAScript 명세가 정의하는 기능이 아닙니다.

브라우저에서는 HTML 표준의 타이머 처리 모델과
브라우저의 이벤트 루프가 관련됩니다.

JavaScript 엔진은 콜백 함수 자체를 실행하지만,
언제 실행 대상으로 전달할지는
호스트 환경이 관리합니다.

```text
JavaScript 코드가 setTimeout 호출
              │
              ▼
브라우저가 타이머 등록
              │
              ▼
지정 시간이 지난 뒤 실행 가능한 작업으로 준비
              │
              ▼
이벤트 루프가 콜백 실행 기회를 선택
              │
              ▼
JavaScript 엔진이 콜백 함수 실행
```

`fetch()`와 DOM 이벤트도
세부 과정은 다르지만 같은 관점으로 이해할 수 있습니다.

브라우저 기능이 작업을 준비하고,
실행할 JavaScript 콜백이 생기면
JavaScript 엔진이 해당 함수를 실행합니다.

## `<script>`를 만나면 어떤 일이 일어날까?

HTML 파서가 문서를 읽다가
일반적인 클래식 `<script>` 요소를 만나면
스크립트 로딩과 실행 조건에 따라
HTML 파싱이 멈출 수 있습니다.

```html
<h1>제목</h1>
<script src="app.js"></script>
<p>본문</p>
```

단순화한 흐름은 다음과 같습니다.

```text
HTML 파싱 시작
      │
      ▼
<h1> 처리
      │
      ▼
<script> 발견
      │
      ├─ 필요한 파일 로드
      ├─ JavaScript 엔진이 코드 실행
      └─ 실행 완료
      │
      ▼
HTML 파싱 계속
      │
      ▼
<p> 처리
```

스크립트 실행 중에는
이미 만들어진 DOM을 조회하고 변경할 수 있습니다.

```html
<h1 id="title">기존 제목</h1>

<script>
  const title = document.querySelector("#title");
  title.textContent = "스크립트가 변경한 제목";
</script>
```

그러나 스크립트보다 뒤에 있는 요소는
아직 파싱되지 않았을 수 있습니다.

```html
<script>
  const content = document.querySelector("#content");
  console.log(content); // null
</script>

<p id="content">본문</p>
```

스크립트 로딩 방식인 `defer`, `async`, `type="module"`과
HTML 파싱 순서의 자세한 내용은
8번과 10번 문서에서 다룹니다.

## JavaScript가 CSS에 미치는 영향

JavaScript는 DOM뿐 아니라
요소의 클래스와 인라인 스타일도 변경할 수 있습니다.

```js
const panel = document.querySelector(".panel");

panel.classList.add("is-open");
panel.style.width = "320px";
```

JavaScript 엔진은
메서드 호출과 문자열 대입을 실행합니다.

렌더링 엔진은 변경된 클래스와 스타일을 바탕으로
필요한 렌더링 작업을 판단합니다.

변경 종류에 따라 영향 범위가 달라질 수 있습니다.

```text
색상 변경
→ 스타일 계산과 페인트가 필요할 수 있음

너비 변경
→ 스타일 계산, 레이아웃과 페인트가 필요할 수 있음

transform 변경
→ 조건에 따라 합성 단계 중심으로 처리될 수 있음
```

이 구분은 절대적인 규칙이 아닙니다.

실제 처리 방식은 요소 상태,
브라우저 최적화와 레이어 구성에 따라 달라질 수 있습니다.

특정 CSS 속성이 항상 GPU에서만 처리된다고
단정해서는 안 됩니다.

## JavaScript에서 레이아웃 정보를 읽을 때

JavaScript는 요소의 크기와 위치를 읽을 수 있습니다.

```js
const card = document.querySelector(".card");
const rect = card.getBoundingClientRect();

console.log(rect.width, rect.height);
```

브라우저가 이전 스타일 변경의 결과를
아직 계산하지 않았다면,
정확한 값을 반환하기 위해
필요한 스타일 계산이나 레이아웃을 먼저 수행할 수 있습니다.

```js
const card = document.querySelector(".card");

card.style.width = "400px";
console.log(card.getBoundingClientRect().width);
```

이런 읽기와 쓰기를 반복하면
레이아웃 계산이 자주 발생할 수 있습니다.

```js
for (const item of document.querySelectorAll(".item")) {
  item.style.width = `${container.clientWidth}px`;
}
```

이 주제는 **레이아웃 스래싱(layout thrashing)**과 관련됩니다.

크기·좌표 API와 레이아웃 스래싱은
34번부터 39번 문서에서 자세히 다룹니다.

## Worker에서는 렌더링 엔진을 직접 사용할 수 있을까?

일반적인 Web Worker는
페이지의 메인 스레드와 다른 실행 환경에서
JavaScript 코드를 실행합니다.

Worker에는 일반적으로 `document`가 없습니다.

```js
// worker.js
console.log(typeof document); // "undefined"
```

Worker는 페이지의 DOM을 직접 조회하거나 수정할 수 없습니다.

DOM 변경이 필요하면
메인 스레드와 메시지를 주고받아야 합니다.

```js
// worker.js
postMessage({
  type: "result",
  value: 42
});
```

```js
// main.js
worker.addEventListener("message", (event) => {
  resultElement.textContent = String(event.data.value);
});
```

이 구조를 통해
무거운 계산은 Worker에서 수행하고,
DOM 변경은 메인 스레드에서 처리할 수 있습니다.

Worker, 구조화 복제와 `postMessage()`는
104번과 105번 문서에서 자세히 다룹니다.

## 렌더링 엔진과 GPU의 관계

렌더링 엔진이 페이지의 시각적 결과를 계산한다고 해서
모든 픽셀 작업을 렌더링 엔진의 메인 스레드가 직접 수행한다는 뜻은 아닙니다.

현대 브라우저는 그래픽 작업 일부를
GPU 프로세스, 컴포지터 스레드와
래스터 작업 스레드에 분배할 수 있습니다.

단순화하면 다음과 같습니다.

```text
렌더링 엔진
├─ 어떤 요소를 어디에 그릴지 계산
├─ 페인트 명령과 레이어 정보 생성
└─ 그래픽 작업 전달
        │
        ▼
컴포지터·래스터·GPU 관련 구성 요소
├─ 레이어 래스터화
├─ 텍스처 처리
├─ 레이어 합성
└─ 화면 출력
```

정확한 작업 분배는
브라우저와 플랫폼에 따라 달라집니다.

`transform`이나 `opacity`를 사용하면
항상 별도 GPU 레이어가 만들어진다고 보장할 수도 없습니다.

브라우저가 비용과 상황을 판단하여
레이어 승격과 합성 방식을 결정합니다.

## 브라우저마다 결과가 왜 다를 수 있을까?

웹 표준은 브라우저가 지켜야 할
동작과 인터페이스를 정의합니다.

하지만 엔진 내부의 자료 구조,
프로세스 배치, 최적화 전략과
그래픽 처리 방식까지 모두 같게 만들지는 않습니다.

따라서 같은 HTML·CSS·JavaScript라도
다음 부분에서 차이가 나타날 수 있습니다.

- 아직 완전히 표준화되지 않은 기능
- 브라우저별 구현 시점
- 글꼴과 운영체제의 텍스트 렌더링
- 그래픽 드라이버와 GPU 환경
- 성능 최적화 방식
- 실험적 기능의 활성화 여부
- 브라우저 버그

웹 개발자는 특정 엔진의 내부 동작만을 전제로 하지 않고
표준과 실제 브라우저 호환성을 확인해야 합니다.

## 엔진 이름을 외우는 것보다 중요한 것

엔진 이름 자체보다
다음 관계를 이해하는 것이 중요합니다.

```text
ECMAScript 코드
→ JavaScript 엔진이 실행

DOM·이벤트·네트워크 API
→ 브라우저가 제공

DOM과 스타일 변경
→ 렌더링 엔진이 결과 갱신

긴 JavaScript 실행
→ 렌더링과 입력 처리를 지연시킬 수 있음
```

이 관계를 이해하면
다음 문제를 더 정확하게 분석할 수 있습니다.

- DOM을 변경했는데 왜 화면이 바로 바뀌지 않는가?
- 긴 반복문이 왜 화면을 멈추게 하는가?
- `document`가 왜 Node.js에는 없는가?
- CSS 변경이 왜 레이아웃 비용을 만들 수 있는가?
- Worker에서 왜 DOM을 직접 사용할 수 없는가?

## 브라우저 지원과 Baseline

렌더링 엔진과 JavaScript 엔진은
브라우저 내부 구조를 설명하는 개념입니다.

특정 Web API가 아니므로
이 개념 자체에는 MDN Baseline 연도가 적용되지 않습니다.

이 문서의 실습에서 사용하는 다음 기능은
현대 브라우저에서 널리 지원됩니다.

- `document.querySelector()`
- `textContent`
- `addEventListener()`
- `performance.now()`
- `requestAnimationFrame()`
- `setTimeout()`

실제 프로젝트에서는
각 API의 MDN 호환성 표와 Baseline 정보를 별도로 확인해야 합니다.

<Callout>
  **Baseline은 브라우저 엔진 이름에 붙는 등급이 아닙니다.**

  웹 기능이 주요 브라우저에서
  어느 시점부터 안정적으로 지원되는지를 나타내는 정보입니다.
</Callout>

## 직접 확인하기

Chrome이나 Edge의 DevTools Performance 패널을 사용하면
JavaScript 실행과 렌더링 작업의 관계를 관찰할 수 있습니다.

브라우저와 버전에 따라
패널 이름과 표시 항목은 조금 다를 수 있습니다.

### 1. 실습 파일을 만든다

다음 내용을 `engine-demo.html`로 저장합니다.

```html
<!doctype html>
<html lang="ko">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>엔진 동작 확인</title>
    <style>
      .box {
        width: 120px;
        height: 120px;
        background: royalblue;
        transition: transform 300ms;
      }

      .box.is-moved {
        transform: translateX(240px);
      }
    </style>
  </head>
  <body>
    <button id="moveButton">이동</button>
    <button id="blockButton">2초간 차단</button>
    <p id="status">대기 중</p>
    <div class="box"></div>

    <script>
      const moveButton = document.querySelector("#moveButton");
      const blockButton = document.querySelector("#blockButton");
      const status = document.querySelector("#status");
      const box = document.querySelector(".box");

      moveButton.addEventListener("click", () => {
        box.classList.toggle("is-moved");
      });

      blockButton.addEventListener("click", () => {
        status.textContent = "작업 중";

        const endTime = performance.now() + 2000;

        while (performance.now() < endTime) {
          // 실습을 위한 의도적인 메인 스레드 차단
        }

        status.textContent = "작업 완료";
      });
    </script>
  </body>
</html>
```

### 2. DevTools를 연다

페이지를 브라우저에서 연 뒤
개발자 도구의 Performance 패널을 엽니다.

### 3. 기록을 시작한다

Performance 기록을 시작하고
`이동` 버튼과 `2초간 차단` 버튼을 차례대로 클릭합니다.

### 4. 기록을 중지한다

기록을 중지한 뒤
메인 스레드의 작업 구간을 확인합니다.

다음과 비슷한 항목을 찾을 수 있습니다.

- 이벤트 처리
- JavaScript 함수 실행
- 스타일 재계산
- 레이아웃
- 페인트
- 합성 관련 작업

### 5. 긴 작업을 확인한다

`2초간 차단` 버튼을 클릭한 구간에는
긴 JavaScript 실행 작업이 표시됩니다.

그 구간 동안 사용자 입력과 화면 갱신이
지연되는 것을 확인합니다.

### 6. DOM 변경과 렌더링을 구분한다

`status.textContent = "작업 중"`은
긴 반복문보다 먼저 실행됩니다.

하지만 화면에 중간 상태가 보이지 않을 수 있습니다.

DOM 상태 변경과 실제 픽셀 출력이
서로 다른 단계라는 점을 확인합니다.

## 흔한 실수

### 렌더링 엔진과 JavaScript 엔진을 같은 것으로 생각한다

렌더링 엔진은 HTML·CSS·DOM과
페이지의 시각적 결과를 처리합니다.

JavaScript 엔진은 ECMAScript 코드를 실행합니다.

둘은 연결되어 있지만 같은 구성 요소가 아닙니다.

### V8이 DOM을 제공한다고 생각한다

V8은 JavaScript와 WebAssembly 엔진입니다.

`document`, `Element`, `fetch()`와 같은 기능은
브라우저 호스트 환경이 제공합니다.

V8을 사용하는 Node.js에
DOM이 기본 제공되지 않는 이유도 여기에 있습니다.

### DOM을 변경하면 화면도 즉시 바뀐다고 생각한다

DOM 객체의 상태는 JavaScript 실행 중에 변경될 수 있습니다.

하지만 화면 갱신은 렌더링 엔진이
스타일, 레이아웃, 페인트와 합성 작업을 수행한 뒤 나타납니다.

긴 JavaScript 작업이 계속되면
화면 출력이 늦어질 수 있습니다.

### JavaScript는 항상 한 줄씩 해석만 된다고 생각한다

현대 JavaScript 엔진은
인터프리터와 여러 컴파일 계층,
실행 중 최적화를 조합할 수 있습니다.

정확한 방식은 엔진마다 다르며
웹 표준이 특정 구현을 강제하지 않습니다.

### JavaScript가 싱글 스레드이므로 브라우저 전체도 싱글 스레드라고 생각한다

페이지의 주요 JavaScript 실행은
일반적으로 하나의 메인 실행 흐름과 연결됩니다.

그러나 브라우저 전체는
네트워크, GPU, 합성, 래스터화,
Worker와 여러 보조 작업을 위해
다수의 프로세스와 스레드를 사용합니다.

### CSS 애니메이션은 무조건 JavaScript와 무관하다고 생각한다

CSS 애니메이션과 전환도
초기 스타일 계산과 레이어 구성 같은
렌더링 엔진의 작업이 필요합니다.

일부 속성은 합성 단계에서 효율적으로 처리될 수 있지만
항상 메인 스레드 작업이 전혀 없다고 단정할 수는 없습니다.

### `transform`을 사용하면 항상 GPU 가속된다고 생각한다

브라우저는 요소 상태와 비용을 고려하여
레이어와 합성 방식을 결정합니다.

특정 CSS 속성을 사용했다는 사실만으로
항상 별도 GPU 레이어가 생성된다고 보장할 수 없습니다.

### 엔진 내부 구현을 웹 표준처럼 의존한다

V8의 컴파일 단계나
Blink의 내부 최적화 방식은 변경될 수 있습니다.

웹 코드는 표준에 정의된 동작과
공개된 Web API를 기준으로 작성해야 합니다.

## 확인 문제

### 1. 렌더링 엔진과 JavaScript 엔진의 역할 차이는 무엇일까?

<details>
  <summary>정답 보기</summary>

  렌더링 엔진은 HTML과 CSS를 처리하고,
  DOM·스타일·레이아웃·페인트 등
  페이지의 시각적 결과를 만듭니다.

  JavaScript 엔진은 ECMAScript 코드를 분석하고 실행하며
  JavaScript 객체의 메모리를 관리합니다.

</details>

### 2. `document.querySelector()`는 JavaScript 엔진만으로 실행될까?

<details>
  <summary>정답 보기</summary>

  아닙니다.

  JavaScript 엔진이 메서드 호출 코드를 실행하지만,
  `document`와 DOM 검색 기능은 브라우저가 제공합니다.

  호출은 브라우저의 연결 계층을 통해
  렌더링 엔진의 DOM 구현으로 전달됩니다.

</details>

### 3. DOM을 변경했는데 화면이 바로 바뀌지 않을 수 있는 이유는 무엇일까?

<details>
  <summary>정답 보기</summary>

  DOM 상태 변경과 실제 화면 렌더링은
  서로 다른 단계이기 때문입니다.

  JavaScript가 메인 스레드를 계속 점유하면
  브라우저가 스타일 계산, 레이아웃과 페인트를 수행할
  기회를 얻지 못할 수 있습니다.

</details>

### 4. V8을 사용하는 환경이면 항상 `document`를 사용할 수 있을까?

<details>
  <summary>정답 보기</summary>

  아닙니다.

  V8은 JavaScript 엔진이며
  `document`는 브라우저가 제공하는 DOM 객체입니다.

  V8을 사용하는 Node.js에는
  DOM이 기본 제공되지 않습니다.

</details>

### 5. 긴 JavaScript 작업이 사용자 경험에 어떤 영향을 줄 수 있을까?

<details>
  <summary>정답 보기</summary>

  메인 스레드의 실행 시간을 오래 사용하여
  클릭, 키보드 입력, 스크롤,
  애니메이션과 화면 갱신을 지연시킬 수 있습니다.

</details>

## 요약

- 렌더링 엔진은 HTML·CSS·DOM을 처리하고 페이지의 시각적 결과를 만듭니다.
- JavaScript 엔진은 ECMAScript 코드를 분석하고 실행하며 JavaScript 메모리를 관리합니다.
- Chromium 계열은 대표적으로 Blink와 V8, Firefox는 Gecko와 SpiderMonkey, Safari는 WebKit과 JavaScriptCore를 사용합니다.
- `document`, DOM, 이벤트, 타이머와 `fetch()`는 JavaScript 엔진 자체가 아니라 브라우저가 제공하는 Web API입니다.
- 브라우저는 Web API 연결 계층을 통해 JavaScript 코드와 렌더링 엔진의 기능을 연결합니다.
- DOM 상태 변경과 실제 화면 출력은 같은 순간에 처리되는 하나의 작업이 아닙니다.
- 긴 JavaScript 실행은 메인 스레드를 점유하여 입력 처리와 렌더링을 지연시킬 수 있습니다.
- JavaScript 엔진은 인터프리터와 컴파일러, 실행 중 최적화를 조합할 수 있지만 정확한 구조는 엔진의 구현 세부 사항입니다.
- Worker는 JavaScript를 실행할 수 있지만 일반적으로 페이지의 DOM을 직접 사용할 수 없습니다.
- 브라우저 엔진 내부 구현보다 웹 표준과 공개된 Web API를 기준으로 코드를 작성해야 합니다.
