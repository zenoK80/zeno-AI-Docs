## 2. 개발 환경 준비와 첫 실행

1편에서 자바스크립트가 어떤 언어인지 살펴봤다. 이번 편의 목표는 하나다. **내 컴퓨터에서 자바스크립트 코드를 직접 실행할 수 있는 상태**를 만드는 것. 3편부터는 코드를 계속 쳐보면서 배울 것이므로, 이번 편에서 실행 환경을 확실히 갖춰두자.

그 전에 먼저 짚고 갈 질문이 있다. 자바스크립트는 대체 **어디서** 실행되는 걸까?

---

### 2.1 자바스크립트가 실행되는 두 곳 — 브라우저와 Node.js

자바스크립트를 실행하려면 **자바스크립트 엔진**이 필요하다.

> **자바스크립트 엔진(JavaScript engine)** — 자바스크립트 코드를 해석하고 실행하는 프로그램. 크롬의 V8, 파이어폭스의 SpiderMonkey, 사파리의 JavaScriptCore가 대표적이다.

이 엔진을 내장한 대표적인 환경이 두 가지 있다. **브라우저**와 **Node.js**다. 둘 다 자바스크립트를 실행할 수 있지만, 존재 목적이 다르다.

| | 브라우저 | Node.js |
| --- | --- | --- |
| 목적 | HTML·CSS·JS를 해석해 웹페이지를 화면에 그린다 | 브라우저 밖에서 자바스크립트를 실행한다 |
| 공통점 | ECMAScript(언어 핵심 문법)를 실행할 수 있다 | ECMAScript를 실행할 수 있다 |
| 고유 기능 | **Web API** — DOM 조작, `alert`, `fetch` 등 | **Node.js API** — 파일 읽기·쓰기, 서버 만들기 등 |

핵심은 이것이다. **언어의 핵심(ECMAScript)은 공유하지만, 각자 제공하는 부가 기능은 서로 호환되지 않는다.**

두 가지 대표적인 비호환 사례를 보자.

**Node.js에는 DOM이 없다.** DOM은 HTML 문서를 자바스크립트로 다루기 위한 도구인데, 브라우저 밖에는 애초에 화면에 그릴 HTML이 없기 때문이다. (DOM이 무엇인지는 36편에서 자세히 다룬다.)

**브라우저에는 파일 시스템 접근 기능이 없다.** 이건 보안 때문이다. 웹페이지에 포함된 자바스크립트는 방문하는 순간 자동으로 다운로드되어 실행된다. 만약 이 코드가 사용자의 로컬 파일을 마음대로 읽고 지울 수 있다면, 악성 웹사이트에 접속하는 것만으로 컴퓨터가 망가질 수 있다.

> 💡 **쉽게 말하면** — 브라우저와 Node.js는 같은 언어(자바스크립트)를 쓰는 두 나라와 같다. 말은 통하지만, 각 나라에만 있는 시설(API)이 다르다. 앞으로 "이 기능이 언어 자체의 기능인가, 아니면 실행 환경이 제공하는 기능인가"를 구분하는 감각이 계속 필요하다.

이번 편에서는 두 환경을 모두 준비한다. 순서는 가장 빠른 것부터 — 설치가 전혀 필요 없는 브라우저부터 시작한다.

### 2.2 가장 빠른 실행 — 브라우저 개발자 도구

지금 이 글을 읽고 있다면 이미 자바스크립트 실행 환경을 하나 갖고 있는 셈이다. 브라우저다. 브라우저에는 개발자를 위한 도구 모음인 **개발자 도구(DevTools)**가 내장되어 있다.

이 시리즈는 크롬을 기준으로 한다. 개발자 도구를 여는 단축키는 다음과 같다.

- 윈도우: `F12` 또는 `Ctrl + Shift + I`
- macOS: `⌘ + ⌥ + I`

개발자 도구에는 여러 패널이 있는데, 지금은 이름과 용도만 훑고 지나가자. 각각은 필요한 시점에 다시 만난다.

| 패널 | 용도 |
| --- | --- |
| **Elements** | 현재 페이지의 HTML·CSS 구조를 보고 즉석에서 수정해본다 |
| **Console** | 자바스크립트 코드를 즉시 실행하고, 에러와 `console.log` 출력을 확인한다 |
| **Sources** | 자바스크립트 코드를 한 줄씩 멈춰가며 디버깅한다 |
| **Network** | 페이지가 서버와 주고받는 요청을 확인한다 |
| **Application** | 브라우저에 저장된 데이터(스토리지, 쿠키)를 관리한다 |

#### 첫 코드 실행

Console 패널을 열고, 아래 코드를 입력한 뒤 엔터를 눌러보자.

```js
console.log('Hello, JavaScript!');
```

`Hello, JavaScript!`가 출력되면 성공이다. 방금 자바스크립트 코드를 처음으로 실행한 것이다.

> **`console.log()`** — 괄호 안의 값을 콘솔에 출력하는 함수. 앞으로 이 시리즈의 거의 모든 예제에서 결과 확인용으로 사용한다.

콘솔은 계산기처럼 쓸 수도 있다.

```js
1 + 2 * 3;      // 7
'안녕' + '하세요'; // '안녕하세요'
```

입력한 코드의 **평가 결과**가 바로 아래에 표시된다. 이렇게 짧은 코드를 즉시 실행해보며 확인하는 습관은 학습 속도를 크게 높여준다.

<Callout type="default">
**콘솔은 항상 열어두고 개발하자.** 자바스크립트 에러는 콘솔에 표시되는데, 콘솔이 닫혀 있으면 에러가 났는지조차 모른 채 "왜 안 되지?"만 반복하게 된다. 개발 중에는 콘솔을 열어두는 것이 기본자세다.
</Callout>

### 2.3 HTML에 자바스크립트 넣기 — script 태그

콘솔은 한 줄씩 실험하기엔 좋지만, 여러 줄짜리 프로그램을 작성하고 보관하기엔 부족하다. 웹페이지에서 자바스크립트를 실행하는 정식 방법은 HTML 문서에 `<script>` 태그로 포함시키는 것이다.

방법은 두 가지다.

#### 방법 1 — HTML 안에 직접 작성 (인라인)

```html
<!DOCTYPE html>
<html>
  <body>
    <h1>첫 페이지</h1>
    <script>
      console.log('HTML 안에서 실행됐다');
    </script>
  </body>
</html>
```

#### 방법 2 — 외부 파일로 분리

```html
<!-- index.html -->
<!DOCTYPE html>
<html>
  <body>
    <h1>첫 페이지</h1>
    <script src="app.js"></script>
  </body>
</html>
```

```js
// app.js
console.log('별도 파일에서 실행됐다');
```

실무에서는 **외부 파일 분리가 기본**이다. 이유는 세 가지다.

1. HTML(구조)과 JS(동작)의 역할이 분리되어 코드를 관리하기 쉽다
2. 여러 HTML 페이지에서 같은 JS 파일을 재사용할 수 있다
3. 브라우저가 JS 파일을 캐시(임시 저장)해 다음 방문 시 더 빠르게 로드한다

한 가지 관례도 기억해두자. `<script>` 태그는 보통 **`</body>` 닫는 태그 바로 앞**에 둔다. HTML이 화면에 다 그려진 뒤에 자바스크립트가 실행되도록 하기 위한 것인데, 왜 그런지·그리고 더 현대적인 대안(`defer`)은 무엇인지는 브라우저 렌더링을 다루는 35편에서 자세히 설명한다. 지금은 "스크립트는 body 끝에"만 기억하면 충분하다.

### 2.4 Node.js 설치와 첫 실행

이제 두 번째 실행 환경, Node.js를 준비하자. 당장 브라우저만으로도 학습은 가능하지만, Node.js를 설치해두면 두 가지가 가능해진다.

- HTML 없이 `.js` 파일을 터미널에서 바로 실행할 수 있다
- **npm**을 쓸 수 있다

> **npm(node package manager)** — 전 세계 개발자들이 만든 자바스크립트 패키지(라이브러리·도구)를 설치하고 관리하는 도구. Node.js를 설치하면 함께 설치된다. 본격적인 활용은 43편(빌드 도구와 개발 환경)에서 다룬다.

#### 설치 — LTS를 받자

[nodejs.org](https://nodejs.org)에 접속하면 두 종류의 버전이 보인다.

- **LTS(Long Term Support)** — 장기간 안정적으로 지원되는 버전. 실무 표준.
- **Current** — 최신 기능이 먼저 들어오는 버전. 지원 기간이 짧다.

2026년 7월 현재 LTS는 **24 버전(코드네임 Krypton)**, Current는 26 버전이다. 학습이든 실무든 **LTS를 설치하면 된다.** 이 시리즈에서 다루는 내용은 전부 LTS에서 동작한다.

설치가 끝나면 터미널(윈도우는 PowerShell, macOS는 터미널 앱)에서 확인한다.

```bash
node -v   # v24.x.x 형태의 버전이 출력되면 성공
npm -v
```

#### REPL — 터미널 속의 콘솔

터미널에 `node`만 입력하면 프롬프트가 `>`로 바뀐다. 이 상태를 **REPL**이라 한다.

> **REPL(Read-Eval-Print Loop)** — 코드를 읽고(Read), 평가하고(Eval), 결과를 출력하는(Print) 과정을 반복하는(Loop) 대화형 실행 환경. 브라우저 콘솔의 터미널 버전이라고 생각하면 된다.

```bash
$ node
> 1 + 2
3
> console.log('Node.js에서 실행')
Node.js에서 실행
```

종료는 `Ctrl + C`를 두 번 누른다.

#### 파일 실행

여러 줄짜리 코드는 파일로 저장한 뒤 실행한다. `app.js`라는 파일이 있다면:

```bash
$ node app.js
```

확장자는 생략해도 된다(`node app`). HTML 없이도 자바스크립트 파일을 직접 실행할 수 있다는 것 — 이것이 Node.js가 열어준 가능성이다.

### 2.5 에디터 준비 — VS Code

콘솔과 REPL은 짧은 실험용이다. 파일 단위로 코드를 작성하려면 코드 에디터가 필요하다. 이 시리즈는 가장 널리 쓰이는 **Visual Studio Code(VS Code)**를 기준으로 한다. [code.visualstudio.com](https://code.visualstudio.com)에서 설치하면 된다.

VS Code는 자동 완성, 문법 오류 표시, 내장 터미널을 기본 제공한다. 여기에 확장(Extension) 하나만 추가로 설치해두자.

**Live Server** — HTML 파일을 로컬 서버로 열어주고, 코드를 수정하면 브라우저가 **자동으로 새로고침**된다. 설치 후 HTML 파일에서 우클릭 → "Open with Live Server"를 누르면 된다. HTML + JS 예제를 실행할 때 계속 사용할 것이다.

#### 함정 하나 — "어디서 실행되는가"를 항상 의식하자

VS Code의 내장 터미널에서 `node app.js`로 실행하면 그 코드는 **Node.js 환경**에서 돈다. 그런데 2.1에서 봤듯 Node.js에는 브라우저 전용 기능이 없다.

```js
// app.js
alert('안녕!');
```

```bash
$ node app.js
ReferenceError: alert is not defined
```

`alert`는 브라우저가 제공하는 Web API라서 Node.js에는 존재하지 않는다. 이런 코드는 HTML에 넣어 브라우저(Live Server)로 실행해야 한다. 반대로 파일을 읽는 Node.js 전용 코드는 브라우저에서 돌지 않는다.

에러가 났을 때 "코드가 틀렸나?"보다 먼저 **"지금 어느 환경에서 실행하고 있지?"**를 자문하는 습관을 들이자. 초보 단계에서 마주치는 에러의 상당수가 여기서 나온다.

### 2.6 에러를 읽는 법 — 디버깅 첫걸음

마지막으로, 앞으로 수없이 만나게 될 **에러**를 다루는 기본기를 익히자.

> **디버깅(debugging)** — 코드의 오류(버그)를 찾아내 원인을 제거하는 작업.

에러는 실패가 아니라 **단서**다. 자바스크립트는 에러가 나면 "무엇이, 어디서, 왜 잘못됐는지"를 콘솔에 알려준다. 간단한 예제로 흐름을 체험해보자.

```html
<!DOCTYPE html>
<html>
  <body>
    <p id="greeting"></p>
    <script>
      const el = document.getElementById('greting'); // 오타!
      el.textContent = '환영합니다';
    </script>
  </body>
</html>
```

이 페이지를 열면 화면에 아무것도 나오지 않고, 콘솔에 이런 에러가 표시된다.

```
Uncaught TypeError: Cannot set properties of null (setting 'textContent')
```

디버깅의 기본 루틴은 다섯 단계다.

1. **에러 메시지를 읽는다** — "null에는 textContent를 설정할 수 없다". 즉 `el`이 `null`(아무것도 없음)이라는 뜻이다.
2. **발생 위치로 이동한다** — 에러 오른쪽의 파일명:줄번호 링크를 클릭하면 Sources 패널에서 해당 줄로 이동한다.
3. **의심 지점에 브레이크포인트를 건다** — 줄 번호를 클릭해 표시를 만들고 페이지를 새로고침하면, 실행이 그 줄에서 멈춘다.
4. **변수 값을 확인한다** — 멈춘 상태에서 변수 위에 마우스를 올리면 실제 값이 보인다. `el`이 `null`임을 확인한다.
5. **원인을 제거한다** — `'greting'`이라는 오타 때문에 해당 id를 가진 요소를 찾지 못한 것. `'greeting'`으로 고치면 해결된다.

지금은 `document.getElementById`가 정확히 무엇인지 몰라도 괜찮다(36편에서 다룬다). 중요한 것은 루틴이다. **에러 메시지 읽기 → 위치 확인 → 값 확인 → 원인 제거.** 이 순서만 몸에 익혀도 "왜 안 되지?"에 쓰는 시간이 크게 줄어든다.

### 이번 편 핵심 요약

1. 자바스크립트의 실행 환경은 **브라우저**와 **Node.js** 두 가지다. ECMAScript는 공유하지만 고유 API(Web API ↔ Node.js API)는 서로 호환되지 않는다.
2. 가장 빠른 실행 방법은 **브라우저 콘솔**이다. 개발 중에는 콘솔을 항상 열어두자.
3. 웹페이지의 자바스크립트는 `<script src="...">`로 **외부 파일 분리**가 기본이며, 태그는 `</body>` 직전에 둔다.
4. Node.js는 **LTS 버전**을 설치하고, REPL 또는 `node 파일명`으로 실행한다.
5. 에러가 나면 먼저 **"어느 환경에서 실행 중인가"**를 확인하고, **에러 메시지 → 위치 → 값 → 원인 제거**의 디버깅 루틴을 따른다.

다음 3편에서는 드디어 언어 자체로 들어간다. 프로그래밍의 출발점인 **변수와 상수**다. 이번 편에서 만든 실행 환경으로 예제를 직접 쳐보면서 따라오면 된다.
