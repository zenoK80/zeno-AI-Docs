## CSS란 무엇인가

CSS는 **Cascading Style Sheets**(캐스케이딩 스타일 시트)의 약자로, 웹 페이지의 **표현(presentation)** 을 담당하는 언어입니다. HTML이 문서의 구조와 의미를 정의한다면, CSS는 그 구조 위에 색상·여백·글꼴·레이아웃·애니메이션 같은 시각적 스타일을 입힙니다.

웹을 이루는 세 가지 핵심 기술은 보통 다음과 같이 역할이 나뉩니다.

- **HTML** — 구조와 의미 (무엇인가)
- **CSS** — 표현과 스타일 (어떻게 보이는가)
- **JavaScript** — 동작과 상호작용 (어떻게 반응하는가)

이렇게 역할을 분리하는 것을 **관심사의 분리(separation of concerns)** 라고 합니다. 마크업과 스타일을 떼어 두면 같은 HTML에 다른 스타일을 입히거나, 스타일 하나만 고쳐 사이트 전체 디자인을 바꾸는 일이 쉬워집니다.

<Callout type="info">
  CSS의 첫 글자 **C(Cascading, 캐스케이딩)** 는 "여러 스타일 규칙이 충돌할 때 우선순위 규칙(폭포처럼 위에서 아래로 흐르는)에 따라 최종 값이 결정된다"는 CSS의 핵심 원리를 가리킵니다. 이 캐스케이드는 03장에서 자세히 다룹니다.
</Callout>

## CSS는 선언형 언어다

CSS는 "이걸 이렇게 해라"라고 단계를 지시하는 **명령형(imperative)** 이 아니라, "이 요소는 이런 모습이어야 한다"고 상태를 기술하는 **선언형(declarative)** 언어입니다. 개발자는 원하는 결과를 규칙으로 선언하고, 그 규칙을 실제 픽셀로 그려내는 일은 브라우저가 맡습니다.

```css
/* "모든 h1은 파란색이고, 아래쪽에 여백을 둔다"고 선언 */
h1 {
  color: royalblue;
  margin-block-end: 1rem;
}
```

가장 작은 단위인 **규칙(rule set)** 은 다음과 같은 구조를 가집니다. 자세한 문법은 다음 장에서 다룹니다.

```css
selector {        /* 선택자: 어떤 요소에 적용할지 */
  property: value; /* 선언: 무엇을 어떤 값으로 */
}
```

## CSS의 짧은 역사

CSS는 웹이 문서 위주였던 시절, "구조와 표현을 분리하자"는 문제의식에서 출발해 지금의 강력한 레이아웃·모션 언어로 성장했습니다.

| 시기 | 사건 |
| --- | --- |
| 1994 | Håkon Wium Lie가 CSS를 처음 제안 |
| 1996 | **CSS1** W3C 권고안(Recommendation) 확정 |
| 1998 | **CSS2** 발표 (positioning, z-index 등 도입) |
| 2011 | **CSS2.1** 정식 권고안 |
| 2010년대~ | **CSS3**부터 하나의 거대 명세 대신 **모듈(Module)** 단위로 분리 개발 |
| 현재 | Flexbox·Grid·Container Queries·`:has()` 등 모듈별로 계속 진화 |

<Callout type="warning">
  흔히 "CSS3", "CSS4"라고 부르지만, 사실 **공식적인 "CSS4"는 없습니다.** CSS3 이후로는 Selectors, Grid, Color 같은 **모듈마다 독립적으로 레벨(Level 4, 5 …)** 을 매기며 발전합니다. 그래서 "이 기능은 CSS 몇이냐"보다 "어느 모듈의 몇 레벨이고, 브라우저가 지원하느냐(Baseline)"가 더 중요합니다.
</Callout>

## 브라우저는 CSS를 어떻게 렌더링하는가

브라우저가 HTML과 CSS를 받아 화면에 그리기까지의 과정을 **핵심 렌더링 경로(Critical Rendering Path)** 라고 합니다. CSS가 성능과 어떤 관계인지 이해하려면 이 흐름을 알아두는 것이 좋습니다.

<Steps>

### HTML 파싱 → DOM 생성

브라우저는 HTML을 위에서부터 읽어 **DOM(Document Object Model)** 트리를 만듭니다. DOM은 문서의 구조(요소들의 부모–자식 관계)를 담은 객체 트리입니다.

### CSS 파싱 → CSSOM 생성

`<style>`, 외부 `.css`, 인라인 스타일을 읽어 **CSSOM(CSS Object Model)** 트리를 만듭니다. 이때 캐스케이드·상속 규칙이 계산되어 각 요소가 어떤 스타일 값을 가질지 결정됩니다.

### 렌더 트리(Render Tree) 구성

DOM과 CSSOM을 결합해 **실제로 화면에 그려질 요소만** 모은 렌더 트리를 만듭니다. `display: none` 인 요소나 `<head>` 처럼 시각적으로 표시되지 않는 부분은 여기서 제외됩니다.

### 레이아웃(Layout / Reflow)

각 요소가 화면의 **어디에, 얼마만한 크기로** 놓일지 위치와 크기를 계산합니다. 뷰포트 크기가 바뀌거나 요소의 크기·위치에 영향을 주는 변경이 생기면 이 과정이 다시 일어나는데, 이를 **리플로우(reflow)** 라고 합니다.

### 페인트(Paint)

계산된 결과를 바탕으로 색상, 테두리, 그림자, 텍스트 등 실제 픽셀을 칠합니다. 크기·위치는 그대로인데 색상 같은 시각 속성만 바뀌면 레이아웃 없이 다시 칠하는 **리페인트(repaint)** 만 발생합니다.

### 컴포지트(Composite)

페인트된 여러 레이어를 순서에 맞게 합성해 최종 화면을 출력합니다. `transform`, `opacity` 같은 속성은 레이아웃·페인트를 건드리지 않고 이 합성 단계에서 처리될 수 있어 애니메이션 성능이 좋습니다.

</Steps>

## 성능 관점에서 기억할 점

- **CSS는 렌더링 차단 리소스(render-blocking resource)** 입니다. 브라우저는 CSSOM이 완성되기 전에는 페이지를 그리지 않으므로, 스타일을 늦게·크게 불러오면 첫 화면 표시가 늦어집니다.
- **리플로우 > 리페인트 > 컴포지트** 순으로 비용이 큽니다. 애니메이션에 `top`/`left`/`width` 대신 `transform`/`opacity`를 쓰라고 하는 이유가 여기에 있습니다. (자세한 내용은 45장 성능 편에서 다룹니다.)

<Callout type="default">
  지금은 "CSS가 DOM과 만나 렌더 트리를 만들고 → 배치하고 → 칠한다"는 큰 그림만 기억하면 충분합니다. 이 흐름은 이후 레이아웃·모션·성능 챕터를 이해하는 밑바탕이 됩니다.
</Callout>
