## 왜 권한을 두 번 다루는가

05편에서는 `ls -l` 한 줄을 읽는 법을 배웠습니다. 여기서는 **계산과 내부 동작**으로 들어갑니다. 이 시험에서 권한은 두 가지 방식으로 출제됩니다.

- **읽기 문제** — 권한 표기를 주고 의미를 묻습니다. 05편 수준입니다.
- **계산 문제** — umask 값을 주고 결과 권한을 묻습니다. 여기서 다룹니다.

계산 문제는 단순 뺄셈으로 푸는 사람이 많은데, umask가 홀수 자리를 포함하면 뺄셈이 틀립니다. 그 이유를 비트 수준에서 이해해야 어떤 값이 나와도 풀 수 있습니다.

> **쉽게 말하면:** umask는 빼는 것이 아니라 **가리는 것**입니다. 대부분의 경우 결과가 뺄셈과 같아서 착각하기 쉬울 뿐입니다.

## 1. umask — 비트를 제거하는 마스크

### 왜 필요한가

파일을 만들 때마다 권한을 지정하는 것은 번거롭습니다. 그래서 시스템은 기본값을 정해 두는데, 그 기본값이 너무 열려 있으면 위험합니다. **"기본값에서 무엇을 빼고 시작할 것인가"** 를 사용자별·세션별로 정해 두는 장치가 umask입니다.

### 기준값 두 개

| 대상 | 기준 권한 | 8진수 | 왜 |
|------|-----------|-------|-----|
| 일반 파일 | `rw-rw-rw-` | 666 | 실행 권한은 위험하므로 애초에 주지 않음 |
| 디렉터리 | `rwxrwxrwx` | 777 | 들어가려면 `x`가 반드시 필요 |

새로 만든 텍스트 파일이 실행 권한을 갖지 않는 이유가 여기 있습니다. 기준값 자체에 `x`가 없습니다. 컴파일한 프로그램에 실행 권한을 주려면 `chmod +x`를 별도로 해야 하는 것도 같은 이유입니다.

### 정확한 연산 — 뺄셈이 아니다

umask의 실제 동작은 **비트 단위 AND NOT**입니다. 수식으로 쓰면 이렇습니다.

$$
\text{최종 권한} = \text{기준 권한} \;\wedge\; \lnot(\text{umask})
$$

각 기호의 뜻은 다음과 같습니다.

- $\wedge$ — 비트 단위 AND. 두 비트가 모두 1일 때만 1
- $\lnot$ — 비트 단위 NOT. 1과 0을 뒤집음
- 기준 권한 — 파일이면 666, 디렉터리면 777

말로 풀면 **"umask에서 켜진 비트를 기준 권한에서 끈다"** 입니다.

### 계산 예 1 — umask 022, 파일

기준값 666을 이진수로 펼칩니다.

$$
666_{(8)} = 110\ 110\ 110_{(2)}
$$

umask 022도 펼칩니다.

$$
022_{(8)} = 000\ 010\ 010_{(2)}
$$

umask에서 켜진 자리(1인 자리)를 기준값에서 끕니다.

$$
110\ 110\ 110 \;\rightarrow\; 110\ 100\ 100 = 644_{(8)}
$$

결과는 **644**, 곧 `rw-r--r--`입니다. 그룹과 기타의 쓰기 비트(2)가 제거되었습니다.

디렉터리는 기준값이 777입니다.

$$
777_{(8)} = 111\ 111\ 111_{(2)}
$$

$$
111\ 111\ 111 \;\rightarrow\; 111\ 101\ 101 = 755_{(8)}
$$

결과는 **755**, 곧 `rwxr-xr-x`입니다.

### 계산 예 2 — umask 027, 보안 강화 설정

umask 027은 서버에서 권장되는 값입니다. 기타 사용자에게 아무 권한도 주지 않습니다.

$$
027_{(8)} = 000\ 010\ 111_{(2)}
$$

파일:

$$
110\ 110\ 110 \;\rightarrow\; 110\ 100\ 000 = 640_{(8)}
$$

디렉터리:

$$
111\ 111\ 111 \;\rightarrow\; 111\ 101\ 000 = 750_{(8)}
$$

파일은 **640**(`rw-r-----`), 디렉터리는 **750**(`rwxr-x---`)입니다. 기타 사용자는 파일을 읽을 수도, 디렉터리에 들어갈 수도 없습니다.

### 계산 예 3 — 뺄셈이 틀리는 경우

umask **133**으로 파일을 만들면 어떻게 될까요? 뺄셈으로 하면 `666 - 133 = 533`입니다. 그런데 실제 답은 다릅니다.

$$
666_{(8)} = 110\ 110\ 110_{(2)}
$$

$$
133_{(8)} = 001\ 011\ 011_{(2)}
$$

기준값에 없는 비트는 뺄 것이 없으므로 그냥 무시됩니다. 자리마다 확인해 봅시다.

- 소유자: 기준 `110`, 마스크 `001` → 마스크의 1번째 자리(실행)는 기준값에 이미 0이므로 변화 없음 → `110` = 6
- 그룹: 기준 `110`, 마스크 `011` → 쓰기 비트가 꺼짐, 실행은 원래 없음 → `100` = 4
- 기타: 기준 `110`, 마스크 `011` → 같은 이유 → `100` = 4

$$
\text{결과} = 644_{(8)}
$$

뺄셈으로 구한 533과 전혀 다릅니다. **umask는 없는 비트를 음수로 만들지 않고 그냥 무시하기 때문**입니다. 이것이 "뺄셈이 아니라 마스크"라는 말의 실질적 의미입니다.

> **쉽게 말하면:** umask는 이미 꺼져 있는 스위치를 다시 끄려 해도 아무 일도 일어나지 않습니다. 뺄셈처럼 음수로 내려가지 않습니다.

### umask 확인과 설정

```bash
$ umask            # 8진수로 출력
0022
$ umask -S         # 기호로 출력 (허용되는 권한을 보여 줌)
u=rwx,g=rx,o=rx
$ umask 027        # 현재 셸에만 적용
```

`umask -S`가 헷갈립니다. **8진수는 "제거할 비트"를, 기호 출력은 "남는 권한"을** 보여 줍니다. 서로 반대 방향의 표현입니다.

umask는 셸 세션마다 적용되므로 영구 설정은 프로파일 파일에 씁니다.

| 파일 | 적용 범위 |
|------|-----------|
| `/etc/profile`, `/etc/bashrc` | 전체 사용자 |
| `~/.bash_profile`, `~/.bashrc` | 개인 사용자 |
| `/etc/login.defs`의 `UMASK` | 로그인 시 기본값 |

RHEL 계열은 `/etc/profile`에서 UID가 199보다 크고 사용자 이름과 그룹 이름이 같으면 002, 아니면 022를 주는 조건문을 두고 있습니다. 이것이 **UPG**(User Private Group, 사용자 개인 그룹) 정책과 맞물린 설계이며 12편에서 다시 다룹니다.

## 2. 특수 권한 비트 세 가지

일반 권한 9비트 위에 3비트가 더 있습니다. 8진수로 표현하면 **네 자리**가 됩니다.

| 비트 | 8진수 | 위치 | 표시 |
|------|-------|------|------|
| setuid | 4000 | 소유자 실행 자리 | `s` (실행 권한 있음) / `S` (없음) |
| setgid | 2000 | 그룹 실행 자리 | `s` / `S` |
| sticky bit | 1000 | 기타 실행 자리 | `t` / `T` |

**대문자와 소문자의 차이**가 함정으로 나옵니다. 원래 실행 권한(`x`)이 있는 자리에 특수 비트가 붙으면 **소문자**, 실행 권한이 없는데 특수 비트만 붙으면 **대문자**입니다. 대문자 `S`는 대개 설정 실수를 뜻합니다.

### setuid — 실행 중 소유자 권한 획득

**왜 필요한가.** 일반 사용자가 자기 비밀번호를 바꾸려면 `/etc/shadow`를 수정해야 합니다. 그런데 그 파일의 권한은 `----------`(000)이고 소유자는 root입니다. root만 쓸 수 있습니다. 그렇다고 사용자에게 root 권한을 줄 수는 없습니다.

**해결.** 프로그램 파일에 setuid를 걸어, **그 프로그램이 실행되는 동안만** 소유자 권한을 빌려줍니다.

```
-rwsr-xr-x. 1 root root 27856 Apr  1  2020 /usr/bin/passwd
```

```bash
# chmod 4755 프로그램      # 8진수 방식
# chmod u+s 프로그램       # 기호 방식
```

setuid는 강력한 만큼 위험합니다. setuid가 걸린 프로그램에 보안 결함이 있으면 공격자가 root 권한을 얻습니다. 그래서 보안 점검에서 setuid 파일 목록을 정기적으로 확인합니다.

```bash
# find / -perm -4000 -type f 2>/dev/null
```

`-perm -4000`에서 앞의 하이픈은 "이 비트를 **포함하는**"이라는 뜻입니다. 하이픈이 없으면 정확히 일치하는 것만 찾습니다. 이 미묘한 차이가 문항으로 나옵니다.

### setgid — 그룹 권한 획득과 그룹 상속

setgid는 **파일에 걸 때와 디렉터리에 걸 때 효과가 완전히 다릅니다.**

| 대상 | 효과 |
|------|------|
| 실행 파일 | 실행되는 동안 **파일의 소유 그룹 권한**을 획득 |
| **디렉터리** | 그 안에 새로 만든 파일·디렉터리가 **디렉터리의 그룹을 상속** |

디렉터리 setgid가 실무에서 훨씬 자주 쓰입니다. 팀 공유 디렉터리를 생각해 봅시다.

```bash
# mkdir /project
# chgrp devteam /project
# chmod 2770 /project
```

이제 `/project` 안에 누가 파일을 만들든 그 파일의 그룹은 자동으로 `devteam`이 됩니다. setgid가 없다면 파일의 그룹은 만든 사람의 기본 그룹이 되어, 다른 팀원이 접근하지 못합니다.

```bash
$ ls -ld /project
drwxrws---. 2 root devteam 4096 Mar 11 09:30 /project
```

그룹 실행 자리에 `s`가 보입니다.

### sticky bit — 공유 디렉터리의 삭제 제한

**왜 필요한가.** `/tmp`는 모든 사용자가 파일을 만들 수 있어야 하므로 `w` 권한을 전부 열어야 합니다. 그런데 05편에서 봤듯 **파일 삭제 권한은 디렉터리의 `w`에 달려 있으므로**, 누구나 남의 임시 파일을 지울 수 있게 됩니다.

**해결.** sticky bit를 걸면 그 디렉터리 안에서는 **파일의 소유자와 디렉터리 소유자, 그리고 root만 삭제**할 수 있습니다.

```
drwxrwxrwt. 15 root root 4096 Mar 11 09:30 /tmp
```

```bash
# chmod 1777 /tmp
# chmod +t /tmp
```

| 비트 | 실무 대표 사례 | 판별 문장 |
|------|-----------------|-----------|
| setuid | `/usr/bin/passwd` | "실행하는 동안 소유자 권한으로" |
| setgid (디렉터리) | 팀 공유 디렉터리 | "새로 만든 파일이 그룹을 상속" |
| sticky bit | `/tmp` | "자기 파일만 삭제 가능" |

## 3. 특수 비트를 포함한 8진수 계산

특수 비트가 있으면 8진수가 네 자리가 됩니다.

$$
\text{전체} = (\text{특수 비트}) \times 1000 + (\text{일반 권한})
$$

- 특수 비트 자리 — setuid 4, setgid 2, sticky 1을 더한 값
- 일반 권한 — 05편에서 배운 세 자리

예를 들어 setuid와 setgid를 모두 걸고 권한이 755라면 4 더하기 2로 6이므로 **6755**입니다. `/tmp`처럼 sticky만 걸고 777이면 **1777**입니다.

`chmod`에 세 자리만 주면 특수 비트가 **0으로 초기화**됩니다. setuid가 걸린 파일에 `chmod 755`를 하면 setuid가 사라집니다. 이 함정이 실무에서도 시험에서도 자주 나옵니다.

## 4. ACL — 권한 모델의 확장

### 왜 필요한가

기존 권한 모델은 대상이 **소유자, 그룹, 기타** 셋뿐입니다. 다음 요구를 표현할 수 있을까요?

> `report.txt`는 소유자 posein이 읽고 쓰고, `ihd` 그룹은 읽기만 하고, 그런데 **`kim`이라는 특정 사용자 한 명에게만** 쓰기 권한을 추가로 주고 싶다.

셋뿐인 모델로는 불가능합니다. 새 그룹을 만들어 우회할 수는 있지만, 이런 예외가 늘어날수록 그룹이 폭증합니다.

**ACL**(Access Control List, 접근 제어 목록)은 파일마다 **사용자별·그룹별 권한 항목을 여러 개 붙일 수 있게** 하는 확장입니다.

### getfacl과 setfacl

```bash
$ getfacl report.txt
# file: report.txt
# owner: posein
# group: ihd
user::rw-
user:kim:rw-
group::r--
mask::rw-
other::r--
```

| 항목 | 의미 |
|------|------|
| `user::rw-` | 소유자 권한 (기존 모델의 u) |
| `user:kim:rw-` | **명명된 사용자**(named user) kim의 권한 |
| `group::r--` | 소유 그룹 권한 |
| `group:팀명:권한` | 명명된 그룹의 권한 |
| `mask::rw-` | **유효 권한의 상한선** |
| `other::r--` | 기타 권한 |

설정 명령입니다.

```bash
# setfacl -m u:kim:rw report.txt        # 사용자 kim에게 읽기 쓰기
# setfacl -m g:devteam:r report.txt     # 그룹에게 읽기
# setfacl -x u:kim report.txt           # kim 항목 제거
# setfacl -b report.txt                 # ACL 전체 제거
# setfacl -R -m u:kim:rx /data          # 재귀 적용
```

| 옵션 | 뜻 |
|------|-----|
| `-m` | modify – 항목 추가·수정 |
| `-x` | 특정 항목 삭제 |
| `-b` | remove all – ACL 전부 제거 |
| `-d` | **기본(default) ACL** – 디렉터리 전용, 하위에 상속 |
| `-R` | 재귀 |
| `-k` | 기본 ACL 제거 |

ACL이 설정된 파일은 `ls -l`에서 권한 끝에 **`+` 기호**가 붙습니다.

```
-rw-rw-r--+ 1 posein ihd 1024 Mar 11 09:30 report.txt
```

이 `+` 기호를 알아보는 것이 실무의 시작이고 시험의 단서입니다. 참고로 끝의 `.` 하나는 SELinux 컨텍스트가 있다는 표시입니다. **`+`는 ACL, `.`은 SELinux**로 구분합니다.

### 마스크 — 가장 헷갈리는 부분

ACL에는 `mask` 항목이 있습니다. 이것은 **소유자와 기타를 제외한 모든 항목(명명된 사용자, 소유 그룹, 명명된 그룹)의 권한 상한선**입니다.

어떤 항목에 `rwx`를 줘도 마스크가 `r--`이면 **실제 유효 권한은 `r--`** 입니다. `getfacl` 출력에서 마스크에 걸려 깎인 항목은 옆에 `#effective:` 표시가 붙습니다.

```
user:kim:rwx            #effective:r--
mask::r--
```

마스크가 존재하는 이유는 **기존 `chmod`와의 호환** 때문입니다. ACL을 모르는 오래된 프로그램이 `chmod 640`을 실행하면, 그 그룹 비트 `4`가 ACL의 마스크로 반영됩니다. 이렇게 하면 ACL 항목을 일일이 건드리지 않고도 "전체적으로 권한을 조인다"는 의도가 지켜집니다.

> **쉽게 말하면:** 마스크는 수도꼭지 전체를 잠그는 밸브입니다. 각 방의 수도를 아무리 열어도 밸브가 잠겨 있으면 물이 안 나옵니다.

### 기본 ACL과 umask의 상호작용

디렉터리에 **기본 ACL**(default ACL)을 걸면, 그 안에 새로 만드는 파일이 그 ACL을 상속합니다.

```bash
# setfacl -d -m u:kim:rw /project
```

여기서 중요한 규칙이 있습니다. **기본 ACL이 설정된 디렉터리에서 파일을 만들면, umask가 적용되지 않고 기본 ACL이 결정합니다.** umask는 ACL이 없을 때만 작동하는 셈입니다.

이 규칙 때문에, 팀 디렉터리에 기본 ACL을 걸어 두면 팀원마다 umask가 달라도 **일관된 권한**이 보장됩니다. ACL을 쓰는 실무적 이유가 여기 있습니다.

| 상황 | 새 파일 권한 결정자 |
|------|---------------------|
| 기본 ACL 없음 | **umask** |
| 기본 ACL 있음 | **기본 ACL** (umask 무시) |

### ACL을 쓰려면 파일시스템이 지원해야 한다

ACL은 파일시스템의 확장 속성(extended attribute)에 저장됩니다. 그래서 마운트 옵션에 `acl`이 필요할 수 있습니다.

```
/dev/sdb1  /data  ext4  defaults,acl  0 2
```

현대 배포판의 ext4와 XFS는 기본적으로 ACL이 켜져 있습니다. 데비안·우분투는 `acl` 패키지를 별도로 설치해야 `getfacl`·`setfacl` 명령을 쓸 수 있는 경우가 있습니다.

## 5. 파일 속성 — chattr와 lsattr

권한·ACL과 별개로 **파일 속성**(attribute)이라는 층이 하나 더 있습니다. ext 계열과 XFS에서 지원합니다.

| 속성 | 효과 |
|------|------|
| `i` | immutable – **수정·삭제·이름 변경·링크 생성 전부 불가** |
| `a` | append only – **내용 추가만 가능**, 기존 내용 수정·삭제 불가 |
| `s` | 삭제 시 블록을 0으로 덮어씀 |
| `A` | atime을 갱신하지 않음 |

```bash
# chattr +a /etc/services      # 추가만 가능하게
# chattr +i /etc/passwd        # 완전 불변
# chattr -i /etc/passwd        # 해제
# lsattr /etc/passwd           # 속성 확인
```

기출 문항입니다.

> `/etc/services` 파일의 수정은 불가하고 **내용 추가만 가능**하도록 설정하는 명령으로 알맞은 것은?

정답은 `chattr +a /etc/services`입니다. `+i`는 추가조차 막으므로 오답입니다. 보기에 `setfacl -m +a` 같은 형태가 섞여 나오는데, **ACL과 속성은 완전히 다른 층**이라는 점을 알면 걸러집니다.

**중요:** `chattr +i`가 걸린 파일은 **root조차 수정할 수 없습니다.** 먼저 속성을 해제해야 합니다. 이것이 로그 파일 무단 삭제 방지에 쓰이는 이유입니다.

| 층 | 도구 | 저장 위치 |
|----|------|-----------|
| 기본 권한 | `chmod`, `chown` | inode의 모드 비트 |
| 확장 권한 | `setfacl`, `getfacl` | 확장 속성 |
| 파일 속성 | `chattr`, `lsattr` | inode의 속성 플래그 |
| 보안 컨텍스트 | `chcon`, `semanage` | SELinux 확장 속성 |

## 핵심 정리

- umask는 뺄셈이 아니라 **비트 제거**입니다. 파일 기준 666, 디렉터리 기준 777에서 umask에 켜진 비트를 끕니다. 기준값에 없는 비트는 무시되므로 뺄셈과 결과가 다를 수 있습니다.
- 대표 결과는 **umask 022이면 파일 644 디렉터리 755**, **umask 027이면 파일 640 디렉터리 750**입니다.
- **setuid(4000)는 실행 중 소유자 권한**, **디렉터리 setgid(2000)는 그룹 상속**, **sticky bit(1000)는 자기 파일만 삭제**입니다. 실행 권한이 없는 자리에 붙으면 대문자로 표시됩니다.
- `chmod`에 세 자리만 주면 **특수 비트가 초기화**됩니다.
- ACL은 사용자·그룹별 권한 항목을 추가하는 확장이며, `ls -l`에서 **`+` 기호**로 확인합니다. `mask`는 소유자와 기타를 제외한 항목들의 **유효 권한 상한선**입니다.
- **기본 ACL이 걸린 디렉터리에서는 umask가 적용되지 않고 기본 ACL이 권한을 결정합니다.**
- `chattr +a`는 추가만 허용, **`chattr +i`는 root도 수정 불가**입니다.
