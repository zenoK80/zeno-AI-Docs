## 왜 커널을 이 깊이까지 보는가

2과목 "리눅스 시스템 관리"는 20문항밖에 없는데, 그중 **커널 모듈과 커널 컴파일이 4~5문항**을 차지하는 회차가 흔합니다. 과락선이 8문항인 과목에서 5문항은 전체의 절반이 넘습니다. 즉 이 주제를 버리면 과락 위험이 급격히 올라갑니다.

그런데 다행히 출제 범위는 좁습니다. 시험은 커널 코드를 묻지 않습니다. **모듈 관리 명령 넷의 차이**, **컴파일 단계 순서**, **커널 파라미터 조작법** — 이 세 덩어리가 거의 전부입니다.

> **쉽게 말하면:** 커널 문항은 "커널을 만들 줄 아는가"가 아니라 "커널을 관리하는 도구를 구분할 줄 아는가"를 묻습니다.

02편에서 커널과 사용자 공간의 구조를 봤습니다. 이 편은 그 구조를 **실제로 조작하는 방법**으로 내려갑니다.

## 1. 커널의 정체 다시 보기

### 모놀리식 커널과 마이크로 커널

운영체제 커널은 설계 철학에 따라 두 갈래로 나뉩니다.

| 구분 | 모놀리식 커널(monolithic) | 마이크로 커널(micro) |
|------|---------------------------|----------------------|
| 구조 | 파일시스템·드라이버·네트워크가 **전부 커널 공간에** | 최소 기능만 커널에, 나머지는 **사용자 공간 서버**로 |
| 속도 | 빠름 (모드 전환이 적음) | 느림 (메시지 전달 비용) |
| 안정성 | 드라이버 하나가 커널 전체를 죽일 수 있음 | 한 서버가 죽어도 격리됨 |
| 대표 | **리눅스**, 전통 유닉스 | MINIX, Mach, QNX |

리눅스는 모놀리식이지만, **동적 적재 모듈**(LKM, Loadable Kernel Module)을 지원해 마이크로 커널의 유연성 일부를 흡수했습니다. 그래서 "모듈형 모놀리식 커널"이라고 부르기도 합니다. 참고로 미닉스(MINIX)는 앤드루 타넨바움이 만든 마이크로 커널 교육용 유닉스이고, 리누스 토발즈가 이를 참고해 리눅스를 만들었다는 문항이 1번 문제로 자주 나옵니다.

### 커널 버전 표기 읽기

```bash
$ uname -r
3.10.0-1160.el7.x86_64
```

| 부분 | 의미 |
|------|------|
| `3` | 메이저(major) 버전 |
| `10` | 마이너(minor) 버전 |
| `0` | 패치 레벨 |
| `-1160` | 배포판이 붙인 릴리스 번호 |
| `el7` | Enterprise Linux 7 계열임을 표시 |
| `x86_64` | 아키텍처 |

2.6 버전대까지는 **마이너 번호가 짝수면 안정판, 홀수면 개발판**이라는 규칙이 있었습니다. 이 규칙은 3.0부터 폐지되었지만 시험에는 여전히 출제됩니다. 2.4.18은 안정판, 2.5.1은 개발판입니다.

`uname` 명령의 옵션도 함께 나옵니다.

| 옵션 | 출력 |
|------|------|
| `-r` | 커널 릴리스(버전) |
| `-s` | 커널 이름 (Linux) |
| `-n` | 호스트 이름 |
| `-m` | 하드웨어 아키텍처 |
| `-a` | 전부 |

## 2. 커널 모듈 관리 — 이 편의 최대 빈출

### 모듈이란 무엇인가

모듈은 **실행 중인 커널에 붙였다 뗄 수 있는 기능 조각**입니다. 확장자는 `.ko`(kernel object)이고, `/lib/modules/커널버전/` 아래에 커널 버전별로 따로 보관됩니다. 커널 버전이 바뀌면 모듈도 새로 빌드해야 하는 이유가 이것입니다.

> **쉽게 말하면:** 모듈은 커널이라는 본체에 끼우는 확장 카드입니다. 카드마다 맞는 본체 규격(커널 버전)이 정해져 있습니다.

### 네 명령의 정확한 차이

| 명령 | 하는 일 | 의존성 처리 | 대상 지정 방식 |
|------|---------|-------------|-----------------|
| `insmod` | 모듈 적재 | **안 함** | **파일 경로 전체** 필요 |
| `rmmod` | 모듈 제거 | **안 함** | 모듈 이름 |
| `modprobe` | 모듈 적재, `-r`이면 제거 | **함** | 모듈 이름 |
| `depmod` | 의존성 파일 `modules.dep` 생성·갱신 | 의존성 정보를 **만듦** | – |
| `lsmod` | 적재된 모듈 목록 출력 | – | – |
| `modinfo` | 모듈의 정보(설명, 저자, 파라미터) 출력 | – | 모듈 이름 |

여기서 세 가지 갈림길이 시험 문항을 만듭니다.

**갈림길 1 — 의존성.** 어떤 모듈이 다른 모듈의 기능을 필요로 하면 순서대로 올려야 합니다. `insmod`는 그 순서를 모르므로 "Unknown symbol" 오류를 내고 실패합니다. `modprobe`는 `modules.dep` 파일을 읽어 필요한 모듈을 먼저 올립니다. 제거할 때도 마찬가지로 `modprobe -r`가 딸린 모듈까지 정리합니다.

**갈림길 2 — 대상 지정.** `insmod`는 커널이 모듈을 어디서 찾을지 모르므로 전체 경로를 줘야 합니다.

```bash
# insmod /lib/modules/3.10.0-1160.el7.x86_64/kernel/net/netfilter/iptable_filter.ko
# modprobe iptable_filter
```

같은 일을 하는데 타이핑 양이 이만큼 차이 납니다. 실무에서 `modprobe`만 쓰는 이유입니다.

**갈림길 3 — `depmod`의 위치.** `depmod`는 모듈을 올리거나 내리는 명령이 아닙니다. `/lib/modules/커널버전/modules.dep` 파일을 **다시 계산해서 쓰는** 명령입니다. 새 모듈을 그 디렉터리에 복사한 뒤 `depmod -a`를 실행해야 `modprobe`가 그 모듈을 찾을 수 있습니다.

기출 문항 두 개가 나란히 나온 적이 있습니다.

```bash
# ( 괄호 ) -r iptable_filter      → modprobe
# ( 괄호 ) iptable_filter         → modprobe
```

두 문항 모두 정답이 `modprobe`입니다. 첫 번째는 `-r`가 붙었으니 제거, 두 번째는 적재입니다. 보기에는 `insmod`와 `rmmod`가 함께 나오지만, **의존성을 고려하는 표준 방법**을 묻는 것이므로 답은 `modprobe`입니다. 그리고 별도 문항으로 "커널 모듈 간의 의존성을 갱신할 때 사용하는 명령"이 나오면 그때가 `depmod`입니다.

### lsmod 출력 읽기

```
$ lsmod
Module                  Size  Used by
iptable_filter         12810  1
ip_tables              27239  1 iptable_filter
xfs                   996780  2
```

| 컬럼 | 의미 |
|------|------|
| Module | 모듈 이름 |
| Size | 메모리 점유 크기 |
| Used by | **사용 횟수**와 **이 모듈을 쓰는 다른 모듈 이름** |

`ip_tables` 줄의 `1 iptable_filter`는 "1개가 나를 쓰고 있고, 그것은 `iptable_filter`다"라는 뜻입니다. 그래서 `ip_tables`를 먼저 제거하려 하면 실패합니다. **의존하는 쪽을 먼저 내려야** 하며, `modprobe -r`가 이 순서를 자동으로 처리합니다.

## 3. 커널 컴파일 — 순서가 전부다

### 왜 컴파일하는가

배포판이 제공하는 커널로 대부분 충분하지만, 다음 경우에 직접 빌드합니다.

- 특정 하드웨어 드라이버를 커널에 내장하고 싶을 때
- 불필요한 기능을 제거해 커널 크기를 줄이고 싶을 때
- 새 커널 기능을 미리 써 보고 싶을 때

### 표준 순서

<Steps>
1. **소스 준비** — `/usr/src/linux` 등에 커널 소스를 풀어 놓습니다.
2. **`make mrproper`** — 이전 설정과 컴파일 결과물을 **모두 삭제**해 완전히 깨끗한 상태로 만듭니다.
3. **`make menuconfig`** — 어떤 기능을 내장(`y`), 모듈(`m`), 제외(`n`)로 할지 고릅니다. 결과는 `.config` 파일에 저장됩니다.
4. **`make bzImage`** — 압축된 커널 이미지를 생성합니다.
5. **`make modules`** — 모듈로 지정한 것들을 빌드합니다.
6. **`make modules_install`** — 빌드된 모듈을 `/lib/modules/` 아래에 설치합니다.
7. **`make install`** — 커널 이미지를 `/boot`에 복사하고 부트로더 설정을 갱신합니다.
8. **재부팅** — 새 커널로 부팅해 확인합니다.
</Steps>

기출은 이 중 **앞 세 단계의 순서**를 묻습니다.

> 가. make menuconfig  나. make bzImage  다. make mrproper

정답 순서는 **다 → 가 → 나**, 즉 `mrproper` → `menuconfig` → `bzImage`입니다. 논리는 단순합니다. **청소 → 설정 → 빌드**. 청소를 나중에 하면 설정이 날아가고, 설정 전에 빌드하면 빌드할 내용이 없습니다.

### 청소 명령 세 가지 구분

| 명령 | 지우는 범위 |
|------|-------------|
| `make clean` | 컴파일 결과물(오브젝트 파일)만. `.config`는 **유지** |
| `make mrproper` | 결과물 + **`.config` 설정 파일까지** |
| `make distclean` | mrproper + 편집기 백업 파일 등 **모든 부산물** |

지우는 범위가 `clean` → `mrproper` → `distclean` 순으로 넓어집니다. "이전 설정을 완전히 초기화한다"는 문장이 있으면 `mrproper`입니다.

### 설정 도구 네 가지 — X 윈도 필요 여부

| 명령 | 인터페이스 | X 윈도 필요? |
|------|-----------|---------------|
| `make config` | 질문에 하나씩 답하는 순수 텍스트 | **불필요** |
| `make menuconfig` | ncurses 기반 텍스트 메뉴 | **불필요** |
| `make xconfig` | Qt 기반 그래픽 창 | **필요** |
| `make gconfig` | GTK 기반 그래픽 창 | **필요** |

기출은 "X 윈도가 미설치된 환경에서 사용할 수 있는 조합"을 묻습니다. 정답은 `make config`와 `make menuconfig`입니다. 이름에 **`x`와 `g`가 들어간 것이 그래픽 도구**라는 규칙으로 기억하면 헷갈리지 않습니다.

### 결과물의 이름

| 이름 | 정체 |
|------|------|
| `vmlinux` | 압축되지 않은 커널 이미지 |
| `vmlinuz` | **압축된** 커널 이미지 (`z`는 압축을 의미) |
| `bzImage` | big zImage – 512KB를 넘는 큰 커널 이미지 형식 |
| `zImage` | 구형의 작은 커널 이미지 형식 |
| `System.map` | 커널 심볼과 주소의 대응표 |

`bzImage`의 `bz`는 bzip2가 아니라 **big zImage**입니다. 이 오해를 유도하는 보기가 나올 수 있습니다.

## 4. `/proc` — 커널을 파일처럼 들여다보기

### 가상 파일시스템이라는 발상

`/proc`은 디스크에 존재하지 않습니다. 커널이 **메모리 위에 만들어 내는 가상 파일시스템**(procfs)입니다. 커널 내부의 상태를 파일 읽기라는 익숙한 방식으로 노출하는 창구입니다.

```bash
$ cat /proc/cpuinfo        # CPU 정보
$ cat /proc/meminfo        # 메모리 사용 현황
$ cat /proc/version        # 커널 버전과 빌드 정보
$ cat /proc/partitions     # 인식된 파티션 목록
$ cat /proc/mdstat         # 소프트웨어 RAID 상태
$ cat /proc/modules        # 적재된 모듈 (lsmod의 원본)
$ ls /proc/1234/           # PID 1234 프로세스의 상세 정보
```

시험에 특히 자주 나오는 것은 **`/proc/mdstat`** 입니다. 소프트웨어 RAID 장치의 레벨과 동기화 상태를 실시간으로 보여 주는 파일로, 13편의 RAID 설명에서 다시 나옵니다. 보기에는 `/proc/mdadm`, `/proc/raidtools` 같은 존재하지 않는 경로가 함께 나오므로 **이름을 정확히** 기억해야 합니다.

### `/proc/sys`와 sysctl — 커널을 바꾸는 손잡이

`/proc/sys` 아래의 파일은 읽기만 하는 것이 아니라 **쓰면 커널 동작이 즉시 바뀝니다.**

```bash
# cat /proc/sys/net/ipv4/ip_forward
0
# echo 1 > /proc/sys/net/ipv4/ip_forward
```

같은 일을 하는 전용 명령이 `sysctl`입니다.

| 명령 | 하는 일 |
|------|---------|
| `sysctl -a` | 모든 커널 파라미터 출력 |
| `sysctl 이름` | 특정 파라미터 값 조회 |
| `sysctl -w 이름=값` | 값 **변경**(write) |
| `sysctl -n 이름` | 이름 없이 **값만** 출력 |
| `sysctl -p` | `/etc/sysctl.conf`를 읽어 적용 |

기출 문항입니다.

> iptables를 이용해서 인터넷 공유나 IP 마스커레이드 정책을 사용하려고 한다.

정답은 `sysctl -w net.ipv4.ip_forward=1`입니다. 판별 지점이 두 개입니다.

- **`-w`인가 `-n`인가** — 값을 바꾸는 것이므로 write의 `w`입니다. `-n`은 출력 형식 옵션일 뿐 값을 바꾸지 못합니다.
- **0인가 1인가** — 리눅스를 라우터처럼 써서 패킷을 다른 인터페이스로 넘기려면 IP 포워딩을 **켜야** 하므로 1입니다.

**IP 포워딩**(IP forwarding)은 리눅스가 자기에게 온 것이 아닌 패킷을 다른 네트워크로 전달해 주는 기능입니다. 기본값은 0(꺼짐)이며, NAT나 인터넷 공유를 하려면 반드시 켜야 합니다. 20편의 방화벽 편에서 다시 등장합니다.

`sysctl -w`로 바꾼 값은 **재부팅하면 사라집니다.** 영구 적용하려면 `/etc/sysctl.conf`(또는 `/etc/sysctl.d/` 아래 파일)에 기록합니다. 이 "일시 vs 영구" 구분도 자주 출제됩니다.

## 5. 사용자 공간에서 커널을 관찰하기

### dmesg — 커널이 남긴 메시지

커널은 부팅 중과 실행 중에 발생한 메시지를 **커널 링 버퍼**(ring buffer)라는 고정 크기 메모리 영역에 씁니다. 이를 읽는 명령이 `dmesg`(display message)입니다.

```bash
$ dmesg | tail
[    2.345678] EXT4-fs (sda1): mounted filesystem with ordered data mode
[    3.112233] IPv6: ADDRCONF(NETDEV_UP): eth0: link is not ready
```

앞의 대괄호 숫자는 부팅 후 경과 초입니다. 하드웨어 인식 실패나 드라이버 오류를 확인할 때 가장 먼저 보는 곳입니다. 16편의 로그 편에서 `journalctl -k`와 비교합니다.

### 커널과 라이브러리의 경계 다시 확인

02편에서 봤듯 `ldd`는 **사용자 공간 라이브러리** 의존성을, `depmod`는 **커널 공간 모듈** 의존성을 다룹니다. 이름이 비슷해 보기로 함께 나오므로 아래 표를 붙잡으십시오.

| 명령 | 다루는 것 | 있는 곳 |
|------|-----------|---------|
| `ldd` | 공유 라이브러리 의존성 조회 | 사용자 공간 |
| `ldconfig` | 라이브러리 캐시 갱신 | 사용자 공간 |
| `depmod` | 커널 모듈 의존성 파일 갱신 | 커널 공간 |
| `modprobe` | 커널 모듈 적재·제거 | 커널 공간 |

## 핵심 정리

- 리눅스는 **모놀리식 커널**이지만 동적 적재 모듈로 유연성을 확보했습니다. 미닉스는 마이크로 커널입니다.
- 모듈 명령 중 **의존성을 처리하는 것은 `modprobe`뿐**이며, 제거는 `modprobe -r`입니다. `depmod`는 의존성 파일 `modules.dep`를 갱신합니다.
- 커널 컴파일 순서는 **`make mrproper` → `make menuconfig` → `make bzImage`**, 즉 청소 → 설정 → 빌드입니다.
- 설정 도구 중 이름에 `x`나 `g`가 들어간 `xconfig`와 `gconfig`는 X 윈도가 필요하고, `config`와 `menuconfig`는 필요 없습니다.
- `/proc`은 커널이 메모리에 만드는 가상 파일시스템이며, RAID 상태는 **`/proc/mdstat`** 에서 봅니다.
- 커널 파라미터 변경은 **`sysctl -w`**, 영구 적용은 `/etc/sysctl.conf`입니다. IP 포워딩을 켜려면 값을 1로 설정합니다.
