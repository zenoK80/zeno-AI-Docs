## 테스트 원칙 (7가지)

1. 테스팅은 결함이 없음을 보여주지 않는다 (결함 존재 증명)
2. 완벽한 테스팅은 불가능하다
3. 테스팅은 개발 초기에 시작해야 한다
4. 결함 집중 (결함은 특정 모듈에 집중됨, 파레토 법칙)
5. 테스트는 독립적으로 수행해야 한다
6. 살충제 패러독스 (반복된 동일 테스트는 효과 감소)
7. 테스팅은 상황에 따라 다르다

## 화이트박스 테스트

내부 코드·로직 구조를 알고 테스트합니다. 개발자 관점.

| 기법 | 설명 |
|------|------|
| 구문 커버리지(Statement) | 모든 구문을 최소 1번 실행 |
| 결정(분기) 커버리지(Decision/Branch) | 모든 조건의 T/F 분기 실행 |
| 조건 커버리지(Condition) | 각 조건의 T/F 모두 실행 |
| MC/DC 커버리지 | 각 조건이 독립적으로 결정에 영향 |
| 경로 커버리지(Path) | 모든 가능한 경로 실행 |

**커버리지 강도:** 경로 > MC/DC > 조건 > 결정 > 구문

---

## 블랙박스 테스트

내부 구조를 모르고 요구사항·명세서 기반으로 테스트합니다. 사용자 관점.

| 기법 | 설명 |
|------|------|
| 동등 분류(Equivalence Partitioning) | 입력값을 동등 클래스로 분류 후 대표값으로 테스트 |
| 경계값 분석(Boundary Value Analysis) | 경계 값 (최솟값, 최댓값, 경계±1)을 테스트 |
| 결정 테이블(Decision Table) | 조건 조합에 따른 동작 표로 명세 |
| 상태 전이 테스트 | 상태 변화에 따른 시스템 동작 검증 |
| 유즈케이스 테스트 | 유스케이스 시나리오 기반 테스트 |

---

## 테스트 레벨

| 레벨 | 대상 | 주체 |
|------|------|------|
| 단위 테스트(Unit) | 개별 모듈·함수 | 개발자 |
| 통합 테스트(Integration) | 모듈 간 인터페이스 | 개발자/QA |
| 시스템 테스트(System) | 전체 시스템 기능 | QA |
| 인수 테스트(Acceptance) | 사용자 요구사항 충족 여부 | 사용자/고객 |

### 통합 테스트 방식

| 방식 | 설명 |
|------|------|
| 상향식(Bottom-up) | 하위 모듈부터 통합, 드라이버(Driver) 필요 |
| 하향식(Top-down) | 상위 모듈부터 통합, 스텁(Stub) 필요 |
| 빅뱅 | 모든 모듈을 동시에 통합, 오류 원인 파악 어려움 |
| 샌드위치 | 상향식·하향식 혼합 |

---

## 테스트 용어

| 용어 | 설명 |
|------|------|
| 스텁(Stub) | 하위 모듈 대신 임시로 사용하는 더미 모듈 |
| 드라이버(Driver) | 상위 모듈 대신 테스트 대상 모듈을 호출하는 모듈 |
| 목(Mock) | 예상 동작을 미리 정의한 테스트 대체 객체 |
| 결함(Defect) | 소프트웨어 동작이 기대와 다른 것 |

---

## 핵심 정리

- 화이트박스: 내부 구조 알고 테스트 / 블랙박스: 명세 기반 테스트
- 경계값 분석: 경계±1 중요
- 통합 하향식: 스텁 필요 / 통합 상향식: 드라이버 필요
- 인수 테스트: 사용자/고객이 수행
