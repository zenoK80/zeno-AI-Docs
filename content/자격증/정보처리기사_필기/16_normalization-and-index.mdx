## 왜 정규화가 필요한가? — 이상 현상(Anomaly)

**정규화(Normalization)**는 데이터 중복을 줄이고 데이터 불일치를 막기 위해 테이블을 여러 개로 쪼개는 작업입니다. 왜 필요한지, 정규화되지 않은 테이블을 직접 봅니다.

**예시: 수강 정보를 한 테이블에 몰아넣은 경우**

| 학번 | 학생명 | 과목코드 | 과목명 | 담당교수 |
|------|--------|----------|--------|----------|
| S01 | 김민수 | C01 | 자료구조 | 이교수 |
| S01 | 김민수 | C02 | DB개론 | 박교수 |
| S02 | 이지은 | C01 | 자료구조 | 이교수 |

이 표는 세 가지 문제(이상 현상)를 일으킵니다.

| 이상 현상 | 설명 | 위 표에서의 예 |
|-----------|------|----------------|
| **삽입 이상** | 원하지 않는 데이터도 함께 넣어야 함 | 아직 아무도 수강하지 않은 새 과목(C03)을 등록하려면, 강제로 가짜 학생 정보까지 넣어야 함 |
| **삭제 이상** | 특정 데이터 삭제 시 다른 유용한 데이터도 함께 사라짐 | 김민수가 C02를 취소해서 그 행을 지우면, "DB개론 담당은 박교수"라는 정보 자체가 사라짐(다른 곳에 안 남아 있으면) |
| **갱신 이상** | 중복된 데이터 중 일부만 고쳐서 불일치 발생 | 이교수 이름이 바뀌면 "이교수"가 적힌 모든 행을 다 찾아 고쳐야 함. 하나라도 놓치면 데이터 불일치 |

> **쉽게 말하면:** 한 테이블에 여러 종류의 정보(학생 정보 + 과목 정보 + 교수 정보)를 뒤섞어 놓으면, 정보가 여기저기 중복되어 문제가 생깁니다. 정규화는 "이 정보는 이 테이블에, 저 정보는 저 테이블에" 나눠서 중복을 없애는 작업입니다.

## 정규화 단계 — 위 예시를 직접 정규화하기

### 1NF (제1정규형) — 원자값 만들기

**조건:** 모든 속성(칸)이 더 이상 쪼갤 수 없는 하나의 값(원자값)이어야 합니다. 반복되는 그룹이나 한 칸에 여러 값이 들어가면 안 됩니다.

```
❌ 위반: 학생 김민수가 수강과목을 [C01, C02]처럼 한 칸에 여러 개 저장
✅ 1NF: 위 표처럼 한 행에 학생-과목 한 쌍씩만 저장 (이미 1NF는 만족)
```

### 2NF (제2정규형) — 부분 함수 종속 제거

이 표의 기본키는 `{학번, 과목코드}`(두 개를 합쳐야 각 행을 구별하는 복합키)입니다.

- **함수 종속(Functional Dependency)**: "A값이 정해지면 B값도 자동으로 하나로 정해진다"는 관계를 $A \to B$로 씁니다.
- **완전 함수 종속**: 기본키 **전체**에 종속. `{학번, 과목코드} → 담당교수`처럼 두 값을 모두 알아야 결정됨.
- **부분 함수 종속**: 기본키의 **일부에만** 종속. 위 표에서 `학번 → 학생명`은 과목코드 없이 학번만으로 결정됩니다. 이것이 부분 함수 종속입니다.

> **조건:** 1NF를 만족하고, 부분 함수 종속을 제거(별도 테이블로 분리)해야 2NF입니다.

**2NF로 분해:**

```
학생 테이블: {학번(기본키), 학생명}
수강 테이블: {학번, 과목코드(복합기본키), 과목명, 담당교수}
```

여전히 수강 테이블에는 문제가 남아 있습니다 — `과목코드 → 과목명, 담당교수`가 학번과 무관하게 성립합니다.

### 3NF (제3정규형) — 이행적 함수 종속 제거

**이행적 함수 종속**: $A \to B$이고 $B \to C$이면 $A \to C$가 성립하는 관계입니다. 수강 테이블에서 `과목코드 → 담당교수`, 그리고 `과목코드`는 기본키의 일부이지만 `담당교수`는 기본키가 아닌 `과목코드`(비키 속성)에 종속되어 있습니다.

> **조건:** 2NF를 만족하고, 기본키가 아닌 속성이 다른 비키 속성에 종속되는 것(이행적 종속)을 제거해야 3NF입니다.

**3NF로 최종 분해:**

```
학생 테이블: {학번(기본키), 학생명}
과목 테이블: {과목코드(기본키), 과목명, 담당교수}
수강 테이블: {학번, 과목코드(복합기본키)}
```

이제 "이교수" 이름이 바뀌어도 과목 테이블 한 곳만 고치면 됩니다. 갱신 이상이 사라졌습니다.

### BCNF (보이스-코드 정규형)

**조건:** 3NF를 만족하고, **모든 결정자가 후보키**여야 합니다. (결정자: 화살표 왼쪽에 있는, 다른 값을 결정하는 속성)

3NF까지는 만족하지만 "기본키가 아닌 일반 속성이 후보키를 결정하는" 특수한 경우가 남아있을 때 BCNF로 한 단계 더 나눕니다. 3NF보다 조건이 더 엄격합니다.

### 함수 종속 개념 정리

| 개념 | 설명 | 위반 시 |
|------|------|---------|
| 완전 함수 종속 | 기본키 전체에 종속 | (정상) |
| 부분 함수 종속 | 기본키의 일부에만 종속 | 2NF 위반 |
| 이행적 함수 종속 | $A \to B$, $B \to C$ | 3NF 위반 |

## 역정규화 (Denormalization)

성능 향상을 위해 의도적으로 정규화를 되돌리는 기법입니다.

- 조인 연산 감소로 성능 향상
- 데이터 중복 증가, 무결성 관리 어려움

---

## 인덱스 (Index)

데이터 검색 속도를 향상시키는 데이터 구조입니다.

### 인덱스 유형

| 유형 | 설명 |
|------|------|
| 클러스터형 인덱스 | 인덱스 순서대로 실제 데이터 저장 (테이블당 1개) |
| 비클러스터형 인덱스 | 인덱스와 실제 데이터 위치 분리 (다수 가능) |
| 유일 인덱스 | 중복 값 허용 안 함 |
| 복합 인덱스 | 여러 컬럼으로 구성 |

### 인덱스 특징

- 검색(SELECT) 속도 향상
- 삽입(INSERT)·수정(UPDATE)·삭제(DELETE) 성능 저하
- B-트리 구조를 주로 사용

```sql
CREATE INDEX idx_emp_name ON employee(name);
CREATE UNIQUE INDEX idx_emp_email ON employee(email);
DROP INDEX idx_emp_name ON employee;
```

## 뷰 (View)

실제 데이터를 저장하지 않는 가상 테이블입니다.

### 뷰 특징

| 특징 | 설명 |
|------|------|
| 독립성 | 기반 테이블 변경에도 응용 프로그램 영향 최소화 |
| 편의성 | 복잡한 쿼리를 단순화 |
| 보안성 | 민감 데이터 접근 제한 |

```sql
-- 뷰 생성
CREATE VIEW emp_dept AS
SELECT e.name, d.dept_name
FROM employee e
JOIN department d ON e.dept_id = d.dept_id;

-- 뷰 삭제
DROP VIEW emp_dept;
```

---

## 핵심 정리

- 1NF: 원자값 / 2NF: 부분 종속 제거 / 3NF: 이행적 종속 제거 / BCNF: 결정자=후보키
- 클러스터형 인덱스: 데이터 정렬 저장, 테이블당 1개
- 뷰: 가상 테이블, 실제 데이터 미저장
- 이상 현상: 삽입, 삭제, 갱신 이상
