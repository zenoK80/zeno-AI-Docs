## DBMS란? 왜 필요한가?

**DBMS**(DataBase Management System, 데이터베이스 관리 시스템)는 데이터를 체계적으로 저장·관리·검색하는 소프트웨어입니다.

> **왜 파일로 저장하면 안 되나?** 엑셀 파일 여러 개에 회원 정보를 흩어 저장한다고 상상해 보세요. 같은 사람 정보가 여러 파일에 중복 저장되고(중복 문제), 한 파일만 수정하면 다른 파일과 정보가 달라지고(불일치 문제), 여러 사람이 동시에 파일을 열면 충돌이 납니다(동시 접근 문제). DBMS는 이런 문제를 해결하기 위해 만들어졌습니다.

### DBMS 기능

| 기능 | 설명 |
|------|------|
| 데이터 정의 | DDL로 테이블 구조(스키마) 정의 |
| 데이터 조작 | DML로 삽입·조회·수정·삭제(CRUD) 수행 |
| 데이터 제어 | DCL로 "누가 어떤 데이터에 접근 가능한지" 권한 관리 |
| 동시성 제어 | 여러 사용자가 동시에 접근해도 데이터가 꼬이지 않게 관리 |
| 무결성 유지 | 데이터가 항상 정확하고 일관되게 유지되도록 규칙 강제 |
| 회복(Recovery) | 정전, 오류 등 장애 발생 시 데이터를 이전 상태로 복구 |

### 대표 DBMS

| 유형 | 제품 | 특징 |
|------|------|------|
| 관계형(RDBMS) | Oracle, MySQL, PostgreSQL, SQL Server | 표(테이블) 형태, SQL 사용 |
| NoSQL | MongoDB, Redis, Cassandra | 유연한 구조, 대용량·비정형 데이터에 강함 |
| NewSQL | CockroachDB, Google Spanner | RDBMS의 일관성 + NoSQL의 확장성 결합 |

## 3단계 스키마 구조 — 데이터 독립성을 지키는 장치

**스키마**(Schema)는 데이터베이스의 구조를 설계도처럼 정의한 것입니다. ANSI/SPARC는 이 설계도를 3단계로 나눠서, 한 단계가 바뀌어도 다른 단계에 영향이 최소화되도록 설계했습니다.

> **비유:** 아파트에 비유하면, **내부 스키마**는 "콘크리트와 배관이 실제로 어떻게 놓였는지"(물리적 구조), **개념 스키마**는 "이 아파트의 전체 평면도"(논리적 전체 구조), **외부 스키마**는 "각 세대 주민이 실제로 보는 자기 집 내부"(사용자 관점)입니다. 배관 공사(내부)를 바꿔도 평면도(개념)나 주민이 보는 집 구조(외부)는 그대로 유지됩니다.

| 단계 | 스키마 | 설명 |
|------|--------|------|
| 외부 단계 | 외부 스키마 (External) | 사용자·응용 프로그램이 보는 부분적 관점 (뷰) |
| 개념 단계 | 개념 스키마 (Conceptual) | 조직 전체가 공유하는 데이터베이스의 논리적 구조 |
| 내부 단계 | 내부 스키마 (Internal) | 데이터가 디스크에 실제로 저장되는 물리적 구조 |

### 데이터 독립성

- **논리적 독립성**: 개념 스키마가 바뀌어도(예: 테이블에 컬럼 추가) 외부 스키마(응용 프로그램이 쓰는 뷰)는 영향받지 않습니다.
- **물리적 독립성**: 내부 스키마가 바뀌어도(예: 저장 방식 변경, 인덱스 추가) 개념 스키마는 영향받지 않습니다.

> **쉽게 말하면:** "물리적으로 어떻게 저장하는지"를 바꿔도 "논리적으로 어떤 데이터가 있는지"는 그대로이고, "논리적 구조"가 바뀌어도 "사용자가 실제로 보는 화면"은 그대로 유지되도록 각 계층을 분리한 것입니다.

## ERD (Entity-Relationship Diagram, 개체-관계 다이어그램)

데이터베이스를 설계하기 전에, 어떤 데이터(개체)들이 있고 서로 어떻게 연결되는지(관계) 그림으로 그리는 것이 ERD입니다.

### ERD 구성요소

| 요소 | 표기 | 설명 |
|------|------|------|
| 개체(Entity) | 사각형 | 독립적으로 존재하며 관리 대상이 되는 데이터 집합 (예: 학생, 과목) |
| 속성(Attribute) | 타원 | 개체가 가진 하나하나의 특성 (예: 학생의 이름, 학번) |
| 관계(Relationship) | 마름모 | 개체와 개체 사이의 연관성 (예: 학생이 과목을 "수강한다") |
| 기본키 속성 | 밑줄 타원 | 개체를 고유하게 식별하는 속성 |
| 다중값 속성 | 이중 타원 | 하나의 개체가 여러 값을 가질 수 있는 속성 (예: 한 사람의 여러 전화번호) |

**간단한 예시 — "학생이 과목을 수강한다":**

```
[학생] ──── (수강한다) ──── [과목]
  │                            │
학번(밑줄), 이름              과목코드(밑줄), 과목명
```

### 카디널리티 (Cardinality) — 관계의 대응 개수

두 개체 사이에서 "하나가 몇 개와 대응되는지"를 나타냅니다.

| 관계 | 설명 | 예시 |
|------|------|------|
| 1:1 (일대일) | 한쪽이 다른 쪽 하나와만 대응 | 사람 - 여권 (한 사람은 여권 하나) |
| 1:N (일대다) | 한쪽이 여러 쪽과 대응 | 부서 - 직원 (한 부서에 여러 직원) |
| N:M (다대다) | 양쪽 모두 여러 개와 대응 | 학생 - 과목 (한 학생이 여러 과목을, 한 과목을 여러 학생이 수강) |

<Callout type="warning">
  **N:M 관계는 실제 테이블로 그대로 구현할 수 없습니다.** 관계형 데이터베이스에서는 N:M 관계를 그대로 표현할 방법이 없어서, 중간에 별도의 "연결 테이블"(예: 수강 테이블)을 만들어 1:N + N:1로 쪼개서 구현합니다.
</Callout>

## 관계형 모델 (Relational Model)

관계형 모델은 데이터를 **표**(테이블) 형태로 표현합니다. 용어들이 일상 용어(행, 열)와 학술 용어(튜플, 속성)로 둘 다 쓰이므로 대응 관계를 명확히 알아두어야 합니다.

| 학술 용어 | 일상 용어 | 설명 |
|-----------|-----------|------|
| 릴레이션(Relation) | 테이블 | 데이터 전체를 담는 표 |
| 튜플(Tuple) | 행(Row) | 표의 한 줄 (레코드 하나) |
| 속성(Attribute) | 열(Column) | 표의 한 칸 종류 (필드) |
| 도메인(Domain) | - | 속성이 가질 수 있는 값의 범위 (예: 성별은 '남'/'여'만) |
| 카디널리티(Cardinality) | - | 튜플(행)의 **개수** |
| 차수(Degree) | - | 속성(열)의 **개수** |

<Callout type="warning">
  **주의:** "카디널리티"라는 단어가 ERD에서는 "관계의 대응 형태(1:N 등)"를, 관계형 모델에서는 "튜플의 개수"를 뜻합니다. 같은 단어가 문맥에 따라 다른 의미로 쓰이므로 헷갈리지 않아야 합니다.
</Callout>

### 키의 종류 — 포함 관계로 이해하기

다섯 가지 키는 서로 포함 관계에 있습니다. 큰 개념에서 좁혀가며 이해하면 헷갈리지 않습니다.

```
슈퍼키 (유일성만 만족, 불필요하게 많은 속성 포함 가능)
  └─ 후보키 (슈퍼키 중 "최소성"까지 만족 — 딱 필요한 속성만)
       ├─ 기본키 (후보키 중 대표로 선택된 하나)
       └─ 대체키 (기본키로 선택되지 않은 나머지 후보키)

외래키 (다른 테이블의 기본키를 참조하는 속성 — 위 계층과 별개)
```

**예시:** 학생 테이블에 `학번`, `주민번호`, `이메일`이 모두 중복 없이 고유하다고 합시다.

- `{학번, 이름}`: 유일하긴 하지만 이름이 없어도 학번만으로 충분 → **슈퍼키**(불필요한 속성 포함)
- `학번`, `주민번호`, `이메일` 각각: 더 줄일 수 없는 최소 단위로 유일 → 모두 **후보키**
- `학번`: 이 중 대표로 선택 → **기본키**
- `주민번호`, `이메일`: 후보키였지만 기본키가 아님 → **대체키**

| 키 | 조건 |
|----|------|
| 슈퍼키(Super Key) | 유일성(중복 없음)만 만족 |
| 후보키(Candidate Key) | 유일성 + 최소성(꼭 필요한 속성만) 만족 |
| 기본키(Primary Key) | 후보키 중 대표로 선택. 유일성 + NOT NULL(값 필수) |
| 대체키(Alternate Key) | 후보키였지만 기본키로 선택되지 않은 나머지 |
| 외래키(Foreign Key) | 다른 테이블의 기본키를 참조하는 속성. 두 테이블을 연결 |

## 핵심 정리

- **DBMS**: 데이터 중복·불일치·동시 접근 문제를 해결하는 소프트웨어.
- **3단계 스키마**: 외부(사용자 관점) → 개념(전체 논리 구조) → 내부(물리적 저장). 계층 분리로 데이터 독립성 확보.
- **ERD**: 개체(사각형), 속성(타원), 관계(마름모). N:M은 실제 구현 시 연결 테이블로 분해.
- **릴레이션 용어**: 튜플=행, 속성=열, 카디널리티=행 개수, 차수=열 개수.
- **키 계층**: 슈퍼키 ⊃ 후보키 ⊃ `{기본키, 대체키}`. 외래키는 별도로 다른 테이블 참조.
- **기본키 규칙**: 유일성 + NOT NULL(개체 무결성).
