## 시각화 설계 4원칙

### 원칙 1: 목적부터 정한다

차트를 그리기 전에 "무엇을 보여주려 하는가"를 먼저 결정해야 합니다.

| 목적 | 추천 차트 | 예시 |
|------|-----------|------|
| 비교 | 막대 차트(Bar Chart) | 지역별 매출 비교 |
| 분포 | 히스토그램, 박스플롯 | 연령대별 구매 금액 분포 |
| 관계 | 산점도(Scatter Plot) | 광고비와 매출의 상관관계 |
| 추세 | 꺾은선 그래프(Line Chart) | 월별 가입자 추이 |
| 비율 | 파이 차트, 누적 막대 | 제품군별 매출 구성비 |

### 원칙 2: 잉크 대비 데이터 비율을 높인다 (Data-Ink Ratio)

에드워드 터프티(Edward Tufte)가 제안한 원칙으로, 차트의 모든 요소는 데이터를 표현하는 데 기여해야 합니다.

**제거해야 할 요소들:**
- 3D 효과, 그림자, 그라데이션 배경
- 불필요한 격자선
- 의미 없는 배경 이미지
- 과도한 범례 반복

### 원칙 3: 색상을 전략적으로 사용한다

- 색상은 최대 5~7가지로 제한 (그 이상은 구분 불가)
- 적록 색맹을 고려하여 적녹 조합 대신 **청색-주황색 팔레트** 활용
- 강조색은 단 하나 (나머지는 회색 계열)
- 의미 있는 색 연결: 빨강=위험, 초록=안전, 파랑=정보 등 일관성 유지

### 원칙 4: 축을 정직하게 설정한다

- Y축은 **0에서 시작**하는 것이 원칙 (막대 차트)
- 꺾은선 그래프에서 변화 강조 시 Y축 범위 조정 가능하나, 이를 **명시적으로 표기**해야 함
- 로그 축(Log Scale) 사용 시 반드시 레이블에 "(로그 축)" 명기

## 잘못된 시각화 함정

| 함정 유형 | 문제점 | 올바른 대안 |
|-----------|--------|-------------|
| 잘린 Y축 | 작은 차이를 크게 왜곡, 시각적 과장 | Y축을 0에서 시작하거나 잘린 축임을 명시 |
| 3D 파이 차트 | 원근법으로 앞 조각이 실제보다 크게 보임 | 일반 2D 파이 차트 또는 누적 막대 사용 |
| 이중 Y축 | 두 지표의 관계를 임의로 조작 가능 | 별도 차트로 분리하거나 정규화된 값 사용 |
| 과도한 색상 | 시각적 혼란, 중요 항목 구분 불가 | 5가지 이하 색상, 강조색 1개 원칙 |
| 파이 차트 조각 과다 | 5개 이상이면 면적 비교 불가 | 상위 N개 + 기타로 묶기, 막대 차트 대체 |

## 대시보드 설계 원칙

### 레이아웃 구성

1. **핵심 KPI 상단 배치**: 가장 중요한 지표(매출, 전환율, 이탈율 등)를 최상단에
2. **시간 흐름은 왼쪽→오른쪽**: 꺾은선 그래프 방향 통일
3. **드릴다운 구조**: 요약 수치 → 세부 내역 → 원인 분석 순서로 배치
4. **화면 밀도 조절**: 한 화면에 최대 5~7개 차트, 과밀 배치 금지

### 갱신 주기 선택

| 방식 | 특징 | 적합한 상황 |
|------|------|-------------|
| 실시간(스트리밍) | 데이터가 발생 즉시 반영 | 서비스 오류 모니터링, 주문 현황 |
| 준실시간(미니 배치) | 수 분 간격으로 갱신 | 광고 성과, 실시간 재고 |
| 배치 | 일/주/월 단위 갱신 | 월별 매출 보고, KPI 리뷰 |

실시간 갱신은 인프라 비용이 크므로, 정말 즉각적인 판단이 필요한 경우에만 사용합니다.

## 모델 배포(Deployment) 방식

분석 모델을 실제 서비스에서 활용하는 방식은 크게 3가지입니다.

### 방식 1: REST API (실시간 예측)

- 사용자 요청이 오면 **즉시** 예측값을 반환
- 예: 전자상거래 추천 시스템, 실시간 신용 평가
- 장점: 최신 데이터 반영 가능, 유연한 확장
- 단점: 응답 지연(Latency) 관리 필요, 서버 상시 운영 비용

```
사용자 요청 → API 서버 → 모델 예측 → 결과 반환 (수십ms)
```

### 방식 2: 배치 예측 (Batch Prediction)

- 주기적(일/주)으로 대량 데이터에 대한 예측값을 미리 계산하여 DB에 저장
- 예: 다음 날 발송할 이탈 위험 고객 목록 생성
- 장점: 처리 효율 높음, 복잡한 계산도 시간 여유 있게 수행
- 단점: 실시간 반영 불가, 예측 시점과 사용 시점 사이의 데이터 변화 반영 못함

```
야간 배치 실행 → 전체 고객 예측 → DB 저장 → 다음 날 마케팅팀 활용
```

### 방식 3: 임베디드 (Embedded)

- 모델을 앱이나 디바이스에 직접 내장
- 예: 스마트폰 카메라 앱의 얼굴 인식, 오프라인 번역 앱
- 장점: 네트워크 불필요, 빠른 응답
- 단점: 모델 업데이트 시 앱 배포 필요, 기기 성능 한계

## A/B 테스트

배포 전 새로운 모델이 기존 모델보다 실제로 나은지 검증하는 방법입니다.

**진행 과정:**
1. 사용자를 무작위로 두 그룹(A: 기존 모델, B: 새 모델)으로 분리
2. 일정 기간 동안 두 그룹의 성과(전환율, 클릭율 등)를 측정
3. 통계적 유의성 검정(t-검정, 카이제곱 검정)으로 차이가 우연인지 확인
4. 유의미한 차이가 있으면 새 모델 전면 배포

**주의사항:**
- 그룹 간 다른 요인이 개입되지 않도록 동시에 실험
- 충분한 표본 크기 확보 (파워 분석으로 사전 계산)
- 조기 종료 금지 (처음에 좋아 보여도 기다려야 함)

## 모델 모니터링

배포 후에도 모델 성능을 지속적으로 관찰해야 합니다.

### 데이터 드리프트 (Data Drift)

입력 데이터의 **분포** 자체가 변하는 현상입니다.

**예시**: 코로나19 팬데믹으로 온라인 구매 패턴이 급변 → 기존 구매 예측 모델의 입력 특성(연령별 구매 비율, 카테고리 분포 등)이 훈련 당시와 크게 달라짐

### 컨셉 드리프트 (Concept Drift)

입력과 출력 사이의 **관계** 자체가 변하는 현상입니다.

**예시**: "광고 클릭 → 구매"의 관계가 시간이 지나면서 약해짐 (광고 피로도 증가, 경쟁사 등장)

| 구분 | 변하는 것 | 탐지 방법 |
|------|-----------|-----------|
| 데이터 드리프트 | 입력 분포 | 입력 특성의 평균·분산 모니터링 |
| 컨셉 드리프트 | 입력-출력 관계 | 예측 정확도 추이 모니터링 |

### 재학습(Retraining) 전략

- **주기적 재학습**: 월 1회, 분기 1회 등 정해진 주기
- **성능 기반 재학습**: 모니터링 지표가 임계값 이하로 떨어질 때 자동 트리거
- **이벤트 기반 재학습**: 데이터 드리프트 탐지 시 즉시 재학습

## 핵심 정리

- 시각화 4원칙: 목적 명확히 → Data-Ink Ratio 극대화 → 색상 전략 → 정직한 축
- 3대 시각화 함정: 잘린 Y축, 3D 파이 차트, 이중 Y축
- 배포 방식 3가지: REST API(실시간), 배치(주기적), 임베디드(앱 내장)
- A/B 테스트: 두 그룹 분리 → 통계적 유의성 확인 → 전면 배포
- 드리프트 2종: 데이터 드리프트(입력 분포 변화) vs 컨셉 드리프트(관계 변화)
- 모니터링 없는 배포는 반쪽짜리 프로젝트
