## 데이터 자체가 곧 가치는 아니다

데이터가 많이 쌓였다고 자동으로 좋은 의사결정이 만들어지지는 않습니다. 가치(Value)는 데이터를 통해 질문에 답하고, 행동을 바꾸고, 그 결과를 다시 측정할 때 생깁니다.

```text
수집 -> 정리 -> 분석 -> 의사결정 -> 실행 -> 결과 측정
```

이 흐름 중 하나가 빠지면 "분석 보고서"는 남아도 실제 개선으로 이어지기 어렵습니다.

<Callout type="info">
  먼저 "무슨 데이터를 가지고 있는가"보다 "어떤 결정을 더 잘하고 싶은가"를 질문하세요. 그다음 필요한 데이터를 거꾸로 찾는 편이 효율적입니다.
</Callout>

## 가치가 만들어지는 세 단계

| 단계 | 핵심 질문 | 예시 |
| --- | --- | --- |
| 현상 파악 | 무엇이 일어났는가? | 지난주 주문이 왜 줄었는가 |
| 원인 추정 | 왜 일어났는가? | 특정 지역의 배송 지연 때문인가 |
| 행동 선택 | 무엇을 할 것인가? | 해당 시간대 배차를 늘릴 것인가 |

이 세 단계는 각각 기술통계, 진단 분석, 예측·처방 분석으로 연결해 설명할 수 있습니다. 다만 시험이나 실무 모두에서 중요한 것은 이름보다 질문과 답의 연결입니다.

## 사례: 이탈 위험을 낮추고 싶다면

구독 서비스가 "다음 달 해지 가능성이 높은 고객을 미리 찾고 싶다"고 가정해 봅시다.

### 질문을 지표로 바꾼다

해지라는 결과를 정하고, 최근 접속 횟수, 고객 문의, 결제 실패, 기능 사용량처럼 관련 있을 만한 정보를 검토합니다.

### 데이터의 한계를 확인한다

접속 기록이 빠졌거나, 해지 고객만 과거 데이터를 볼 수 있다면 결론이 왜곡될 수 있습니다. 개인정보와 목적 외 사용 여부도 함께 검토해야 합니다.

### 실행 가능한 행동을 정한다

위험 점수가 높은 모든 고객에게 무작정 할인 쿠폰을 보내는 대신, 고객 상태에 따라 안내, 오류 해결, 기능 교육처럼 다른 조치를 설계할 수 있습니다.

### 결과를 측정한다

조치한 집단과 비교 집단의 해지율, 만족도, 비용을 비교해야 "모델 점수"가 아니라 실제 가치가 있었는지 판단할 수 있습니다.

## 분석 유형과 활용 관점

| 분석 관점 | 질문 | 예시 |
| --- | --- | --- |
| 기술 분석 | 무엇이 있었나? | 월별 매출, 방문자 수 |
| 진단 분석 | 왜 그랬나? | 특정 채널 전환율 하락 원인 |
| 예측 분석 | 앞으로 무엇이 일어날까? | 다음 주 수요 예측 |
| 처방 분석 | 무엇을 하는 게 좋을까? | 재고 배분, 추천 순위 |

분석은 항상 예측 모델일 필요가 없습니다. 정확한 현황을 공유하는 대시보드나 데이터 품질을 고치는 일도 중요한 가치 창출 활동입니다.

## 가치 판단에서 놓치기 쉬운 것

- **정확도만 보기**: 모델 정확도가 높아도 실제 조치 비용이 너무 크거나 사용자가 신뢰하지 않으면 가치가 낮다.
- **상관관계와 원인을 같은 말로 쓰기**: 함께 움직인다고 해서 한쪽이 다른 쪽의 원인이라고 단정할 수 없다.
- **성과를 측정하지 않기**: 실행 전후와 비교 기준을 정하지 않으면 개선 여부를 알 수 없다.
- **개인정보를 사후에 검토하기**: 수집 목적, 접근 권한, 보관 기간은 분석 시작 전에 확인해야 한다.

## 직접 점검하기

자주 쓰는 서비스 하나를 골라 다음 문장을 채워 보세요.

```text
개선하고 싶은 결정:
필요한 결과 지표:
확인할 데이터:
데이터 품질 또는 개인정보 위험:
분석 뒤 실행할 행동:
성공 여부를 볼 기준:
```

이 여섯 줄이 채워지면 "데이터를 많이 모으자"보다 훨씬 구체적인 분석 과제가 됩니다.

## 이번 편 정리

- 데이터의 가치는 분석 결과가 행동과 측정으로 이어질 때 생긴다.
- 현상 파악, 원인 추정, 행동 선택을 구분해 질문한다.
- 모델 성능뿐 아니라 비용, 위험, 실행 가능성, 성과 측정까지 봐야 한다.
