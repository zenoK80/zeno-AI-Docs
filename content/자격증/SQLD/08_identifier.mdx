## 이번 편의 목표

- 식별자가 필요한 이유와 좋은 식별자의 네 조건을 설명한다.
- 후보식별자에서 주식별자와 보조식별자를 선택한다.
- 내부·외부, 단일·복합, 본질·인조 식별자를 사례로 구분한다.
- 논리 식별자가 기본키·고유키·외래키로 구현되는 과정을 이해한다.

## 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| 식별자 | 인스턴스 하나를 다른 인스턴스와 구분하는 속성 또는 속성 묶음 |
| 후보식별자 | 유일성과 최소성을 만족해 대표가 될 수 있는 식별자 후보 |
| 주식별자 | 후보 중 엔터티를 대표하도록 선택한 식별자 |
| 보조식별자 | 대표로 선택되지 않았지만 여전히 유일하게 구분할 수 있는 후보 |
| 복합식별자 | 두 개 이상의 속성을 묶어 인스턴스를 구분하는 식별자 |
| 외부식별자 | 다른 엔터티와의 관계를 통해 가져온 식별자 |
| 본질식별자 | 업무에서 원래 존재하는 의미 있는 값으로 만든 식별자 |
| 인조식별자 | 안정적인 구분을 위해 시스템이 새로 만든 값 |

## 선수지식과 핵심 질문

앞에서 엔터티는 인스턴스를 식별할 수 있어야 하고, 1:N 관계의 N쪽은 보통 1쪽 식별자를 외래키로 가진다고 배웠다.

이번 편의 질문은 이것이다.

> 회원의 이름이 같고 이메일도 바뀔 수 있다면, 회원 한 명을 계속 같은 사람으로 어떻게 구분할까?

## 먼저 같은 이름 두 명을 표로 보기

| member_id | member_name | email |
| ---: | --- | --- |
| 101 | 민지 | minji1@example.com |
| 102 | 민지 | minji2@example.com |

`member_name = 민지`만으로 조회하면 두 행이 나온다. 이름은 사람을 설명하는 좋은 속성이지만 사람 한 명을 **유일하게** 고르는 식별자로는 부족하다.

```text
"민지를 찾아라"      → 2명이라 모호함
"회원번호 101을 찾아라" → 1명으로 확정
```

식별자는 값에 붙은 멋진 이름이 아니라, 어떤 정상 데이터에서도 한 인스턴스만 찾게 하는 업무 규칙이다.

## 식별자는 인스턴스의 이름표다

**식별자(identifier)** 는 엔터티 안의 각 인스턴스를 유일하게 구분하는 속성 또는 속성의 조합이다.

```text
회원번호 101, 이름 민지
회원번호 102, 이름 민지
```

이름만 보면 두 회원을 구분할 수 없지만 회원번호는 다르다. 주문 취소, 배송지 변경, 포인트 적립처럼 특정 회원을 정확히 찾아야 하는 모든 작업은 안정적인 식별을 전제로 한다.

<Callout type="important">
  식별자는 단순히 값이 지금 우연히 다른 속성이 아니다. 업무의 모든 정상 데이터에서 유일함을 보장할 규칙이 있어야 한다.
</Callout>

## 좋은 주식별자의 네 조건

### 유일성

식별자값이 각 인스턴스를 하나만 가리켜야 한다. 회원번호 `101`이 두 회원에게 동시에 부여되면 안 된다.

### 최소성

유일하게 구분하는 데 꼭 필요한 속성만 포함한다.

```text
회원번호만으로 유일함
→ (회원번호, 이름)은 유일하지만 이름은 불필요
→ 최소성을 만족하지 않는 조합
```

### 불변성

한 번 정한 식별자값은 가능하면 바뀌지 않아야 한다. 전화번호와 이메일은 변경될 수 있으므로 대표 식별자로 신중해야 한다.

### 존재성

주식별자값은 반드시 존재해야 한다. 아직 발급되지 않은 값이나 자주 비어 있는 값은 주식별자로 적합하지 않다.

| 조건 | 확인 질문 |
| --- | --- |
| 유일성 | 같은 값이 두 인스턴스에 생길 수 있는가? |
| 최소성 | 속성 하나를 빼도 여전히 유일한가? |
| 불변성 | 업무 중 값이 바뀌거나 재사용될 수 있는가? |
| 존재성 | 생성 시점부터 반드시 값이 있는가? |

## 후보식별자, 주식별자와 보조식별자

회원에게 `회원번호`와 `이메일`이 있고 서비스에서 이메일 중복을 금지한다고 하자.

- 회원번호: 유일하고 필수이며 시스템이 변경하지 않는다.
- 이메일: 현재 유일하지만 회원이 변경할 수 있다.

둘 다 후보가 될 수 있지만 회원번호를 **주식별자**, 이메일을 **보조식별자**로 선택할 수 있다. 물리 테이블에서는 주식별자를 `PRIMARY KEY`, 보조식별자를 `UNIQUE` 제약으로 구현하는 경우가 많다.

```sql
CREATE TABLE members (
  member_id BIGINT PRIMARY KEY,
  email     VARCHAR(255) NOT NULL UNIQUE,
  name      VARCHAR(100) NOT NULL
);
```

생성된 규칙에 데이터를 대입하면 다음처럼 판단된다.

| 시도 | 결과 | 이유 |
| --- | --- | --- |
| `101, a@example.com, 민지` | 저장됨 | 회원번호와 이메일 모두 처음 나온 값 |
| `102, b@example.com, 준호` | 저장됨 | 두 고유값이 기존 행과 다름 |
| `101, c@example.com, 소라` | 거부 | 기본키 `member_id=101` 중복 |
| `103, a@example.com, 소라` | 거부 | 보조식별자 이메일의 UNIQUE 위반 |

한 테이블의 기본키는 하나지만 고유 제약은 여러 개 둘 수 있다. 기본키는 대표 식별자이고, UNIQUE는 대표로 선택하지 않은 후보의 유일성도 지킨다.

## 생성 위치에 따른 내부식별자와 외부식별자

### 내부식별자

자신의 엔터티 안에서 만들어진 식별자다. 회원의 회원번호, 상품의 상품번호가 예다.

### 외부식별자

다른 엔터티와 관계를 맺으면서 받아 온 식별자다. 주문의 회원번호, 주문상세의 주문번호와 상품번호가 예다.

```text
회원.회원번호       → 회원의 내부식별자
주문.회원번호       → 회원에서 온 외부식별자
주문상세.주문번호   → 주문에서 온 외부식별자
주문상세.상품번호   → 상품에서 온 외부식별자
```

외부식별자는 물리 모델에서 보통 외래키 역할을 한다. 관계에 따라 주식별자 일부가 될 수도 있고 일반 속성으로만 남을 수도 있다.

## 속성 수에 따른 단일식별자와 복합식별자

### 단일식별자

속성 하나로 인스턴스를 구분한다. `회원번호`, `주문번호`가 예다.

### 복합식별자

두 개 이상의 속성을 함께 사용한다. 같은 상품이 한 주문에 한 번만 들어간다는 규칙이 있다면 주문상세의 `(주문번호, 상품번호)` 조합이 식별자가 될 수 있다.

```text
주문번호 1001 + 상품번호 10 → 주문상세 A
주문번호 1001 + 상품번호 20 → 주문상세 B
```

주문번호만으로는 한 주문 안의 여러 상품을 구분하지 못하고, 상품번호만으로는 여러 주문의 같은 상품을 구분하지 못한다. 둘을 함께 써야 유일하다.

```sql
CREATE TABLE order_items (
  order_id   BIGINT REFERENCES orders(order_id),
  product_id BIGINT REFERENCES products(product_id),
  quantity   INTEGER NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
```

복합키는 두 열을 **한 묶음**으로 비교한다.

| order_id | product_id | 저장 가능? | 이유 |
| ---: | --- | --- | --- |
| 1001 | P10 | 가능 | 조합이 처음 등장 |
| 1001 | P20 | 가능 | 주문번호는 같지만 상품번호가 다름 |
| 1002 | P10 | 가능 | 상품번호는 같지만 주문번호가 다름 |
| 1001 | P10 | 거부 | 두 값의 조합이 첫 행과 완전히 같음 |

따라서 `order_id` 하나도, `product_id` 하나도 단독으로 유일할 필요는 없다. **두 값을 함께 보았을 때** 유일하면 된다.

## 본질식별자와 인조식별자

### 본질식별자

업무에서 원래 사용하는 의미 있는 값이다. 국제표준도서번호 ISBN, 사업자등록번호처럼 업무 규칙상 존재하는 값이 예가 될 수 있다.

장점은 값만 보고 의미를 알 수 있다는 것이다. 단점은 정책 변경, 재발급, 복합 구조와 개인정보 노출 위험이 있을 수 있다는 점이다.

### 인조식별자

시스템이 식별만을 위해 새로 만든 의미 없는 값이다. 자동 증가 번호, UUID 등이 예다.

```text
주문상세의 본질 후보: (주문번호, 상품번호)
인조식별자 도입: 주문상세번호
```

인조식별자를 도입해도 원래 업무상 중복 금지 규칙이 사라지는 것은 아니다.

```sql
CREATE TABLE order_items (
  order_item_id BIGINT PRIMARY KEY,
  order_id      BIGINT NOT NULL REFERENCES orders(order_id),
  product_id    BIGINT NOT NULL REFERENCES products(product_id),
  quantity      INTEGER NOT NULL,
  UNIQUE (order_id, product_id)
);
```

`order_item_id`가 행을 식별하고, `(order_id, product_id)`의 고유 제약은 같은 상품 중복을 막는다.

| order_item_id | order_id | product_id | 결과 |
| ---: | ---: | --- | --- |
| 1 | 1001 | P10 | 저장됨 |
| 2 | 1001 | P20 | 저장됨 |
| 3 | 1001 | P10 | 거부됨 |

세 번째 행은 새 인조키 3을 가졌지만 업무상으로는 주문 1001의 P10이 이미 있다. 인조키만 보면 서로 다른 행이지만 `UNIQUE (order_id, product_id)`가 업무 중복을 잡아낸다.

<Callout type="warning">
  인조식별자를 추가했다는 이유로 본질적인 유일성 규칙을 제거하면 중복 데이터가 들어올 수 있다. 기본키와 업무 고유 규칙을 따로 확인한다.
</Callout>

## 식별 관계와 비식별 관계 맛보기

부모 엔터티의 식별자가 자식 엔터티의 주식별자에 포함되면 **식별 관계**, 포함되지 않고 일반 외부식별자로만 존재하면 **비식별 관계**라고 한다.

```text
복합키 주문상세
PK: 주문번호 + 상품번호
→ 부모 식별자가 자식 PK에 포함됨

인조키 주문상세
PK: 주문상세번호
FK: 주문번호, 상품번호
→ 부모 식별자는 자식 PK에 포함되지 않음
```

어느 한쪽이 항상 정답은 아니다. 자식의 존재 의존성, 키 길이, 변경 가능성과 다른 엔터티에서 참조할 때의 편의성을 함께 본다.

## 주식별자를 고르는 실무 순서

<Steps>

### 후보를 모두 찾는다

현재 데이터 표본이 아니라 업무 규칙상 유일할 수 있는 속성 조합을 찾는다.

### 네 조건을 검사한다

유일성, 최소성, 불변성, 존재성을 확인한다.

### 관계 전파를 생각한다

이 식별자가 자식 엔터티의 외래키로 복사될 때 너무 길거나 자주 바뀌지 않는지 본다.

### 주식별자와 보조식별자를 정한다

대표 하나를 선택하고 나머지 후보의 고유 규칙도 보존한다.

### 물리 제약으로 구현한다

기본키, 고유키, NOT NULL, 외래키 제약으로 실제 데이터 오류를 막는다.

</Steps>

## 완결 사례: 회원 식별자 선택

후보는 `회원번호`, `이메일`, `(휴대전화번호, 생년월일)`이다.

| 후보 | 유일성 | 불변성 | 존재성 | 판단 |
| --- | --- | --- | --- | --- |
| 회원번호 | 시스템이 보장 | 변경하지 않음 | 가입 즉시 발급 | 주식별자로 적합 |
| 이메일 | 중복 금지 가능 | 변경 가능 | 소셜 가입에서 없을 수 있음 | 보조식별자 또는 조건부 고유 규칙 |
| 휴대전화+생년월일 | 가족·공용 번호 등 중복 가능 | 번호 변경 가능 | 일부 값 누락 가능 | 안정적인 식별자로 부적합 |

이 판단은 서비스의 실제 정책에 따라 달라진다. 이메일을 절대 변경하지 않고 모든 회원에게 필수로 받는 시스템이라면 평가가 달라질 수 있다.

## 흔한 실수와 진단법

| 실수 | 문제 | 진단법 |
| --- | --- | --- |
| 이름을 식별자로 사용 | 동명이인을 구분하지 못함 | 업무 전체에서 중복이 불가능한가? |
| 현재 데이터만 보고 유일하다고 판단 | 미래 데이터에서 중복 발생 | 제약으로 보장할 업무 규칙이 있는가? |
| 복합키에 불필요한 속성 추가 | 최소성 위반과 긴 외래키 | 속성 하나를 빼도 유일한가? |
| 변경 가능한 값을 주식별자로 선택 | 모든 참조 값 변경 부담 | 발급 후 값이 바뀌거나 재사용되는가? |
| 인조키만 만들고 업무 고유 제약 제거 | 의미상 중복 허용 | 원래 후보식별자에 UNIQUE가 필요한가? |

## 시험 연결

1. 주식별자는 유일성, 최소성, 불변성과 존재성을 만족해야 한다.
2. 주식별자로 선택되지 않은 후보식별자는 보조식별자가 된다.
3. 외부식별자는 다른 엔터티와의 관계를 통해 유입된다.
4. 복합식별자는 여러 속성을 모두 합쳐야 유일하며 각 구성 속성이 단독으로 유일할 필요는 없다.
5. 인조식별자를 사용해도 본질적인 업무 중복 방지 규칙은 별도로 유지해야 한다.

## 짧은 확인

주문상세에 `주문상세번호`를 새 기본키로 만들었다. 같은 주문에 같은 상품이 중복되면 안 된다는 규칙은 어떻게 보존할까?

<Collapse title="확인하기">

`(주문번호, 상품번호)` 조합에 UNIQUE 제약을 둔다. 인조 기본키는 행을 식별하지만 원래 업무 중복 규칙까지 자동으로 보장하지 않는다.

</Collapse>

## 정리

<Callout type="default">
  - 식별자는 인스턴스를 유일하게 구분하는 최소 속성 조합이다.
  - 주식별자는 유일성·최소성·불변성·존재성을 만족해야 한다.
  - 식별자는 대표성, 생성 위치, 속성 수와 업무 의미에 따라 여러 방식으로 분류한다.
  - 인조식별자는 참조를 단순하게 만들 수 있지만 업무 고유 규칙을 대신하지 않는다.
  - 논리 식별자는 물리 모델에서 기본키·고유키·외래키 제약으로 구현된다.
</Callout>
