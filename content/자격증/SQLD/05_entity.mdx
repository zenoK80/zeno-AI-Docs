## 이번 편의 목표

- 엔터티, 인스턴스, 속성을 서로 구분한다.
- 업무 문장에서 엔터티 후보를 찾고 제외 이유를 설명한다.
- 유형·개념·사건 엔터티를 구분한다.
- 엔터티가 갖추어야 할 조건과 올바른 이름 규칙을 적용한다.

## 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| 엔터티 | 업무에서 같은 종류로 묶어 독립적으로 관리할 대상의 집합 |
| 인스턴스 | 엔터티에 실제로 들어 있는 개별 대상 하나 |
| 속성 | 인스턴스를 설명하는 값 |
| 식별자 | 인스턴스를 서로 구분하는 값 |
| 관계 | 엔터티의 인스턴스들이 업무에서 연결되는 방식 |
| 발생 | 업무 사건으로 새로운 인스턴스가 만들어지는 것 |
| 기본 엔터티 | 다른 엔터티에 크게 의존하지 않고 먼저 존재하는 대상 |
| 행위 엔터티 | 둘 이상의 대상 사이의 업무 활동을 기록하기 위해 생기는 대상 |

“회원”은 같은 종류의 대상을 묶은 엔터티이고, “회원번호 101인 민지”는 실제 한 명인 인스턴스다. “민지”와 “회원”을 같은 수준으로 보지 않는 것이 첫 구분이다.

## 주변 개념 지도

엔터티는 나중에 보통 테이블로 구현되지만 두 용어는 완전히 같은 단계가 아니다. 엔터티는 업무를 분석하는 모델의 대상이고, 테이블은 그 결정을 DBMS에 구현한 구조다.

<Callout type="info">
요구사항에 명사가 나온다고 모두 엔터티가 되지는 않는다. 독립적으로 식별하고 여러 건을 계속 관리하며 다른 대상과 관계를 맺는지 확인한다.
</Callout>

## 엔터티는 업무에서 관리할 대상이다

**엔터티(entity)** 는 업무에서 독립적으로 식별하고 지속적으로 관리할 필요가 있는 대상의 집합이다.

쇼핑몰의 `회원`은 엔터티다. 개별 회원 민지와 준호는 회원 엔터티에 속하는 **인스턴스(instance)** 다. 회원 이름과 전화번호는 회원을 설명하는 **속성(attribute)** 이다.

```text
엔터티: 회원
인스턴스: 회원번호 101인 민지, 회원번호 102인 준호
속성: 회원번호, 이름, 전화번호
```

<Callout type="important">
  엔터티는 보통 여러 인스턴스의 집합을 뜻한다. "민지" 한 명은 회원 엔터티가 아니라 회원 인스턴스다.
</Callout>

## 물건만 엔터티가 되는 것은 아니다

눈에 보이는 사람과 물건뿐 아니라 개념과 사건도 독립적으로 관리하면 엔터티가 된다.

| 유형 | 설명 | 예 |
| --- | --- | --- |
| 유형 엔터티 | 물리적 형태가 있고 비교적 지속됨 | 사원, 상품, 장비 |
| 개념 엔터티 | 물리적 형태가 없는 관리 개념 | 조직, 보험상품, 과목 |
| 사건 엔터티 | 업무에서 발생하고 이력을 남김 | 주문, 결제, 수강신청 |

주문은 손으로 만질 수 없지만 주문번호, 시각, 상태를 가지고 생성부터 취소·완료까지 변화하므로 중요한 사건 엔터티다.

## 엔터티 후보를 판단하는 다섯 질문

요구사항에서 명사를 발견했다고 모두 엔터티로 만들면 안 된다. 다음을 확인한다.

### 업무에서 실제로 관리하는가

시스템 범위 밖의 대상은 엔터티가 아니다. 쇼핑몰이 택배기사 개인 정보를 관리하지 않고 택배사에 배송만 요청한다면 `택배기사`는 현재 범위의 엔터티가 아닐 수 있다.

### 여러 인스턴스가 존재하는가

하나의 값이나 설명 문구보다 여러 개별 대상을 관리할 수 있어야 한다.

### 각 인스턴스를 구분할 수 있는가

주문번호처럼 한 주문을 다른 주문과 구분할 식별자가 필요하다.

### 관리할 속성이 있는가

이름만 존재하고 설명할 정보가 전혀 없다면 별도 엔터티인지 다시 검토한다.

### 다른 엔터티와 관계를 맺는가

회원은 주문을 하고, 상품은 주문상세에 포함된다. 엔터티는 보통 업무 안에서 다른 대상과 관계를 가진다.

## 엔터티와 속성을 구분하기

다음 후보를 보자.

| 후보 | 판단 | 이유 |
| --- | --- | --- |
| 회원 | 엔터티 | 독립 식별·관리하며 주문과 관계를 가짐 |
| 회원 이름 | 속성 | 회원을 설명하는 값 |
| 주소 | 상황에 따라 다름 | 하나만 저장하면 회원 속성, 여러 배송지를 관리하면 엔터티 가능 |
| 주문상태 | 보통 속성 또는 코드 | 주문을 설명하는 값, 별도 정책 관리 시 코드 엔터티 가능 |
| 주문 | 엔터티 | 독립 식별되는 사건과 상태 변화가 있음 |

주소처럼 같은 용어도 업무 규칙에 따라 판단이 달라진다.

```text
회원당 주소 하나만 저장 → 회원의 주소 속성
회원이 여러 배송지를 등록하고 이름·수령인·기본 여부 관리 → 배송지 엔터티
```

## 기본 엔터티, 중심 엔터티, 행위 엔터티

발생 시점과 업무 흐름을 기준으로도 분류한다.

### 기본 엔터티

업무의 기반이 되며 비교적 독립적으로 생성된다. 회원, 상품, 부서가 예다.

### 중심 엔터티

기본 엔터티에서 발생하고 업무의 중심 역할을 한다. 주문, 계약, 사고가 예다.

### 행위 엔터티

두 개 이상의 엔터티 관계에서 생기며 내용이 계속 쌓인다. 주문상세, 수강신청, 계약이력이 예다.

이 분류의 명칭을 외우는 것보다 **어디에서 생기고 무엇과 연결되는지**를 이해해야 한다.

## 엔터티 이름을 정하는 법

- 업무에서 실제 사용하는 용어를 쓴다.
- 가능하면 약어보다 의미가 분명한 이름을 쓴다.
- 단수 명사형을 사용하고, 프로세스 이름처럼 짓지 않는다.
- 같은 의미는 같은 용어로, 다른 의미는 다른 용어로 구분한다.
- 이름만 보고 무엇을 관리하는지 추측할 수 있어야 한다.

`회원관리`, `주문처리`는 행위를 나타내므로 엔터티 이름으로 모호하다. `회원`, `주문`처럼 관리 대상을 이름으로 삼는 편이 낫다.

## 사례: 수강신청 시스템

요구사항을 읽어 보자.

> 학생은 학기에 개설된 강좌를 신청한다. 신청일과 성적을 기록하며, 한 강좌는 한 교수가 담당한다.

후보를 분류한다.

```text
학생: 기본 엔터티
교수: 기본 엔터티
과목: 개념 엔터티
강좌: 특정 학기에 개설된 중심 엔터티
수강신청: 학생과 강좌 사이에서 발생한 행위 엔터티
신청일, 성적: 수강신청의 속성
```

`과목`과 `강좌`를 나누는 이유도 중요하다. 데이터베이스 과목은 하나지만 2026년 1학기 A반과 B반 강좌는 서로 다른 담당 교수와 시간을 가질 수 있다.

## 시험형 선지 분석

1. "엔터티는 반드시 물리적으로 존재해야 한다." → 거짓. 개념과 사건도 엔터티가 된다.
2. "엔터티는 업무에서 관리할 필요가 있고 식별 가능해야 한다." → 참.
3. "하나의 엔터티는 일반적으로 하나의 인스턴스만 가진다." → 거짓.
4. "속성이 여러 개면 반드시 별도 엔터티로 분리한다." → 거짓. 독립 식별·관리와 관계를 함께 본다.

## 정리

<Callout type="default">
  - 엔터티는 업무에서 독립적으로 식별하고 관리하는 대상의 집합이다.
  - 개별 대상은 인스턴스, 대상을 설명하는 값은 속성이다.
  - 물리적 대상뿐 아니라 개념과 사건도 엔터티가 된다.
  - 엔터티 여부는 이름이 아니라 업무 범위, 식별자, 속성, 관계로 판단한다.
</Callout>
