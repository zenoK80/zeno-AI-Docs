## 엔터티란 무엇일까?

엔터티(Entity)는 업무에서 **독립적으로 구분하고 관리할 가치가 있는 대상**입니다. 사람이나 물건만 엔터티가 되는 것은 아닙니다. 주문, 예약, 계약, 상담처럼 발생한 사건도 엔터티가 될 수 있습니다.

데이터베이스에서는 보통 하나의 엔터티가 하나의 테이블 후보가 됩니다. 다만 "테이블 하나 = 무조건 엔터티 하나"로 외우기보다, 왜 따로 관리해야 하는지를 설명할 수 있어야 합니다.

| 후보 | 엔터티인가? | 이유 |
| --- | --- | --- |
| 회원 | 예 | 회원 번호로 구분하고 여러 정보를 관리한다 |
| 상품 | 예 | 상품마다 독립적인 생명주기와 속성이 있다 |
| 회원 이름 | 아니오 | 회원에 딸린 하나의 정보다 |
| 주문 | 예 | 주문 번호로 구분되는 업무 사건이다 |
| 주문 수량 | 아니오 | 주문상세에 속하는 정보다 |

## 엔터티로 판단하는 세 가지 질문

### 다른 것과 구분할 수 있는가?

각 대상을 구별할 식별자가 필요한가를 봅니다. 회원 번호, 주문 번호, 상품 코드처럼 개별 대상을 구별해야 하면 엔터티일 가능성이 큽니다.

### 여러 정보를 관리하는가?

이름 하나만 가진 대상보다, 이름·상태·등록일처럼 여러 속성을 함께 관리해야 하는 대상이 엔터티에 가깝습니다.

### 독립적인 변화나 이력이 있는가?

주문은 생성, 결제, 취소, 배송 완료처럼 상태가 바뀝니다. 이런 생명주기가 있으면 별도 엔터티로 관리할 이유가 생깁니다.

<Callout type="warning">
  화면에 보인다는 이유만으로 엔터티가 되지는 않습니다. 화면의 회원 이름은 회원 엔터티의 속성을 보여 주는 것일 수 있습니다.
</Callout>

## 속성과 관계에서 구분하기

엔터티, 속성, 관계를 헷갈릴 때는 값이 결정되는 위치를 물어보면 좋습니다.

```text
회원: 회원번호, 이름, 이메일
상품: 상품번호, 상품명, 정가
주문: 주문번호, 주문일시
주문상세: 주문수량, 주문 당시 판매가
```

`주문 당시 판매가`는 상품의 현재 정가와 다를 수 있습니다. 또한 주문마다 달라지므로 상품 속성이 아니라 주문과 상품을 잇는 주문상세의 속성이 됩니다.

## 유형별 엔터티 예시

| 유형 | 설명 | 예시 |
| --- | --- | --- |
| 유형 엔터티 | 비교적 안정적인 대상 | 회원, 상품, 부서 |
| 사건 엔터티 | 업무에서 발생하는 행위나 기록 | 주문, 결제, 수강신청 |
| 코드 엔터티 | 정해진 분류값을 관리 | 주문상태, 지역코드 |

이 분류는 판단을 돕는 도구입니다. 중요한 것은 각 엔터티가 어떤 업무 규칙을 담고 있는지입니다.

## 직접 해보기

다음 문장을 모델로 바꿔 보세요.

> 고객은 상담을 신청한다. 상담사는 여러 고객의 상담을 진행한다. 상담 일시와 상담 결과를 기록한다.

먼저 고객, 상담사, 상담을 후보로 적을 수 있습니다. `상담`은 고객과 상담사를 연결하면서 상담 일시와 결과를 갖고, 취소나 완료 같은 상태도 가질 수 있습니다. 그러므로 단순한 선이 아니라 독립적인 사건 엔터티로 보는 편이 자연스럽습니다.

```text
고객 1명 --- 여러 상담 --- 1명 상담사
상담: 상담번호, 상담일시, 상담결과, 상태
```

## 자주 하는 실수

- **속성을 엔터티로 분리하기**: 회원의 전화번호를 별도 관리할 이유가 없는데 테이블로 나누면 조회가 불필요하게 복잡해진다.
- **반복되는 값을 한 칸에 넣기**: 주문 상품 목록을 문자열 하나에 저장하면 개별 상품을 조회하거나 집계하기 어렵다.
- **이력을 무시하기**: 상태 변경 시점이나 주문 당시 가격처럼 시간이 지나도 보존할 값은 현재 값과 분리해야 한다.

## 이번 편 정리

- 엔터티는 독립적으로 식별하고 관리할 업무 대상이다.
- 구분 가능성, 관리할 속성, 생명주기를 기준으로 판단한다.
- 관계에서 결정되는 값은 연결 엔터티의 속성인지 확인한다.
