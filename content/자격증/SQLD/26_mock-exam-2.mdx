## 1과목: 데이터 모델링의 이해

### 문제 1

다음 설명에서 엔터티의 종류를 올바르게 분류한 것은?

> - 고객: 서비스를 이용하는 실체
> - 주문: 고객이 상품을 구매하는 행위로 생성되는 정보
> - 고객등급: 구매 금액에 따라 시스템이 자동 부여하는 등급

1. 고객(기본 엔터티), 주문(중심 엔터티), 고객등급(행위 엔터티)
2. 고객(기본 엔터티), 주문(행위 엔터티), 고객등급(중심 엔터티)
3. 고객(중심 엔터티), 주문(행위 엔터티), 고객등급(기본 엔터티)
4. 고객(기본 엔터티), 주문(행위 엔터티), 고객등급(기본 엔터티)

<Callout type="success">
  **정답: 2번**

  엔터티 종류 분류:
  - **기본 엔터티(Fundamental Entity)**: 업무에 원래부터 존재하는 독립적 실체. 다른 엔터티로부터 생성되지 않음 → **고객**
  - **행위 엔터티(Activity Entity)**: 두 개 이상의 부모 엔터티로부터 행위를 통해 생성 → **주문** (고객 + 상품의 구매 행위)
  - **중심 엔터티(Main Entity)**: 기본 엔터티로부터 발생되며, 행위 엔터티 생성의 중심 → **고객등급** (고객의 누적 구매에서 파생)

  실제로 고객등급은 기본 엔터티에 가까운 분류도 가능하나, 시험에서는 다른 엔터티(고객, 주문)의 집계로부터 파생되는 경우 중심 엔터티로 구분합니다.
</Callout>

### 문제 2

다음은 어떤 테이블의 함수 종속 다이어그램입니다. 이 테이블을 3NF로 만들기 위해 필요한 작업은?

```
배송정보(주문번호, 배송코드, 배송업체명, 수령인, 배송지주소)
기본키: 주문번호

함수 종속:
- 주문번호 → 배송코드
- 배송코드 → 배송업체명
- 주문번호 → 수령인, 배송지주소
```

1. 이미 3NF를 만족하므로 변경이 필요 없다.
2. 배송코드를 기본키에 추가하여 복합키로 만든다.
3. 배송정보 테이블에서 (배송코드, 배송업체명)을 별도 테이블로 분리한다.
4. 주문번호만으로 결정되는 모든 속성을 새 테이블로 분리한다.

<Callout type="success">
  **정답: 3번**

  현재 테이블에 이행 함수 종속이 존재합니다:
  - 주문번호 → 배송코드 (직접)
  - 배송코드 → 배송업체명 (직접)
  - **따라서: 주문번호 → 배송업체명 (이행 함수 종속)**

  이것은 3NF 위반입니다. 해결 방법: **배송업체(배송코드, 배송업체명)** 테이블을 분리하고, 배송정보 테이블에는 배송코드만 남깁니다.

  **변환 후:**
  - 배송정보(주문번호, 배송코드, 수령인, 배송지주소)
  - 배송업체(배송코드, 배송업체명)
</Callout>

### 문제 3

다음 중 식별 관계(Identifying Relationship)와 비식별 관계(Non-Identifying Relationship)의 차이로 올바른 것은?

1. 식별 관계: 자식 엔터티가 부모 엔터티의 기본키를 외래키로만 가짐 / 비식별 관계: 부모 기본키가 자식의 기본키에 포함됨
2. 식별 관계: 부모 기본키가 자식의 기본키를 구성함 / 비식별 관계: 부모 기본키가 자식의 일반 속성(외래키)으로만 존재함
3. 식별 관계: 자식이 부모 없이 존재 가능 / 비식별 관계: 자식이 부모 없이 존재 불가
4. 식별 관계와 비식별 관계는 외래키 여부로만 구분한다.

<Callout type="success">
  **정답: 2번**

  핵심 구분:
  - **식별 관계**: 부모 엔터티의 기본키가 자식 엔터티의 **기본키의 일부 또는 전체**를 구성합니다. 자식은 부모 없이 존재할 수 없습니다. ERD에서 실선으로 표현.
  - **비식별 관계**: 부모 엔터티의 기본키가 자식 엔터티의 **일반 속성(외래키)**으로만 존재합니다. 자식이 부모 없이 존재할 수 있습니다(선택적). ERD에서 점선으로 표현.

  예시:
  - 식별: 주문(주문번호 PK) ← 주문상세(주문번호 PK + 상품번호 PK) — 주문번호가 PK에 포함
  - 비식별: 고객(고객번호 PK) ← 주문(주문번호 PK, 고객번호 FK) — 고객번호가 일반 FK
</Callout>

### 문제 4

다음 상관 서브쿼리(Correlated Subquery)의 결과 행 수는?

```sql
-- 직원 테이블
-- 직원번호 | 부서코드 | 급여
--   E001  |   D01   | 300
--   E002  |   D01   | 400
--   E003  |   D02   | 250
--   E004  |   D02   | 350
--   E005  |   D02   | 200

-- (단위: 만원)

SELECT 직원번호, 부서코드, 급여
FROM 직원 A
WHERE 급여 > (
    SELECT AVG(급여)
    FROM 직원 B
    WHERE B.부서코드 = A.부서코드
);
```

1. 1행
2. 2행
3. 3행
4. 4행

<Callout type="success">
  **정답: 2번 (2행)**

  이 쿼리는 각 직원마다 같은 부서의 평균 급여를 계산하여 비교합니다(상관 서브쿼리).

  **D01 부서 평균**: (300 + 400) / 2 = **350**
  - E001(300): 300 > 350? → 거짓 → 제외
  - E002(400): 400 > 350? → 참 → **포함**

  **D02 부서 평균**: (250 + 350 + 200) / 3 = **266.67**
  - E003(250): 250 > 266.67? → 거짓 → 제외
  - E004(350): 350 > 266.67? → 참 → **포함**
  - E005(200): 200 > 266.67? → 거짓 → 제외

  결과: E002, E004 → **2행**
</Callout>

### 문제 5

다음 ROLLUP 쿼리의 결과에서 NULL이 나타나는 행의 의미로 올바른 것은?

```sql
-- 판매 테이블: 지역(서울/부산), 상품(A/B), 각 조합 1행

SELECT 지역, 상품, SUM(매출) AS 매출합계
FROM 판매
GROUP BY ROLLUP(지역, 상품);

-- 결과 일부:
-- 서울 | A   | 100
-- 서울 | B   | 150
-- 서울 | NULL| 250   ← 이 행의 의미는?
```

1. 지역이 서울이고 상품 데이터가 없는 행
2. 지역 서울의 모든 상품에 대한 소계
3. 오류로 인해 상품 값이 누락된 행
4. ROLLUP 없이 일반 GROUP BY를 사용한 결과와 동일

<Callout type="success">
  **정답: 2번**

  ROLLUP에서 NULL은 소계 또는 합계 행을 나타냅니다.

  - `지역='서울', 상품=NULL, 매출합계=250`: **서울 지역 전체 소계** (A: 100 + B: 150 = 250)
  - `지역=NULL, 상품=NULL, 매출합계=전체합계`: **전체 합계** 행

  이 NULL은 실제 데이터가 NULL인 것이 아니라 ROLLUP이 소계/합계 계산을 위해 생성한 집계 행의 표시입니다. `GROUPING()` 함수를 사용하면 이 NULL이 소계인지 실제 NULL인지 구분할 수 있습니다.
</Callout>

### 문제 6

다음 계층형 질의(Hierarchical Query)에 대한 설명으로 올바른 것은?

```sql
-- 조직도 테이블(사원번호, 이름, 상위사원번호)
-- 1 | 대표이사 | NULL
-- 2 | 부장A   | 1
-- 3 | 부장B   | 1
-- 4 | 과장A   | 2
-- 5 | 과장B   | 2

SELECT LEVEL, 이름, 사원번호
FROM 조직도
START WITH 상위사원번호 IS NULL
CONNECT BY PRIOR 사원번호 = 상위사원번호;
```

1. 결과는 대표이사 1명만 반환된다.
2. LEVEL 값: 대표이사=1, 부장A·B=2, 과장A·B=3
3. CONNECT BY PRIOR는 현재 행의 사원번호가 다음 행의 사원번호와 같아야 연결된다.
4. START WITH 조건을 생략하면 모든 행이 루트 노드가 된다.

<Callout type="success">
  **정답: 2번**

  계층형 쿼리 분석:
  - `START WITH 상위사원번호 IS NULL`: 루트 노드(대표이사, 상위 없음)에서 시작
  - `CONNECT BY PRIOR 사원번호 = 상위사원번호`: 현재 행의 사원번호가 자식 행의 상위사원번호가 되어 하향(부모→자식) 방향으로 탐색

  **LEVEL 결과:**
  - 대표이사(1): LEVEL = **1** (루트)
  - 부장A(2), 부장B(3): LEVEL = **2** (1단계 하위)
  - 과장A(4), 과장B(5): LEVEL = **3** (2단계 하위)

  총 5행 반환. ③은 틀림(PRIOR 사원번호는 부모의 사원번호를 의미).
</Callout>

### 문제 7

다음 MERGE 문 실행 후 TARGET 테이블의 최종 상태는?

```sql
-- TARGET: 고객등급(고객번호, 등급, 할인율)
-- C001 | 실버 | 5%
-- C002 | 골드 | 10%
-- C003 | 일반 | 0%

-- SOURCE: 변경등급(고객번호, 신등급, 신할인율)
-- C002 | 플래티넘 | 15%
-- C004 | 실버     | 5%

MERGE INTO 고객등급 T
USING 변경등급 S ON (T.고객번호 = S.고객번호)
WHEN MATCHED THEN
    UPDATE SET T.등급 = S.신등급, T.할인율 = S.신할인율
WHEN NOT MATCHED THEN
    INSERT (고객번호, 등급, 할인율) VALUES (S.고객번호, S.신등급, S.신할인율);
```

1. C001(실버,5%), C002(플래티넘,15%), C003(일반,0%)
2. C001(실버,5%), C002(플래티넘,15%), C003(일반,0%), C004(실버,5%)
3. C002(플래티넘,15%), C004(실버,5%)
4. C001(실버,5%), C002(골드,10%), C003(일반,0%), C004(실버,5%)

<Callout type="success">
  **정답: 2번**

  SOURCE 행별 처리:
  - C002: TARGET에 존재 → MATCHED → `UPDATE: 등급=플래티넘, 할인율=15%`
  - C004: TARGET에 없음 → NOT MATCHED → `INSERT: (C004, 실버, 5%)`

  변경되지 않은 TARGET 행:
  - C001: SOURCE에 없음 → 그대로 유지 (실버, 5%)
  - C003: SOURCE에 없음 → 그대로 유지 (일반, 0%)

  최종: C001(실버,5%), C002(플래티넘,15%), C003(일반,0%), C004(실버,5%)
</Callout>

### 문제 8

다음 쿼리에서 UNION ALL 대신 UNION을 사용했을 때 결과 행 수의 차이는?

```sql
-- 2024_수강 테이블: 학번 A001, A002, A002, A003  (A002 중복 포함, 총 4행)
-- 2025_수강 테이블: 학번 A002, A003, A004  (총 3행)

-- UNION ALL
SELECT 학번 FROM 2024_수강
UNION ALL
SELECT 학번 FROM 2025_수강;
-- UNION
SELECT 학번 FROM 2024_수강
UNION
SELECT 학번 FROM 2025_수강;
```

1. UNION ALL: 7행, UNION: 4행 (3행 줄어듦)
2. UNION ALL: 7행, UNION: 5행 (2행 줄어듦)
3. UNION ALL: 6행, UNION: 4행
4. UNION ALL: 7행, UNION: 3행

<Callout type="success">
  **정답: 1번**

  **UNION ALL** (중복 제거 없음): 4 + 3 = **7행**
  - A001, A002, A002, A003, A002, A003, A004

  **UNION** (중복 제거): 중복 값을 모두 제거
  - 고유값: A001, A002, A003, A004 → **4행**

  차이: 7 - 4 = **3행** 줄어듦

  UNION은 내부적으로 DISTINCT를 수행하므로, 두 테이블 합친 결과에서 중복을 제거합니다. UNION ALL의 A002(3번 등장)와 A003(2번 등장)이 각각 1번으로 줄어들어 3행 감소.
</Callout>

### 문제 9

다음 윈도우 함수 쿼리 결과에서 '박민수'의 누적합계(누적매출) 값은?

```sql
-- 월별매출 테이블
-- 영업사원 | 월  | 매출
-- 박민수  |  1  | 100
-- 박민수  |  2  | 150
-- 박민수  |  3  | 200
-- 김지수  |  1  | 120

SELECT 영업사원, 월, 매출,
       SUM(매출) OVER (
           PARTITION BY 영업사원
           ORDER BY 월
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS 누적매출
FROM 월별매출
WHERE 영업사원 = '박민수';
```

박민수의 3월 누적매출 값은?

1. 200
2. 350
3. 450
4. 570

<Callout type="success">
  **정답: 3번 (450)**

  `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`는 "첫 번째 행부터 현재 행까지"를 의미합니다.

  박민수 기준 (PARTITION BY 영업사원):
  - 1월: 누적 = 100 (1월만)
  - 2월: 누적 = 100 + 150 = **250**
  - 3월: 누적 = 100 + 150 + 200 = **450**

  3월의 누적매출 = **450**
</Callout>

### 문제 10

다음 DELETE와 TRUNCATE에 관한 상황에서 올바른 선택은?

> **상황**: 테스트 환경의 `임시_주문내역` 테이블에 100만 건의 데이터가 있다. 이 데이터를 모두 빠르게 삭제해야 하며, 삭제 후 되돌릴 필요가 없다. 테이블 구조는 유지해야 한다.

1. `DELETE FROM 임시_주문내역;` — DML이라 ROLLBACK 가능하므로 안전하다.
2. `TRUNCATE TABLE 임시_주문내역;` — DDL이라 빠르고 즉시 COMMIT되므로 적합하다.
3. `DROP TABLE 임시_주문내역;` — 가장 빠르게 삭제할 수 있다.
4. `DELETE FROM 임시_주문내역 WHERE 1=1;` — 조건을 명시해야 전체 삭제가 된다.

<Callout type="success">
  **정답: 2번**

  요구사항 분석:
  - 모든 데이터 삭제 (전체)
  - 빠른 처리 필요
  - 되돌릴 필요 없음
  - 테이블 구조 유지 필요

  **TRUNCATE**:
  - 전체 삭제, WHERE 조건 없음 → 요구사항 충족
  - 로그 최소화로 DELETE보다 훨씬 빠름 → 100만 건에 적합
  - DDL이라 자동 COMMIT → 되돌릴 필요 없으므로 문제없음
  - 테이블 구조 유지 → 요구사항 충족

  **③ DROP**: 테이블 자체가 삭제되어 구조도 사라짐 → 요구사항 불충족
  **①④ DELETE**: 행별 로그 남겨 100만 건 처리가 느림, ROLLBACK 가능하지만 속도 문제
</Callout>

## 최종 점검 체크리스트

시험 당일 확인할 핵심 개념을 최종 점검하세요.

### 데이터 모델링

- [ ] ERD 기호: `|`(필수,최솟값1), `O`(선택,최솟값0), `||`(최댓값1), `<>`(최댓값N) 구분
- [ ] 정규화 3단계: 1NF(원자값), 2NF(부분종속제거), 3NF(이행종속제거) 조건 암기
- [ ] 이상현상 3종: 삽입·삭제·갱신 이상의 발생 상황 구분
- [ ] 식별/비식별 관계: 기본키 포함 여부(식별=PK포함, 비식별=FK만)
- [ ] 반정규화 목적: 조회 성능 향상, 부작용: 무결성 관리 비용 증가

### SQL 기본

- [ ] NULL 규칙: NULL과의 산술=NULL, `=NULL` 불가, `IS NULL`만 가능
- [ ] COUNT(*) vs COUNT(컬럼): NULL 포함 여부 차이
- [ ] NOT IN + NULL: 항상 0건 반환 함정
- [ ] SQL 실행순서: FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY
- [ ] HAVING vs WHERE: 집계 함수 사용 가능 위치
- [ ] JOIN 결과 행 수: INNER(교집합), LEFT(왼쪽전체), FULL(합집합)

### SQL 활용

- [ ] 단일행 서브쿼리: `=, >, <` 사용, 다중행이면 오류
- [ ] 다중행 서브쿼리: `IN, ANY, ALL, EXISTS` 사용
- [ ] UNION vs UNION ALL: 중복 제거 여부 차이
- [ ] RANK vs DENSE_RANK: 동점 시 건너뜀 여부 (RANK:건너뜀, DENSE_RANK:연속)
- [ ] ROLLUP 행 수: ROLLUP(A,B) → A종류×(B종류+1)+1
- [ ] TCL: COMMIT(확정), ROLLBACK(전체취소), ROLLBACK TO(부분취소)
- [ ] DDL 자동COMMIT: CREATE/ALTER/DROP/TRUNCATE는 자동 COMMIT
- [ ] MERGE: ON 조건 일치 시 MATCHED, 불일치 시 NOT MATCHED 실행
- [ ] CONNECT BY PRIOR: 계층형 쿼리에서 부모→자식 방향 탐색
