## 이번 편의 목표

- 엔터티, 인스턴스, 속성의 관계를 한 문장으로 설명한다.
- 업무 문장에서 필요한 속성을 찾고 엔터티와 구분한다.
- 기본·설계·파생 속성과 단일·복합·다중값 속성을 구분한다.
- 속성의 도메인과 이름을 정하고 잘못된 설계를 고친다.

## 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| 속성 | 한 인스턴스를 설명하기 위해 저장하는 값의 항목 |
| 속성값 | 특정 인스턴스가 실제로 가진 값 |
| 도메인 | 한 속성에 들어올 수 있는 값의 범위와 규칙 |
| 원자값 | 현재 업무에서 더 나누지 않고 하나로 다루는 값 |
| 기본 속성 | 업무에서 원래 수집하는 값 |
| 설계 속성 | 모델을 식별하거나 편리하게 관리하려고 새로 만든 값 |
| 파생 속성 | 다른 속성값으로 계산할 수 있는 값 |
| 다중값 속성 | 한 인스턴스가 동시에 여러 값을 가질 수 있는 항목 |

`회원`은 엔터티이고 `회원번호 101인 민지`는 인스턴스다. `이름`, `가입일`, `등급`은 회원을 설명하는 속성이며, 민지의 이름인 `민지`는 속성값이다.

## 선수지식과 핵심 질문

선수지식은 [05. 엔터티](./05_entity)에서 배운 엔터티와 인스턴스의 차이다.

이번 편의 핵심 질문은 이것이다.

> 어떤 정보를 엔터티 안의 속성으로 두고, 어떤 정보는 별도 엔터티로 분리해야 할까?

## 속성은 대상을 설명하는 최소 정보 단위다

**속성(attribute)** 은 업무에서 관리할 필요가 있고, 한 인스턴스를 설명하는 의미 있는 정보 항목이다. 관계형 데이터베이스로 구현하면 보통 테이블의 열에 대응한다.

```text
엔터티: 회원
인스턴스: 회원번호 101인 민지
속성: 회원번호, 이름, 이메일, 가입일
속성값: 101, 민지, minji@example.com, 2026-08-10
```

속성은 단순히 화면에 보이는 모든 글자가 아니다. 업무 규칙을 판단하거나 검색·저장·변경해야 하는 정보여야 한다.

<Callout type="info">
  엔터티는 같은 종류 대상의 집합, 인스턴스는 실제 대상 하나, 속성은 그 대상을 설명하는 항목이다. 시험에서는 이 세 수준을 바꾸어 선지로 제시한다.
</Callout>

## 좋은 속성을 판단하는 네 가지 질문

### 업무에 필요한가

쇼핑몰이 회원의 혈액형을 사용하지 않는다면 `혈액형`은 회원 속성으로 둘 이유가 없다. 저장할 수 있다는 이유만으로 수집하면 모델이 복잡해지고 개인정보 위험도 커진다.

### 해당 엔터티를 직접 설명하는가

`회원이름`은 회원을 직접 설명한다. 반면 주문 엔터티의 `회원이름`은 회원번호를 통해 회원에서 찾을 수 있으므로 중복일 가능성이 높다.

```text
주문.회원번호 → 회원.회원번호
회원.회원번호 → 회원.회원이름
```

주문 시점의 이름을 반드시 보존해야 하는 별도 업무 규칙이 있다면 `주문자표시명`처럼 의미를 분명히 한 스냅숏 속성이 될 수 있다. 같은 글자라도 왜 저장하는지에 따라 판단이 달라진다.

### 한 인스턴스에서 한 값을 가지는가

회원 한 명이 여러 전화번호를 가진다면 `전화번호1`, `전화번호2`, `전화번호3`처럼 반복 속성을 추가하지 않는다. 전화번호를 여러 건 관리해야 한다면 `회원전화번호` 엔터티로 분리한다.

### 더 작게 나눌 실무적 이유가 있는가

주소 전체를 출력만 한다면 문자열 하나로 관리할 수 있다. 시·도별 배송비를 계산하거나 우편번호로 검색해야 한다면 `우편번호`, `기본주소`, `상세주소`처럼 분리하는 편이 낫다.

## 속성의 이름과 도메인

**도메인(domain)** 은 한 속성이 가질 수 있는 값의 범위다. 자료형만 뜻하지 않고 길이, 허용값, 형식, 단위까지 포함한다.

| 속성 | 자료형 예 | 추가 규칙 |
| --- | --- | --- |
| 회원번호 | 정수 | 양수, 중복 불가, 비어 있을 수 없음 |
| 이메일 | 문자열 | 최대 길이, 서비스 안에서 중복 불가 |
| 가입일시 | 날짜·시간 | 미래 시각 금지 |
| 주문상태 | 문자열 | `PAYMENT_WAIT`, `PAID`, `SHIPPED`, `CANCELED` 중 하나 |
| 주문금액 | 숫자 | 0 이상, 원 단위 |

`상태`라는 이름만 쓰면 회원상태인지 주문상태인지 모호하다. 속성 이름은 업무에서 실제 사용하는 단어를 선택하고 같은 뜻은 같은 이름으로 통일한다.

```sql
CREATE TABLE orders (
  order_id      BIGINT PRIMARY KEY,
  order_status  VARCHAR(20) NOT NULL
                CHECK (order_status IN
                  ('PAYMENT_WAIT', 'PAID', 'SHIPPED', 'CANCELED')),
  ordered_at    TIMESTAMP NOT NULL,
  total_amount  NUMERIC(12, 0) NOT NULL CHECK (total_amount >= 0)
);
```

이 코드는 논리 모델의 속성과 도메인 규칙 일부를 실제 테이블의 자료형과 제약조건으로 옮긴 예다.

## 발생 방식에 따른 속성 분류

### 기본 속성

업무에서 원래 발생해 수집하는 값이다. 회원 이름, 상품명, 주문수량이 예다. 다른 값으로 계산해서 만든 것이 아니다.

### 설계 속성

업무를 모델로 표현하거나 편리하게 식별하기 위해 설계자가 만든 값이다. 의미 없는 일련번호인 `회원번호`, 주문과 상품을 연결하는 `주문상세번호` 등이 예다.

설계 속성이 가짜 데이터라는 뜻은 아니다. 시스템 안에서 인스턴스를 안정적으로 식별하는 중요한 역할을 한다.

### 파생 속성

다른 속성으로 계산할 수 있는 값이다.

```text
주문상세금액 = 주문수량 × 주문단가
나이 = 기준일 - 생년월일
```

파생 속성을 저장하면 조회는 빨라질 수 있지만 원본이 바뀔 때 함께 갱신하지 않으면 값이 어긋난다. 계산 비용, 조회 빈도, 변경 빈도와 일관성 유지 방법을 함께 검토한다.

<Callout type="warning">
  파생 속성이라고 무조건 삭제하거나 무조건 저장하지 않는다. 계산 가능 여부와 저장 필요성은 다른 질문이다. 저장한다면 원본과 동기화하는 규칙이 필요하다.
</Callout>

## 값의 구성에 따른 속성 분류

### 단일 속성과 복합 속성

**단일 속성**은 의미상 더 나눌 필요가 없는 속성이다. 회원번호와 성별코드가 예다.

**복합 속성**은 여러 세부 의미로 나눌 수 있다. 주소를 우편번호·기본주소·상세주소로, 사람 이름을 성·이름으로 나누는 경우다.

중요한 기준은 글자 수가 아니라 업무에서 부분값을 따로 사용하는지다. `20260810`은 한 문자열이어도 연·월·일을 검색한다면 날짜형으로 다루어야 한다.

### 단일값 속성과 다중값 속성

**단일값 속성**은 한 인스턴스에서 한 값만 가진다. 회원의 가입일이 예다.

**다중값 속성**은 한 인스턴스가 여러 값을 가질 수 있다. 회원의 여러 배송지나 상품의 여러 이미지가 예다. 관계형 테이블에서는 보통 별도 엔터티로 분리한다.

```text
나쁜 구조
회원(회원번호, 이름, 전화번호1, 전화번호2, 전화번호3)

개선 구조
회원(회원번호, 이름)
회원전화번호(전화번호ID, 회원번호, 전화번호, 용도)
```

## 일관된 쇼핑몰 예제로 속성 배치하기

| 엔터티 | 주요 속성 | 판단 근거 |
| --- | --- | --- |
| 회원 | 회원번호, 이름, 이메일, 가입일시 | 회원을 직접 설명함 |
| 상품 | 상품번호, 상품명, 현재가격, 판매상태 | 상품의 현재 정보를 설명함 |
| 주문 | 주문번호, 회원번호, 주문일시, 주문상태 | 주문 사건과 주문한 회원을 기록함 |
| 주문상세 | 주문번호, 상품번호, 주문수량, 주문단가 | 한 주문에 포함된 상품별 사실을 기록함 |

상품의 `현재가격`과 주문상세의 `주문단가`는 숫자가 같을 때도 있지만 의미가 다르다. 상품 가격이 나중에 바뀌더라도 과거 주문 금액은 바뀌면 안 되므로 주문단가는 주문 시점의 사실이다.

## 흔한 실수와 진단법

| 실수 | 문제 | 진단 질문 |
| --- | --- | --- |
| `전화번호1`, `전화번호2` 반복 | 개수가 늘 때 열을 계속 추가해야 함 | 한 인스턴스가 여러 값을 가질 수 있는가? |
| 주문에 회원 이름을 그대로 중복 | 회원 이름 변경 시 값이 어긋날 수 있음 | 이 속성은 어느 식별자에 직접 의존하는가? |
| 모든 계산값을 저장 | 원본과 파생값 불일치 가능 | 다시 계산할 수 있고 계산 비용은 어느 정도인가? |
| `구분`, `상태`처럼 모호한 이름 | 속성 의미와 도메인을 알기 어려움 | 이름만 보고 업무 의미를 구분할 수 있는가? |
| 단위 없는 숫자 | 원·달러, kg·g를 혼동 | 자료형 외에 단위와 허용 범위를 정했는가? |

## 시험 연결

시험에서는 다음 경계를 자주 바꿔 묻는다.

1. 기본 속성은 업무에서 원래 수집하며, 설계 속성은 모델링 과정에서 필요해 만든다.
2. 파생 속성은 다른 속성으로 계산할 수 있다.
3. 도메인은 자료형뿐 아니라 허용 범위와 업무 규칙을 포함한다.
4. 한 속성은 현재 업무 기준에서 한 인스턴스당 하나의 값을 갖도록 설계한다.
5. 다중값을 반복 열로 두는 것보다 별도 엔터티와 관계로 표현하는 편이 확장에 유리하다.

## 짧은 확인

상품의 현재가격이 10,000원이고 주문 당시 할인 단가가 8,000원이라면 주문상세에는 어떤 값을 두어야 할까?

<Collapse title="확인하기">

주문상세에는 주문 당시 사실인 `주문단가 8,000원`을 둔다. 상품의 현재가격과 의미가 다르며, 과거 주문 금액을 재현하기 위해 필요하다.

</Collapse>

## 정리

<Callout type="default">
  - 속성은 한 인스턴스를 설명하는 의미 있는 정보 항목이다.
  - 도메인은 자료형, 길이, 허용값, 단위 같은 값의 규칙이다.
  - 속성은 발생 방식에 따라 기본·설계·파생 속성으로 구분한다.
  - 다중값이나 반복 속성은 별도 엔터티로 분리할지 검토한다.
  - 속성은 자신이 속한 엔터티의 식별자에 직접 의존해야 한다.
</Callout>
