## 이번 편의 목표

- 개념·논리·물리 데이터 모델의 질문과 산출물을 구분한다.
- ERD에서 엔터티, 식별자, 관계 수, 선택성을 순서대로 읽는다.
- 논리 모델의 한 요소가 물리 테이블로 어떻게 변환되는지 설명한다.
- 모델 단계가 서로 단절된 문서가 아니라 점진적 구체화라는 점을 이해한다.

## 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| 개념 모델 | 업무의 중요한 대상과 큰 관계를 이해관계자와 확인하는 상위 수준 모델 |
| 논리 모델 | 속성, 식별자, 관계 규칙까지 DBMS와 무관하게 자세히 표현한 모델 |
| 물리 모델 | 선택한 DBMS에서 실제 테이블·열·자료형·인덱스로 구현할 모델 |
| ERD | 엔터티와 관계를 그림으로 나타낸 다이어그램 |
| 카디널리티 | 한쪽 인스턴스가 다른 쪽 몇 개와 연결될 수 있는지 나타내는 수 |
| 선택성 | 관계 참여가 필수인지 선택인지 나타내는 조건 |
| 기본키 | 각 행을 유일하게 구분하도록 선택한 키 |
| 외래키 | 다른 테이블의 기본키를 참조해 관계를 구현하는 열 |

같은 업무도 누구와 무엇을 확인하느냐에 따라 모델의 자세함이 다르다. 개념·논리·물리는 서로 경쟁하는 모델이 아니라 앞 단계의 결정을 구체화하는 과정이다.

## 주변 개념 지도

ERD의 상자는 관리 대상을, 선은 관계를 나타낸다. 물리 모델에서는 이 관계가 외래키로 구현되는 경우가 많지만, 개념 모델 단계부터 특정 DBMS 문법을 먼저 결정하지는 않는다.

<Callout type="info">
1:N은 “한쪽 하나가 다른 쪽 여러 개와 연결될 수 있다”는 뜻이다. 어느 쪽이 1이고 어느 쪽이 N인지 업무 문장으로 먼저 읽는다.
</Callout>

## 지도도 목적에 따라 자세함이 다르다

전국 지도에는 도시와 고속도로가 보이고, 동네 지도에는 골목과 건물 번호가 보인다. 둘 중 하나가 틀린 지도가 아니라 사용하는 목적과 상세 수준이 다르다.

데이터 모델도 마찬가지다.

```text
업무의 큰 대상과 관계
→ 속성과 식별자까지 갖춘 논리 구조
→ 특정 DBMS에서 실행할 물리 구조
```

## 개념 데이터 모델

**개념 모델**은 업무에서 무엇을 관리하고 큰 관계가 어떻게 되는지 표현한다. 세부 컬럼과 자료형보다 업무 범위를 합의하는 데 집중한다.

```text
회원 ─ 주문 ─ 상품
```

이 단계의 질문은 다음과 같다.

- 주문과 결제는 같은 사건인가, 별도 관리 대상인가?
- 비회원 주문을 허용하는가?
- 상품은 판매 중지 후에도 주문 이력과 연결되어야 하는가?

## 논리 데이터 모델

**논리 모델**은 DBMS에 크게 종속되지 않은 상태에서 엔터티, 속성, 식별자, 관계, 정규화 규칙을 구체화한다.

```text
회원(회원번호, 이름, 연락처)
주문(주문번호, 주문일시, 상태, 회원번호)
상품(상품번호, 상품명, 현재가격)
주문상세(주문번호, 상품번호, 수량, 주문가격)
```

이 단계에서는 기본 식별자와 관계 수, 속성의 필수 여부 같은 업무 규칙이 보여야 한다.

## 물리 데이터 모델

**물리 모델**은 선택한 DBMS에서 실제로 구현할 테이블명, 컬럼명, 자료형, 제약조건, 인덱스, 저장 전략을 정한다.

```sql
CREATE TABLE orders (
  order_id   BIGINT PRIMARY KEY,
  member_id  BIGINT NOT NULL,
  ordered_at TIMESTAMP NOT NULL,
  status     VARCHAR(20) NOT NULL,
  CONSTRAINT fk_orders_member
    FOREIGN KEY (member_id) REFERENCES members(member_id)
);
```

`BIGINT`, `VARCHAR(20)`, 인덱스 방식은 물리 구현 선택이다. 같은 논리 모델이라도 DBMS와 예상 데이터량에 따라 물리 모델은 달라질 수 있다.

| 구분 | 핵심 질문 | 대표 산출물 |
| --- | --- | --- |
| 개념 | 무엇을 관리하며 큰 관계는 무엇인가? | 핵심 엔터티와 관계 |
| 논리 | 어떤 속성·식별자·업무 규칙이 있는가? | 정규화된 ERD |
| 물리 | 특정 DBMS에 어떻게 구현할 것인가? | 테이블, 자료형, 제약, 인덱스 |

<Callout type="important">
  물리 모델을 만들 때 논리 모델의 업무 의미가 사라지면 안 된다. 이름을 짧게 바꾸더라도 원래 용어와 대응 관계를 추적할 수 있어야 한다.
</Callout>

## ERD를 읽는 순서

**ERD(Entity Relationship Diagram)** 는 엔터티와 관계를 시각적으로 표현한 그림이다. 표기법은 달라도 읽는 질문은 비슷하다.

<Steps>

### 엔터티의 의미를 읽는다

이름만 보지 말고 어떤 업무 대상을 나타내는지 정의를 확인한다. `주문`이 장바구니인지 결제 요청인지 조직마다 다를 수 있다.

### 식별자를 찾는다

각 인스턴스를 유일하게 구분하는 속성을 찾는다. 주문번호가 중복되거나 바뀔 수 있다면 좋은 식별자가 아니다.

### 일반 속성을 확인한다

속성이 어느 엔터티에 속하는지, 필수인지, 반복값을 한 칸에 넣고 있지는 않은지 본다.

### 관계의 수를 읽는다

한 회원이 주문 몇 건과 연결되는지처럼 1:1, 1:N, N:M을 확인한다.

### 선택성을 읽는다

반드시 연결되어야 하는지, 연결되지 않아도 되는지 확인한다. 비회원 주문을 허용한다면 주문과 회원의 관계는 선택적일 수 있다.

</Steps>

## 관계 수와 선택성

```text
회원 1 ─── 0..N 주문
주문 1 ─── 1..N 주문상세
```

- 회원은 가입만 하고 주문하지 않을 수 있으므로 회원 한 명에 주문은 0건 이상이다.
- 확정 주문은 상품을 하나 이상 포함해야 한다는 규칙이라면 주문 한 건에 주문상세는 1건 이상이다.

관계 수는 데이터에서 우연히 관찰된 개수가 아니라 **업무가 허용하는 최소·최대 규칙**이다.

## 모델 변환을 한 단계씩 보기

업무 문장부터 물리 구현까지 연결해 보자.

```text
업무: 회원은 여러 배송지를 등록할 수 있다.
```

### 개념

회원과 배송지는 별도 관리 대상이며 1:N 관계다.

### 논리

```text
회원(회원번호, 이름)
배송지(배송지번호, 수령인, 주소, 회원번호)
```

### 물리

```sql
CREATE TABLE addresses (
  address_id BIGINT PRIMARY KEY,
  member_id  BIGINT NOT NULL,
  recipient  VARCHAR(50) NOT NULL,
  address    VARCHAR(300) NOT NULL,
  FOREIGN KEY (member_id) REFERENCES members(member_id)
);
```

각 단계는 앞 단계의 결정을 더 구체적으로 표현한다.

## 시험형 선지 분석

1. "개념 모델은 특정 DBMS의 자료형과 인덱스를 결정한다." → 거짓. 물리 모델의 역할이다.
2. "논리 모델은 엔터티·속성·관계·식별자를 구체화한다." → 참.
3. "관계의 선택성은 현재 데이터에 NULL이 있는지만 보면 결정된다." → 거짓. 업무 규칙으로 결정한다.
4. "물리 모델은 성능과 저장 환경을 고려할 수 있다." → 참.

## 정리

<Callout type="default">
  - 개념 모델은 업무의 큰 대상, 논리 모델은 속성과 규칙, 물리 모델은 DBMS 구현을 다룬다.
  - ERD는 엔터티 -> 식별자 -> 속성 -> 관계 수 -> 선택성 순으로 읽으면 안정적이다.
  - 관계 수와 선택성은 현재 데이터가 아니라 업무 규칙에서 나온다.
  - 각 모델 단계는 앞 단계의 의미를 보존하며 구체화한다.
</Callout>

다음 편에서는 모델의 기본 단위인 엔터티를 판단하는 기준과 인스턴스, 속성의 차이를 깊게 다룬다.
