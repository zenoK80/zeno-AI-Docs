## 데이터가 쌓이면 파일만으로는 부족해진다

작은 쇼핑몰을 운영한다고 생각해 보자. 처음에는 회원 목록과 주문 목록을 엑셀 파일로 관리해도 된다. 하지만 주문이 늘면 “김민수 회원이 지난달에 주문한 상품은 무엇인가?” 같은 질문에 여러 파일을 열어 이름을 맞춰 봐야 한다.

데이터베이스는 관련 있는 데이터를 일정한 규칙으로 저장해, 필요한 정보를 정확하고 빠르게 찾을 수 있게 하는 체계다. 단순히 파일을 한곳에 모으는 것이 아니라 **데이터 사이의 관계와 사용 규칙까지 관리**한다.

## 테이블로 보는 데이터베이스

관계형 데이터베이스에서는 보통 데이터를 표 형태의 테이블로 나눈다.

| members |  |
| --- | --- |
| member_id | name |
| M001 | 김민수 |
| M002 | 이지수 |

| orders |  |  |
| --- | --- | --- |
| order_id | member_id | amount |
| O101 | M001 | 30000 |
| O102 | M001 | 12000 |

`orders.member_id`는 주문이 누구의 것인지 알려 준다. 회원 이름을 주문마다 반복해 쓰지 않아도 두 테이블을 연결해 필요한 정보를 얻을 수 있다. 이 연결을 설계하는 일이 데이터 모델링이고, SQLD의 중요한 출발점이다.

<Callout type="important">
데이터베이스는 데이터를 저장하는 장소이고, DBMS는 그 데이터를 저장·조회·수정·보호하도록 도와주는 소프트웨어다. MySQL, PostgreSQL, Oracle 등이 DBMS의 예다.
</Callout>

## SQL은 데이터에 질문하는 언어다

SQL은 DBMS에 데이터를 정의하고, 조회하고, 바꾸도록 요청하는 언어다. 아직 문법을 외울 필요는 없지만, 아래 문장이 어떤 질문인지 읽어 보자.

```sql
SELECT name, amount
FROM members
JOIN orders ON members.member_id = orders.member_id
WHERE members.member_id = 'M001';
```

이 쿼리는 “M001 회원의 이름과 주문 금액을 보여 달라”는 요청이다. SQL은 단순 암기 과목이 아니라, **데이터가 어떤 구조로 연결되어 있는지 읽고 필요한 결과를 표현하는 언어**다.

## SQLD에서 왜 데이터 모델링을 먼저 배울까?

좋은 SQL도 테이블 구조가 잘못되면 원하는 결과를 안정적으로 만들기 어렵다. 예를 들어 주문 테이블에 회원 이름만 저장하면, 이름이 바뀌었을 때 과거 주문의 이름까지 모두 고쳐야 할 수 있다. 회원을 별도 테이블로 나누고 식별자로 연결하면 이런 문제를 줄일 수 있다.

SQLD도 이 흐름을 따른다. 공식 안내 기준으로 데이터 모델링의 이해를 바탕으로 SQL 기본 및 활용 능력을 검정한다.

## 직접 확인하기

아래 질문을 답하려면 어떤 테이블이 필요한지 생각해 보자.

```txt
“회원 김민수가 주문한 금액의 합계는 얼마인가?”
```

회원 이름을 찾으려면 `members`, 주문 금액을 합치려면 `orders`가 필요하다. 두 테이블을 `member_id`로 연결해야 한다는 점까지 떠올리면 충분하다.

## 흔한 실수

- 데이터베이스와 DBMS를 같은 뜻으로 쓰기
- SQL을 단순히 “데이터를 꺼내는 명령어”로만 이해하기: 정의, 조작, 권한, 트랜잭션도 다룬다.
- 테이블을 많이 나누면 무조건 좋다고 생각하기: 관계와 조회 목적에 맞게 나누어야 한다.

## 이번 편 정리

- 데이터베이스는 관계 있는 데이터를 규칙 있게 관리하는 체계다.
- DBMS는 데이터베이스를 실제로 운영하는 소프트웨어다.
- SQL은 데이터 구조를 바탕으로 필요한 정보를 요청하는 언어다.

다음 편에서는 데이터베이스가 여러 사용자의 데이터를 안전하게 다룰 수 있는 이유를 살펴본다.
