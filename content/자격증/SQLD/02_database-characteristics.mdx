## 데이터베이스는 저장소 이상의 역할을 한다

회원 한 명이 주문을 하는 동안 다른 직원은 배송 상태를 바꾸고, 또 다른 사용자는 주문 내역을 조회할 수 있다. 이런 상황에서 값이 엉키지 않도록 만드는 것이 데이터베이스의 역할이다.

SQLD에서는 용어를 따로 외우기보다 “여러 사람이 같은 데이터를 사용할 때 어떤 문제가 생길까?”를 먼저 생각하면 이해하기 쉽다.

| 특징 | 해결하려는 문제 | 주문 예시 |
| --- | --- | --- |
| 공유 | 같은 데이터를 여러 사람이 써야 함 | 고객센터와 배송팀이 같은 주문을 봄 |
| 무결성 | 틀린 값이 들어오면 안 됨 | 존재하지 않는 회원 번호의 주문 차단 |
| 동시성 | 동시에 바꾸면 값이 꼬일 수 있음 | 재고 1개를 두 사람이 동시에 구매 |
| 보안 | 모두가 모든 정보를 보면 안 됨 | 일반 직원은 급여 정보에 접근 불가 |
| 회복 | 장애 뒤에도 데이터를 복구해야 함 | 서버 오류 뒤 주문 기록 복원 |

## 무결성: 데이터가 맞는 상태를 지키기

무결성은 데이터가 정해진 규칙을 지키는 성질이다. `amount`에 음수가 들어가거나, 주문에 없는 회원 번호가 들어가면 이후 조회와 집계가 모두 틀어질 수 있다.

```sql
CREATE TABLE orders (
  order_id VARCHAR(10) PRIMARY KEY,
  member_id VARCHAR(10) NOT NULL,
  amount INTEGER CHECK (amount > 0)
);
```

위 예시는 주문 번호가 중복되지 않고, 회원 번호가 비어 있지 않으며, 주문 금액이 0보다 커야 한다는 규칙을 표현한다. 실제 제약 조건 문법은 DBMS마다 차이가 있지만, **데이터를 넣기 전에 규칙을 정한다**는 원리는 같다.

## 동시성: 같은 순간의 수정 문제

재고가 1개 남은 상품을 A와 B가 동시에 결제한다고 하자. 둘 다 “재고가 1개다”라고 읽고 각각 1개씩 판매하면 재고가 -1이 될 수 있다. DBMS는 트랜잭션과 잠금 같은 기능으로 이런 충돌을 제어한다.

<Callout type="info">
트랜잭션은 여러 작업을 하나의 묶음으로 보는 단위다. 주문 생성과 재고 차감은 함께 성공하거나 함께 실패해야 자연스럽다.
</Callout>

## 직접 확인하기

다음 상황에 가장 먼저 필요한 특징을 골라 보자.

1. 직원마다 고객 전화번호를 다르게 수정했다. -> **공유와 무결성**
2. 서버가 꺼진 뒤 오전 주문이 사라졌다. -> **회복**
3. 인턴 계정이 모든 고객 정보를 조회할 수 있다. -> **보안**

상황 하나에 특징이 하나만 연결되는 것은 아니다. 다만 어떤 위험을 막으려는 기능인지 설명할 수 있어야 한다.

## 흔한 실수

- 무결성을 “데이터가 많다”는 뜻으로 이해하기: 값의 정확성과 관계 규칙을 지키는 성질이다.
- 동시성 문제를 프로그램 버그로만 보기: DBMS 차원의 제어도 필요하다.
- 백업과 회복을 같은 작업으로 보기: 백업은 복구를 위한 수단이고, 회복은 장애 뒤 정상 상태로 되돌리는 과정이다.

## 이번 편 정리

- 데이터베이스는 공유, 무결성, 동시성, 보안, 회복을 지원한다.
- 제약 조건은 잘못된 데이터를 처음부터 막는 방법이다.
- 여러 작업이 함께 성공해야 하는 상황은 트랜잭션으로 생각한다.
