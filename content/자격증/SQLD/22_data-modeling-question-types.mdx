## 유형 1. ERD 읽기 — 차수와 선택성 판단

ERD 문제는 엔터티 사이의 관계선을 읽고 "몇 개와 연결될 수 있는가(차수)"와 "반드시 존재해야 하는가(선택성)"를 판단합니다.

**기호 해석 요약**

| 기호 | 의미 |
|------|------|
| `|` (단선) | 최솟값 1 (필수) |
| `O` (원) | 최솟값 0 (선택) |
| `||` (이중선) | 최댓값 1 |
| `<` 또는 `>` (까마귀 발) | 최댓값 N |

---

**[예제 1-1]** 다음 ERD 설명을 읽고 관계의 차수와 선택성이 올바르게 설명된 것을 고르세요.

> 업무 규칙
> - 부서는 반드시 1명 이상의 직원을 보유한다.
> - 직원은 반드시 하나의 부서에 소속된다.
> - 하나의 부서에는 여러 명의 직원이 소속될 수 있다.

1. 부서(1, 필수) : 직원(1, 필수) — 1:1 관계
2. 부서(1, 필수) : 직원(N, 필수) — 1:N 관계, 양쪽 필수
3. 부서(1, 선택) : 직원(N, 선택) — 1:N 관계, 양쪽 선택
4. 부서(N, 필수) : 직원(1, 선택) — N:1 관계

<Callout type="success">
  **정답: 2번**

  - 부서 입장: 직원을 "1명 이상" 보유 → 부서는 직원과 최솟값 1(필수), 최댓값 N(다수)으로 연결됩니다.
  - 직원 입장: "반드시 하나의 부서에 소속" → 최솟값 1(필수), 최댓값 1(하나만)으로 연결됩니다.
  - 전체 관계: 부서 1 : 직원 N, 양쪽 모두 필수(Mandatory) 관계입니다.
  - 오답 분석: ①은 차수 오류(직원이 여럿일 수 있음), ③은 선택성 오류(업무 규칙에 필수라고 명시), ④는 차수 자체가 반대입니다.
</Callout>

---

**[예제 1-2]** 다음 중 ERD에서 "선택적(Optional) 관계"가 필요한 업무 상황으로 가장 적합한 것은?

1. 주문은 반드시 고객 정보를 포함해야 한다.
2. 사원은 반드시 소속 부서가 있어야 한다.
3. 학생은 동아리에 가입하지 않을 수도 있다.
4. 제품은 반드시 하나의 카테고리에 속해야 한다.

<Callout type="success">
  **정답: 3번**

  선택적 관계(0 표기, 원 기호)는 최솟값이 0인 경우, 즉 반드시 연결되지 않아도 되는 경우에 사용합니다. "가입하지 않을 수도 있다"는 0개와 연결 가능 → 선택적 관계입니다. 나머지 ①②④는 모두 "반드시"가 포함되어 필수(Mandatory) 관계입니다.
</Callout>

## 유형 2. 정규화 판단 — 정규형 식별과 이상현상

정규화 문제는 "이 테이블은 몇 정규형인가?" 또는 "어떤 이상현상이 발생하는가?"를 묻습니다.

**핵심 요약**

| 정규형 | 조건 |
|--------|------|
| 1NF | 모든 속성이 원자값(반복 그룹 없음) |
| 2NF | 1NF + 부분 함수 종속 제거(복합 키일 때 일부 키에만 종속된 속성 제거) |
| 3NF | 2NF + 이행 함수 종속 제거(비키 속성이 다른 비키 속성을 결정) |

---

**[예제 2-1]** 다음 테이블에 대한 설명으로 올바른 것은?

```
수강신청(학번, 과목코드, 학생이름, 과목명, 성적)
기본키: (학번, 과목코드)
```

| 학번 | 과목코드 | 학생이름 | 과목명 | 성적 |
|------|----------|----------|--------|------|
| S001 | C101 | 김철수 | 데이터베이스 | A |
| S001 | C102 | 김철수 | 알고리즘 | B |
| S002 | C101 | 이영희 | 데이터베이스 | A+ |

1. 1NF를 만족하지 않는다.
2. 2NF를 만족한다.
3. 학생이름은 학번에만 종속되므로 부분 함수 종속이 존재한다.
4. 성적은 학번만으로 결정되므로 이행 함수 종속이 존재한다.

<Callout type="success">
  **정답: 3번**

  - 기본키가 (학번, 과목코드)인 복합키인데, 학생이름은 학번만 알면 결정됩니다(학번 → 학생이름). 과목명은 과목코드만 알면 결정됩니다(과목코드 → 과목명). 이처럼 복합 기본키의 일부에만 종속된 경우를 **부분 함수 종속**이라 합니다.
  - 이 테이블은 1NF는 만족하지만 2NF를 위반합니다(부분 함수 종속 존재).
  - 성적은 (학번, 과목코드) 모두 있어야 결정되므로 완전 함수 종속입니다 → ④는 오답.
</Callout>

---

**[예제 2-2]** 다음 중 삭제 이상(Deletion Anomaly)이 발생하는 상황으로 가장 적절한 것은?

1. 동일한 데이터가 여러 행에 중복 저장되어 수정 시 일부만 바뀐다.
2. 새 학생을 등록하려면 수강 과목이 없어도 반드시 과목코드를 입력해야 한다.
3. 특정 학생의 수강 기록을 삭제했더니 그 학생 정보 자체가 사라졌다.
4. 같은 학번의 학생에 대해 학생이름이 서로 다르게 저장되어 있다.

<Callout type="success">
  **정답: 3번**

  **이상현상 구분**
  - 삽입 이상: 원하지 않는 데이터를 함께 입력해야만 삽입 가능 → ②번
  - 갱신 이상: 중복 데이터를 모두 수정하지 않아 불일치 발생 → ①④번
  - 삭제 이상: 하나의 사실을 삭제하려 할 때 의도치 않게 다른 사실도 삭제됨 → ③번이 정답
</Callout>

## 유형 3. 엔터티·속성·관계 분류

주어진 업무 설명에서 무엇이 엔터티이고 무엇이 속성인지를 판단하는 유형입니다.

**핵심 기준**

- **엔터티**: 독립적으로 관리할 필요가 있는 대상. 인스턴스(행)가 여러 개 존재할 수 있음.
- **속성**: 엔터티의 특징이나 상태를 나타내는 값. 인스턴스를 추가로 가지지 않음.
- **관계**: 두 엔터티 사이의 업무적 연관성.

---

**[예제 3-1]** 다음 업무 설명에서 엔터티로 관리해야 할 대상만 모두 고른 것은?

> 온라인 서점에서는 회원이 도서를 주문할 수 있다. 각 도서는 출판사가 발행하며, 주문 시 배송지 주소를 기록한다. 도서에는 ISBN, 제목, 정가 정보가 있다.

1. 회원, 도서, 주문
2. 회원, 도서, 주문, 출판사
3. 회원, 도서, 주문, 출판사, ISBN, 배송지 주소
4. 회원, 도서, 주문, ISBN, 정가

<Callout type="success">
  **정답: 2번**

  - **엔터티** (독립 관리 필요): 회원, 도서, 주문, 출판사 — 각각 여러 인스턴스를 가지며 독립적으로 관리합니다.
  - **속성** (엔터티의 특징): ISBN(도서의 속성), 제목(도서의 속성), 정가(도서의 속성), 배송지 주소(주문의 속성)
  - ③과 ④는 속성인 ISBN, 정가, 배송지 주소를 엔터티로 잘못 분류했습니다.
  - 출판사는 별도로 출판사명, 연락처 등을 관리해야 하므로 엔터티입니다.
</Callout>

## 유형 4. 식별자 선택 — 후보키와 기본키

**핵심 개념**

| 용어 | 설명 |
|------|------|
| 후보키(Candidate Key) | 유일성 + 최소성을 만족하는 속성(집합) |
| 기본키(Primary Key) | 후보키 중 대표로 선택된 키, NULL 불가 |
| 대체키(Alternate Key) | 후보키 중 기본키로 선택되지 않은 나머지 |
| 외래키(Foreign Key) | 다른 테이블의 기본키를 참조하는 속성 |

---

**[예제 4-1]** 다음 테이블에서 후보키가 될 수 있는 것을 모두 고른 것은?

```
직원(직원번호, 주민등록번호, 이름, 부서코드, 이메일)
```

조건:
- 직원번호는 회사가 부여한 고유 번호로 중복 없음
- 주민등록번호는 개인마다 고유함
- 이메일은 직원마다 고유하게 등록함
- 이름과 부서코드는 중복될 수 있음

1. 직원번호
2. 직원번호, 주민등록번호
3. 직원번호, 주민등록번호, 이메일
4. 직원번호, 이름

<Callout type="success">
  **정답: 3번**

  후보키가 되려면 ① 유일성(모든 행에서 값이 다름)과 ② 최소성(더 이상 속성을 줄일 수 없음)을 모두 만족해야 합니다.

  - 직원번호 → 유일, 단독으로 최소성 만족 → **후보키 O**
  - 주민등록번호 → 유일, 단독으로 최소성 만족 → **후보키 O**
  - 이메일 → 고유하게 등록되므로 유일, 단독 최소성 만족 → **후보키 O**
  - 이름 → 중복 가능 → 후보키 X
  - (직원번호, 주민등록번호) 조합은 유일하지만 각각이 이미 후보키이므로 최소성 위반 → 후보키 X

  따라서 후보키: 직원번호, 주민등록번호, 이메일 → 정답 3번.
</Callout>

---

**[예제 4-2]** 주민등록번호가 후보키인데도 기본키로 선택하지 않는 이유로 가장 적절한 것은?

1. 주민등록번호는 유일성을 만족하지 않기 때문이다.
2. 주민등록번호는 개인정보 보호 관점에서 노출 위험이 있고 변경 가능성이 있기 때문이다.
3. 주민등록번호는 숫자가 너무 길어 인덱스 성능이 떨어지기 때문이다.
4. 주민등록번호는 외래키로 사용할 수 없기 때문이다.

<Callout type="success">
  **정답: 2번**

  기본키 선택 기준: 유일성·최소성·안정성·단순성·친숙성을 고려합니다. 주민등록번호는 유일하지만 **개인정보 보호법상 불필요한 수집 제한**, **외부 기관에 의해 부여되는 식별자로 변경 가능성** 존재, **시스템 간 공유 시 보안 위험** 등의 이유로 실무에서 기본키로 잘 사용하지 않습니다. 대신 내부적으로 생성한 대리키(Surrogate Key)를 기본키로 사용하는 것이 일반적입니다.
</Callout>

## 유형 5. 함수 종속 — 부분 vs 완전 함수 종속

**핵심 구분**

| 구분 | 설명 | 예시 |
|------|------|------|
| 완전 함수 종속 | 기본키 전체가 있어야 결정 | (학번, 과목코드) → 성적 |
| 부분 함수 종속 | 기본키 일부만으로 결정 가능 | 학번 → 학생이름 |
| 이행 함수 종속 | A→B, B→C이면 A→C | 학번→부서코드, 부서코드→부서명 → 학번→부서명 |

---

**[예제 5-1]** 다음 중 이행 함수 종속(Transitive Functional Dependency)에 해당하는 것은?

```
주문(주문번호, 고객번호, 고객등급, 상품코드, 수량)
- 주문번호 → 고객번호
- 고객번호 → 고객등급
- 주문번호 → 상품코드
- (주문번호, 상품코드) → 수량
```

1. 주문번호 → 상품코드
2. 주문번호 → 고객등급
3. (주문번호, 상품코드) → 수량
4. 고객번호 → 고객등급

<Callout type="success">
  **정답: 2번**

  이행 함수 종속은 A → B이고 B → C일 때 A → C가 성립하는 경우입니다.
  - 주문번호 → 고객번호 (직접 종속)
  - 고객번호 → 고객등급 (직접 종속)
  - 따라서 **주문번호 → 고객등급** 은 이행 함수 종속입니다.

  이를 해결하려면 고객 테이블(고객번호, 고객등급)을 분리하고 주문 테이블에서 고객등급을 제거해야 합니다(3NF로 변환).
</Callout>

## 유형 6. 반정규화 — 필요 상황 판단

반정규화는 성능 향상을 위해 의도적으로 정규화 규칙을 어기는 것입니다. 조회 성능은 올라가지만 데이터 무결성 관리 비용이 증가합니다.

**반정규화가 필요한 대표 상황**

1. 조회 빈도가 매우 높고 JOIN이 복잡한 경우
2. 집계(합계, 평균) 값을 매번 계산하는 비용이 높은 경우
3. 이력 데이터를 별도로 관리해야 하는 경우

---

**[예제 6-1]** 다음 상황에서 반정규화가 가장 적합한 경우는?

1. 신규 회원가입 처리 시스템에서 INSERT 성능이 중요한 상황
2. 일별 매출 합계를 실시간으로 제공해야 하는데 주문 테이블에 수백만 건이 있어 매번 SUM을 계산하면 응답이 5초를 초과하는 상황
3. 개인정보 보호를 위해 민감 정보를 별도 테이블로 분리해야 하는 상황
4. 여러 테이블에 분산된 데이터를 정확하게 관리하기 위해 트랜잭션 무결성이 중요한 상황

<Callout type="success">
  **정답: 2번**

  반정규화의 핵심 목적은 **조회 성능 향상**입니다. ②처럼 집계 연산이 매우 느리고 조회 빈도가 높다면, 매출_합계 컬럼을 별도로 관리(컬럼 반정규화 또는 집계 테이블 추가)하는 것이 적합합니다.

  - ①: INSERT 성능 문제는 반정규화로 해결하지 않음(인덱스 조정 등으로 접근)
  - ③: 분리는 정규화 방향 → 반정규화의 반대
  - ④: 무결성 중시 시스템에서는 반정규화를 피해야 함
</Callout>

**[예제 6-2]** 다음 반정규화 기법 중 "테이블 반정규화"에 해당하는 것은?

1. 자주 사용되는 계산 값을 컬럼으로 추가한다.
2. 조회 조건으로 자주 사용되는 컬럼을 다른 테이블에 중복 저장한다.
3. 두 개의 테이블을 하나로 합친다.
4. 긴 문자열 컬럼을 별도 테이블로 분리한다.

<Callout type="success">
  **정답: 3번**

  반정규화 기법 분류:
  - **테이블 반정규화**: 테이블 병합(두 테이블을 하나로), 테이블 분할, 중복 테이블 추가 → ③번
  - **컬럼 반정규화**: 중복 컬럼 추가(①②), 파생 컬럼 추가(계산 값 저장)
  - ④ 분리는 수직 분할(정규화 방향에 가까움)로 반정규화 기법 중 수직 분할에 해당하나, 일반적으로 반정규화는 "합치는" 방향임에 주의
</Callout>
