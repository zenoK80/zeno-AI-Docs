## 이번 편의 목표

- 데이터 모델링을 "테이블 그리기"보다 넓은 과정으로 설명한다.
- 업무 문장에서 엔터티, 속성, 관계 후보를 찾는다.
- 주문과 상품 사이에 주문상세가 필요한 이유를 설명한다.
- 좋은 모델의 기준과 모델링 시 주의점을 적용한다.

## 코딩 전에 업무 규칙을 그리는 이유

쇼핑몰 요구사항이 다음 한 문장뿐이라고 하자.

> 회원은 상품을 주문할 수 있다.

바로 테이블을 만들기에는 모르는 것이 많다.

- 회원 한 명이 주문을 여러 번 할 수 있는가?
- 주문 하나에 상품이 여러 개 들어갈 수 있는가?
- 주문 당시 가격은 현재 상품 가격과 따로 보관해야 하는가?
- 회원 탈퇴 후 주문 이력은 남겨야 하는가?

**데이터 모델링(data modeling)** 은 업무에 필요한 데이터와 규칙을 발견하고, 관계자들이 이해할 수 있는 구조로 표현한 뒤, 데이터베이스로 구현할 수 있게 구체화하는 과정이다.

<Callout type="important">
  모델링의 첫 결과는 테이블이 아니라 업무에 대한 합의다. 같은 용어를 서로 다르게 이해한 채 테이블부터 만들면 나중에 더 큰 수정 비용이 생긴다.
</Callout>

## 모델링에서 찾는 네 가지

### 엔터티

업무에서 독립적으로 식별하고 관리할 대상이다. 회원, 상품, 주문처럼 사람·물건뿐 아니라 사건도 엔터티가 된다.

### 속성

엔터티를 설명하는 값이다. 회원의 이름, 상품의 가격, 주문의 주문일시가 속성이다.

### 관계

엔터티 사이의 업무 연결이다. "회원이 주문한다", "주문에 상품이 포함된다"가 관계다.

### 식별자

각 인스턴스를 다른 것과 구분하는 값이다. 회원번호와 주문번호가 예다.

| 업무 문장 | 모델 후보 |
| --- | --- |
| 회원은 여러 주문을 할 수 있다 | 회원, 주문, 1:N 관계 |
| 상품은 상품번호와 이름, 현재 가격을 가진다 | 상품 엔터티와 세 속성 |
| 주문할 때 수량과 판매가격을 기록한다 | 주문상세 엔터티의 속성 후보 |

## 요구사항에서 모델을 만드는 과정

다음 요구사항을 계속 사용한다.

> 회원은 여러 주문을 할 수 있다. 주문 하나에는 여러 상품이 담길 수 있다. 같은 상품도 여러 주문에 담길 수 있다. 주문 시점의 수량과 판매가격을 보존한다.

<Steps>

### 명사와 사건을 표시한다

회원, 주문, 상품은 독립적으로 관리할 후보며 주문은 발생하는 사건이다.

### 각 후보의 식별자를 찾는다

회원번호, 주문번호, 상품번호처럼 한 대상을 유일하게 구분할 값을 정한다.

### 관계의 수를 읽는다

회원 한 명은 주문 여러 건과 연결되므로 1:N이다. 주문과 상품은 서로 여러 건과 연결되므로 N:M이다.

### 관계에 속한 정보를 찾는다

수량과 주문 당시 판매가격은 상품 하나만으로 결정되지 않고 특정 주문과 상품의 조합에서 결정된다.

### 연결 엔터티로 N:M을 해소한다

주문과 상품 사이에 `주문상세`를 두어 두 개의 1:N 관계로 바꾼다.

</Steps>

```text
회원 1 ─── N 주문 1 ─── N 주문상세 N ─── 1 상품

회원: 회원번호, 이름, 연락처
주문: 주문번호, 주문일시, 주문상태, 회원번호
상품: 상품번호, 상품명, 현재가격
주문상세: 주문번호, 상품번호, 수량, 주문가격
```

## 주문가격은 왜 상품에 두지 않을까

상품의 현재가격이 10,000원에서 12,000원으로 바뀌어도 지난 주문 영수증은 10,000원을 보여야 한다. 주문 당시의 가격은 상품의 현재 상태가 아니라 **거래 당시 사실**이므로 주문상세에 보관한다.

이 예는 속성의 위치를 판단하는 좋은 질문을 준다.

> 이 값은 어떤 대상을 하나 정하면 결정되는가?

- 상품 하나를 정하면 현재가격이 결정된다 → 상품 속성
- 주문과 상품을 함께 정해야 주문가격이 결정된다 → 주문상세 속성

## 데이터 모델링의 세 가지 관점

### 데이터 관점

무엇을 저장하며 데이터 사이에 어떤 관계가 있는지 본다.

### 프로세스 관점

업무가 데이터를 어떻게 생성·조회·변경하는지 본다. 주문 취소가 재고와 결제 상태에 어떤 변화를 만드는지가 예다.

### 데이터와 프로세스의 상관 관점

각 프로세스가 어떤 데이터를 어떤 방식으로 다루는지 함께 본다. 모델에 데이터는 있는데 이를 생성하는 업무가 없거나, 업무에 필요한 데이터가 모델에 없다면 누락을 의심한다.

## 좋은 모델의 기준

- **완전성**: 필요한 업무 규칙과 데이터가 빠지지 않는다.
- **중복 배제**: 같은 사실을 불필요하게 여러 곳에 저장하지 않는다.
- **업무 규칙 표현**: 필수 여부, 유일성, 관계 수를 드러낸다.
- **이해 가능성**: 이름과 정의가 일관되어 관계자가 같은 뜻으로 읽는다.
- **확장 가능성**: 예상 가능한 업무 변화에 과도한 수정 없이 대응한다.

## 모델링할 때 피해야 할 일

### 중복

같은 회원 연락처를 회원과 모든 주문에 저장하면 변경 시 불일치가 생긴다.

### 비유연성

현재 화면 하나만 그대로 테이블로 만들면 화면이 바뀔 때 데이터 구조도 함께 흔들린다. 업무의 본질적 대상을 모델링한다.

### 비일관성

`고객`, `회원`, `사용자`를 같은 뜻으로 섞어 쓰면 관계자가 서로 다르게 해석한다. 표준 용어와 정의를 관리한다.

## 시험형 선지 분석

1. "데이터 모델링은 물리 테이블과 인덱스를 결정하는 단계만을 뜻한다." → 거짓. 개념·논리·물리 수준을 포함한다.
2. "관계에 속성이 존재하면 연결 엔터티를 검토할 수 있다." → 참.
3. "화면의 입력 항목은 모두 하나의 엔터티 속성이다." → 거짓. 화면은 여러 엔터티의 값을 함께 보여 줄 수 있다.
4. "좋은 모델은 업무 규칙을 데이터 구조와 제약으로 표현한다." → 참.

<Callout type="default">
  - 데이터 모델링은 업무 요구를 데이터와 규칙의 구조로 바꾸는 과정이다.
  - 엔터티, 속성, 관계, 식별자를 함께 찾아야 한다.
