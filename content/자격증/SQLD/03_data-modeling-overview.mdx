## 데이터 모델링은 무엇일까?

데이터 모델링은 업무에서 필요한 정보를 정리해, **저장하고 조회할 수 있는 구조와 규칙**으로 표현하는 작업입니다. SQL을 작성하기 전에 "무엇을 저장해야 하고, 서로 어떻게 연결되는가"를 먼저 합의하는 과정이라고 생각하면 됩니다.

예를 들어 쇼핑몰에 주문 기능을 만든다고 해 봅시다. 주문한 사람은 누구인지, 한 주문에 상품이 몇 개 들어가는지, 주문 당시 수량과 가격은 어디에 남기는지부터 정해야 합니다. 이런 질문의 답을 구조로 옮기는 일이 데이터 모델링입니다.

<Callout type="info">
  데이터 모델은 데이터베이스 관리자만 보는 설계도가 아닙니다. 기획자, 개발자, 분석가가 같은 업무 규칙을 확인하는 공통 언어입니다.
</Callout>

## 왜 SQLD에서 먼저 배울까?

잘못 모델링한 구조에서는 SQL 문법이 맞아도 원하는 결과가 나오지 않거나, 같은 정보가 여러 곳에 반복되어 수정 오류가 생깁니다. 반대로 모델이 명확하면 필요한 조인과 조건을 자연스럽게 떠올릴 수 있습니다.

| 상황 | 모델링 없이 시작 | 모델링 후 시작 |
| --- | --- | --- |
| 주문 상품 저장 | 주문 행에 상품을 하나만 넣기 쉽다 | 주문과 주문상세를 분리한다 |
| 회원 이름 변경 | 과거 주문 행을 모두 수정할 수 있다 | 회원 정보는 회원에서 한 번 관리한다 |
| 분석 질문 추가 | 컬럼 의미를 다시 해석해야 한다 | 엔터티와 관계를 기준으로 찾는다 |

## 요구사항을 모델로 바꾸는 흐름

<Steps>

### 업무 문장을 모은다

"회원은 여러 주문을 할 수 있다", "주문 하나에는 여러 상품이 담긴다"처럼 주어와 행동이 있는 문장을 적습니다.

### 관리할 대상을 찾는다

독립적으로 구분하고 관리해야 하는 대상을 후보로 뽑습니다. 위 예시에서는 회원, 주문, 상품이 후보입니다.

### 각 대상의 정보를 분리한다

회원에는 회원 번호와 이름, 상품에는 상품 번호와 상품명처럼 각 대상에만 속하는 정보를 붙입니다.

### 연결 규칙을 확인한다

회원 한 명과 주문 여러 건은 1:N 관계입니다. 주문과 상품은 서로 여러 건이 연결되므로 주문상세 같은 연결 대상을 추가해야 합니다.

### 식별자와 업무 규칙을 적는다

각 행을 구분하는 값, 필수 여부, 중복 가능 여부를 정합니다. 이 규칙이 이후 키와 제약조건의 근거가 됩니다.

</Steps>

## 작은 사례로 연습하기

다음 요구사항을 읽고 모델 후보를 찾아 보세요.

> 회원은 여러 번 주문할 수 있다. 주문에는 한 개 이상의 상품이 포함된다. 같은 상품도 서로 다른 주문에 포함될 수 있다. 주문할 때 수량을 기록한다.

처음에는 회원, 주문, 상품 세 개만 떠오를 수 있습니다. 하지만 주문과 상품의 관계는 N:M입니다. 이 관계 자체에 `수량`이라는 정보가 붙으므로, 다음처럼 **주문상세**를 별도 대상으로 두는 것이 자연스럽습니다.

```text
회원 1명  ---  여러 주문
주문 1건  ---  여러 주문상세
상품 1개  ---  여러 주문상세
```

`수량`은 상품의 속성이 아닙니다. 같은 상품이라도 주문마다 수량이 달라지므로 주문상세에 두어야 합니다. "어느 문맥에서 값이 결정되는가"를 묻는 습관이 모델링의 핵심입니다.

## 자주 하는 혼동

### 테이블부터 만들기

테이블 이름과 자료형을 먼저 정하면 업무 규칙이 뒤늦게 따라붙기 쉽습니다. 개념과 관계를 먼저 정하고 물리적인 테이블 설계로 내려가는 편이 안전합니다.

### 화면 하나를 엔터티 하나로 보기

주문 화면에 회원 이름과 상품명이 보인다고 해서 모든 값을 주문에 저장할 필요는 없습니다. 화면은 여러 데이터를 함께 보여 주는 결과일 수 있습니다.

### 관계에 필요한 정보를 놓치기

주문-상품 사이의 수량, 수강신청-과목 사이의 성적처럼 관계에서 결정되는 값은 별도 연결 엔터티가 필요한 신호입니다.

## 이번 편 정리

- 데이터 모델링은 업무 요구를 데이터 구조와 규칙으로 표현하는 과정이다.
- 요구사항에서 관리 대상, 속성, 관계, 식별자 순서로 찾아간다.
- N:M 관계에 업무 정보가 붙으면 연결 엔터티를 검토한다.

다음 편에서는 데이터 모델을 개념, 논리, 물리 수준으로 나누어 보겠습니다.
