## 이번 편의 목표

- 논리 모델의 관계, 물리 모델의 외래키와 SQL JOIN의 역할을 구분한다.
- PK와 FK를 사용해 올바른 조인 조건을 작성한다.
- 1:N과 M:N 관계에서 조인 결과의 행 수를 예측한다.
- INNER JOIN과 LEFT JOIN의 결과 차이와 잘못된 조인 조건을 진단한다.

## 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| 조인 | 여러 테이블의 관련 행을 조건에 따라 한 결과로 연결하는 연산 |
| 조인 조건 | 어떤 열의 값이 서로 맞을 때 행을 연결할지 정한 식 |
| 내부 조인 | 양쪽에서 조건에 맞는 행만 반환하는 조인 |
| 외부 조인 | 조건에 맞지 않아도 기준 쪽 행을 남기는 조인 |
| 기준 테이블 | LEFT JOIN에서 결과에 모두 남기려는 왼쪽 테이블 |
| 카테시안 곱 | 모든 왼쪽 행과 모든 오른쪽 행이 조합된 결과 |
| 참조 무결성 | 외래키값이 실제 부모 행을 가리키도록 유지하는 규칙 |
| NULL 확장 | 외부 조인에서 짝이 없는 쪽 열을 NULL로 채우는 것 |

## 선수지식과 핵심 질문

앞에서 회원 1 : N 주문, 주문 1 : N 주문상세, 상품 1 : N 주문상세 관계를 만들고 각 엔터티에 식별자를 정했다. 정규화로 테이블도 분리했다.

이번 편의 질문은 이것이다.

> 나누어 저장한 회원·주문·상품 정보를 한 주문 목록 화면에서 어떻게 다시 함께 볼까?

## 관계, 외래키와 JOIN은 이어지지만 다르다

세 용어는 서로 다른 단계에 있다.

| 단계 | 표현 | 역할 |
| --- | --- | --- |
| 논리 모델 | 회원 1 : N 주문 | 업무에서 누가 무엇과 연결되는지 정의 |
| 물리 모델 | `orders.member_id` FK | 존재하지 않는 회원을 주문이 참조하지 못하게 함 |
| SQL 조회 | `members JOIN orders` | 분리된 행을 필요한 결과로 결합 |

```text
업무 규칙
주문은 반드시 회원 한 명에 속한다.

논리 관계
회원 1 ─── N 주문

물리 구현
orders.member_id → members.member_id

조회
members.member_id = orders.member_id인 행끼리 연결
```

<Callout type="important">
  외래키를 선언하지 않았어도 값이 맞으면 SQL 조인은 실행할 수 있다. 하지만 외래키가 없으면 잘못된 회원번호가 저장되는 것을 DBMS가 막지 못한다. 조인 가능 여부와 참조 무결성 보장은 다른 문제다.
</Callout>

## 예제 데이터 준비

앞 편과 같은 쇼핑몰 데이터를 사용한다.

### 회원

| member_id | member_name |
| --- | --- |
| M01 | 민지 |
| M02 | 준호 |
| M03 | 소라 |

### 주문

| order_id | member_id | order_status |
| --- | --- | --- |
| 1001 | M01 | PAID |
| 1002 | M01 | SHIPPED |
| 1003 | M02 | PAID |

### 상품

| product_id | product_name |
| --- | --- |
| P10 | 키보드 |
| P20 | 마우스 |
| P30 | 모니터 |
| P40 | 헤드셋 |

### 주문상세

| order_id | product_id | quantity | unit_price |
| --- | --- | ---: | ---: |
| 1001 | P10 | 1 | 50000 |
| 1001 | P20 | 2 | 28000 |
| 1002 | P20 | 1 | 30000 |
| 1003 | P30 | 1 | 250000 |

회원 M03은 아직 주문이 없고 상품 P40도 아직 주문되지 않았다. 이 두 행이 INNER JOIN과 OUTER JOIN의 차이를 보여준다.

## INNER JOIN: 양쪽에 짝이 있는 행만

회원 이름과 주문번호를 함께 조회한다.

```sql
SELECT m.member_id,
       m.member_name,
       o.order_id,
       o.order_status
FROM members AS m
JOIN orders AS o
  ON o.member_id = m.member_id;
```

`JOIN`만 쓰면 일반적으로 `INNER JOIN`과 같다. `ON` 뒤에는 회원 PK와 주문 FK가 같은지를 적었다.

| member_id | member_name | order_id | order_status |
| --- | --- | ---: | --- |
| M01 | 민지 | 1001 | PAID |
| M01 | 민지 | 1002 | SHIPPED |
| M02 | 준호 | 1003 | PAID |

M03 소라는 주문이 없으므로 결과에 나오지 않는다.

## 1:N 조인에서는 1쪽 행이 반복된다

회원 M01은 주문 두 건과 연결된다. 조인 결과에서는 민지의 회원 정보가 주문마다 한 번씩 나타난다.

```text
회원 M01 한 행
  ├─ 주문 1001
  └─ 주문 1002

JOIN 결과
  M01 + 1001
  M01 + 1002
```

이것은 데이터 중복 저장이 아니라 조회 결과에서 관계를 펼친 것이다. 1:N 관계를 조인하면 결과의 기본 행 단위는 대체로 N쪽이 된다.

<Callout type="info">
  조인 후 행 수가 늘었다고 무조건 중복 오류가 아니다. 원래 관계가 1:N인지, 결과 한 행이 회원인지 주문인지 먼저 확인한다.
</Callout>

## LEFT JOIN: 왼쪽 행은 모두 남긴다

주문하지 않은 회원까지 보고 싶다면 회원을 왼쪽 기준으로 둔다.

```sql
SELECT m.member_id,
       m.member_name,
       o.order_id
FROM members AS m
LEFT JOIN orders AS o
  ON o.member_id = m.member_id;
```

| member_id | member_name | order_id |
| --- | --- | ---: |
| M01 | 민지 | 1001 |
| M01 | 민지 | 1002 |
| M02 | 준호 | 1003 |
| M03 | 소라 | NULL |

소라와 일치하는 주문은 없지만 왼쪽 회원 행은 남고 주문 열이 NULL로 채워진다.

### 주문이 없는 회원 찾기

```sql
SELECT m.member_id,
       m.member_name
FROM members AS m
LEFT JOIN orders AS o
  ON o.member_id = m.member_id
WHERE o.order_id IS NULL;
```

LEFT JOIN으로 모든 회원을 남긴 뒤 오른쪽 주문 식별자가 NULL인 행만 고른다.

## LEFT JOIN의 조건 위치를 조심한다

배송 완료 주문이 있는지 보되 회원은 모두 남기고 싶다고 하자.

```sql
SELECT m.member_name,
       o.order_id
FROM members AS m
LEFT JOIN orders AS o
  ON o.member_id = m.member_id
 AND o.order_status = 'SHIPPED';
```

주문 상태 조건을 `ON`에 두면 배송 완료 주문이 없는 회원도 NULL과 함께 남는다.

```sql
SELECT m.member_name,
       o.order_id
FROM members AS m
LEFT JOIN orders AS o
  ON o.member_id = m.member_id
WHERE o.order_status = 'SHIPPED';
```

두 번째 쿼리는 조인 후 `WHERE`에서 NULL 행을 제거하므로 결과상 주문이 있는 회원만 남을 수 있다. 외부 조인에서 오른쪽 테이블 조건을 어디에 두는지는 결과 보존 범위를 바꾼다.

## M:N 관계는 연결 테이블을 거쳐 조인한다

주문과 상품은 주문상세를 통해 연결된다.

```sql
SELECT o.order_id,
       p.product_name,
       oi.quantity,
       oi.unit_price,
       oi.quantity * oi.unit_price AS line_amount
FROM orders AS o
JOIN order_items AS oi
  ON oi.order_id = o.order_id
JOIN products AS p
  ON p.product_id = oi.product_id
ORDER BY o.order_id, p.product_id;
```

| order_id | product_name | quantity | unit_price | line_amount |
| ---: | --- | ---: | ---: | ---: |
| 1001 | 키보드 | 1 | 50000 | 50000 |
| 1001 | 마우스 | 2 | 28000 | 56000 |
| 1002 | 마우스 | 1 | 30000 | 30000 |
| 1003 | 모니터 | 1 | 250000 | 250000 |

결과 한 행은 주문 전체가 아니라 **주문에 포함된 상품 한 종류**, 즉 주문상세 인스턴스 하나를 나타낸다.

## 올바른 조인 조건은 키 관계에서 찾는다

다음 조건은 잘못됐다.

```sql
-- 이름이 같다고 같은 회원이라는 보장이 없음
ON m.member_name = o.orderer_name

-- 서로 의미가 다른 식별자를 비교
ON m.member_id = o.order_id
```

일반적으로 부모 PK와 자식 FK처럼 같은 업무 의미와 도메인을 가진 열을 연결한다.

```sql
ON m.member_id = o.member_id
```

복합키를 참조한다면 조인 조건도 구성 열을 빠뜨리지 않아야 한다.

```sql
ON child.tenant_id = parent.tenant_id
AND child.user_id = parent.user_id
```

## 조인 조건을 빠뜨리면 카테시안 곱이 생긴다

회원 3행과 주문 3행을 조건 없이 결합하면 최대 `3 × 3 = 9행`이 나온다.

```sql
SELECT *
FROM members AS m
CROSS JOIN orders AS o;
```

`CROSS JOIN`은 모든 조합이 필요할 때 의도적으로 사용한다. 그러나 일반 JOIN에서 연결 조건을 빠뜨려 예상보다 행이 폭증하면 먼저 조인 조건을 확인한다.

```text
예상: 주문 3건에 회원 이름 붙이기 → 3행
실제: 회원 3 × 주문 3 → 9행
진단: 회원번호 조인 조건이 누락되었는가?
```

## 조인 결과 행 수를 예측하는 순서

<Steps>

### 결과 한 행의 의미를 정한다

회원 한 명인지, 주문 한 건인지, 주문상품 한 건인지 정한다.

### 관계의 카디널리티를 확인한다

1:1, 1:N, M:N 중 어떤 관계를 펼치는지 본다.

### 조인 종류를 확인한다

INNER JOIN이면 짝 없는 행이 제외되고 LEFT JOIN이면 왼쪽 행이 보존된다.

### 조인 조건의 유일성을 확인한다

PK-FK가 아닌 비유일 열을 연결하면 예상보다 여러 행이 매칭될 수 있다.

### WHERE 조건을 마지막에 적용한다

외부 조인으로 남긴 NULL 행이 WHERE에서 다시 제거되는지 확인한다.

</Steps>

## 관계와 참조 무결성

외래키는 조인 결과를 자동으로 만들어 주지는 않지만 관계 데이터의 품질을 지킨다.

```sql
ALTER TABLE orders
ADD CONSTRAINT orders_member_fk
FOREIGN KEY (member_id)
REFERENCES members(member_id);
```

이 제약이 있으면 존재하지 않는 회원번호를 가진 주문을 저장할 수 없다. 따라서 회원-주문 조인에서 잘못된 고아 주문이 생기는 것을 막는다.

## 흔한 실수와 진단법

| 실수 | 결과 | 진단법 |
| --- | --- | --- |
| 조인 조건 누락 | 모든 조합으로 행 폭증 | 각 JOIN마다 ON 조건이 있는지 확인 |
| 이름 같은 비유일 열로 조인 | 동명이인 등 잘못된 다중 매칭 | PK-FK 관계를 찾음 |
| 1:N 조인 결과를 중복 오류로 오해 | 정상 결과를 잘못 제거 | 결과 한 행의 의미를 정의 |
| LEFT JOIN 후 오른쪽 조건을 WHERE에 둠 | NULL 보존 행이 제거됨 | ON과 WHERE의 역할 비교 |
| 복합키 일부만 조인 | 다른 부모 행까지 잘못 연결 | 참조 키의 모든 열을 조건에 포함 |

## 시험 연결

1. 관계는 업무 규칙, 외래키는 무결성 제약, 조인은 조회 연산이다.
2. INNER JOIN은 양쪽에 일치하는 행만, LEFT JOIN은 왼쪽 행을 모두 보존한다.
3. 1:N 관계를 조인하면 1쪽 행이 N쪽 행마다 반복될 수 있다.
4. M:N 관계는 연결 테이블을 거쳐 조인하며 결과 한 행의 기준이 연결 엔터티가 될 수 있다.
5. 조인 조건 누락이나 비유일 열 조인은 예상보다 많은 결과를 만든다.

## 짧은 확인

상품 P40 헤드셋은 주문된 적이 없다. 모든 상품과 주문 횟수를 함께 보려면 어느 테이블을 왼쪽에 두고 어떤 조인을 사용해야 할까?

<Collapse title="확인하기">

상품을 왼쪽에 두고 주문상세를 `LEFT JOIN`한다. 주문 횟수는 `COUNT(oi.order_id)`처럼 오른쪽의 실제 값이 있는 열을 세어야 주문 없는 상품이 0으로 계산된다.

</Collapse>

## 정리

<Callout type="default">
  - 논리 관계는 외래키로 구현되고 SQL JOIN으로 조회 결과에 펼쳐진다.
  - 올바른 조인 조건은 같은 업무 의미를 가진 PK와 FK에서 찾는다.
  - 1:N 조인에서는 1쪽 정보가 N쪽 행마다 반복되는 것이 정상이다.
  - INNER JOIN과 LEFT JOIN은 짝 없는 행을 보존하는 방식이 다르다.
  - 조인 결과가 예상과 다르면 카디널리티, 조건 누락, 조건 위치를 순서대로 점검한다.
</Callout>
