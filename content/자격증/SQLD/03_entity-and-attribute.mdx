## 엔터티(Entity)란?

**엔터티**(Entity)는 업무에서 관리해야 할 **정보의 대상**입니다. 현실 세계에서 독립적으로 존재하며, 데이터로 저장할 가치가 있는 것들입니다.

쉽게 말하면 "테이블이 될 대상"이라고 생각하면 됩니다.

### 엔터티가 되려면?

엔터티가 되기 위한 조건은 4가지입니다.

1. **업무에서 관리해야 할 정보여야 한다**: 업무와 관련 없는 데이터는 엔터티가 아닙니다
2. **두 개 이상의 속성을 가져야 한다**: 속성이 하나뿐이면 독립 엔터티로 의미가 없습니다
3. **두 개 이상의 인스턴스**(행)**가 있어야 한다**: 데이터가 항상 한 건뿐이라면 엔터티로 만들 필요가 없습니다
4. **다른 엔터티와 최소 하나의 관계를 가져야 한다**: 완전히 고립된 엔터티는 존재 의미가 없습니다

## 엔터티의 유형: 발생 시점 기준

엔터티는 언제 발생하는지에 따라 **기본**(키) **엔터티**, **중심 엔터티**, **행위 엔터티** 세 가지로 나뉩니다.

| 유형 | 특징 | 예시 |
|------|------|------|
| **기본**(키) **엔터티** | 독립적으로 존재. 다른 엔터티에 의존하지 않음 | 고객, 직원, 상품, 부서 |
| **중심 엔터티** | 기본 엔터티로부터 발생. 업무의 핵심 | 주문, 계약, 신청서 |
| **행위 엔터티** | 두 개 이상의 엔터티가 활동하여 발생 | 주문상품, 수강내역, 결제이력 |

**발생 순서:** 고객·상품(기본) → 주문(고객이 있어야 발생) → 주문상품(주문과 상품이 만나야 발생)

- **고객**과 **상품**은 독립적으로 존재합니다 → 기본 엔터티
- **주문**은 고객이 있어야 발생합니다 → 중심 엔터티
- **주문상품**은 주문과 상품 두 엔터티가 연결될 때 발생합니다 → 행위 엔터티

## 엔터티의 유형: 유형/무형 기준

또 다른 분류 기준은 **실체가 있는지 여부**입니다.

| 유형 | 설명 | 예시 |
|------|------|------|
| **유형 엔터티** | 물리적으로 실존하는 대상 | 직원, 상품, 창고 |
| **개념 엔터티** | 개념적으로 존재하는 대상 | 조직, 계좌, 보험상품 |
| **사건 엔터티** | 업무 활동으로 발생하는 대상 | 주문, 입출금, 수강신청 |

## 속성(Attribute)이란?

**속성**(Attribute)은 엔터티가 가지는 특성이나 성질입니다. 테이블에서는 **열**(Column)에 해당합니다.

예를 들어 **고객** 엔터티의 속성은 고객번호, 이름, 이메일, 가입일, 등급 등입니다.

### 속성이 되기 위한 조건

- 해당 엔터티를 설명하는 특성이어야 합니다
- 원자성을 가져야 합니다 (더 이상 쪼갤 수 없는 하나의 값)
- 업무적으로 의미 있는 값이어야 합니다

## 속성의 유형: 성격에 따른 분류

속성은 어떻게 값이 결정되는지에 따라 세 가지로 구분합니다.

### 기본 속성 (Basic Attribute)

**업무로부터 직접 도출되는 원래의 속성**입니다. 다른 속성으로부터 계산되거나 변형되지 않습니다.

예시: 이름, 생년월일, 주소, 전화번호, 입사일

### 설계 속성 (Designed Attribute)

**업무 필요에 의해 새로 만들어진 속성**입니다. 원래 업무에는 없었지만, 데이터 관리를 위해 설계 과정에서 추가됩니다.

예시:
- **고객번호**: 원래 사람에게 번호가 없지만, DB 관리를 위해 생성
- **주문번호**: 주문에 식별자를 부여하기 위해 설계
- **코드값**: 'M/F' 대신 '1/2'를 사용하는 성별 코드

### 파생 속성 (Derived Attribute)

**다른 속성의 값으로부터 계산되어 나오는 속성**입니다. 원칙적으로는 저장하지 않아도 되지만, 성능 등의 이유로 저장하기도 합니다.

| 파생 속성 | 원본 속성 | 계산 방법 |
|-----------|-----------|-----------|
| 나이 | 생년월일 | 현재 날짜 - 생년월일 |
| 주문금액 합계 | 단가 × 수량 | SUM(단가 × 수량) |
| 재직기간 | 입사일 | 현재 날짜 - 입사일 |
| 할인후가격 | 정가, 할인율 | 정가 × (1 - 할인율) |

<Callout type="warning">
  파생 속성은 원본 속성이 바뀌면 파생 속성도 변경되어야 합니다. 저장된 파생 속성의 값이 원본과 불일치하면 데이터 불일치 문제가 생깁니다. SQLD에서 파생 속성의 문제점을 묻는 문제가 자주 출제됩니다.
</Callout>

### 속성 유형 종합 예시 - 직원 엔터티

```
직원 엔터티의 속성들:

기본 속성: 이름, 생년월일, 주소, 연락처
설계 속성: 직원번호(PK), 부서코드, 직급코드
파생 속성: 나이(생년월일에서 계산), 근속년수(입사일에서 계산)
```

## 도메인(Domain)이란?

**도메인**(Domain)은 속성이 가질 수 있는 **값의 범위**(집합)입니다. 어떤 속성에 어떤 값이 들어올 수 있는지를 정의합니다.

### 도메인을 정의하는 이유

도메인을 명확히 정의하면 **잘못된 데이터 입력을 방지**할 수 있습니다.

| 속성 | 도메인 정의 |
|------|------------|
| 성별 | 'M' 또는 'F' (다른 값 불가) |
| 등급 | 'GOLD', 'SILVER', 'BRONZE' 중 하나 |
| 나이 | 0 이상 150 이하의 정수 |
| 이메일 | '@'를 포함하는 문자열 |
| 가입일 | 날짜 형식 (YYYY-MM-DD) |

### 도메인과 데이터 타입

물리적 모델링에서 도메인은 SQL의 데이터 타입과 제약조건으로 구현됩니다.

```sql
CREATE TABLE 고객 (
    고객번호  NUMBER(10)     NOT NULL,       -- 10자리 이내 숫자
    이름      VARCHAR2(50)   NOT NULL,       -- 최대 50자 문자열
    이메일    VARCHAR2(100),                  -- 최대 100자 문자열
    성별      CHAR(1)        CHECK (성별 IN ('M', 'F')),  -- M 또는 F만
    나이      NUMBER(3)      CHECK (나이 >= 0 AND 나이 <= 150),
    등급      VARCHAR2(10)   CHECK (등급 IN ('GOLD', 'SILVER', 'BRONZE'))
);
```

`CHECK` 제약조건이 도메인을 구현하는 방법 중 하나입니다.

## 속성의 개수와 단순/복합 속성

### 단순 속성 vs 복합 속성

**단순 속성**(Simple Attribute)은 더 이상 분해할 수 없는 속성입니다. 예) 나이, 가격, 성별

**복합 속성**(Composite Attribute)은 여러 하위 속성으로 구성된 속성입니다.
예) 주소 = 시/도 + 시/군/구 + 동/읍/면 + 상세주소

관계형 DB에서는 복합 속성을 분해하여 저장하는 것이 권장됩니다.

### 단일값 속성 vs 다중값 속성

**단일값 속성**은 하나의 값만 가집니다. 예) 생년월일, 이름

**다중값 속성**은 여러 값을 가질 수 있습니다. 예) 전화번호 (집/회사/휴대폰)

관계형 DB에서 다중값 속성은 별도 테이블로 분리해야 합니다.

```
-- 잘못된 방식 (다중값을 한 칸에)
고객: (1001, 김민준, '010-1234-5678, 02-9999-8888')

-- 올바른 방식 (별도 테이블)
고객: (1001, 김민준)
고객전화번호: (1001, '010-1234-5678', '휴대폰')
고객전화번호: (1001, '02-9999-8888', '집')
```

## 핵심 정리

- **엔터티**는 업무에서 관리해야 할 정보의 대상으로, 기본/중심/행위 엔터티로 구분된다
- **속성**은 엔터티의 특성으로, 기본/설계/파생 속성으로 구분된다
- **파생 속성**은 다른 속성으로부터 계산되며, 데이터 불일치 위험이 있다
- **도메인**은 속성이 가질 수 있는 값의 범위로, 데이터 품질을 보장한다
- 복합 속성과 다중값 속성은 분해하거나 별도 테이블로 분리해야 한다
