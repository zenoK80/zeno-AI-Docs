## 데이터 모델링의 정의 및 특징

데이터 모델링이란 현실 세계의 복잡한 비즈니스 프로세스 및 데이터 구조를 단순화하여 데이터베이스로 구축하기 위해 모델로 표현하는 과정을 말합니다[cite: 7, 39].

<Callout type="info">
**데이터 모델링의 3대 요소**
* **Things (개체)**: 업무가 관여하는 사람, 장소, 물건, 사건 등 (엔터티)
* **Attributes (속성)**: 개체가 가지는 세부적인 성격이나 특징
* **Relationships (관계)**: 개체 간에 존재하는 연관성 및 비즈니스 규칙
</Callout>

### 데이터 모델링의 주요 특징

1. **단순화 (Simplification)**: 복잡한 현실 세계를 약속된 규칙과 기호에 따라 단순하게 표현합니다.
2. **추상화 (Abstraction)**: 현실의 복잡한 현상을 일정한 양식에 맞추어 개괄적으로 종합 표현합니다.
3. **명확화 (Clarity)**: 모호함을 제거하고 누구나 이해하기 쉽고 명확하게 기술합니다.

---

## 데이터 모델링 3단계 구조

데이터 모델링은 추상화 수준에 따라 **개념적**, **논리적**, **물리적** 모델링으로 구분됩니다[cite: 7, 39].

<Steps>
### 1단계: 개념적 데이터 모델링 (Conceptual Data Modeling)
* **특징**: 가장 높은 추상화 수준의 모델링입니다.
* **주요 작업**: 전사적 관점에서 핵심 엔터티(Entity)와 그들 간의 관계(Relationship)를 정의합니다. (ERD 작성) [cite: 7]

### 2단계: 논리적 데이터 모델링 (Logical Data Modeling)
* **특징**: 특정 DBMS 제품에 독립적인 상세 모델링입니다.
* **주요 작업**: 속성, 식별자, 관계를 상세히 정의하며 **정규화(Normalization)**를 수행하여 데이터 중복을 제거합니다[cite: 7, 39].

### 3단계: 물리적 데이터 모델링 (Physical Data Modeling)
* **특징**: 실제 적용할 특정 DBMS(Oracle, MySQL, SQL Server 등) 성능과 하드웨어 특성을 고려합니다[cite: 7].
* **주요 작업**: 테이블, 컬럼, 데이터 타입, 인덱스, 반정규화(De-normalization) 및 데이터베이스 객체를 설계합니다[cite: 7, 39].
</Steps>

| 구분 | 추상화 수준 | 주요 대상 | 핵심 키워드 |
| :--- | :--- | :--- | :--- |
| **개념적 모델링** | 높음 (개괄적) | 전사적 핵심 엔터티 | 주제 영역, ERD |
| **논리적 모델링** | 중간 (상세) | 전체 엔터티, 속성, 관계 | **정규화**, 식별자, 재사용성 [cite: 7, 39] |
| **물리적 모델링** | 낮음 (구체적) | 테이블, 컬럼, 인덱스 | **DBMS 종속성**, 반정규화, 성능 [cite: 7, 39] |

## 데이터 독립성 (Data Independence)

ANSI-SPARC 3단계 구조는 데이터베이스의 내부 구조를 숨기고, 데이터 독립성을 확보하기 위해 제시된 아키텍처입니다[cite: 7, 39].

+---------------------------------------------------+
|               외부 스키마 (External Schema)        |
|  (사용자 / 응용프로그램 관점 - 여러 개 존재 가능)   |
+---------------------------------------------------+
│
[ 외부/개념 사상 (Logical Mapping) ]
│
+---------------------------------------------------+
|               개념 스키마 (Conceptual Schema)      |
|    (전합적 관점 - 전체 데이터베이스 구조 정의)     |
+---------------------------------------------------+
│
[ 개념/내부 사상 (Physical Mapping) ]
│
+---------------------------------------------------+
|               내부 스키마 (Internal Schema)        |
|    (물리적 저장 구조 관점 - 실제 Disk 저장 방식)   |
+---------------------------------------------------+


### 3단계 구조 및 독립성 유형

<Tabs items={['외부 스키마', '개념 스키마', '내부 스키마']}>
  <Tabs.Tab>
    **외부 스키마 (External Schema)**
    * 사용자나 응용프로그램 관점의 데이터베이스 구조입니다[cite: 33, 34].
    * 동일한 데이터베이스라도 서식이나 목적에 따라 여러 개의 외부 스키마가 존재할 수 있습니다[cite: 33].
  </Tabs.Tab>
  <Tabs.Tab>
    **개념 스키마 (Conceptual Schema)**
    * 데이터베이스의 전체적인 논리 구조로, 모든 응용시스템이나 사용자들이 필요로 하는 범용적 구조입니다[cite: 34, 35].
    * 엔터티, 속성, 관계, 제약조건, 보안 정책 등이 포함됩니다.
  </Tabs.Tab>
  <Tabs.Tab>
    **내부 스키마 (Internal Schema)**
    * 물리적 저장장치 관점에서 데이터가 실제로 디스크에 어떻게 저장되는지를 정의합니다[cite: 36].
    * 데이터 레코드 구조, 인덱스, 칼럼 크기, 파일 조직 등이 포함됩니다.
  </Tabs.Tab>
</Tabs>

<Callout type="warning">
**시험 단골! 2가지 데이터 독립성**
* **논리적 데이터 독립성**: **개념 스키마**가 변경되어도 **외부 스키마**에 영향을 주지 않음 (외부/개념 사상 이용) [cite: 7, 34]
* **물리적 데이터 독립성**: **내부 스키마**(저장 구조)가 변경되어도 **개념 스키마**에 영향을 주지 않음 (개념/내부 사상 이용) [cite: 7, 35, 36]
</Callout>

## 엔터티 (Entity)

엔터티란 업무상 관리하고자 하는 **대상이나 개념, 사건(Event)**의 집합을 의미합니다 (예: 고객, 주문, 상품)[cite: 7, 39].

### 엔터티의 주요 특징

1. **업무 필요성**: 반드시 대상 시스템의 비즈니스 로직에서 관리해야 하는 정보여야 합니다.
2. **유일한 식별자**: 인스턴스를 구분할 수 있는 주식별자가 존재해야 합니다[cite: 8, 39].
3. **2개 이상의 인스턴스 집합**: 엔터티 내에는 최소 2개 이상의 인스턴스(행, Row)가 존재해야 합니다.
4. **2개 이상의 속성**: 엔터티는 최소 2개 이상의 속성(열, Column)을 가져야 합니다.
5. **관계 존재**: 다른 엔터티와 최소 1개 이상의 관계를 맺어야 합니다[cite: 7, 39]. *(단, 통계성 엔터티나 공통 코드 엔터티 등은 예외일 수 있음)*

### 발생 시점에 따른 엔터티 분류

<Cards>
  <Cards.Card title="기본 엔터티 (Basic Entity)" href="#">
    업무에 원래 존재하는 고유한 정보를 담는 엔터티입니다[cite: 7, 39]. 다른 엔터티에 의존하지 않고 독립적으로 생성됩니다 (예: 고객, 사원, 상품)[cite: 7, 39].
  </Cards.Card>
  <Cards.Card title="중심 엔터티 (Main Entity)" href="#">
    기본 엔터티로부터 발생하며 업무의 중심 역할을 하는 엔터티입니다[cite: 7, 39]. 많은 행위 엔터티를 생성합니다 (예: 주문, 계좌, 접수)[cite: 7, 39].
  </Cards.Card>
  <Cards.Card title="행위 엔터티 (Action Entity)" href="#">
    2개 이상의 부모 엔터티나 업무 처리 과정에서 자주 생성되고 변경되는 엔터티입니다 [cite: 7, 39] (예: 주문상세, 결제내역, 변경이력) [cite: 7, 39].
  </Cards.Card>
</Cards>

## 속성 (Attribute)

속성이란 엔터티가 가지고 있는 세부적인 고유 성격이나 특징을 의미하며, 의미상 더 이상 쪼개지지 않는 **최소의 데이터 단위**입니다[cite: 7, 39].

### 속성의 분류 (특성에 따른 분류)

1. **기본 속성 (Basic Attribute)**
   * 업무 분석을 통해 도출된 가장 일반적이고 본래적인 속성 (예: 고객명, 제품가격, 생년월일) [cite: 7, 39]
2. **설계 속성 (Designed Attribute)**
   * 업무상 원래 존재하지 않았으나 개발이나 설계 편의를 위해 새롭게 정의한 속성 (예: 주문번호, 일련번호, 결제코드) [cite: 7, 39]
3. **파생 속성 (Derived Attribute)**
   * 다른 속성의 값을 계산하거나 가공하여 생성된 속성으로, 정밀한 관리가 필요함 (예: 합계금액, 평균점수, 나이) [cite: 7, 39]

### 도메인 (Domain)

* 각 속성이 가질 수 있는 **값의 범위 및 데이터 타입, 제약조건**을 의미합니다[cite: 7, 39].
* 예: `나이` 속성의 도메인은 `0 이상의 정수`, `성별` 속성의 도메인은 `'M', 'F'` 문자열[cite: 7, 39].

## 🎯 기출 변형 핵심 실전 문제

### Q1. 다음 중 논리적 데이터 모델링의 특징으로 가장 올바른 것은? [cite: 7]

1. 특정 DBMS 제품의 제약사항이나 기술적 특성을 최우선으로 반영한다[cite: 7].
2. 엔터티 간의 정규화를 수행하여 데이터 중복을 최소화하고 신뢰성을 확보한다[cite: 7, 39].
3. 전사적 관점에서 가장 높은 추상화 수준으로 주요 주제 영역만 구성한다[cite: 7].
4. 디스크 I/O 최적화를 위해 인덱스 및 반정규화 구조를 적극 설계한다[cite: 7, 39].

<details>
<summary><b>정답 및 해설 보기</b></summary>

* **정답**: **2번**
* **해설**:
  * 1번, 4번은 **물리적 데이터 모델링**에 대한 설명입니다[cite: 7, 39].
  * 3번은 **개념적 데이터 모델링**에 대한 설명입니다[cite: 7].
  * 정규화 수행 및 DBMS 독립적인 상세 설계는 **논리적 데이터 모델링**의 핵심 역할입니다[cite: 7, 39].
</details>

---

### Q2. 다음 중 엔터티(Entity)의 성격 및 특징으로 가장 올바르지 않은 것은? [cite: 7, 39]

1. 비즈니스 프로세스에서 반드시 관리되어야 하는 대상이어야 한다[cite: 7, 39].
2. 유일한 인스턴스를 구분할 수 있는 주식별자가 존재해야 한다[cite: 8, 39].
3. 데이터의 재사용성을 높이기 위해 속성은 최소 1개만으로 구성되어야 한다[cite: 7, 39].
4. 일반적으로 2개 이상의 인스턴스(Instance) 집합이어야 가치가 있다[cite: 7, 39].

<details>
<summary><b>정답 및 해설 보기</b></summary>

* **정답**: **3번**
* **해설**:
  * 엔터티는 **최소 2개 이상의 속성**과 **2개 이상의 인스턴스**를 가져야 합니다[cite: 7, 39]. 속성이 1개뿐이라면 별도의 엔터티로 분리할 필요가 없이 다른 엔터티의 속성으로 흡수되어야 합니다[cite: 7, 39].
</details>

---

### Q3. 다음 속성 중 '파생 속성(Derived Attribute)'에 해당하는 것은? [cite: 7, 39]

1. 고객 엔터티의 `고객ID` [cite: 7, 39]
2. 주문 엔터티의 `주문총금액` [cite: 7, 39]
3. 사원 엔터티의 `입사일자` [cite: 7, 39]
4. 상품 엔터티의 `상품명` [cite: 7, 39]

<details>
<summary><b>정답 및 해설 보기</b></summary>

* **정답**: **2번**
* **해설**:
  * `주문총금액`은 주문 상세 항목들의 `(수량 * 단가)`를 계산 및 합산하여 얻어진 결과값이므로 **파생 속성**입니다[cite: 7, 39].
  * `고객ID`는 **설계 속성**, `입사일자`와 `상품명`은 **기본 속성**에 해당합니다[cite: 7, 39].
</details>
