## 이번 편의 목표

- 본질식별자와 인조식별자의 생성 배경을 구분한다.
- 변경 가능성·길이·개인정보·관계 전파를 기준으로 식별자를 선택한다.
- 인조식별자를 사용해도 업무상 유일성 규칙을 보존해야 하는 이유를 설명한다.
- 식별 관계와 비식별 관계에서 부모 키가 자식에게 전달되는 모습을 읽는다.

## 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| 본질식별자 | 업무에서 원래 존재하며 의미를 가진 값으로 만든 식별자 |
| 인조식별자 | 시스템이 행 구분만을 위해 새로 만든 의미 없는 값 |
| 자연키 | 본질식별자와 비슷하게 업무 값으로 만든 키 |
| 대리키 | 인조식별자를 물리 키로 구현한 값 |
| 업무 유일성 | 업무 규칙상 같은 사실이 두 번 존재하면 안 된다는 조건 |
| 키 전파 | 부모의 식별자가 관계를 통해 자식의 외래키로 전달되는 것 |

## 선수지식과 핵심 질문

08편에서 식별자의 유일성·최소성·불변성·존재성과 인조키 사용 후 UNIQUE 보존을 배웠다. 이번에는 선택 기준을 더 깊게 다룬다.

> 이메일이 이미 회원을 구분하는데 왜 별도 회원번호를 만들며, 만들었다면 이메일 중복을 허용해도 될까?

## 같은 회원을 두 방식으로 식별하기

### 이메일을 본질식별자로 사용

| email (PK) | member_name | joined_at |
| --- | --- | --- |
| minji@example.com | 민지 | 2026-08-01 |

이메일은 업무에서 실제 사용하는 값이라 이해하기 쉽다. 하지만 회원이 이메일을 바꾸면 이 값을 참조하는 주문·배송지·문의의 외래키도 영향을 받을 수 있다.

### 회원번호를 인조식별자로 사용

| member_id (PK) | email (UNIQUE) | member_name |
| ---: | --- | --- |
| 101 | minji@example.com | 민지 |

회원번호 101은 그 자체로 업무 의미가 없지만 바뀌지 않는 연결 기준이 된다. 이메일은 변경할 수 있으면서도 UNIQUE로 중복을 막는다.

```text
회원번호 101은 그대로
   ├─ 이메일: old@example.com → new@example.com
   ├─ 주문: member_id 101 그대로
   └─ 배송지: member_id 101 그대로
```

## 본질식별자의 장점과 주의점

본질식별자는 업무에서 원래 존재하는 값을 사용한다. ISBN, 국가 코드, 조직이 보장하는 사번 등이 후보가 될 수 있다.

| 장점 | 주의점 |
| --- | --- |
| 값만 보아도 업무 의미를 알기 쉬움 | 정책 변경으로 값이 바뀔 수 있음 |
| 별도 번호 발급 규칙이 불필요할 수 있음 | 복합키가 길어지면 자식 외래키도 길어짐 |
| 업무 중복 규칙을 키 자체가 표현 | 개인정보가 여러 테이블에 전파될 수 있음 |

“업무에서 쓰는 값”이라고 무조건 좋은 키는 아니다. 주민등록번호나 휴대전화번호처럼 변경·재발급·개인정보 노출 문제가 있는 값은 신중해야 한다.

## 인조식별자의 장점과 주의점

인조식별자는 자동 증가 숫자나 UUID처럼 시스템이 만든 값이다.

| 장점 | 주의점 |
| --- | --- |
| 짧고 안정적인 참조 기준 | 값만 보아서는 업무 의미를 알 수 없음 |
| 업무 값 변경이 자식 키에 미치는 영향 감소 | 원래 업무 중복 규칙을 잊기 쉬움 |
| 복합 본질키를 한 열로 단순화 | 불필요하게 모든 엔터티에 번호를 만들 수 있음 |

<Callout type="important">
  인조식별자는 업무 식별자를 없애는 도구가 아니다. 행을 참조하는 대표 키를 단순화할 뿐, 원래 중복되면 안 되는 업무 값에는 UNIQUE 같은 규칙이 남아야 한다.
</Callout>

## 주문상세에서 두 선택 비교

업무 규칙은 “한 주문에 같은 상품은 한 번만 담는다”이다.

### 본질 조합을 기본키로 사용

```sql
CREATE TABLE order_items (
  order_id   BIGINT NOT NULL REFERENCES orders(order_id),
  product_id VARCHAR(10) NOT NULL REFERENCES products(product_id),
  quantity   INTEGER NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
```

| order_id | product_id | quantity | 저장 결과 |
| ---: | --- | ---: | --- |
| 1001 | P10 | 1 | 허용 |
| 1001 | P20 | 2 | 허용 |
| 1001 | P10 | 3 | 복합 PK 중복으로 거부 |

### 인조키를 기본키로 사용

```sql
CREATE TABLE order_items (
  order_item_id BIGINT PRIMARY KEY,
  order_id      BIGINT NOT NULL REFERENCES orders(order_id),
  product_id    VARCHAR(10) NOT NULL REFERENCES products(product_id),
  quantity      INTEGER NOT NULL,
  UNIQUE (order_id, product_id)
);
```

| order_item_id | order_id | product_id | 저장 결과 |
| ---: | ---: | --- | --- |
| 1 | 1001 | P10 | 허용 |
| 2 | 1001 | P20 | 허용 |
| 3 | 1001 | P10 | UNIQUE 위반으로 거부 |

두 설계 모두 업무 중복을 막는다. 차이는 다른 테이블이 주문상세를 참조할 때 `(order_id, product_id)` 두 열을 가져갈지 `order_item_id` 한 열을 가져갈지에 있다.

## 키 전파로 선택 결과 보기

주문상세에 배송 추적 이벤트가 여러 건 생긴다고 가정하자.

```text
복합 본질키 사용
order_item_events(order_id, product_id, event_no, ...)

인조키 사용
order_item_events(order_item_id, event_no, ...)
```

부모 키가 길면 자식과 손자의 외래키도 길어질 수 있다. 그렇다고 무조건 인조키가 정답은 아니다. 복합키 자체가 자식의 의미와 존재 의존성을 잘 표현하는지 함께 본다.

## 식별 관계와 비식별 관계

| 관계 | 부모 식별자의 위치 | 예 |
| --- | --- | --- |
| 식별 관계 | 자식 주식별자에 포함 | 주문상세 PK가 주문번호+상품번호 |
| 비식별 관계 | 자식 일반 외래키에만 포함 | 주문상세 PK가 주문상세번호 |

식별 관계는 자식이 부모 없이 식별될 수 없음을 강하게 표현한다. 비식별 관계는 자식에 독립적인 식별자를 주어 키 전파를 줄일 수 있다.

## 선택 체크리스트

<Steps>

### 업무 후보를 찾는다

업무에서 이미 유일하다고 보장되는 값과 조합을 모두 적는다.

### 변경과 재사용을 확인한다

발급 뒤 바뀌는지, 탈퇴·폐기 후 같은 값을 다시 쓸 수 있는지 묻는다.

### 자식으로의 전파를 그린다

키가 몇 단계 관계로 전달되며 길이와 개인정보 노출이 어떤지 본다.

### 인조키를 도입해도 업무 규칙을 남긴다

원래 후보식별자에 UNIQUE가 필요한지 확인한다.

</Steps>

## 흔한 실수와 진단법

| 실수 | 문제 | 진단 질문 |
| --- | --- | --- |
| 이메일이 현재 유일하므로 불변이라고 판단 | 변경 정책을 놓침 | 발급 후 변경·재사용 가능한가? |
| 인조키를 만들고 업무 UNIQUE 제거 | 의미상 중복 허용 | 같은 업무 사건이 두 번 들어올 수 있는가? |
| 의미 있는 값은 모두 본질키로 사용 | 긴 키·개인정보 전파 | 자식 테이블까지 전달해도 안전한가? |
| 모든 테이블에 무조건 자동번호 | 업무 식별 기준이 숨음 | 원래 유일성 규칙은 무엇인가? |

## 시험 연결

1. 본질식별자는 업무에서 발생하고 인조식별자는 모델링 과정에서 만든다.
2. 인조식별자는 불변성과 짧은 키 전파에 유리할 수 있다.
3. 인조키를 사용해도 본질적인 후보식별자의 유일성은 별도 제약으로 유지한다.
4. 부모 식별자가 자식 주식별자에 포함되면 식별 관계다.

## 짧은 확인

수강신청에 `수강신청ID`를 새 기본키로 만들었다. 같은 학생이 같은 강좌를 두 번 신청하면 안 된다면 무엇이 더 필요한가?

<Collapse title="확인하기">

`(학생ID, 강좌ID)` 조합에 UNIQUE 제약을 둔다. 수강신청ID는 행을 구분하지만 같은 학생-강좌 조합의 업무 중복까지 자동으로 막지는 않는다.

</Collapse>

## 정리

<Callout type="default">
  - 본질식별자는 업무 의미가 있고 인조식별자는 시스템이 만든 참조 기준이다.
  - 선택할 때 유일성뿐 아니라 변경·재사용·길이·개인정보·키 전파를 본다.
  - 인조키를 사용해도 원래 업무 유일성을 UNIQUE로 보존한다.
  - 식별 관계 여부는 부모 키가 자식 주식별자에 포함되는지로 판단한다.
</Callout>
