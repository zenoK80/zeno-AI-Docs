## 이번 편의 목표

- 성능을 응답시간·처리량·자원 사용으로 나누어 설명한다.
- 데이터 모델의 관계와 키가 SQL 조인 경로에 미치는 영향을 판단한다.
- 카디널리티와 선택도를 쉬운 숫자로 계산한다.
- 측정 없이 구조를 바꾸는 조기 최적화의 위험을 설명한다.

## 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| 응답시간(Response Time) | 한 요청이 시작해 결과를 받을 때까지 걸린 시간 |
| 처리량(Throughput) | 일정 시간 동안 처리한 요청이나 행의 양 |
| I/O(Input/Output) | 디스크·메모리에서 데이터 블록을 읽고 쓰는 작업 |
| 카디널리티(Cardinality) | 문맥에 따라 열의 서로 다른 값 수 또는 단계의 예상 행 수 |
| 선택도(Selectivity) | 전체 행 중 조건을 통과하는 비율 |
| 접근 경로 | 필요한 행을 찾기 위해 테이블·인덱스를 읽는 방법 |
| 실행계획 | DBMS가 SQL 결과를 만들기 위해 선택한 작업 순서와 방법 |

## 선수지식과 핵심 질문

선수지식은 [3. 데이터 모델링의 이해](./03_data-modeling-overview), [7. 관계](./07_relationship), [21. 조인](./21_joins)이다.

핵심 질문은 **업무 사실을 어떤 행과 관계로 저장했는지가 왜 SQL이 읽고 연결할 데이터 양을 결정하는가**이다.

<Callout type="info">
  현재 KDATA SQLD 공식 상세 범위는 관리 구문까지 제시한다. 40~48편은 최신 시험 범위를 대체하지 않는 성능 기초 확장 과정이며, 모델과 SQL을 더 깊이 이해하기 위해 학습한다.
</Callout>

## 모델에서 실행까지

```mermaid
flowchart LR
  A["업무 규칙"] --> B["엔터티·키·관계 모델"]
  B --> C["테이블·제약조건·인덱스"]
  C --> D["SQL과 조건"]
  D --> E["옵티마이저 실행계획"]
  E --> F["읽은 행·I/O·응답시간"]
```

느린 SQL을 쿼리 문자열만의 문제로 보면 안 된다. 모델이 불필요한 중복·모호한 관계·지나치게 넓은 행을 만들면 SQL도 더 많은 데이터를 읽거나 복잡하게 연결한다.

## 성능은 하나의 숫자가 아니다

| 상황 | 중요한 지표 | 예시 |
| --- | --- | --- |
| 사용자가 주문 조회 | 응답시간 | 200ms 안에 화면 표시 |
| 야간 정산 | 처리량 | 1시간에 주문 1천만 건 처리 |
| 동시 접속 급증 | CPU·I/O·대기 | 잠금 대기와 디스크 읽기 |
| 데이터 적재 | 쓰기량·로그 | 초당 입력 행 수 |

응답시간을 줄이려고 캐시·중복을 늘리면 쓰기 비용과 일관성 관리가 커질 수 있다. 목표 지표와 업무 우선순위를 먼저 정한다.

## 같은 업무, 다른 모델

요구사항: 회원의 최근 주문 10건과 각 주문 상품을 보여 준다.

### 관계가 명확한 모델

```text
members 1 ─ N orders 1 ─ N order_items N ─ 1 products
```

- `orders.member_id`로 회원 주문을 찾는다.
- `order_items.order_id`로 해당 주문 상세를 찾는다.
- 각 관계의 외래키와 인덱스를 검토할 수 있다.

### 한 열에 상품 목록을 저장한 모델

| order_id | member_id | product_ids |
| ---: | --- | --- |
| 1001 | M01 | `P10,P20,P30` |

상품별 조인·수량·제약조건 적용이 어렵고 문자열을 매번 분해해야 한다. 읽기 한 번이 간단해 보이지만 다른 요구사항과 데이터 무결성 비용이 커진다.

<Callout type="warning">
  한 화면만 빠르게 보이는 구조와 전체 업무에서 예측 가능한 구조는 다를 수 있다. 조회·입력·수정·삭제 경로를 함께 평가한다.
</Callout>

## 결과 한 행의 단위가 성능과 정확성을 좌우한다

회원 1명, 주문 100건, 주문상세 주문당 5건이면 세 테이블을 조인한 상세 결과는 최대 500행이다.

```text
회원 1행
  × 주문 100행
  × 주문당 상세 5행
  = 상세 결과 500행
```

회원 정보만 필요하면서 주문상세까지 조인하면 불필요한 500행 중복을 만들 수 있다. 존재 여부만 필요하면 EXISTS, 먼저 주문을 10건으로 제한한 뒤 상세를 조인하는 등 결과 grain과 순서를 설계한다.

## 카디널리티와 선택도

회원 테이블 100만 행에서 `member_id = 'M01'`이 한 행이면 선택도는 다음과 같다.

```text
선택도 = 조건 결과 행 수 / 전체 행 수
       = 1 / 1,000,000
       = 0.0001%
```

매우 적은 행을 찾는 조건이다. 반대로 `status = 'ACTIVE'`가 95만 행이면 선택도는 95%로 대부분을 읽는다.

| 조건 | 예상 행 | 선택도 | 일반적 특징 |
| --- | ---: | ---: | --- |
| 기본키 1건 | 1 | 매우 낮음 | 인덱스 탐색 후보 |
| 등급 GOLD | 10만 | 10% | 분포·조회 열에 따라 판단 |
| 상태 ACTIVE | 95만 | 95% | 전체 읽기가 유리할 수도 있음 |

낮은 선택도가 항상 인덱스를 뜻하거나 높은 선택도가 항상 전체 스캔을 뜻하는 절대 규칙은 아니다. 테이블 크기, 클러스터링, 반환 열, 캐시와 비용 모델이 함께 작용한다.

## 키와 관계가 주는 정보

- 기본키·UNIQUE는 값이 최대 한 행이라는 정보를 제공한다.
- 외래키는 자식이 어떤 부모를 참조하는지 보장한다.
- NOT NULL은 값 부재 가능성을 줄인다.
- 정확한 데이터 타입은 비교와 통계를 일관되게 만든다.

옵티마이저는 제약조건과 통계를 이용해 행 수와 가능한 변환을 판단할 수 있다. 제약을 애플리케이션 문서에만 적고 DB에 선언하지 않으면 데이터 품질뿐 아니라 최적화 정보도 잃을 수 있다.

## 넓은 행과 읽기량

목록 화면에 `member_id`, `name`만 필요한데 회원 테이블에 큰 프로필 문서와 이미지 메타데이터가 함께 있다면 `SELECT *`는 불필요한 데이터를 전달한다.

| 조회 | 필요한 열 | 전송·메모리 관점 |
| --- | --- | --- |
| `SELECT *` | 모든 열 | 큰 열까지 읽고 전송 가능 |
| 필요한 열 명시 | id, name | 결과 폭을 줄임 |

열을 분리할지는 접근 빈도, 행 저장 방식, DBMS 특성을 측정해 결정하지만 SQL에서는 우선 필요한 열만 선택한다.

## 성능 문제를 찾는 순서

<Steps>

### 느린 업무와 목표를 정의한다

어떤 SQL이 언제 몇 초 걸리고 목표가 얼마인지 기록한다.

### 실행계획과 실제 행 수를 확인한다

어느 단계의 예상과 실제 행 수가 크게 다른지 찾는다.

### 모델의 관계와 SQL 결과 grain을 확인한다

불필요한 다대다 증폭, 조건 누락, 중복 행을 찾는다.

### 통계·인덱스·SQL·모델 대안을 비교한다

한 요소만 무조건 원인으로 단정하지 않는다.

### 같은 데이터와 부하로 다시 측정한다

응답시간뿐 아니라 쓰기·저장공간·동시성 부작용도 확인한다.

</Steps>

## 시험·실무 연결

- 관계 카디널리티로 조인 결과 행 수를 예측한다.
- 선택도가 낮은 조건과 높은 조건의 접근 방식 차이를 판단한다.
- 반정규화가 조회를 줄이는 대신 쓰기·일관성 비용을 늘릴 수 있음을 묻는다.
- 실행계획의 추정 행 수가 모델·통계 정보에 의존한다는 점을 연결한다.

## 짧은 확인

주문 100행과 주문상세 500행이 있고 각 상세가 정확히 한 주문을 참조한다. 두 테이블의 정상 내부 조인 결과는 몇 행인가?

<Collapse title="확인하기">

500행이다. 주문상세 한 행마다 부모 주문 한 행과 연결된다. 주문 수 100을 더하거나 곱하는 것이 아니다.

</Collapse>

## 흔한 실수와 진단법

| 실수 | 진단법 |
| --- | --- |
| 느리면 무조건 인덱스 추가 | 실행계획과 결과 행 수부터 확인 |
| 한 조회만 보고 모델 변경 | 쓰기·다른 조회·일관성 비용 비교 |
| 행 수 증폭을 DB 성능 문제로만 봄 | 관계와 조인 조건 검증 |
| 추정치를 실제값으로 믿음 | EXPLAIN ANALYZE 등 실제 측정 비교 |

## 정리

<Callout type="default">
  - 데이터 모델은 SQL이 따라갈 관계와 읽을 행의 구조를 정한다.
  - 성능은 응답시간·처리량·I/O·대기를 목표별로 측정한다.
  - 카디널리티와 선택도로 단계별 데이터 양을 예측한다.
  - 실행계획과 실제 측정 없이 모델을 성급히 바꾸지 않는다.
</Callout>
