## 이번 편의 목표

- 정규화가 쓰기 일관성과 저장 중복에 주는 이점을 설명한다.
- 정규화 전후의 수정 행 수와 조인 경로를 비교한다.
- “조인이 있으니 정규화는 느리다”라는 단정을 반박한다.
- 성능 문제를 정규화 수준이 아니라 실행계획과 업무 비율로 판단한다.

## 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| 정규화 | 서로 다른 사실을 주인 테이블로 분리해 중복과 이상 현상을 줄이는 과정 |
| 갱신 비용 | 데이터를 바꿀 때 찾아서 수정·검증해야 하는 행과 작업의 양 |
| 참조 일관성 | 연결된 데이터가 존재하고 같은 사실을 모순 없이 가리키는 상태 |
| 조인 비용 | 분리된 테이블의 관련 행을 찾고 연결하는 데 필요한 처리 |
| 쓰기 증폭 | 하나의 업무 변경이 여러 위치의 반복값을 수정하게 만드는 현상 |

## 선수지식과 핵심 질문

선수지식은 [9. 정규화](./09_normalization)와 [40. 데이터 모델과 성능](./40_data-model-and-performance)이다.

핵심 질문은 **사실을 한 곳에 저장해 얻는 쓰기·일관성 이점과 조회 때 다시 연결하는 비용을 어떻게 비교하는가**이다.

## 정규화 전후 흐름

```mermaid
flowchart LR
  A["주문마다 회원명·상품명 반복"] --> B["함수 종속 분석"]
  B --> C["회원·상품·주문·주문상세 분리"]
  C --> D["수정은 사실의 주인 한 곳"]
  C --> E["조회는 키로 JOIN"]
```

정규화는 비용을 없애는 마법이 아니라 반복 수정 비용을 줄이고 필요한 조회에 연결 비용을 지불하도록 구조를 바꾼다.

## 수정 성능과 정확성 비교

비정규화 주문 원장에 민지 이름이 주문 10만 행에 반복돼 있다고 하자.

| 구조 | 이름 변경 대상 | 실패 위험 |
| --- | ---: | --- |
| 주문마다 회원명 반복 | 최대 10만 행 UPDATE | 일부 행 누락·긴 잠금·로그 증가 |
| members에 회원명 한 번 | 1행 UPDATE | 한 곳만 변경 |

정규화 구조:

```sql
UPDATE members
SET name = '김민지'
WHERE member_id = 'M01';
```

주문은 member_id로 회원을 참조하므로 과거 10만 주문의 회원 이름 표시도 다음 조회에서 새 이름을 사용한다.

## 입력·삭제 이상도 성능 문제다

- 새 상품을 주문 전에는 등록할 수 없는 입력 이상은 불필요한 가짜 주문을 만든다.
- 마지막 주문 삭제로 상품 정보까지 사라지는 삭제 이상은 복구·재입력 비용을 만든다.
- 반복값 불일치는 조회 때 DISTINCT·정제 로직을 추가하게 한다.

잘못된 모델의 비용은 단순 쿼리 시간뿐 아니라 데이터 정정, 장애 대응, 복잡한 애플리케이션 코드까지 포함한다.

## 정규화 조회에는 조인이 생긴다

```sql
SELECT o.order_id, m.name, p.product_name, i.quantity
FROM orders o
JOIN members m ON m.member_id = o.member_id
JOIN order_items i ON i.order_id = o.order_id
JOIN products p ON p.product_id = i.product_id
WHERE o.order_id = 1001;
```

### 입력 규모

| 테이블 | 전체 행 | 조건 후 예상 행 |
| --- | ---: | ---: |
| orders | 1천만 | order_id 기본키로 1 |
| members | 100만 | 회원 기본키로 1 |
| order_items | 5천만 | 주문 1001의 상세 3 |
| products | 10만 | 상품 키 세 개 |

관계 키에 적절한 인덱스와 통계가 있다면 전체 테이블을 매번 곱하는 것이 아니라 필요한 소수 행을 찾아 연결할 수 있다.

<Callout type="info">
  SQL에 JOIN이 세 번 적혔다고 항상 느린 것은 아니다. 각 단계가 몇 행을 받고 어떤 접근 경로를 쓰는지가 중요하다.
</Callout>

## 정규화가 행 폭을 줄이는 효과

주문 1천만 행마다 회원명 50바이트와 상품설명 500바이트를 반복하지 않으면 저장공간뿐 아니라 스캔할 데이터 블록 수, 캐시 효율, 백업·복제량을 줄일 수 있다.

| 반복 열 | 행당 크기 | 1천만 행 단순 반복량 |
| --- | ---: | ---: |
| 회원명 | 50B | 약 500MB |
| 상품설명 | 500B | 약 5GB |

실제 저장 크기는 압축·인코딩·블록 오버헤드에 따라 달라지지만 중복 열이 읽기량에 영향을 준다는 방향을 보여 준다.

## 너무 많은 분리도 점검한다

정규화 규칙을 이름만 따라 모든 속성을 1:1 테이블로 쪼개면 자주 함께 조회·변경하는 값에도 불필요한 조인이 늘 수 있다.

예를 들어 회원 기본정보와 필수 프로필이 항상 1:1이고 같은 수명주기라면 별도 엔터티가 필요한 업무 이유가 있는지 확인한다. 정규형은 함수 종속과 업무 사실을 기준으로 적용하며 “열 하나당 테이블 하나”가 아니다.

## 이력 데이터는 현재값과 다르다

주문 당시 판매가격은 products.current_price에만 두면 안 된다. 현재가격 변경 후 과거 주문 금액까지 바뀌기 때문이다.

| 값 | 사실의 주인 |
| --- | --- |
| 현재 상품 가격 | products.current_price |
| 주문 당시 판매 가격 | order_items.sale_price |

두 값이 겉보기에는 중복돼도 의미와 결정 시점이 다르다. 이것은 무조건 제거할 중복이 아니라 서로 다른 사실이다.

## 읽기와 쓰기 비율 평가

| 질문 | 확인할 측정값 |
| --- | --- |
| 이름 변경이 잦은가? | UPDATE 빈도·영향 행·잠금 시간 |
| 주문 상세 조회가 느린가? | 실행계획·I/O·조인별 실제 행 |
| 같은 조인을 반복하는가? | 캐시·뷰·요약 데이터 후보 |
| 중복 저장이 큰가? | 테이블 크기·백업·복제량 |

정규화를 먼저 올바른 모델의 기준으로 만들고, 실제 병목이 입증되면 인덱스·SQL 개선·캐시·선택적 반정규화를 비교한다.

## 시험·실무 연결

- 정규화가 입력·수정·삭제 이상을 줄이는 이유를 묻는다.
- 분해 후 조인이 늘어도 키 기반 소수 행 연결은 효율적일 수 있음을 판단한다.
- 주문가격처럼 결정 시점이 다른 속성을 단순 중복으로 오해하는 선지를 구분한다.
- 넓은 반복 행이 저장·I/O·로그량을 늘릴 수 있음을 연결한다.

## 짧은 확인

고객 주소가 주문마다 반복되고 고객 한 명의 주문이 5만 건이다. 주소 변경 시 정규화 전후 수정 행 수는 어떻게 달라질까?

<Collapse title="확인하기">

반복 저장 구조는 최대 5만 주문 행을 수정해야 한다. 고객 테이블에 현재 주소 한 번만 저장한 정규화 구조는 고객 1행을 수정한다. 단, 과거 배송지 보존이 업무 요구라면 주문 배송지는 별도 시점 사실로 저장해야 한다.

</Collapse>

## 흔한 실수와 진단법

| 실수 | 바로잡기 |
| --- | --- |
| 조인 수만 세어 느리다고 판단 | 각 단계 실제 행·I/O 측정 |
| 비슷한 값은 전부 중복이라고 판단 | 결정 주체와 시점 비교 |
| 정규화면 조회가 무조건 빠르다고 판단 | 쓰기·읽기 목표를 분리 측정 |
| 성능 때문에 제약부터 제거 | 무결성·옵티마이저 정보 손실 평가 |

## 정리

<Callout type="default">
  - 정규화는 한 사실을 한 곳에 두어 쓰기 증폭과 불일치를 줄인다.
  - 조회에는 조인이 생기지만 키·인덱스로 필요한 소수 행을 연결할 수 있다.
  - 결정 시점이 다른 값은 겉모양이 같아도 서로 다른 사실일 수 있다.
  - 정규화 수준은 실행계획과 업무 읽기·쓰기 비율로 평가한다.
</Callout>
