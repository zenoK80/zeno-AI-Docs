## 이번 편의 목표

- `INNER`, `LEFT`, `RIGHT`, `FULL OUTER`, `CROSS JOIN`의 보존 범위를 구분한다.
- `ON`과 `USING`의 문법 및 결과 열 차이를 설명한다.
- 외부 조인에서 조건의 위치가 결과를 바꾸는 이유를 판단한다.
- `NATURAL JOIN`의 편리함과 위험을 함께 설명한다.

## 먼저 알아둘 말

| 용어 | 쉬운 뜻 |
| --- | --- |
| ANSI SQL | 여러 DBMS가 공통으로 따르도록 정한 SQL 표준 |
| 보존 테이블 | 외부 조인에서 짝이 없어도 행을 남기는 쪽 |
| `ON` | 서로 이름이 다를 수도 있는 열을 원하는 조건으로 연결하는 절 |
| `USING` | 양쪽의 같은 이름 열 하나를 연결 열로 지정하는 문법 |
| 자연 조인 | 같은 이름의 열을 DBMS가 자동으로 찾아 모두 비교하는 조인 |
| 완전 외부 조인 | 양쪽의 짝 없는 행을 모두 보존하는 조인 |

## 선수지식과 핵심 질문

선수지식은 [21. 조인](./21_joins)이다. 이번 편은 **짝이 없는 행을 어느 쪽까지 남길 것인지 SQL에 어떻게 정확히 표현하는가**에 답한다.

## 표준 조인 기본 모양

```sql
SELECT 표시할_열
FROM 왼쪽_테이블
[INNER | LEFT | RIGHT | FULL] JOIN 오른쪽_테이블
  ON 연결_조건;
```

`JOIN`만 쓰면 일반적으로 `INNER JOIN`과 같다. `LEFT`와 `RIGHT`에서 방향은 SQL의 `FROM`에 적은 순서를 기준으로 한다.

### 공통 입력

`members`

| member_id | name |
| --- | --- |
| M01 | 민지 |
| M02 | 준호 |
| M03 | 소라 |
| M04 | 현우 |

`orders`

| order_id | member_id | status |
| ---: | --- | --- |
| 1001 | M01 | PAID |
| 1002 | M01 | SHIPPED |
| 1003 | M02 | PAID |
| 1004 | M03 | CANCELED |
| 1006 | M99 | PAID |

M04는 주문이 없고, M99는 회원 표에 없는 값이라고 가정한다. 실제 데이터베이스에서 외래키가 정상 적용됐다면 M99 주문은 거부되지만, 조인 차이를 보기 위해 불완전한 데이터를 넣었다.

## INNER JOIN: 양쪽 모두 짝이 있는 행

```sql
SELECT m.name, o.order_id
FROM members m
INNER JOIN orders o
  ON m.member_id = o.member_id
ORDER BY o.order_id;
```

| name | order_id |
| --- | ---: |
| 민지 | 1001 |
| 민지 | 1002 |
| 준호 | 1003 |
| 소라 | 1004 |

M04와 M99는 반대쪽 짝이 없어 사라진다.

## LEFT OUTER JOIN: 왼쪽을 보존

```sql
SELECT m.name, o.order_id
FROM members m
LEFT OUTER JOIN orders o
  ON m.member_id = o.member_id
ORDER BY m.member_id, o.order_id;
```

| name | order_id |
| --- | ---: |
| 민지 | 1001 |
| 민지 | 1002 |
| 준호 | 1003 |
| 소라 | 1004 |
| 현우 | NULL |

왼쪽 `members`가 보존된다. 주문이 없는 현우도 남고, 오른쪽 주문 열만 `NULL`로 채워진다. 오른쪽에만 있는 M99 주문은 보존 대상이 아니다.

## RIGHT OUTER JOIN: 오른쪽을 보존

```sql
SELECT m.name, o.order_id
FROM members m
RIGHT JOIN orders o
  ON m.member_id = o.member_id
ORDER BY o.order_id;
```

| name | order_id |
| --- | ---: |
| 민지 | 1001 |
| 민지 | 1002 |
| 준호 | 1003 |
| 소라 | 1004 |
| NULL | 1006 |

오른쪽 `orders`를 모두 보존하므로 회원이 없는 1006도 나온다. 같은 결과는 테이블 순서를 바꾼 `orders LEFT JOIN members`로도 표현할 수 있다.

## FULL OUTER JOIN: 양쪽을 모두 보존

```sql
SELECT m.name, o.order_id
FROM members m
FULL OUTER JOIN orders o
  ON m.member_id = o.member_id;
```

내부 조인 4행에 `현우 | NULL`, `NULL | 1006`이 더해져 6행이다.

<Callout type="warning">
  DBMS마다 지원 범위가 다르다. 예를 들어 MySQL은 `FULL OUTER JOIN` 문법을 직접 지원하지 않는다. 시험에서는 표준 의미를 먼저 이해하고 제품별 차이는 별도로 확인한다.
</Callout>

## ON과 USING의 차이

### ON: 조건을 직접 작성

```sql
SELECT m.member_id, o.member_id, m.name, o.order_id
FROM members m
JOIN orders o
  ON m.member_id = o.member_id;
```

양쪽 연결 열을 각각 결과에 표시할 수 있고, 열 이름이 서로 달라도 연결할 수 있다.

### USING: 같은 이름의 연결 열을 한 번만 표시

```sql
SELECT member_id, m.name, o.order_id
FROM members m
JOIN orders o
  USING (member_id);
```

`USING (member_id)`은 양쪽에 `member_id`가 있어야 한다. 결과의 연결 열은 하나로 합쳐지므로 일반적으로 `m.member_id`처럼 한쪽으로 한정하지 않고 `member_id`라고 쓴다.

| 기준 | ON | USING |
| --- | --- | --- |
| 열 이름 | 달라도 가능 | 같아야 함 |
| 복합 조건 | 자유롭게 가능 | 괄호 안 같은 이름 열 목록 |
| 결과의 연결 열 | 양쪽 열이 별개 | 한 열로 합침 |
| 읽기 쉬움 | 조건이 명시적 | 단순 동일 열 조인에 간결 |

## NATURAL JOIN은 왜 조심해야 할까

```sql
SELECT *
FROM members
NATURAL JOIN orders;
```

`NATURAL JOIN`은 양쪽에서 이름이 같은 모든 열을 자동으로 조인 조건에 넣는다. 처음에는 `member_id`만 같았더라도 나중에 두 테이블에 `created_at` 열이 추가되면 이 열까지 자동 비교한다. 쿼리를 수정하지 않았는데 결과가 달라질 수 있어 실무에서는 명시적인 `ON`이나 `USING`이 더 안전하다.

## 외부 조인에서 ON과 WHERE의 위치

취소되지 않은 주문만 붙이되 주문 없는 회원도 보고 싶다고 하자.

### 조건을 ON에 둔 경우

```sql
SELECT m.name, o.order_id, o.status
FROM members m
LEFT JOIN orders o
  ON m.member_id = o.member_id
 AND o.status <> 'CANCELED';
```

| name | order_id | status |
| --- | ---: | --- |
| 민지 | 1001 | PAID |
| 민지 | 1002 | SHIPPED |
| 준호 | 1003 | PAID |
| 소라 | NULL | NULL |
| 현우 | NULL | NULL |

`ON`은 어떤 주문을 짝으로 인정할지 정한다. 소라는 취소 주문밖에 없어 짝은 없지만 왼쪽 회원 행은 보존된다.

### 조건을 WHERE에 둔 경우

```sql
SELECT m.name, o.order_id, o.status
FROM members m
LEFT JOIN orders o
  ON m.member_id = o.member_id
WHERE o.status <> 'CANCELED';
```

소라와 현우의 `o.status`는 `NULL`이고, `NULL <> 'CANCELED'`는 참이 아니라 UNKNOWN이다. WHERE는 참만 남기므로 두 회원 모두 사라진다. 이 조건은 결과적으로 외부 조인의 보존 효과를 약하게 만든다.

<Callout type="info">
  `ON`은 **짝을 만드는 조건**, `WHERE`는 **조인이 끝난 결과를 거르는 조건**이라고 먼저 구분하자.
</Callout>

## CROSS JOIN

```sql
SELECT c.color, s.size
FROM colors c
CROSS JOIN sizes s;
```

색상 3개와 크기 2개라면 상품 옵션 조합 6개를 만든다. 의도적인 모든 조합에는 쉼표 문법보다 `CROSS JOIN`을 명시하는 편이 뜻이 분명하다.

## 시험에서는 어떻게 묻나

- 왼쪽·오른쪽·양쪽 중 어느 행을 보존하는지 결과표를 고르게 한다.
- `ON`의 조건을 `WHERE`로 옮겼을 때 짝 없는 행이 사라지는지 묻는다.
- `USING`에서 연결 열이 한 번만 나타난다는 점을 묻는다.
- `NATURAL JOIN`이 같은 이름의 모든 열을 사용한다는 점을 함정으로 낸다.

## 짧은 확인

상품 3개 중 판매 기록이 있는 상품은 2개다. 판매가 없는 상품까지 보려면 `products`를 어느 쪽에 둔 어떤 조인이 알맞을까?

<Collapse title="확인하기">

`products LEFT JOIN sales`가 자연스럽다. 상품을 왼쪽 보존 테이블로 두면 판매가 없는 상품도 판매 열이 `NULL`인 행으로 남는다.

</Collapse>

## 흔한 실수와 진단법

| 실수 | 결과 | 진단 질문 |
| --- | --- | --- |
| LEFT와 RIGHT를 단어만 암기 | 테이블 순서가 바뀌면 혼동 | 어느 쪽 행을 모두 남겨야 하는가? |
| 오른쪽 조건을 WHERE에 둠 | NULL 보존 행이 제거됨 | 조건이 짝 조건인가, 최종 필터인가? |
| NATURAL JOIN 남용 | 스키마 변경 후 결과 변화 | 실제 자동 연결 열이 몇 개인가? |
| USING 열을 테이블 별칭으로 한정 | DBMS에 따라 오류 | 합쳐진 연결 열로 참조해야 하는가? |

## 정리

<Callout type="default">
  - INNER는 짝 있는 조합만, LEFT·RIGHT는 지정한 한쪽, FULL은 양쪽을 보존한다.
  - ON은 자유로운 연결 조건, USING은 같은 이름의 연결 열을 간단히 적는 문법이다.
  - 외부 조인의 오른쪽 조건을 WHERE에 두면 NULL 보존 행이 사라질 수 있다.
  - NATURAL JOIN은 같은 이름의 모든 열을 자동 사용하므로 변경에 취약하다.
</Callout>
