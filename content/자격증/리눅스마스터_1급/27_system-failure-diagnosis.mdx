</Callout>

## 장애 진단 원칙

```
증상 파악 → 로그 확인 → 원인 분리 → 최소 변경 → 검증
```

1. **증상 파악:** 사용자가 경험하는 현상을 정확하게 파악합니다 (어디서? 언제부터? 어떤 에러?)
2. **로그 확인:** `/var/log/`, `journalctl`, 애플리케이션 로그를 확인합니다
3. **원인 분리:** 네트워크? 서비스? 파일 시스템? 보안? 원인 범위를 좁힙니다
4. **최소 변경:** 확인된 원인에 대해 최소한의 변경만 적용합니다
5. **검증:** 변경 후 증상이 해소됐는지 반드시 확인합니다

<Callout type="warning">
  **절대 하지 말 것:** 원인 파악 전에 서버를 재부팅하거나, 여러 변경을 동시에 적용하는 것은 원인 추적을 불가능하게 만듭니다.
</Callout>

## 시나리오 1: 웹 서버 접속 불가

**증상:** 외부에서 http://서버IP 로 접속이 안 된다.

### 단계별 진단

**Step 1: 네트워크 연결 확인**

```bash
# 서버까지 네트워크가 닿는지 확인
ping -c 4 서버IP
ping -c 4 서버도메인

# DNS 해석 확인
nslookup 도메인이름
dig 도메인이름
```

응답 없음 → 네트워크/라우팅 문제. 응답 있음 → 다음 단계로.

**Step 2: 포트 열림 여부 확인**

```bash
# 서버에서 80 포트 LISTEN 여부 확인
ss -tuln | grep :80

# 또는
netstat -tlnp | grep :80

# 외부에서 확인 (클라이언트 측)
nc -zv 서버IP 80
telnet 서버IP 80
```

포트가 없음 → 서비스가 실행되지 않음. 다음 단계로.

**Step 3: 서비스 상태 확인**

```bash
# Apache 상태 확인
systemctl status httpd

# Nginx 상태 확인
systemctl status nginx

# 서비스 시작 및 부팅 시 자동 시작 설정
systemctl start httpd
systemctl enable httpd
```

Active 상태가 failed 또는 inactive → 에러 로그 확인.

**Step 4: 에러 로그 확인**

```bash
# Apache 에러 로그 최근 50줄
tail -50 /var/log/httpd/error_log

# Nginx 에러 로그
tail -50 /var/log/nginx/error.log

# systemd 로그로 서비스 실패 원인 확인
journalctl -u httpd -n 50 --no-pager
journalctl -u httpd --since "10 minutes ago"
```

설정 파일 오류, 포트 충돌, 권한 문제 등이 로그에 남습니다.

**Step 5: 방화벽 확인**

```bash
# firewalld 상태 및 허용 서비스/포트 확인
firewall-cmd --list-all

# HTTP 서비스 허용
firewall-cmd --add-service=http --permanent
firewall-cmd --add-port=80/tcp --permanent
firewall-cmd --reload

# iptables 사용 시
iptables -L -n -v | grep 80
```

**Step 6: SELinux 확인**

```bash
# SELinux 현재 모드 확인
getenforce
# Enforcing: 정책 강제 적용 중

# SELinux 감사 로그에서 httpd 관련 deny 확인
grep httpd /var/log/audit/audit.log | grep denied
ausearch -m AVC -ts recent | grep httpd

# httpd가 네트워크 연결을 허용하는 불리언
getsebool -a | grep httpd_can_network

# httpd 포트 SELinux 허용
semanage port -a -t http_port_t -p tcp 8080
```

### 진단 흐름 요약

```
ping 통함?
  └ NO → 네트워크/방화벽(OS 외부) 점검
  └ YES → ss -tuln | grep :80
            └ LISTEN 없음 → systemctl start httpd
            └ LISTEN 있음 → firewall-cmd --list-all
                             └ 차단됨 → 포트 허용
                             └ 허용됨 → getenforce → SELinux deny 확인
```

## 시나리오 2: 디스크 꽉 참

**증상:** "No space left on device" 에러 발생, 파일 생성 불가.

### 단계별 진단

**Step 1: 어느 파티션이 꽉 찼는지 확인**

```bash
# 파일 시스템별 사용률 확인
df -h

# inode 사용률 확인 (파일 수 고갈)
df -i
```

출력 예시:

```
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        20G   20G     0 100% /
/dev/sdb1       100G   30G   70G  30% /data
```

`/dev/sda1`이 100% 사용 중.

**Step 2: 어느 디렉토리가 용량을 차지하는지 찾기**

```bash
# 루트 하위 디렉토리별 용량 (에러 출력 무시)
du -sh /* 2>/dev/null | sort -rh | head -10

# /var 하위 상세 확인
du -sh /var/* 2>/dev/null | sort -rh | head -10

# 특정 경로 재귀 확인
du -sh /var/log/* 2>/dev/null | sort -rh
```

**Step 3: 대용량 로그 파일 찾기**

```bash
# /var/log에서 100MB 초과 파일 찾기
find /var/log -name "*.log" -size +100M -ls

# 전체 시스템에서 500MB 초과 파일
find / -xdev -size +500M -ls 2>/dev/null
```

**Step 4: 오래된 로그·임시 파일 정리**

```bash
# journald 로그를 500MB로 제한
journalctl --vacuum-size=500M

# 7일 이상 된 로그 삭제
journalctl --vacuum-time=7d

# 특정 로그 파일 비우기 (삭제하지 않고)
> /var/log/httpd/access_log

# 오래된 패키지 캐시 정리 (RHEL 계열)
dnf clean all

# /tmp 정리
find /tmp -mtime +7 -delete 2>/dev/null
```

**Step 5: 삭제됐지만 프로세스가 점유 중인 파일 확인**

```bash
# 삭제됐지만 파일 핸들이 열려 있는 파일 (공간을 차지하고 있음)
lsof | grep deleted

# 해당 프로세스 재시작하면 공간 반환
systemctl restart httpd
```

<Callout type="warning">
  **함정:** 파일을 삭제해도 프로세스가 파일을 열고 있으면 실제 디스크 공간이 반환되지 않습니다. `lsof | grep deleted`로 확인 후 해당 프로세스를 재시작해야 합니다.
</Callout>

## 시나리오 3: SSH 접속 불가

**증상:** 원격에서 SSH로 접속이 안 된다.

### 단계별 진단

**Step 1: 콘솔(물리/가상 콘솔)로 직접 접속**

원격 접속이 불가하면 반드시 **물리적 콘솔이나 KVM/iDRAC/iLO**로 직접 서버에 접속합니다. 이후 진단은 콘솔에서 진행합니다.

**Step 2: SSH 서비스 상태 확인**

```bash
# sshd 서비스 상태 확인
systemctl status sshd

# 중지된 경우 시작
systemctl start sshd
systemctl enable sshd

# systemd 로그 확인
journalctl -u sshd -n 30 --no-pager
```

**Step 3: 인증 로그 확인**

```bash
# /var/log/secure (RHEL 계열) 또는 /var/log/auth.log (Debian 계열)
grep sshd /var/log/secure | tail -30
grep "Failed password" /var/log/secure | tail -20

# 접속 시도 거부 원인 확인
grep "error" /var/log/secure | grep sshd
```

**Step 4: 포트 LISTEN 확인**

```bash
# 22번 포트 LISTEN 여부
ss -tuln | grep :22

# /etc/ssh/sshd_config에서 포트 변경 여부 확인
grep ^Port /etc/ssh/sshd_config
```

**Step 5: 설정 파일 문법 검사**

```bash
# sshd 설정 파일 문법 오류 확인
sshd -t
# 문제 없으면 아무것도 출력되지 않음

# 자세한 테스트
sshd -T | head -30
```

**Step 6: 방화벽 확인**

```bash
# SSH 포트 허용 여부
firewall-cmd --list-all | grep ssh

# SSH 서비스 허용
firewall-cmd --add-service=ssh --permanent
firewall-cmd --reload

# 비표준 포트(예: 2222) 사용 시
firewall-cmd --add-port=2222/tcp --permanent
```

**Step 7: SELinux 및 hosts.deny 확인**

```bash
# /etc/hosts.deny 차단 여부
cat /etc/hosts.deny

# TCP Wrapper 설정 확인
cat /etc/hosts.allow
cat /etc/hosts.deny

# SELinux - SSH 비표준 포트 허용
semanage port -l | grep ssh
semanage port -a -t ssh_port_t -p tcp 2222
```

## 시나리오 4: 시스템 응답 느림

**증상:** 서버 전반적으로 응답이 느리고, 명령어 실행도 지연된다.

### 단계별 진단

**Step 1: 로드 애버리지 확인 **(CPU 병목 여부)

```bash
uptime
# load average: 15.42, 12.35, 8.76 → 코어 수보다 훨씬 높으면 CPU 병목

# CPU 코어 수 확인
nproc
```

**Step 2: CPU/메모리 자원 소비 프로세스 확인**

```bash
# CPU 사용률 상위 프로세스
top
# 'P' 키: CPU 순 정렬, 'M' 키: 메모리 순 정렬

# 단일 실행 확인
ps aux --sort=-%cpu | head -10
ps aux --sort=-%mem | head -10
```

**Step 3: 디스크 I/O 대기 확인**

```bash
# top의 %wa (I/O wait)가 높으면 디스크 병목
# 상세 I/O 확인: 1초 간격 3회
iostat -x 1 3

# I/O를 유발하는 프로세스 확인
iotop -o
```

출력에서 `%util`이 90% 이상이면 디스크가 병목입니다.

**Step 4: 메모리 및 스왑 확인**

```bash
# 메모리 사용량
free -h

# 스왑 사용 중이면 (si/so 항목)
vmstat 1 5
```

스왑 사용 중이면 메모리 부족으로 디스크 I/O가 급증하여 전체 시스템이 느려집니다.

**Step 5: 좀비 프로세스 및 프로세스 상태 확인**

```bash
# 좀비 프로세스 수 확인 (top 헤더의 zombie 항목)
ps aux | grep Z

# 프로세스 트리 확인
ps auxf | head -30
pstree -p
```

**Step 6: 종합 점검**

```bash
# 종합 분석
dstat -cdmn 1 10

# 시스템 전체 활동 요약
sar -A -f /var/log/sa/sa$(date +%d) | head -50
```

### 원인별 해결 방법

| 원인 | 확인 명령 | 해결 방법 |
|------|---------|---------|
| CPU 과부하 | `top` - %us 높음 | 문제 프로세스 종료 또는 우선순위 조정 (`renice`) |
| 메모리 부족 | `free -h` - available 거의 없음 | 불필요한 서비스 중지, 스왑 추가 |
| 디스크 I/O | `iostat %util` > 90% | I/O 유발 프로세스 제한, 디스크 업그레이드 |
| 스왑 과다 | `vmstat` si/so 높음 | 메모리 증설, 캐시 수동 해제 |

```bash
# 프로세스 우선순위 조정 (nice값: -20 높음 ~ 19 낮음)
renice 10 -p PID         # 실행 중인 프로세스의 nice값 올림
nice -n 10 명령어         # 낮은 우선순위로 실행

# 페이지 캐시 해제 (응급 시에만)
sync
echo 3 > /proc/sys/vm/drop_caches
```

## 핵심 정리

- **장애 진단 원칙:** 증상 파악 → 로그 확인 → 원인 분리 → 최소 변경 → 검증
- **웹 접속 불가:** ping → ss -tuln | grep :80 → systemctl status → 에러 로그 → firewall-cmd → getenforce
- **디스크 꽉 참:** df -h → du -sh /* | sort -rh → find -size +100M → journalctl --vacuum-size → lsof | grep deleted
- **SSH 불가:** 콘솔 직접 접속 → systemctl status sshd → /var/log/secure → ss -tuln | grep :22 → sshd -t
- **응답 느림:** uptime(로드) → top(CPU/메모리) → iostat -x(디스크 I/O wait) → free -h(스왑)
- **sshd -t:** 설정 파일 문법 검사 (오류 없으면 아무 출력 없음)
- **lsof | grep deleted:** 삭제됐지만 프로세스가 점유 중인 파일 → 공간 반환 안 됨
