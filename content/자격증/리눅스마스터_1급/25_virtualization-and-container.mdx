## 가상화 유형 이해

### 전가상화 vs 반가상화

| 구분 | 전가상화 (Full Virtualization) | 반가상화 (Para-Virtualization) |
|------|-------------------------------|-------------------------------|
| 게스트 OS 수정 | 불필요 (원본 OS 그대로 사용) | 필요 (하이퍼바이저 인식 드라이버 포함) |
| 성능 | 하드웨어 에뮬레이션으로 오버헤드 큼 | 게스트-하이퍼바이저 직접 통신으로 빠름 |
| 호환성 | 높음 (Windows 포함 대부분 OS 가능) | 낮음 (수정된 커널 필요) |
| 대표 기술 | KVM (VT-x/AMD-V 활용), VMware ESXi | Xen (반가상화 모드) |

- **KVM은 Intel VT-x 또는 AMD-V 하드웨어 가상화 기능을 활용**해 전가상화이면서도 성능이 우수합니다.
- CPU가 가상화 지원 여부를 확인하려면 `/proc/cpuinfo`의 `vmx`(Intel) 또는 `svm`(AMD) 플래그를 확인합니다.

```bash
# CPU 가상화 지원 확인
grep -E 'vmx|svm' /proc/cpuinfo | head -5

# 현재 가상화 환경 감지
systemd-detect-virt
```

### Type 1 vs Type 2 하이퍼바이저

| 구분 | Type 1 (베어메탈) | Type 2 (호스트형) |
|------|------------------|-----------------|
| 동작 방식 | 하드웨어 위에 하이퍼바이저가 직접 구동 | 호스트 OS 위에서 애플리케이션으로 동작 |
| 성능 | 높음 (호스트 OS 오버헤드 없음) | 낮음 (호스트 OS를 거침) |
| 용도 | 서버 가상화, 데이터센터 | 개발·테스트 환경, 개인 PC |
| 예시 | VMware ESXi, KVM (Linux 커널 내장), Hyper-V | VirtualBox, VMware Workstation, QEMU |

<Callout type="warning">
  **시험 포인트:** KVM은 Linux 커널 모듈로 동작하므로 Type 1과 Type 2의 경계가 모호합니다. KVM은 일반적으로 **Type 1에 가까운** 구조로 분류됩니다. 호스트 커널이 하이퍼바이저 역할을 직접 수행하기 때문입니다.
</Callout>

## KVM 가상머신 관리

### virsh 명령어

`virsh`는 KVM/libvirt 가상머신을 관리하는 CLI 도구입니다.

```bash
# 실행 중인 VM 목록 조회
virsh list

# 모든 VM 목록 조회 (중지된 것 포함)
virsh list --all

# VM 시작
virsh start vm-이름

# VM 정상 종료 (게스트 OS에 종료 신호 전달)
virsh shutdown vm-이름

# VM 강제 종료 (전원 off)
virsh destroy vm-이름

# VM 재부팅
virsh reboot vm-이름

# VM 상세 정보 확인
virsh dominfo vm-이름

# VM 일시 중단 / 재개
virsh suspend vm-이름
virsh resume vm-이름

# VM 자동 시작 설정
virsh autostart vm-이름
virsh autostart --disable vm-이름
```

`virsh dominfo` 출력 예시:

```
Name:           centos7-vm
UUID:           a1b2c3d4-e5f6-7890-abcd-ef1234567890
OS Type:        hvm
State:          running
CPU(s):         2
Max memory:     2097152 KiB
Used memory:    2097152 KiB
Persistent:     yes
Autostart:      disable
```

### QEMU 이미지 관리

```bash
# 이미지 정보 확인
qemu-img info 이미지.qcow2

# 새 이미지 생성 (qcow2 형식, 20GB)
qemu-img create -f qcow2 새이미지.qcow2 20G

# 이미지 변환 (raw → qcow2)
qemu-img convert -f raw -O qcow2 원본.img 변환.qcow2

# 이미지 스냅샷 생성
qemu-img snapshot -c snap1 이미지.qcow2

# 이미지 크기 확장 (기존 20G → 30G)
qemu-img resize 이미지.qcow2 30G
```

`qemu-img info` 출력 예시:

```
image: centos7.qcow2
file format: qcow2
virtual size: 20 GiB (21474836480 bytes)
disk size: 3.5 GiB
cluster_size: 65536
```

<Callout type="info">
  **qcow2 vs raw:** qcow2(QEMU Copy-On-Write v2)는 스냅샷, 씬 프로비저닝(실제 사용량만 차지), 압축을 지원합니다. raw는 성능이 더 빠르지만 이런 기능을 지원하지 않습니다.
</Callout>

## 컨테이너 vs 가상머신 비교

| 구분 | 가상머신 (VM) | 컨테이너 |
|------|-------------|---------|
| 커널 | 각 VM이 독립 커널 보유 | 호스트 커널 공유 |
| 격리 수준 | 완전한 하드웨어 수준 격리 | 프로세스 수준 격리 |
| 부팅 시간 | 수십 초 ~ 수 분 | 수 밀리초 ~ 수 초 |
| 리소스 사용 | 많음 (OS 오버헤드 포함) | 적음 (애플리케이션만) |
| 이미지 크기 | 수 GB | 수십 ~ 수백 MB |
| 보안 격리 | 강함 | 상대적으로 약함 |
| 이식성 | OS 의존적 | 높음 (이미지 단위 배포) |

## Docker 기본 개념

### 핵심 구성 요소

- **이미지 (Image):** 컨테이너 실행에 필요한 파일 시스템과 설정의 읽기 전용 템플릿. 레이어 구조로 저장됩니다.
- **컨테이너 (Container):** 이미지를 기반으로 생성된 실행 가능한 인스턴스. 쓰기 가능한 레이어가 추가됩니다.
- **레지스트리 (Registry):** 이미지를 저장하고 배포하는 저장소. Docker Hub가 대표적이며, 사설 레지스트리도 구축 가능합니다.
- **Dockerfile:** 이미지 생성 방법을 정의한 스크립트 파일.

### Docker 핵심 명령어

```bash
# 이미지 다운로드
docker pull nginx:latest
docker pull ubuntu:22.04

# 이미지 목록 확인
docker images

# 컨테이너 실행
# -d: 백그라운드 실행, -p: 포트 매핑(호스트:컨테이너), --name: 컨테이너 이름
docker run -d -p 8080:80 --name my-nginx nginx

# 실행 중인 컨테이너 목록
docker ps

# 모든 컨테이너 목록 (중지된 것 포함)
docker ps -a

# 컨테이너 중지
docker stop my-nginx

# 컨테이너 시작 (중지된 것 재시작)
docker start my-nginx

# 컨테이너 재시작
docker restart my-nginx

# 컨테이너 삭제 (중지 후 삭제)
docker stop my-nginx
docker rm my-nginx

# 실행 중인 컨테이너에 명령 실행 (인터랙티브 bash)
docker exec -it my-nginx bash

# 컨테이너 로그 확인
docker logs my-nginx
docker logs -f my-nginx    # 실시간 로그 추적

# 이미지 삭제
docker rmi nginx:latest

# 이미지 빌드 (현재 디렉토리의 Dockerfile 사용)
docker build -t my-app:1.0 .
docker build -t my-app:1.0 -f /path/to/Dockerfile .
```

### Dockerfile 기본 구조

```dockerfile
# FROM: 베이스 이미지 지정 (반드시 첫 번째 명령)
FROM ubuntu:22.04

# 메타데이터 설정
LABEL maintainer="admin@example.com"
LABEL version="1.0"

# RUN: 이미지 빌드 시 실행할 명령어 (레이어 생성)
RUN apt-get update && apt-get install -y \
    nginx \
    curl \
    && rm -rf /var/lib/apt/lists/*

# WORKDIR: 작업 디렉토리 설정
WORKDIR /var/www/html

# COPY: 호스트 파일을 이미지로 복사
COPY ./html/ .

# ADD: COPY와 유사하지만 URL 다운로드, tar 압축 해제 기능 추가
ADD https://example.com/config.tar.gz /etc/myapp/

# ENV: 환경변수 설정
ENV APP_ENV=production
ENV PORT=8080

# EXPOSE: 컨테이너가 사용할 포트 문서화 (실제 포트 오픈은 docker run -p 로)
EXPOSE 80

# VOLUME: 데이터 영구 저장을 위한 볼륨 마운트 포인트
VOLUME ["/var/log/nginx"]

# CMD: 컨테이너 시작 시 실행할 기본 명령 (docker run으로 덮어쓸 수 있음)
CMD ["nginx", "-g", "daemon off;"]

# ENTRYPOINT: 항상 실행될 명령 (CMD와 달리 덮어쓰기 어려움)
# ENTRYPOINT ["nginx"]
```

<Callout type="warning">
  **CMD vs ENTRYPOINT 차이:**
  - `CMD`는 `docker run` 시 인수를 전달하면 덮어씁니다.
  - `ENTRYPOINT`는 항상 실행되며, `docker run` 인수는 ENTRYPOINT의 인수로 전달됩니다.
  - 둘을 함께 쓰면 ENTRYPOINT가 실행 명령, CMD가 기본 인수가 됩니다.
</Callout>

## 컨테이너 격리 원리: 네임스페이스와 cgroups

### Linux 네임스페이스 (Namespace)

네임스페이스는 프로세스가 볼 수 있는 시스템 자원의 범위를 격리합니다. Docker는 6가지 네임스페이스를 활용합니다.

| 네임스페이스 | 격리 대상 | 설명 |
|------------|---------|------|
| `pid` | 프로세스 ID | 컨테이너 내부는 PID 1부터 시작 (호스트와 독립) |
| `net` | 네트워크 | 네트워크 인터페이스, IP, 라우팅 테이블 격리 |
| `mnt` | 파일 시스템 마운트 | 독립적인 파일 시스템 뷰 |
| `uts` | 호스트명 | 컨테이너별 독립 호스트명/도메인명 |
| `ipc` | 프로세스 간 통신 | 공유 메모리, 세마포어 격리 |
| `user` | 사용자/그룹 ID | 컨테이너 내 root가 호스트에서는 일반 사용자 |

```bash
# 네임스페이스 확인 (프로세스의 네임스페이스 링크)
ls -la /proc/1/ns/

# 컨테이너 PID를 호스트에서 확인
docker inspect --format '{{.State.Pid}}' 컨테이너이름
ls -la /proc/<PID>/ns/
```

### cgroups (Control Groups)

cgroups는 프로세스 그룹의 **자원 사용량을 제한·모니터링**합니다.

| 서브시스템 | 제어 대상 |
|-----------|---------|
| `cpu` | CPU 사용 시간 제한 |
| `memory` | 메모리 사용량 제한 |
| `blkio` | 블록 디바이스 I/O 제한 |
| `cpuset` | 특정 CPU 코어 할당 |
| `net_cls` | 네트워크 패킷 분류 |

```bash
# docker run에서 자원 제한 옵션
docker run -d \
  --memory="512m" \
  --memory-swap="1g" \
  --cpus="1.5" \
  --cpu-shares=512 \
  nginx

# 컨테이너 자원 사용량 실시간 모니터링
docker stats

# 특정 컨테이너 통계
docker stats my-nginx
```

<Callout type="info">
  **핵심 요약:** 컨테이너는 네임스페이스로 **격리(isolation)**하고, cgroups로 **자원을 제한(resource limiting)**합니다. 이 두 기술이 컨테이너의 핵심 기반 기술입니다.
</Callout>

## 핵심 정리

- **전가상화:** 게스트 OS 수정 불필요, 하드웨어 에뮬레이션, KVM/VMware ESXi
- **반가상화:** 게스트 OS 수정 필요, 하이퍼바이저와 직접 통신, Xen
- **Type 1:** 하드웨어 위에 직접 구동 (ESXi, KVM), 성능 우수
- **Type 2:** 호스트 OS 위에서 동작 (VirtualBox, VMware Workstation)
- **virsh list --all:** KVM 전체 VM 목록 (중지 포함)
- **virsh start/shutdown/destroy:** VM 시작/정상종료/강제종료
- **qemu-img info:** 이미지 형식·크기·스냅샷 정보 확인
- **컨테이너:** 호스트 커널 공유, 빠른 기동, 가벼움
- **VM:** 독립 커널, 강한 격리, 무거움
- **네임스페이스 6종:** pid, net, mnt, uts, ipc, user → 격리
- **cgroups:** CPU, 메모리, I/O 자원 제한
- **Dockerfile:** FROM(베이스) → RUN(명령) → COPY(파일) → CMD(실행)
