## 왜 파이프라이닝이 필요한가?

06번 문서에서 배운 명령어 사이클(인출→해독→실행)은 한 명령어가 끝나야 다음 명령어를 시작하는 것처럼 보일 수 있습니다. 하지만 세탁기·건조기를 따로 쓰는 것처럼, 한 명령어가 "실행" 단계에 있을 때 다음 명령어를 미리 "인출"해두면 훨씬 효율적이지 않을까요? 이 아이디어가 **파이프라이닝**입니다.

## 파이프라이닝(Pipelining)

> **쉽게 말하면:** 파이프라이닝은 공장의 조립 라인처럼, 명령어 처리 과정을 여러 단계로 나누고 각 단계를 동시에 겹쳐서 처리하는 방법입니다.

**예시:** 세탁(인출) → 건조(해독) → 개기(실행) 3단계로 이루어진 빨래 작업을 3번 반복한다고 합시다.

<Table>
  <thead>
    <tr><th>시간</th><th>1</th><th>2</th><th>3</th><th>4</th><th>5</th></tr>
  </thead>
  <tbody>
    <tr><td>파이프라인 없이</td><td>세탁1</td><td>건조1</td><td>개기1</td><td>세탁2</td><td>건조2</td></tr>
    <tr><td>파이프라인 적용</td><td>세탁1</td><td>세탁2, 건조1</td><td>세탁3, 건조2, 개기1</td><td>건조3, 개기2</td><td>개기3</td></tr>
  </tbody>
</Table>

**해석:** 파이프라인 없이는 3벌을 처리하는 데 9단계가 걸리지만, 파이프라인을 적용하면 5단계 만에 끝납니다. 겹쳐서 동시에 처리하기 때문입니다.

## 파이프라인 해저드(Hazard) — 성능을 방해하는 요인

> **쉽게 말하면:** 해저드는 파이프라인이 매끄럽게 겹쳐 돌아가지 못하고 "덜컹거리는" 상황입니다.

<Table>
  <thead>
    <tr><th>해저드 종류</th><th>원인</th></tr>
  </thead>
  <tbody>
    <tr><td>구조적 해저드(Structural)</td><td>같은 하드웨어 자원(메모리 등)을 두 명령어가 동시에 쓰려고 충돌</td></tr>
    <tr><td>데이터 해저드(Data)</td><td>뒤 명령어가 앞 명령어의 결과값을 필요로 하는데, 앞 명령어가 아직 결과를 내지 못함</td></tr>
    <tr><td>제어 해저드(Control)</td><td>08번 문서에서 배운 JUMP·BRANCH 명령어 때문에 다음에 실행할 명령어를 미리 알 수 없음</td></tr>
  </tbody>
</Table>

<Callout type="warning">
  **자주 틀리는 점:** 파이프라이닝이 각 명령어 개별의 처리 시간(지연시간, Latency)을 줄여주는 것은 **아닙니다.** 한 명령어가 인출부터 실행까지 걸리는 시간 자체는 동일합니다. 파이프라이닝이 향상시키는 것은 **처리량**(Throughput, 단위 시간당 처리하는 명령어 개수)입니다.
</Callout>

## 슈퍼스칼라(Superscalar)

> **쉽게 말하면:** 파이프라인 하나가 "한 줄로 겹쳐 처리하는 조립 라인"이라면, 슈퍼스칼라는 이런 조립 라인을 **여러 개 동시에** 두어 한 번에 여러 명령어를 병렬로 처리하는 구조입니다.

파이프라이닝이 명령어를 "겹쳐서" 처리한다면, 슈퍼스칼라는 여러 개의 실행 유닛(ALU 등)을 두어 명령어를 진짜로 "동시에" 여러 개 처리합니다.

## RISC vs CISC

> **쉽게 말하면:** RISC는 "적고 단순한 명령어를 빠르게 많이 실행"하는 철학이고, CISC는 "복잡하고 다양한 명령어로 한 번에 많은 일을 처리"하는 철학입니다.

<Table>
  <thead>
    <tr><th>구분</th><th>RISC(Reduced Instruction Set Computer)</th><th>CISC(Complex Instruction Set Computer)</th></tr>
  </thead>
  <tbody>
    <tr><td>명령어 개수</td><td>적음, 단순함</td><td>많음, 복잡함</td></tr>
    <tr><td>명령어 길이</td><td>고정 길이(균일)</td><td>가변 길이</td></tr>
    <tr><td>실행 시간</td><td>대부분 1클럭에 실행</td><td>명령어마다 실행 시간이 다양</td></tr>
    <tr><td>제어장치</td><td>07번 문서의 하드와이어드 방식과 궁합이 좋음</td><td>07번 문서의 마이크로프로그램 방식과 궁합이 좋음</td></tr>
    <tr><td>파이프라이닝</td><td>단순하고 균일한 명령어라 파이프라이닝에 유리</td><td>복잡하고 길이가 달라 파이프라이닝이 어려움</td></tr>
    <tr><td>대표 예시</td><td>ARM(모바일 기기 다수)</td><td>x86(인텔·AMD의 PC용 CPU)</td></tr>
  </tbody>
</Table>

<Callout type="info">
  **왜 모바일은 주로 RISC를 쓰는가?**(ARM 계열) RISC는 명령어가 단순해 회로도 단순해지고, 이는 전력 소모가 적다는 장점으로 이어집니다. 배터리로 동작하는 스마트폰 등에서는 이 전력 효율성이 매우 중요해, ARM(RISC 계열)이 널리 쓰입니다. 반면 전원 걱정이 덜한 데스크톱·서버에서는 복잡한 연산을 한 번에 처리하는 CISC(x86 계열)의 강력함이 유리하게 작용해온 역사가 있습니다.
</Callout>

## 핵심 정리

- **파이프라이닝**: 명령어 처리 단계를 겹쳐서 실행해 처리량(Throughput)을 높임. 개별 명령어의 지연시간은 줄이지 않음.
- **파이프라인 해저드**: 구조적(자원 충돌), 데이터(값 의존), 제어(분기로 인한 불확실성) 해저드가 성능을 저해.
- **슈퍼스칼라**: 여러 실행 유닛으로 명령어를 진짜 동시에 병렬 처리.
- **RISC**: 단순·고정 길이 명령어, 하드와이어드·파이프라이닝에 유리, 전력 효율(모바일에 적합).
- **CISC**: 복잡·가변 길이 명령어, 마이크로프로그램 방식과 궁합, 강력한 단일 명령어(데스크톱·서버 전통적 강세).
