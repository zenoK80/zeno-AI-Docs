## 스레드가 왜 필요한가?

웹 브라우저를 예로 들겠습니다. 웹 페이지를 불러오면서 동시에 동영상을 재생하고, 사용자 입력도 받아야 합니다. 만약 이 모든 작업을 하나의 흐름(프로세스 1개)으로만 처리하면, 동영상을 불러오는 동안 키보드 입력이 먹히지 않는 상황이 생깁니다.

이 문제를 해결하기 위해 하나의 프로세스 안에서 여러 작업 흐름을 동시에 처리하는 **스레드(Thread)**가 필요합니다.

**쉽게 말하면:** 프로세스가 공장이라면, 스레드는 공장 안에서 일하는 각각의 직원입니다. 같은 공장(프로세스) 안에서 여러 직원(스레드)이 도구(메모리)를 공유하며 서로 다른 작업을 동시에 진행합니다.

## 스레드란?

**스레드(Thread)**는 프로세스 내에서 실행되는 흐름의 단위입니다. CPU 스케줄링(Scheduling, 순서 결정)의 기본 단위이기도 합니다.

하나의 프로세스 안에 여러 스레드가 존재할 수 있으며, 이들은 프로세스의 자원을 공유합니다.

| 구분 | 프로세스 | 스레드 |
|------|---------|--------|
| 자원 | 독립적인 메모리 공간 | 프로세스 내 자원 공유 |
| 생성 비용 | 높음 (메모리 복사 필요) | 낮음 (공유 자원만 초기화) |
| 통신 방식 | IPC(Inter-Process Communication, 프로세스 간 통신) — 파이프, 메시지 큐 등 | 공유 메모리 직접 접근 |
| 오류 영향 | 프로세스 간 격리 | 하나의 스레드 오류가 전체에 영향 |

## 스레드의 구성 요소

같은 프로세스의 스레드들은 **공유하는 것**과 **개별로 가지는 것**이 구분됩니다.

### 스레드가 공유하는 자원 (프로세스 자원)

- 코드(텍스트) 영역 — 모든 스레드가 같은 코드를 실행할 수 있음
- 데이터 영역 (전역 변수, 정적 변수)
- 힙(Heap) 영역 — 동적으로 할당한 메모리 공간
- 열린 파일, 소켓 등

### 스레드가 개별로 보유하는 자원

- **스택(Stack):** 함수 호출, 지역 변수 — 각 스레드의 독립적인 실행 경로가 필요하기 때문
- **레지스터(Register) 값:** 현재 실행 중인 상태
- **프로그램 카운터(PC, Program Counter):** 다음 실행 명령어 주소
- **스레드 ID(Thread ID)**

```
프로세스 메모리 공간
┌─────────────────────────────┐
│         코드 영역            │ (공유)
├─────────────────────────────┤
│         데이터 영역           │ (공유)
├─────────────────────────────┤
│         힙 영역              │ (공유)
├──────────┬──────────────────┤
│ 스택(T1) │ 스택(T2) │ 스택(T3)│ (개별)
└──────────┴──────────────────┘
```

## 사용자 스레드 vs 커널 스레드

### 사용자 수준 스레드 (User-Level Thread)

운영체제 커널이 모르는 상태에서 **사용자 공간의 라이브러리(Library)**가 스레드를 관리합니다.

**쉽게 말하면:** 운영체제 몰래 프로그램이 자체적으로 직원(스레드)을 관리하는 것입니다.

**장점:**
- 스레드 생성/전환이 빠름 (커널 개입 없음)
- 스케줄링을 응용 프로그램이 직접 제어

**단점:**
- 하나의 스레드가 블록(Block, I/O 대기로 멈춤)되면 **전체 프로세스가 블록**됨
- 멀티코어 CPU를 활용하지 못함 (커널은 프로세스 단위로만 CPU 배분)

### 커널 수준 스레드 (Kernel-Level Thread)

운영체제 **커널이 직접 스레드를 생성하고 관리**합니다. Windows, Linux 등 현대 OS가 사용하는 방식입니다.

**쉽게 말하면:** 운영체제가 직원(스레드)을 직접 알고 관리하는 방식입니다.

**장점:**
- 하나의 스레드가 블록되어도 다른 스레드는 계속 실행 가능
- 멀티코어(Multi-core) CPU를 효율적으로 활용

**단점:**
- 스레드 생성/전환 시 커널 모드 전환 비용 발생
- 사용자 스레드보다 느림

## 멀티스레딩 모델

사용자 스레드와 커널 스레드를 연결하는 방식에 따라 3가지 모델이 있습니다.

### 다대일 모델 (Many-to-One)

여러 사용자 스레드 → 1개의 커널 스레드

- 스레드 관리가 사용자 공간에서 이루어져 효율적
- 하나가 블록되면 모두 블록 / 멀티코어 활용 불가

### 일대일 모델 (One-to-One)

1개의 사용자 스레드 → 1개의 커널 스레드

- Windows, Linux에서 사용
- 멀티코어 활용 가능, 병렬(Parallel) 실행 가능
- 스레드 생성 비용이 높아 수를 제한

### 다대다 모델 (Many-to-Many)

여러 사용자 스레드 ↔ 그보다 적거나 같은 수의 커널 스레드

- 앞선 두 모델의 단점을 보완
- 구현이 복잡함

| 모델 | 특징 | 사용 OS |
|------|------|---------|
| 다대일 | 빠르지만 블록 문제 | 초기 POSIX |
| 일대일 | 병렬 실행 가능 | Windows, Linux |
| 다대다 | 유연하지만 복잡 | Solaris, HP-UX |

## 멀티스레딩의 장점

**멀티스레딩(Multithreading)**은 하나의 프로세스 안에 여러 스레드를 두는 것입니다.

1. **응답성(Responsiveness):** 일부 스레드가 블록되어도 다른 스레드는 계속 실행 — 화면이 멈추지 않음
2. **자원 공유(Resource Sharing):** 메모리를 공유하므로 프로세스 간 통신(IPC)보다 효율적
3. **경제성(Economy):** 프로세스 생성보다 스레드 생성 비용이 훨씬 낮음
4. **멀티코어 활용(Scalability):** 여러 CPU 코어에서 스레드를 병렬 실행

## 멀티스레딩의 문제점

### 경쟁 조건(Race Condition, 레이스 컨디션)

**경쟁 조건**은 여러 스레드가 공유 데이터에 동시에 접근할 때 실행 순서에 따라 결과가 달라지는 문제입니다.

```
스레드 1: x = x + 1  (x가 100일 때)
스레드 2: x = x + 1  (동시에 실행)
예상 결과: x = 102
실제 결과: x = 101 (두 스레드가 동시에 100을 읽어 각각 101로 저장)
```

**쉽게 말하면:** 두 사람이 같은 통장에서 동시에 돈을 출금할 때 잔액 계산이 꼬이는 것과 같습니다.

이 문제를 해결하려면 **동기화(Synchronization)** 메커니즘이 필요합니다. (다음 문서에서 자세히 다룸)

## 핵심 정리

- 스레드(Thread)는 프로세스 내 실행 흐름의 단위로, 코드·데이터·힙은 공유하고 스택·레지스터·PC는 개별 보유
- 사용자 스레드는 빠르지만 블록 문제가 있고, 커널 스레드는 멀티코어를 활용하지만 비용이 높음
- 현대 OS는 일대일 모델(1 사용자 스레드 = 1 커널 스레드)을 주로 사용
- 멀티스레딩의 장점은 응답성, 자원 공유, 경제성, 멀티코어 활용이다
- 공유 자원 접근 시 경쟁 조건(Race Condition) 문제가 발생하며 동기화가 필요하다
