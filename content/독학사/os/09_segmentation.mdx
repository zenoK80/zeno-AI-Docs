## 세그멘테이션이 왜 필요한가?

페이징(Paging)은 외부 단편화를 없애는 훌륭한 기법이지만 한 가지 단점이 있습니다. 프로세스를 **기계적으로** 일정한 크기로 잘라내기 때문에, 코드와 데이터가 같은 페이지에 섞여 들어갈 수 있습니다.

예를 들어, 코드 영역은 "읽기만 가능"하고 데이터 영역은 "읽기/쓰기 가능"해야 합니다. 그런데 페이징은 이 경계를 신경 쓰지 않고 자릅니다. 보호(Protection)와 공유(Sharing)가 논리적 단위로 이루어지지 않아 불편합니다.

**세그멘테이션(Segmentation)**은 이 문제를 해결합니다. 프로세스를 **프로그래머가 의미 있다고 생각하는 단위**로 분리합니다.

**쉽게 말하면:** 페이징이 책을 무조건 10페이지씩 자르는 것이라면, 세그멘테이션은 책을 "서문 / 1장 / 2장 / 부록" 같이 의미 있는 챕터로 나누는 것입니다.

## 세그멘테이션(Segmentation)이란?

**세그멘테이션**은 프로세스를 논리적으로 의미 있는 **가변 크기의 세그먼트(Segment, 세그먼트)**로 나누어 관리하는 기법입니다.

- 코드(Code), 스택(Stack), 힙(Heap), 데이터(Data) 등 논리적 단위로 분할
- 각 세그먼트는 크기가 달라도 됩니다
- 프로그래머(또는 컴파일러)가 주소 공간을 **세그먼트 번호와 오프셋**으로 인식

```
세그먼트 구성 예시:
┌──────────────────┐
│ 세그먼트 0: 코드  │ (5KB) — 읽기 전용
│ 세그먼트 1: 스택  │ (8KB) — 읽기/쓰기
│ 세그먼트 2: 힙    │ (3KB) — 읽기/쓰기
│ 세그먼트 3: 데이터│ (10KB) — 읽기/쓰기
└──────────────────┘
```

각 세그먼트는 물리 메모리 어느 위치에나 올라갈 수 있습니다 (비연속 배치 가능).

## 세그먼트 테이블(Segment Table)

**세그먼트 테이블(Segment Table)**은 각 세그먼트의 **기준 주소(Base, 물리 메모리 시작 위치)**와 **한계(Limit, 세그먼트 크기)**를 저장합니다.

**쉽게 말하면:** 세그먼트 테이블은 각 챕터가 책의 몇 페이지에서 시작하고 몇 페이지까지인지 기록하는 목차와 같습니다.

| 세그먼트 번호 | 기준 주소(Base) | 한계(Limit) |
|-------------|----------------|------------|
| 0 | 1000 | 400 |
| 1 | 6300 | 100 |
| 2 | 4300 | 400 |
| 3 | 3200 | 1100 |

### 주소 변환 과정

논리 주소(Logical Address) = (세그먼트 번호 s, 오프셋 d)

```
1. 세그먼트 테이블에서 s의 기준 주소(base)와 한계(limit) 확인
2. d >= limit이면 → 세그먼트 오류(Segmentation Fault) 발생
3. 정상이면: 물리 주소 = base + d
```

**예시:** 논리 주소 (2, 100)

- 세그먼트 2의 base = 4300, limit = 400
- 100 < 400이므로 정상
- 물리 주소 = 4300 + 100 = **4400**

**예시 (오류):** 논리 주소 (1, 150)

- 세그먼트 1의 base = 6300, limit = 100
- 150 >= 100이므로 **세그먼트 오류** 발생 (프로그램이 허용 범위를 벗어난 주소에 접근)

## STBR과 STLR 레지스터

CPU 안에는 세그먼트 테이블의 위치와 크기를 빠르게 찾기 위한 레지스터가 있습니다.

| 레지스터 | 의미 | 역할 |
|---------|------|------|
| **STBR (Segment-Table Base Register)** | 세그먼트 테이블 기준 레지스터 | 세그먼트 테이블의 메모리 시작 주소 저장 |
| **STLR (Segment-Table Length Register)** | 세그먼트 테이블 한계 레지스터 | 세그먼트 테이블의 총 항목 수 저장 |

세그먼트 번호 s가 STLR보다 크거나 같으면 → 범위를 벗어난 접근이므로 세그먼트 오류 발생

## 세그멘테이션의 장점과 단점

### 장점

- **논리적 분리(Logical Separation):** 코드, 데이터, 스택을 별도로 관리하여 보호가 직관적
- **공유(Sharing) 용이:** 세그먼트 단위로 공유 가능 (공유 라이브러리 등 — 여러 프로세스가 같은 코드 세그먼트를 공유)
- **내부 단편화 없음:** 세그먼트가 필요한 크기만큼 딱 맞게 할당

### 단점

- **외부 단편화(External Fragmentation) 발생:** 가변 크기 할당으로 인해 빈 공간이 조각남
- **크기 예측 어려움:** 특히 스택(Stack), 힙(Heap)은 실행 중 크기가 변함

**비유:** 책상 위에 크기가 모두 다른 물건들을 올려놓다 보면 이리저리 틈새가 생겨 물건을 새로 올릴 공간이 없어지는 것과 비슷합니다.

## 페이징 vs 세그멘테이션 비교

| 구분 | 페이징 | 세그멘테이션 |
|------|--------|-------------|
| 분할 크기 | **고정** (페이지 크기 동일) | **가변** (세그먼트마다 다름) |
| 논리적 단위 | 없음 (임의 분할) | 있음 (코드, 스택 등) |
| 외부 단편화 | **없음** | 발생 |
| 내부 단편화 | 소량 발생 | **없음** |
| 보호(Protection) | 페이지 단위 (다소 부자연스러움) | 세그먼트 단위 (더 직관적) |
| 공유(Sharing) | 가능 | 가능 (세그먼트 단위로 더 쉬움) |

## 페이징과 세그멘테이션의 혼용

두 기법의 단점을 보완하기 위해 **혼용(Hybrid) 기법**을 사용합니다.

- 먼저 프로세스를 **세그먼트**로 나눔 → 논리적 분리와 직관적 보호 확보
- 각 세그먼트를 다시 **페이지**로 나눔 → 외부 단편화 제거

```
주소 변환 과정:
논리 주소 → [세그먼트 번호] → 세그먼트 테이블 → [페이지 번호] → 페이지 테이블 → 물리 주소
```

**쉽게 말하면:** 먼저 챕터(세그먼트)로 나눈 다음, 각 챕터를 다시 일정 크기의 페이지로 나눕니다. 챕터의 장점(논리적 구분, 보호)과 페이지의 장점(외부 단편화 없음)을 동시에 얻습니다.

**Intel x86(인텔 x86)** 아키텍처가 이 혼용 방식을 사용합니다.

| 특성 | 혼용 결과 |
|------|---------|
| 외부 단편화 | 페이징으로 제거 |
| 내부 단편화 | 마지막 페이지에서 소량 발생 |
| 논리적 분리 | 세그먼트로 유지 |
| 보호(Protection) | 세그먼트+페이지 두 단계 |

## 핵심 정리

- 세그멘테이션(Segmentation)은 가변 크기 세그먼트로 논리적 단위(코드, 스택, 힙, 데이터)를 유지하지만 외부 단편화가 발생한다
- 세그먼트 테이블은 각 세그먼트의 기준 주소(Base)와 한계(Limit)를 저장한다
- 논리 주소 (s, d): d >= limit이면 세그먼트 오류, 정상이면 물리 주소 = base + d
- 페이징은 외부 단편화 없음, 세그멘테이션은 내부 단편화 없음
- 혼용 기법은 두 장점을 결합하며 Intel x86이 이를 사용한다
