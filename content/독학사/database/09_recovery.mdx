## 회복(Recovery)이란?

데이터베이스 시스템에서 **장애**(Failure)가 발생했을 때 데이터베이스를 일관된 상태로 복원하는 과정입니다.

**장애 유형:**
| 유형 | 설명 |
|------|------|
| **트랜잭션 장애** | 트랜잭션 수행 중 오류 (논리 오류, 시스템 오류) |
| **시스템 장애** | 하드웨어/소프트웨어 오류로 DB가 중단 (전원 장애 등) |
| **미디어 장애** | 디스크 손상 등 저장 장치 장애 |

## 로그(Log) 기반 회복

모든 데이터베이스 변경 사항을 **로그**(Log, 저널)에 기록하여 장애 시 회복에 사용합니다.

### 로그 레코드 구조

```
[트랜잭션 ID, 작업 유형, 데이터 항목, 이전 값(Before Image), 이후 값(After Image)]
```

**예시:**
```
<T1, START>
<T1, A, 1000, 900>    -- A의 값을 1000에서 900으로 변경
<T1, B, 500, 600>     -- B의 값을 500에서 600으로 변경
<T1, COMMIT>
```

### WAL (Write-Ahead Logging) 원칙

**로그 우선 기록 원칙:** 실제 데이터를 디스크에 쓰기 전에 반드시 로그를 먼저 기록해야 합니다.

- 데이터 페이지를 디스크에 쓰기 전: UNDO 정보 로그 먼저 기록
- COMMIT 전: REDO 정보 로그 먼저 기록

## REDO와 UNDO

### REDO (다시 실행)

**커밋된 트랜잭션**의 변경 내용을 다시 적용합니다.

- 장애 발생 전에 커밋했지만 디스크에 반영되지 않은 데이터를 복원
- 로그의 이후 값(After Image)을 사용
- 순방향(처음 → 끝)으로 수행

**상황:** COMMIT 로그가 있으나 디스크에 반영 안 된 트랜잭션

### UNDO (취소)

**커밋되지 않은 트랜잭션**의 변경 내용을 취소합니다.

- 장애 발생 시 완료되지 않은 트랜잭션을 롤백
- 로그의 이전 값(Before Image)을 사용
- 역방향(끝 → 처음)으로 수행

**상황:** COMMIT 로그가 없는 트랜잭션 (START는 있으나 COMMIT 없음)

### REDO/UNDO 결정

```
장애 발생 후 로그 분석:
  COMMIT 레코드 있음 → REDO 대상
  COMMIT 레코드 없음 → UNDO 대상
```

## 갱신 방식에 따른 회복 기법

### Deferred Update (지연 갱신)

트랜잭션이 **커밋되기 전까지 실제 데이터를 디스크에 쓰지 않습니다.**

```
1. 트랜잭션 수행 → 변경 내용을 로그에만 기록
2. COMMIT 시점에 로그를 디스크에 기록
3. 이후 실제 데이터를 디스크에 반영
```

**회복:**
- 장애 시 커밋되지 않은 트랜잭션: 로그를 무시 (UNDO 불필요)
- 커밋된 트랜잭션 중 미반영: REDO

**No-Steal 정책:** 커밋 전 더티 페이지를 디스크에 쓰지 않음

### Immediate Update (즉시 갱신)

트랜잭션이 **커밋 전에도 변경 내용을 즉시 디스크에 반영**합니다.

```
1. 트랜잭션 수행 → 로그 기록 후 즉시 디스크에 쓰기
2. 커밋 또는 롤백
```

**회복:**
- 장애 시 커밋되지 않은 트랜잭션: UNDO 필요
- 커밋된 트랜잭션 중 미반영: REDO

**Steal 정책:** 커밋 전 더티 페이지를 디스크에 쓸 수 있음

### 비교

| 항목 | Deferred Update | Immediate Update |
|------|----------------|-----------------|
| 갱신 시점 | 커밋 후 | 커밋 전에도 가능 |
| UNDO 필요 | 불필요 | 필요 |
| REDO 필요 | 필요 | 필요 |
| 정책 | No-Steal | Steal |

## 체크포인트 (Checkpoint)

주기적으로 **현재까지의 모든 변경 사항을 디스크에 강제로 반영**하고, 체크포인트 레코드를 로그에 기록합니다.

**목적:** 회복 시 로그 전체를 탐색하지 않고 가장 최근 체크포인트부터 분석

**체크포인트 절차:**
1. 새로운 트랜잭션의 시작을 잠시 중단
2. 버퍼의 모든 더티 페이지를 디스크에 기록
3. `[CHECKPOINT, 활성 트랜잭션 목록]` 로그 기록
4. 트랜잭션 재개

**회복 시 처리:**
- 체크포인트 이후 COMMIT 기록 있음: REDO
- 체크포인트 이후 COMMIT 기록 없음: UNDO
- 체크포인트 이전에 COMMIT된 트랜잭션: 이미 디스크 반영 → 불필요

## 회복 절차 요약

```
1. 로그 분석 (Analysis Pass)
   - 체크포인트부터 끝까지 로그를 읽어 REDO/UNDO 대상 분류

2. REDO Pass (순방향)
   - COMMIT된 트랜잭션의 변경 내용을 로그 순서대로 재실행

3. UNDO Pass (역방향)
   - 미완료 트랜잭션의 변경 내용을 로그 역순으로 취소
```

## 핵심 정리

- WAL: 데이터 쓰기 전 로그 먼저 기록
- REDO: 커밋된 트랜잭션의 이후 값으로 재적용 (순방향)
- UNDO: 미완료 트랜잭션의 이전 값으로 취소 (역방향)
- Deferred Update: 커밋 후 갱신, UNDO 불필요
- Immediate Update: 즉시 갱신, UNDO 필요
- 체크포인트: 주기적 강제 반영으로 회복 범위 단축
