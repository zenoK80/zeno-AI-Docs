## 인덱스(Index)란?

책의 색인처럼 데이터를 **빠르게 검색**하기 위한 데이터 구조입니다.

**장점:**
- 검색(SELECT) 속도 향상
- ORDER BY, GROUP BY 성능 개선

**단점:**
- 추가 저장 공간 필요
- INSERT/UPDATE/DELETE 시 인덱스도 갱신하므로 쓰기 성능 저하

## B+ Tree 인덱스

데이터베이스에서 가장 널리 사용하는 인덱스 구조입니다.

### B+ Tree 구조

```
              [루트 노드]
              [50 | 100]
             /    |    \
    [내부 노드]  [내부 노드]  [내부 노드]
    [20|30]    [60|80]    [110|130]
   /  |  \    /  |  \    /   |   \
[리프] [리프] [리프] ...  [리프] [리프] [리프]
 ↔    ↔    ↔              ↔     ↔     ↔
```

**핵심 특징:**
- **내부 노드(Internal Node):** 키와 포인터만 저장 (실제 레코드 없음)
- **리프 노드(Leaf Node):** 키와 실제 레코드 포인터 저장, **순서대로 연결 리스트로 연결**
- 트리 높이가 일정(균형 트리)하여 모든 검색이 O(log n)
- 범위 검색에 효율적 (리프 노드 연결로 순차 접근 가능)

### B+ Tree vs B Tree

| 항목 | B Tree | B+ Tree |
|------|--------|---------|
| 데이터 저장 위치 | 모든 노드 | 리프 노드만 |
| 범위 검색 | 비효율적 | 리프 연결 리스트로 효율적 |
| 사용 | 파일 시스템 | 데이터베이스 인덱스 |

## Hash 인덱스

해시 함수를 사용하여 키를 버킷에 매핑합니다.

**버킷 주소 = h**(검색 키)

**특징:**
- 등치 검색(=) 시 O(1)의 매우 빠른 성능
- 범위 검색(BETWEEN, >, &lt;)에는 사용 불가
- 정렬 순서 유지 안 함
- 해시 충돌(Collision) 처리 필요

**B+ Tree vs Hash 인덱스:**

| 항목 | B+ Tree | Hash |
|------|---------|------|
| 등치 검색 | O(log n) | O(1) |
| 범위 검색 | 효율적 | 불가 |
| 정렬 | 유지 | 미유지 |
| 주요 사용 | 대부분의 인덱스 | 해시 조인, 메모리 DB |

## 클러스터 인덱스 vs 비클러스터 인덱스

### 클러스터 인덱스 (Clustered Index)

**인덱스의 순서 = 실제 테이블의 물리적 저장 순서**

- 테이블당 **1개만** 가능
- 범위 검색에 매우 효율적
- MySQL InnoDB: 기본 키(Primary Key)가 자동으로 클러스터 인덱스
- 리프 노드에 실제 데이터 행이 저장됨

### 비클러스터 인덱스 (Non-clustered Index)

**인덱스의 순서와 테이블의 물리적 순서가 다름**

- 테이블당 **여러 개** 가능
- 리프 노드에 실제 데이터의 주소(포인터) 저장
- 포인터를 통해 실제 데이터에 접근 (추가 I/O 발생)

**비교:**

| 항목 | 클러스터 | 비클러스터 |
|------|---------|-----------|
| 물리적 순서 | 인덱스와 일치 | 불일치 |
| 테이블당 개수 | 1개 | 여러 개 |
| 범위 검색 | 매우 효율적 | 상대적으로 비효율 |
| 추가 I/O | 없음 | 있음 (포인터 추적) |

## 밀집 인덱스 vs 희소 인덱스

### 밀집 인덱스 (Dense Index)

**모든 레코드에 대해 인덱스 항목이 존재**합니다.

- 인덱스 크기가 크지만 빠른 접근 가능
- 비클러스터 인덱스는 주로 밀집 인덱스

### 희소 인덱스 (Sparse Index)

**일부 레코드(주로 각 블록의 첫 번째 레코드)에만 인덱스 항목**이 존재합니다.

- 인덱스 크기가 작지만 검색 후 블록 내 순차 탐색 필요
- 클러스터 인덱스에서 사용 가능

**비교:**

| 항목 | 밀집 인덱스 | 희소 인덱스 |
|------|-----------|-----------|
| 인덱스 항목 | 모든 레코드 | 일부 레코드 |
| 인덱스 크기 | 큼 | 작음 |
| 검색 속도 | 빠름 | 상대적으로 느림 |

## 복합 인덱스 (Composite Index)

**두 개 이상의 열을 조합**하여 만든 인덱스입니다.

```sql
CREATE INDEX idx_name_dept ON employees (last_name, department);
```

**선두 열(Leftmost Prefix) 규칙:**
- (A, B, C) 복합 인덱스는 A, (A, B), (A, B, C) 검색에 유효
- B만 검색하거나 C만 검색하면 인덱스 비효율적 활용 또는 Full Scan

**활용 예:**
- `WHERE last_name = '김' AND department = '영업'` → 복합 인덱스 최적 활용
- `WHERE department = '영업'` → 선두 열이 없으므로 인덱스 효율 낮음

## 인덱스 설계 가이드

**인덱스 생성이 유리한 경우:**
- WHERE 절에 자주 사용되는 열
- JOIN 조건의 열
- ORDER BY, GROUP BY의 열
- 카디널리티(고유 값 수)가 높은 열

**인덱스 생성이 불리한 경우:**
- 데이터가 매우 적은 테이블
- 자주 변경되는 열
- 카디널리티가 낮은 열 (예: 성별 — 두 가지 값만)

## 핵심 정리

- B+ Tree: 균형 트리, 리프 노드에 데이터+연결 리스트, 범위 검색 효율적
- Hash: 등치 검색 O(1), 범위 검색 불가
- 클러스터 인덱스: 물리적 순서와 일치, 테이블당 1개
- 비클러스터 인덱스: 물리적 순서와 무관, 여러 개 가능
- 밀집: 모든 레코드 / 희소: 일부 레코드
- 복합 인덱스: 선두 열 규칙 (Leftmost Prefix)
