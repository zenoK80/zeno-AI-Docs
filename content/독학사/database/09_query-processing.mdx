## 질의 처리(Query Processing) 과정

> **쉽게 말하면:** 사용자가 작성한 SQL 문(03·07·08번 문서)은 곧바로 실행되는 것이 아니라, DBMS 내부에서 여러 단계를 거쳐 "실제로 데이터를 찾는 절차"로 변환됩니다.

<Steps>
### 1단계: 파싱(Parsing)
SQL 문의 문법이 올바른지 검사하고, 06번 문서에서 배운 관계대수 형태의 내부 표현(파스 트리)으로 변환합니다.

### 2단계: 최적화(Optimization)
같은 결과를 내는 여러 가지 실행 방법(실행 계획) 중, 가장 비용(시간)이 적게 드는 방법을 찾습니다(이 문서의 핵심 주제).

### 3단계: 실행(Execution)
선택된 실행 계획에 따라 실제로 디스크에서 데이터를 읽고 계산해 결과를 반환합니다.
</Steps>

## 왜 "같은 결과"에 "여러 실행 방법"이 존재하는가?

> **쉽게 말하면:** 06번 문서에서 배운 선택(σ), 추출(π), 조인(⋈) 같은 관계대수 연산은 순서를 바꿔도 최종 결과는 똑같지만, 그 과정에서 처리해야 하는 데이터의 양(따라서 걸리는 시간)은 크게 달라질 수 있습니다.

## 질의 변환 규칙 — 대표 사례

### 선택 연산을 최대한 먼저(아래로) 밀어 넣기

> **쉽게 말하면:** "조인부터 하고 나서 조건으로 거르는 것"보다 "먼저 조건으로 걸러내고 나서 조인하는 것"이 처리할 데이터 양이 훨씬 적어 효율적입니다.

**계산 예시:** 학생(10,000행)과 수강(50,000행)을 조인한 뒤 "학번=1001"인 것만 거르는 방법과, 먼저 "학번=1001"인 학생을 걸러낸(1행) 뒤 조인하는 방법을 비교합니다.

<Table>
  <thead>
    <tr><th>순서</th><th>처리 과정</th><th>비효율성</th></tr>
  </thead>
  <tbody>
    <tr><td>조인 먼저</td><td>10,000×50,000 규모의 조인을 모두 계산한 뒤, 그 결과에서 조건에 맞는 것만 거름</td><td>불필요하게 방대한 중간 결과를 만듦</td></tr>
    <tr><td>선택 먼저(최적화됨)</td><td>학생 테이블에서 "학번=1001"인 1행만 먼저 골라낸 뒤, 그 1행만 수강 테이블과 조인</td><td>훨씬 적은 데이터로 조인 수행</td></tr>
  </tbody>
</Table>

**해석:** 두 방법의 최종 결과는 정확히 같지만, 처리해야 하는 중간 데이터의 양이 크게 다릅니다. DBMS의 최적화 단계는 이런 "선택 연산을 최대한 먼저 수행"하는 등의 변환 규칙을 자동으로 적용해 더 빠른 실행 계획을 찾아냅니다.

### 추출 연산을 최대한 먼저 적용하기

> **쉽게 말하면:** 필요한 열(추출, π)만 최대한 일찍 골라내면, 이후 단계에서 다뤄야 하는 데이터의 "너비"(열의 개수)가 줄어들어 처리가 빨라집니다.

## 비용 계산(Cost Estimation)

> **쉽게 말하면:** DBMS는 여러 실행 계획 후보 각각에 대해 "이 방법을 쓰면 대략 얼마나 걸릴까"를 예측되는 숫자(비용)로 계산해, 그중 가장 비용이 적은 계획을 최종 선택합니다.

<Table>
  <thead>
    <tr><th>비용에 영향을 주는 요소</th><th>설명</th></tr>
  </thead>
  <tbody>
    <tr><td>디스크 접근 횟수</td><td>데이터를 읽기 위해 디스크를 몇 번 읽어야 하는지(가장 중요한 요소인 경우가 많음)</td></tr>
    <tr><td>테이블 크기(행 수)</td><td>처리해야 할 데이터 양이 많을수록 비용 증가</td></tr>
    <tr><td>인덱스 존재 여부</td><td>10번 문서에서 배울 인덱스가 있으면 훨씬 적은 비용으로 원하는 데이터를 찾을 수 있음</td></tr>
  </tbody>
</Table>

<Callout type="info">
  **10번 문서와의 연결:** 질의 최적화기는 "이 조건에 인덱스가 있는가?"를 항상 확인합니다. 인덱스가 있다면 테이블 전체를 순서대로 훑는(Full Scan) 대신, 인덱스를 이용해 원하는 데이터로 바로 건너뛸 수 있어 비용이 극적으로 줄어듭니다. 이것이 인덱스를 적절히 설계하는 것이 실무에서 매우 중요한 이유입니다.
</Callout>

<Callout type="warning">
  **자주 틀리는 점:** 질의 최적화가 "SQL 코드 자체를 더 짧고 예쁘게 다듬는 것"이라고 오해하기 쉽습니다. 실제로는 사용자가 작성한 SQL 문의 **의미**(결과)**는 그대로 유지**한 채, 내부적으로 더 효율적인 **실행 순서·방법**을 찾는 것이 질의 최적화의 목표입니다. 사용자 눈에는 SQL 코드가 전혀 바뀌지 않은 것처럼 보입니다.
</Callout>

## 핵심 정리

- **질의 처리 과정**: 파싱(문법 검사·내부 표현 변환) → 최적화(실행 계획 선택) → 실행.
- 같은 결과를 내는 여러 실행 계획 중, 처리할 데이터 양을 줄이는 것이 핵심 전략.
- **변환 규칙**: 선택(σ)·추출(π) 연산을 최대한 일찍(조인보다 먼저) 적용해 중간 데이터를 줄임.
- **비용 계산**: 디스크 접근 횟수, 테이블 크기, 인덱스 존재 여부 등을 기준으로 가장 효율적인 계획을 선택.
- 질의 최적화는 SQL 코드 자체가 아니라, 그 의미를 유지한 채 내부 실행 방법을 최적화하는 과정.
