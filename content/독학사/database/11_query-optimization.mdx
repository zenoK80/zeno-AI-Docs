## 쿼리 처리 과정

SQL 쿼리는 다음 단계를 거쳐 실행됩니다:

```
SQL 쿼리
  ↓ 파싱(Parsing) — 문법 분석 및 AST 생성
쿼리 트리
  ↓ 의미 검사 — 테이블/열 존재 확인
검증된 쿼리 트리
  ↓ 쿼리 최적화(Query Optimization)
실행 계획(Execution Plan)
  ↓ 실행(Execution)
결과
```

## 실행 계획 (Execution Plan)

DBMS가 쿼리를 어떻게 실행할지 결정한 계획입니다.

**확인 방법:**
```sql
EXPLAIN SELECT * FROM orders WHERE customer_id = 100;
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 100;
```

**실행 계획 주요 항목:**
| 항목 | 설명 |
|------|------|
| 접근 방법 | Index Scan, Full Table Scan 등 |
| 조인 순서 | 어느 테이블을 먼저 처리할지 |
| 조인 방법 | Nested Loop, Hash, Sort-Merge |
| 예상 비용 | I/O 비용 + CPU 비용 |
| 예상 행 수 | 각 연산에서 반환될 행의 수 |

## 최적화 방식

### 규칙 기반 최적화 (RBO, Rule-Based Optimization)

미리 정해진 규칙(우선순위)에 따라 실행 계획을 선택합니다.

- 인덱스가 있으면 항상 사용
- 데이터 통계에 무관하게 동일한 계획
- 현재는 대부분의 DBMS에서 비용 기반으로 대체

### 비용 기반 최적화 (CBO, Cost-Based Optimization)

**통계 정보**를 바탕으로 여러 실행 계획의 비용을 추정하여 가장 낮은 비용의 계획을 선택합니다.

**비용 = I/O 비용 + CPU 비용**

**사용하는 통계 정보:**
- 테이블의 행 수
- 각 열의 카디널리티(고유 값 수)
- 인덱스 깊이
- 데이터 분포(히스토그램)

**통계 수집:**
```sql
-- Oracle
EXEC DBMS_STATS.GATHER_TABLE_STATS('SCHEMA', 'TABLE');

-- PostgreSQL
ANALYZE table_name;
```

## 조인 알고리즘

### Nested Loop Join (중첩 루프 조인)

외부 테이블의 각 행마다 내부 테이블 전체를 반복 탐색합니다.

```
FOR each row r in 외부 테이블 R:
    FOR each row s in 내부 테이블 S:
        IF r.join_key = s.join_key:
            output (r, s)
```

**비용:** $O(|R| \times |S|)$

**특징:**
- 내부 테이블에 인덱스가 있으면 효율적 → Index NL Join
- 소량의 데이터 또는 내부 테이블이 작을 때 적합
- 인덱스 없으면 대량 데이터에 비효율적

### Hash Join

해시 함수를 사용하여 조인 조건 기반으로 버킷을 나눠 조인합니다.

```
-- Build Phase (빌드 단계)
작은 테이블 S에 해시 테이블 생성:
  h(s.join_key) → 버킷

-- Probe Phase (프로브 단계)
큰 테이블 R의 각 행에 대해:
  해당 버킷에서 일치하는 행 탐색
```

**특징:**
- 등치 조인(=)에서 대량 데이터 처리에 효율적
- 정렬 불필요
- 해시 테이블을 메모리에 올려야 하므로 메모리 의존
- 범위 조인에는 사용 불가

### Sort-Merge Join (정렬-병합 조인)

두 테이블을 조인 키 기준으로 정렬 후 병합합니다.

```
1. R을 join_key로 정렬
2. S를 join_key로 정렬
3. 두 정렬된 테이블을 병합하여 일치하는 행 출력
```

**특징:**
- 정렬 비용이 크지만 정렬 후 병합은 선형
- 데이터가 이미 정렬되어 있으면 매우 효율적
- 등치(=) 및 범위(BETWEEN, >, &lt;) 조인 모두 가능
- 대량 데이터에 적합

### 조인 알고리즘 비교

| 항목 | Nested Loop | Hash Join | Sort-Merge |
|------|-------------|-----------|------------|
| 적합한 크기 | 소량/인덱스 있을 때 | 중대량 | 중대량 |
| 등치 조인 | 가능 | 가능 | 가능 |
| 범위 조인 | 가능 | 불가 | 가능 |
| 메모리 요구 | 적음 | 많음 | 중간 |
| 인덱스 활용 | 높음 | 낮음 | 낮음 |

## 쿼리 최적화 기법

### 선택 조건 최대한 먼저 적용 (Selection Pushdown)

조인 전에 WHERE 조건을 최대한 빨리 적용하여 처리할 행 수를 줄입니다.

```sql
-- 비효율
SELECT * FROM orders o JOIN customers c ON o.cid = c.id
WHERE c.city = '서울';

-- 최적화: 필터 먼저 적용
SELECT * FROM orders o
JOIN (SELECT * FROM customers WHERE city = '서울') c ON o.cid = c.id;
```

### 적절한 인덱스 활용

- 자주 검색하는 열에 인덱스 생성
- 복합 인덱스 활용 시 선두 열 규칙 준수

### EXPLAIN 분석 포인트

| 나쁜 신호 | 의미 | 해결책 |
|-----------|------|--------|
| Full Table Scan | 인덱스 미사용 | 인덱스 생성 |
| 높은 rows 추정 | 대량 처리 예상 | 필터 조건 추가 |
| Nested Loop on large table | 비효율 조인 | Hash/Sort-Merge 검토 |

## 힌트 (Query Hint)

옵티마이저의 판단을 개발자가 직접 지정합니다.

```sql
-- MySQL 인덱스 힌트
SELECT /*+ INDEX(orders idx_customer) */ *
FROM orders USE INDEX (idx_customer)
WHERE customer_id = 100;

-- Oracle 힌트
SELECT /*+ FULL(o) */ *
FROM orders o
WHERE amount > 1000;

-- 조인 방법 힌트
SELECT /*+ USE_HASH(a b) */ *
FROM a JOIN b ON a.id = b.id;
```

**힌트 사용 주의사항:**
- 통계가 오래됐거나 옵티마이저 판단이 틀릴 때 사용
- 과도한 힌트는 유지보수를 어렵게 함
- 통계를 최신으로 유지하는 것이 우선

## 핵심 정리

- 비용 기반 최적화(CBO): 통계 정보로 최저 비용 계획 선택
- Nested Loop Join: 내부 테이블 인덱스 있을 때 효율적
- Hash Join: 등치 조인, 대량 데이터, 메모리 필요
- Sort-Merge Join: 정렬 후 병합, 범위 조인도 가능
- 힌트: 옵티마이저 결정을 개발자가 직접 지정
