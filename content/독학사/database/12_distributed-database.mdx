## 분산 데이터베이스란?

물리적으로 분산된 여러 사이트(노드)에 데이터를 저장하고, 이를 논리적으로 하나의 데이터베이스처럼 운영하는 시스템입니다.

**장점:**
- 지역별 데이터 접근 속도 향상
- 장애 발생 시 가용성 증가 (다른 노드가 서비스 유지)
- 수평 확장(Scale-out) 가능

**단점:**
- 복잡성 증가
- 데이터 일관성 유지 어려움
- 네트워크 장애 처리 필요

## 분산 데이터베이스 투명성

사용자가 분산 환경의 복잡성을 인식하지 않아도 되도록 시스템이 처리하는 특성입니다.

| 투명성 종류 | 설명 |
|------------|------|
| **위치 투명성 **(Location Transparency) | 데이터가 어느 사이트에 있는지 알 필요 없음 |
| **분할 투명성 **(Fragmentation Transparency) | 데이터가 어떻게 분할되어 있는지 알 필요 없음 |
| **복제 투명성 **(Replication Transparency) | 데이터가 어디에 복제되어 있는지 알 필요 없음 |
| **병행 투명성 **(Concurrency Transparency) | 다른 트랜잭션의 동시 실행을 인식하지 않아도 됨 |

추가로 **장애 투명성**(Failure Transparency)도 중요합니다: 일부 사이트 장애 시 시스템이 자동으로 처리.

## 데이터 분할 (Fragmentation)

데이터를 여러 사이트에 나누어 저장하는 방식입니다.

### 수평 분할 (Horizontal Fragmentation)

**행(Row) 단위**로 나누어 저장합니다:

```
서울 지점 사이트: SELECT * FROM 주문 WHERE 지역 = '서울'
부산 지점 사이트: SELECT * FROM 주문 WHERE 지역 = '부산'
```

### 수직 분할 (Vertical Fragmentation)

**열(Column) 단위**로 나누어 저장합니다:

```
서버 A: id, name, email  (자주 접근)
서버 B: id, address, phone  (가끔 접근)
```

### 혼합 분할 (Hybrid Fragmentation)

수평 분할과 수직 분할을 혼합합니다.

## 데이터 복제 (Replication)

동일한 데이터를 여러 사이트에 복사하여 저장합니다.

**장점:** 지역 접근성 향상, 가용성 향상

**단점:** 갱신 시 모든 복제본 동기화 필요, 저장 공간 증가

### 복제 전략

| 전략 | 설명 |
|------|------|
| **완전 복제** | 모든 데이터를 모든 사이트에 복제 |
| **부분 복제** | 일부 데이터만 선택적으로 복제 |
| **무복제** | 분할만 사용, 각 데이터는 한 곳에만 저장 |

## 2단계 커밋 (2PC, Two-Phase Commit)

분산 트랜잭션의 원자성을 보장하기 위한 프로토콜입니다. 모든 참여 사이트가 커밋하거나 모두 롤백해야 합니다.

**역할:**
- **코디네이터(Coordinator):** 트랜잭션을 시작한 사이트
- **참여자(Participant):** 트랜잭션에 참여하는 다른 사이트들

### 1단계: 준비 단계 (Prepare Phase)

```
코디네이터 → 모든 참여자: "PREPARE" (커밋 준비 요청)
참여자 → 코디네이터: "YES" (커밋 가능) 또는 "NO" (불가)
```

각 참여자는 "YES"를 보내기 전에 로그에 준비 완료 기록.

### 2단계: 커밋/롤백 단계 (Commit/Abort Phase)

```
모든 참여자 YES:
  코디네이터 → 모든 참여자: "COMMIT"
  참여자들: 커밋 수행 후 완료 응답

하나라도 NO:
  코디네이터 → 모든 참여자: "ABORT"
  참여자들: 롤백 수행
```

### 2PC의 한계

- **블로킹 프로토콜:** 코디네이터 장애 시 참여자가 결과를 모른 채 대기
- 성능 오버헤드: 두 번의 라운드트립 필요
- 해결: 3단계 커밋(3PC) 또는 분산 합의 알고리즘(Paxos, Raft) 사용

## CAP 정리 (CAP Theorem)

Brewer의 정리: 분산 시스템은 다음 세 가지 속성 중 **최대 2가지만** 동시에 만족할 수 있습니다.

| 속성 | 설명 |
|------|------|
| **C **(Consistency, 일관성) | 모든 노드가 항상 동일한 최신 데이터를 반환 |
| **A **(Availability, 가용성) | 모든 요청이 성공 또는 실패 응답을 반환 (타임아웃 없음) |
| **P **(Partition Tolerance, 분단 허용성) | 네트워크 분단(일부 노드 간 통신 불가)에도 시스템 계속 동작 |

**실용적 관점:** 네트워크 분단(P)은 항상 발생할 수 있으므로, 실제 선택은 **C vs A** 트레이드오프:

| 시스템 | 선택 | 예시 |
|--------|------|------|
| **CP** | 일관성 우선, 가용성 희생 | HBase, Zookeeper, 금융 시스템 |
| **AP** | 가용성 우선, 일관성 희생 | Cassandra, CouchDB, DNS |

## BASE vs ACID

분산 NoSQL 시스템에서는 ACID 대신 BASE 속성을 적용합니다:

| BASE | 의미 |
|------|------|
| **Basically Available** | 기본적으로 가용 상태를 유지 |
| **Soft State** | 데이터 상태가 일정 시간 동안 달라질 수 있음 |
| **Eventually Consistent** | 결국에는 일관성이 보장됨 (즉시가 아님) |

## 핵심 정리

- 분산 DB 투명성: 위치/분할/복제/병행 투명성
- 수평 분할: 행 단위 / 수직 분할: 열 단위
- 2PC: 준비 단계 → 커밋/롤백 단계, 모두 커밋 또는 모두 롤백
- CAP 정리: 일관성(C), 가용성(A), 분단 허용성(P) 중 2가지만 가능
- BASE: NoSQL의 완화된 일관성 모델
