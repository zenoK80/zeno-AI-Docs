## 파일 시스템(File System)의 한계

> **쉽게 말하면:** 데이터베이스가 등장하기 전에는, 각 프로그램이 자신만의 파일에 데이터를 따로따로 저장했습니다. 이 방식은 여러 문제를 일으켰습니다.

<Table>
  <thead>
    <tr><th>문제</th><th>설명</th></tr>
  </thead>
  <tbody>
    <tr><td>데이터 중복(Redundancy)</td><td>같은 정보(예: 학생 이름)가 여러 파일에 반복 저장되어 낭비되고, 한쪽만 수정하면 불일치 발생</td></tr>
    <tr><td>데이터 종속성(Dependency)</td><td>파일의 저장 구조가 바뀌면, 그 파일을 사용하는 모든 프로그램의 코드를 함께 수정해야 함</td></tr>
    <tr><td>일관성 결여</td><td>여러 파일에 흩어진 같은 정보가 서로 다른 값을 갖게 되는 모순 발생</td></tr>
    <tr><td>동시 접근의 어려움</td><td>여러 사람이 동시에 파일을 수정하면 충돌·데이터 손실 위험</td></tr>
  </tbody>
</Table>

## 데이터베이스(Database)와 DBMS

> **쉽게 말하면:** 데이터베이스는 이런 문제를 해결하기 위해, 여러 프로그램이 공유하는 하나의 통합된 데이터 저장소를 만들고, 이를 관리하는 소프트웨어(DBMS)를 통해서만 접근하도록 한 시스템입니다.

**DBMS**(DataBase Management System, 데이터베이스 관리 시스템)는 데이터의 저장·조회·수정·삭제를 담당하고, 여러 사용자의 동시 접근을 안전하게 관리하며(11·12번 문서), 데이터의 무결성을 지키는 소프트웨어입니다.

## 데이터 독립성(Data Independence)

> **쉽게 말하면:** 데이터 독립성은 "데이터의 실제 저장 방식이 바뀌어도, 그 데이터를 사용하는 응용 프로그램은 영향을 받지 않는" 성질입니다.

<Table>
  <thead>
    <tr><th>종류</th><th>의미</th></tr>
  </thead>
  <tbody>
    <tr><td>논리적 독립성(Logical Independence)</td><td>테이블 구조(스키마)가 바뀌어도(예: 열 추가), 기존 응용 프로그램은 수정 없이 계속 동작</td></tr>
    <tr><td>물리적 독립성(Physical Independence)</td><td>데이터가 저장되는 실제 방식(디스크 위치, 파일 형식 등)이 바뀌어도, 상위 논리적 구조는 영향받지 않음</td></tr>
  </tbody>
</Table>

<Callout type="warning">
  **자주 틀리는 점:** 데이터 독립성을 "데이터가 어디에도 저장되지 않는다"는 뜻으로 오해하기 쉽습니다. 실제로는 "저장 방식이 바뀌어도 그 위 단계(응용 프로그램, 사용자 관점)에 영향을 주지 않도록 설계 단계를 분리한다"는 뜻입니다. 이 분리를 가능하게 하는 것이 아래의 3단계 스키마 구조입니다.
</Callout>

## 3단계 스키마(Three-Schema Architecture)

> **쉽게 말하면:** 3단계 스키마는 데이터베이스를 "사용자가 보는 관점", "전체 논리적 구조", "실제 저장 방식"의 세 층으로 나눠, 각 층이 독립적으로 바뀔 수 있게 만든 설계 원칙입니다.

<Table>
  <thead>
    <tr><th>단계</th><th>이름</th><th>내용</th></tr>
  </thead>
  <tbody>
    <tr><td>외부 스키마(External Schema)</td><td>사용자 관점</td><td>각 사용자·응용 프로그램이 필요로 하는 데이터의 일부만 보여주는 개인화된 뷰(예: 학생은 자기 성적만 볼 수 있음)</td></tr>
    <tr><td>개념 스키마(Conceptual Schema)</td><td>전체 논리적 구조</td><td>조직 전체의 데이터 구조를 통합적으로 정의(모든 테이블, 관계, 제약 조건)</td></tr>
    <tr><td>내부 스키마(Internal Schema)</td><td>물리적 저장 방식</td><td>데이터가 디스크에 실제로 어떻게 저장되는지(인덱스, 파일 구조 등)</td></tr>
  </tbody>
</Table>

**계산 예시**(독립성과의 연결): 개념 스키마(전체 테이블 구조)는 그대로 둔 채 내부 스키마(저장 파일 형식)만 바꾸면 → **물리적 독립성**이 지켜진 것입니다. 반대로 개념 스키마에 새 열을 추가해도 외부 스키마(기존 사용자가 보는 화면)가 그 열을 노출하지 않도록 설계했다면 → **논리적 독립성**이 지켜진 것입니다.

## 무결성(Integrity)

> **쉽게 말하면:** 무결성은 데이터베이스에 저장된 데이터가 항상 "정확하고 일관된" 상태를 유지하도록 보장하는 규칙입니다.

<Table>
  <thead>
    <tr><th>제약 종류</th><th>규칙</th></tr>
  </thead>
  <tbody>
    <tr><td>개체 무결성(Entity Integrity)</td><td>01번 문서의 기본키는 NULL이 될 수 없고 중복될 수 없음</td></tr>
    <tr><td>참조 무결성(Referential Integrity)</td><td>외래키 값은 반드시 참조하는 테이블에 실제로 존재하는 값이거나 NULL이어야 함(예: 존재하지 않는 학번을 수강 테이블의 외래키로 넣을 수 없음)</td></tr>
  </tbody>
</Table>

## 핵심 정리

- **파일 시스템의 한계**(중복, 종속성, 불일치, 동시 접근 어려움)를 해결하기 위해 **데이터베이스와 DBMS**가 등장.
- **데이터 독립성**: 논리적(스키마 변경이 응용에 무영향), 물리적(저장 방식 변경이 논리 구조에 무영향).
- **3단계 스키마**: 외부(사용자 관점)-개념(전체 구조)-내부(물리적 저장)로 분리해 독립성을 실현.
- **무결성**: 개체 무결성(기본키 규칙), 참조 무결성(외래키가 실제 존재하는 값을 가리켜야 함).
