# 배포가 조용히 실패한 이유: 빌드 서버의 메모리 부족

**한 줄 요약**: 문서를 322편까지 늘렸더니 GitHub 배포가 실패했다. 코드나 문법 문제가 아니라 **빌드하는 컴퓨터에서 Node.js가 쓸 수 있는 메모리 상한(약 4GB)을 넘긴 것**이었고, 설정 한 줄로 상한을 올려 해결했다. 요금과는 아무 상관이 없었다.

## 증상

새 문서 106개를 커밋·푸시한 뒤 사이트를 확인했는데 계속 404가 떴다.

```
try1: 404
try2: 404
...
try14: 404
```

7분 넘게 기다려도 그대로였다. 이전 배포는 5분이면 끝났으니 단순히 느린 게 아니었다.

여기서 처음에 실수를 했다. **"사이트가 커져서 오래 걸리나 보다"라고 넘겨짚고 기다린 것**이다. 로그를 먼저 봤어야 했다.

## 먼저 알아야 할 용어들

이 문제를 이해하려면 단어 몇 개가 필요하다. 하나씩 풀어 쓴다.

### 빌드(build)

우리가 쓰는 `.mdx` 파일은 사람이 읽고 쓰기 좋은 형식이지 브라우저가 바로 이해하는 형식이 아니다. **브라우저가 읽을 수 있는 HTML·CSS·JS 파일로 변환하는 작업**이 빌드다. `npm run build`가 그 명령이다.

이 사이트는 정적 사이트(static site)라서, 빌드할 때 **322개 페이지를 전부 미리 만들어 둔다**. 방문자가 올 때마다 만드는 게 아니라 미리 다 찍어 놓는 방식이다. 그래서 빌드할 때 컴퓨터가 할 일이 많다.

### GitHub Actions와 러너(runner)

우리가 `git push`를 하면 GitHub가 자동으로 빌드하고 사이트에 올려 준다. 이 자동화 장치가 **GitHub Actions**다. 설정은 `.github/workflows/deploy.yml`에 적혀 있다.

이때 GitHub는 **빌드 전용 임시 컴퓨터를 하나 빌려준다.** 이 컴퓨터를 **러너(runner)** 라고 부른다. 우리 노트북이 아니라 GitHub 클라우드에 잠깐 켜졌다 꺼지는 리눅스 가상 머신이다.

- 무료로 제공되는 표준 러너는 **메모리 16GB**짜리다
- 공개 저장소는 사용 시간 제한도 없다
- 빌드가 끝나면 그 컴퓨터는 사라진다

**"러너 힙이 부족하다"는 말은 이 임시 컴퓨터에서 벌어진 일이라는 뜻이지, 돈을 더 내야 한다는 뜻이 아니다.**

### 힙(heap)

프로그램이 실행 중에 데이터를 쌓아 두는 **메모리 작업 공간**을 힙이라고 한다.

요리에 비유하면 이렇다. 냉장고에 재료가 아무리 많아도(= 컴퓨터 전체 메모리 16GB), 실제로 재료를 펼쳐 놓고 작업하는 곳은 **도마 위**다(= 힙). 도마가 좁으면 재료가 넘쳐 흘러 요리를 못 한다.

### 가비지 컬렉션(GC, garbage collection)

Node.js는 도마가 좁아지면 **더 이상 안 쓰는 데이터를 자동으로 치운다.** 이 청소 작업이 가비지 컬렉션이다. 보통은 알아서 잘 돌아간다.

문제는 **치울 게 없을 때**다. 322개 페이지를 만드는 동안 대부분의 데이터가 아직 "쓰는 중"이면 청소해도 공간이 안 난다. 로그에 나온 `Mark-Compact`가 바로 이 청소 작업의 이름이다.

### OOM (Out Of Memory)

메모리가 바닥나서 프로그램이 강제 종료되는 것. "아웃 오브 메모리"라고 읽는다.

## 실제 로그 읽기

GitHub Actions 로그를 받아 보니 이렇게 적혀 있었다.

```
<--- Last few GCs --->

[2138:0x328c0000]  144251 ms: Mark-Compact 3948.8 (4139.6) -> 3948.3 (4132.7) MB,
                   613.55 / 0.00 ms  (average mu = 0.101, current mu = 0.008)
                   allocation failure; GC in old space requested

FATAL ERROR: Ineffective mark-compacts near heap limit
             Allocation failed - JavaScript heap out of memory

Aborted (core dumped)
##[error]Process completed with exit code 134.
```

암호처럼 보이지만 한 줄씩 뜯으면 간단하다.

| 로그 조각 | 뜻 |
|---|---|
| `144251 ms` | 빌드 시작 후 144초 지점에서 벌어진 일 |
| `Mark-Compact` | 가비지 컬렉션(메모리 청소) 작업의 이름 |
| `3948.8 -> 3948.3 MB` | 청소했는데 **0.5MB밖에 못 줄였다**. 거의 아무것도 못 치웠다는 뜻 |
| `(4139.6)` | 괄호 안이 **쓸 수 있는 최대치**. 약 4.1GB가 상한이었다 |
| `613.55 ms` | 청소 한 번에 0.6초를 썼다. 일은 안 하고 청소만 하는 상태 |
| `average mu = 0.101` | 전체 시간 중 **실제 작업에 쓴 비율이 10%**. 나머지 90%는 청소만 했다 |
| `Ineffective mark-compacts` | "청소를 해도 효과가 없다" — Node가 포기를 선언한 문장 |
| `heap out of memory` | 도마가 꽉 찼다 |
| `exit code 134` | 비정상 종료. 128 + 6(SIGABRT)이라는 리눅스 관례 |

정리하면 이렇다. **3948MB까지 찼는데 상한이 4139MB였고, 청소를 해도 0.5MB밖에 못 비워서 Node가 스스로 죽었다.**

## 진짜 원인 — 메모리가 없던 게 아니다

여기가 핵심이다. 러너에는 **메모리 16GB가 있었다.** 그런데 Node는 4GB에서 죽었다. **12GB가 놀고 있는데 죽은 것이다.**

왜 그럴까. **Node.js는 컴퓨터에 메모리가 아무리 많아도 기본적으로 약 4GB까지만 쓰도록 스스로 상한을 걸어 둔다.** 무한정 쓰다가 컴퓨터 전체를 마비시키는 걸 막으려는 안전장치다.

> **쉽게 말하면**: 냉장고에 재료가 16kg 있는데, 도마 크기가 4kg짜리로 고정돼 있어서 그 이상은 못 펼치는 상황이다. 재료가 없어서 못 만든 게 아니라 도마가 작아서 못 만든 것이다.

그동안은 문서가 228페이지라 4GB 안에서 해결됐다. 이번에 322페이지로 늘면서 그 선을 넘었을 뿐이다.

**넘긴 양도 아슬아슬했다.** 3948MB / 4139MB, 즉 상한의 95%까지 차서 죽었다. 조금만 적었어도 통과했을 것이다.

## 왜 내 컴퓨터에서는 됐나

이 부분이 헷갈리기 쉽다. 로컬에서는 같은 코드로 빌드가 **성공했다.** 심지어 캐시를 지우고(`rm -rf .next out`) 다시 해도, 힙을 4GB로 제한해도 통과했다.

이유는 이렇다.

| | 내 컴퓨터 | GitHub 러너 |
|---|---|---|
| 운영체제 | Windows | Linux |
| Node 버전 | 24 | 22 |
| 빌드 캐시 | 있을 때가 많음 | 항상 없음(매번 새 컴퓨터) |
| 다른 프로그램 | 여유 있게 배분 | 최소 환경 |

Node 버전과 OS가 다르면 메모리를 잡는 방식도 조금씩 다르다. **95% 대 105% 같은 경계선에서는 이 작은 차이가 성공과 실패를 가른다.**

그래서 이런 교훈이 남는다. **"내 컴퓨터에서는 되는데요"는 배포 실패의 반박 근거가 되지 못한다.** 특히 메모리·시간처럼 한계선이 있는 문제에서는 환경이 다르면 결과도 다르다.

## 해결

`.github/workflows/deploy.yml`에서 빌드 명령에 환경 변수 한 줄을 붙였다.

```yaml
- run: npm run build
  env:
    NODE_OPTIONS: --max-old-space-size=8192
```

- **`NODE_OPTIONS`**: Node를 실행할 때 옵션을 미리 정해 두는 환경 변수
- **`--max-old-space-size`**: 힙(도마) 크기의 상한을 정하는 옵션. **단위는 MB**
- **`8192`**: 8192MB = 8GB

즉 **"4GB 말고 8GB까지 써도 된다"** 고 알려준 것이다. 러너 메모리가 16GB이므로 8GB를 줘도 절반이 남는다.

`old space`라는 이름은 Node가 힙을 두 구역으로 나눠 관리하기 때문이다. 새로 만든 데이터는 `new space`, 오래 살아남은 데이터는 `old space`로 옮긴다. 페이지를 만드는 동안 계속 붙들고 있어야 하는 데이터가 쌓이는 곳이 `old space`라서 이 옵션이 필요했다.

푸시하니 5분 만에 빌드가 통과했고 새 페이지 전부 200으로 확인됐다.

## 원인을 확인하는 방법

로그를 보는 게 전부다. 명령줄에서 이렇게 확인할 수 있다.

**1) 최근 실행 결과 보기**

```bash
curl -s "https://api.github.com/repos/<계정>/<저장소>/actions/runs?per_page=3"
```

`conclusion` 값이 `success`인지 `failure`인지 나온다.

**2) 어느 단계에서 실패했는지 보기**

```bash
curl -s "https://api.github.com/repos/<계정>/<저장소>/actions/runs/<실행ID>/jobs"
```

각 단계의 `conclusion`을 보면 실패 지점이 나온다. 이번엔 `Run npm run build`였다.

**3) 실제 로그 받기** — 여기는 인증이 필요하다

```bash
TOK=$(printf "protocol=https\nhost=github.com\n\n" | git credential fill | sed -n 's/^password=//p')
curl -sL -H "Authorization: Bearer $TOK" \
  "https://api.github.com/repos/<계정>/<저장소>/actions/runs/<실행ID>/logs" -o logs.zip
unzip -q logs.zip && tail -60 1_build.txt
```

이미 저장돼 있는 git 자격 증명을 그대로 쓰는 방식이라 토큰을 따로 만들 필요가 없다. 물론 브라우저에서 Actions 탭을 열어 봐도 같은 로그를 볼 수 있다.

## 다음에 또 넘치면

문서는 계속 늘어난다. 언젠가 8GB도 부족해질 수 있다. 그때는 순서대로 이렇게 대응한다.

1. **상한을 더 올린다** — `16384`(16GB)까지. 가장 간단하고, 러너 메모리가 16GB라 여기가 현실적인 천장이다
2. **큰 러너로 바꾼다** — 이때부터는 유료다. 여기 오기 전에 아래를 먼저 해 볼 것
3. **한 번에 만드는 페이지 수를 줄인다** — 바뀐 문서만 다시 만드는 증분 빌드나, 페이지를 나눠 빌드하는 방식

**미리 알아채는 방법**도 있다. 로그의 `(4139.6)` 같은 괄호 숫자에 실제 사용량이 몇 퍼센트까지 붙었는지 보면 된다. 90%를 넘기 시작하면 다음 몇 번 안에 터진다는 신호다.

## 남는 교훈

**1. 404가 뜨면 추측하지 말고 로그부터 본다.**

이번에 가장 아까웠던 건 "커져서 느린가 보다"라고 넘겨짚고 7분을 기다린 것이다. 로그에는 원인이 그냥 적혀 있었다. **증상을 보고 원인을 상상하는 시간보다, 로그를 받아 읽는 시간이 거의 항상 짧다.**

**2. 실패 메시지는 원인을 정확히 말해 준다 — 겁먹지 말고 읽으면 된다.**

`FATAL ERROR: JavaScript heap out of memory`는 사실 매우 친절한 문장이다. 어디가 문제인지 이름까지 대 주고 있다. 영어와 낯선 단어 때문에 어려워 보일 뿐, 단어 몇 개만 알면 그대로 읽힌다.

**3. "메모리 부족"이 항상 "메모리를 더 사라"는 뜻은 아니다.**

이번 건은 **자원이 없어서가 아니라 상한 설정 때문**이었다. 비용 문제로 넘어가기 전에 "지금 있는 걸 다 쓰고 있는가"를 먼저 확인해야 한다. 16GB 중 4GB만 쓰고 있었다.

**4. 로컬 성공은 CI 성공을 보장하지 않는다.**

특히 메모리·시간처럼 **한계선이 존재하는 문제**에서 그렇다. OS, 런타임 버전, 캐시 유무가 다르면 경계선 근처에서 결과가 갈린다.
